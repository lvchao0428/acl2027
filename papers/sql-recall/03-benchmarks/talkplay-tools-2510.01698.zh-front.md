## Abstract

摘要认为 LLM 已经能做带自然语言的生成式推荐，但推荐行为仍然窄，元数据和属性过滤这些更简单、也更必要的部件没有被用上。作者提出一个音乐推荐系统，把 LLM 放在工具调用的位置上，做成统一的检索再重排流水线。LLM 理解意图、规划调用，并编排四类部件：布尔过滤（SQL）、稀疏检索（BM25）、稠密检索（嵌入相似度）和生成式检索（semantic ID）。它要预测用哪些工具、什么顺序、什么参数。摘要的实验判断是：按用户查询选择检索方法，这套框架在多种对话推荐场景上具有竞争力。

## 1 Introduction

第 1 节用音乐推荐的历史说明为什么不能只留一种检索。早期系统对听歌日志和标题、艺术家、发行年做布尔过滤。曲库变大之后，主流变成用户和物品嵌入上的检索再重排。表示学习随后把音频、歌词和封面加进来，语义 ID 则把物品量化成离散码，既能生成推荐，也能做多轮对话。

转折是：只靠一种检索盖不住用户同时提出的资料、曲风、情绪、新旧和听歌史。生产系统本来就是多阶段、有路由的流水线。贡献收成三条。第一，把对话音乐推荐写成多检索方法的工具规划，LLM 根据用户画像和对话决定工具种类、顺序和参数。第二，工具集同时包含 SQL、BM25、跨模态稠密检索和 semantic ID。第三，在一个对话推荐基准上做零样本评测，并分析工具行为。这一节没有给 Hit 数字。

式 (1)(2) 把一轮推荐写成：LLM 读当前问句、上一轮对话状态和用户画像，产出工具调用；环境在数据库上执行，得到曲目列表；LLM 再生成一句解释。工具被规定成先后执行，前一个工具缩小后一个工具看到的曲目池，所以顺序会影响结果。提示词把过程拆成检索和重排两段，两类工具不能互相替代。

## 2 Music Recommendation with Tool Calling

第 2 节先用表 1 并列四种工具，再在 2.2 写出每种工具的字段和参数。SQL 是单表 `tracks` 上的布尔过滤，字段包括 title、artist、album、release date、tempo、key、popularity，参数有 SQL 语句和 topk。例子是选出 2020 年及以后的曲目并按速度排序，topk 为 100。BM25 有五套语料：title、artist、album、lyrics、attributes。稠密检索分文本到物品、物品到物品、用户到物品，按模态和 topk 取近邻。用户到物品由画像里的用户 id 触发，不由问句直接触发。Semantic ID 来自残差向量量化，按码或小编辑距离查倒排，也可以作为上下文里的离散码。

这一节强调的是接口形状，不是推荐质量。表 1 用灰色标出那些由上下文而不是由问句激活的工具，用户到物品和 semantic ID 属于这一类。评测协议、Hit@K 和工具成功率留在第 3 节及以后。
