# TalkPlay-Tools: Conversational Music Recommendation with LLM Tool Calling

## Abstract 摘要

尽管大语言模型（large language models, LLMs）的最新进展已经成功地实现了带有自然语言交互的生成式推荐器，其推荐行为仍然有限，使得元数据过滤或属性过滤等更简单却关键的组件在系统中未得到充分利用。我们提出一种带工具调用（tool calling）的、基于 LLM 的音乐推荐系统，作为统一的检索–重排序流水线。该系统将 LLM 定位为端到端推荐系统：它解释用户意图、规划工具调用，并编排专门组件——布尔过滤（SQL）、稀疏检索（BM25）、稠密检索（嵌入相似度）以及生成式检索（语义 ID，semantic IDs）。通过工具规划，系统预测应使用哪些类型的工具、它们的执行顺序，以及为找到符合用户偏好的音乐所需的参数，从而在支持多种模态的同时无缝整合多种数据库过滤方法。我们表明，这一统一的工具调用框架能够根据用户查询有选择地采用合适的检索方法，在多种推荐场景中取得有竞争力的性能，并展望对话式音乐推荐系统的新范式。

## 1 Introduction 引言

音乐推荐长期以来取决于如何按用户偏好过滤数据库。早期系统在收听历史日志以及标题、艺术家、发行年份等元数据上依赖布尔过滤 [1]。大规模音乐物品目录与用户–物品特征学习算法 [12] 的出现，使该领域转向由大规模用户与物品嵌入驱动的检索与重排序流水线 [25, 9]。随着表示学习的进展，该领域已超越收听历史，发展出更深的内容理解 [28, 17]。此外，面向音频 [13]、歌词 [19] 与视觉封面 [8] 的音乐表示使基于样例的推荐成为可能，而多模态音乐表示 [14, 10, 7, 6, 31, 30, 16, 26] 则支持自然语言查询理解。基于大语言模型（LLM）的推荐系统的最新进展 [4, 18] 表明，物品可以表示在语义空间中并量化为离散的语义 ID（Semantic IDs）[20, 15]，从而同时实现生成式推荐以及与用户的交互式对话。在这些方法中，用户可以主动参与，通过多轮交互发现符合其目标与偏好的音乐。

然而，依赖单一检索方法在识别满足用户需求的物品方面有明显局限 [29]。生产级推荐器 [3, 11] 基于多阶段、经路由的检索–重排序流水线运行，必须严格满足运营约束（例如用户画像、流派、情绪、活动、新旧程度等），同时反映听者的历史与文本查询。若不组合多种检索方法，就无法充分捕获推荐的全部相关上下文。

（图 1 标题：带工具调用的音乐推荐智能体概览。）

本文提出一种带工具调用的对话式音乐推荐器。我们的贡献是：（i）将对话式音乐推荐形式化为使用多种检索方法，使 LLM 能够以用户画像和对话上下文为条件，预测工具类型、顺序与参数；（ii）设计一套统一工具，在单一智能体下组合布尔过滤（SQL）、稀疏检索（BM25）、跨模态稠密检索（文本到物品、物品到物品、用户到物品）以及生成式检索（Semantic IDs）；（iii）在对话式推荐基准上展示零样本有效性，相对强基线提高 Hit@K，并对其行为作详细分析。

## 2 Music Recommendation with Tool Calling 带工具调用的音乐推荐

图 1 展示了我们的框架，它由两个主要组件构成。第一个组件是音乐推荐智能体（Music Recommendation Agent），包括 LLM 与工具。第二个组件是外部环境（External Environment），它执行工具，并通过检索与重排序给出最终推荐。

### 2.1 Problem Formulation 问题形式化

给定用户 \(u\) 及其画像 \(p_u\)、先前对话状态 \(s_{t-1}\)，以及当前轮次 \(t\) 的用户查询 \(q_t\)，所提出的系统通过（i）用 LLM 生成工具调用，以及（ii）用预测的工具 \(C_t\) 过滤数据库 \(D\)，产生音乐物品的排序列表 \(m_t\)。最后再次调用 LLM，生成自然语言回复 \(r_t\)，在保持对话上下文的同时对推荐给出对话式解释。

\[
C_t = \mathrm{LLM}(q_t, s_{t-1}, p_u; P_{\mathrm{tool}}, T) \quad (1)
\]

\[
m_t = \mathrm{ToolEnv}(C_t; D) \quad (2)
\]

\[
r_t = \mathrm{LLM}(m_t, q_t, s_{t-1}, p_u; P_{\mathrm{response}}) \quad (3)
\]

令 \(T\) 表示可用工具，\(P\) 表示提示，\(C_t = [(\mathrm{tool}_n, \mathrm{args}_n)]_{n=1}^{N}\) 为 LLM 预测的工具调用序列，工具数量为 \(N\)。工具环境执行每一个 \((\mathrm{tool}_n, \mathrm{args}_n)\) 对，将结果检索并重排序为最终排序列表 \(m_t\)。

（式中序列括号在 PDF 抽取里因换行断开，按 “从 \(n=1\) 到 \(N\) 的工具–参数对序列” 读出。）

工具执行环境作为顺序流水线运行：每个工具的输出直接影响后续工具的输入空间，即每个工具为下游工具过滤并收窄曲目池。因此，工具顺序会显著影响最终推荐质量。通过提示 \(P_{\mathrm{tool}}\)，我们引导 LLM 不把推荐当作单次操作，而是当作由检索与重排序阶段组成的分阶段过程，从而保证工具执行遵循顺序流水线。

### 2.2 Tools 工具

我们的框架纳入多种工具，通过结构化过滤与语义检索实现精确而灵活的音乐推荐。表 1 总结了它们的能力、环境与使用示例。

表 1：不同工具的能力比较。灰色文字表示由上下文信息而非直接的自然语言用户查询激活的工具。

| 工具 | 能力 | 环境 | 查询示例 |
| --- | --- | --- | --- |
| 布尔检索 | | | |
| SQL | 数值过滤 | SQL Server | “Recent songs over 130 BPM” |
| 稀疏检索 | | | |
| BM25 | 词法匹配 | BM25 Index | “Songs from Adele’s 21” |
| 稠密检索 | | | |
| Text-to-Item | 语义匹配 | Qwen3, CLAP, SigLIP2 | “Play a calm piano piece” |
| Item-to-Item | 多模态匹配 | CLAP, SigLIP2, BPR | “Ok, more similar voices” |
| User-to-Item | 个性化 | BPR | user_id:10021 |
| 生成式检索 | | | |
| Semantic ID | 多模态上下文 | Residual VQ Tables | audio:semantic_id:[63, 36, 44, 3] |

**SQL（布尔检索）：** SQL 工具支持对关系型音乐元数据作精确、结构化的查询。我们构建一张表，字段包括 title、artist、album、release date、tempo、key 与 popularity。工具参数包括用于 SQL 语句的 query 以及用于结果上限的 topk，例如 `sql(query="SELECT * FROM tracks WHERE date>=2020 ORDER BY tempo", topk=100)`。

**BM25（稀疏检索）：** 该工具使用 BM25 排序函数 [22] 提供经典的基于词元的文本检索。BM25 提供词法匹配，因此对拼写错误常见、精确字符串匹配困难的文本查询尤其有效。我们构建五个文本语料：title、artist、album、lyrics 以及 attributes（语义标签）。工具参数包括 query、corpus 与 topk，例如 `bm25(query="taylor swift songs", corpus="artist", topk=100)`。

**Text-to-Item（稠密检索）：** 该工具通过把文本查询映射到跨多种模态的音乐内容，借助自然语言描述实现语义音乐发现。利用预训练的文本编码器 [32] 与多模态编码器 [31, 27]，该工具在相应嵌入空间中按余弦相似度检索最相似的物品。工具参数包括 query、物品模态类型、向量数据库类型与 topk，例如 `text_to_item(query="Tracks with an album cover that shows a baby swimming underwater.", item_modality="image", vector_db="image", topk=20)`。

**Item-to-Item（稠密检索）：** 该工具通过用稠密表示寻找相似物品，支持基于样例的推荐。LLM 根据先前推荐的曲目或多轮对话中用户提供的样例生成曲目 ID，然后我们从预先抽取的向量数据库中查找对应嵌入 [31, 27, 21]，进行基于相似度的检索。工具参数包括曲目 ID、物品模态类型、向量数据库类型与 topk，例如 `item_to_item(track_id="22L7bfCiAkJo5xGSQgmiIO", item_modality="audio", vector_db="audio", topk=20)`。

**User-to-Item（稠密检索）：** 该工具使用通过收听历史训练得到的用户嵌入提供个性化推荐 [21]。与由用户查询激活的其他工具不同，该工具使用来自用户画像信息的用户 ID 激活。工具参数包括 user_id 与 topk，例如 `user_to_item(user_id=10021, topk=200)`。

**Semantic IDs（生成式检索）：** 语义 ID 是由物品内容特征导出的离散表示 [20, 15]。内容被编码为稠密嵌入，再用残差向量量化器（Residual Vector Quantizer, RVQ）量化为离散码本索引。语义 ID 作为上下文信息，帮助 LLM 理解音乐的多模态属性。我们从码位到物品 ID 建立倒排索引，以便按精确码匹配或较小编辑距离快速查找。工具参数包括物品模态类型、语义 ID 索引与 topk，例如 `semantic_id(item_modality="audio", indices=[52, 42, 5, 9], topk=20)`。

### 2.3 In-Context Information for Inference 推理所用的上下文信息

在所提出的框架中，推荐基于提供给 LLM 的上下文信息作出。这一条件提示包含四类信息。

**系统提示（System Prompt）：** 框架的两个阶段有两种不同提示：一种用于工具调用，另一种用于回复生成。对于工具调用，我们设计结构化的三阶段提示，把复杂的推荐过程分解为规划、检索与重排序阶段。阶段 1（规划）要求 LLM 选出确切的检索工具与重排序工具，并给出各自选择的理由。阶段 2（检索）执行所选检索工具，从音乐数据库收集至少 topk 个互不重复的 track_id。阶段 3（重排序）应用所选重排序工具对候选重新排序，以提高推荐质量。该工作流施加严格约束：工具必须按顺序使用（检索 → 重排序），角色互补且功能不重叠。回复生成提示旨在清晰解释推荐结果，确保所推荐曲目与用户查询一致。

**工具函数（Tool Functions）：** 我们提供完整的工具函数列表及其 JSON schema，包括名称、描述与参数数据类型。详细函数示例见附录 A。

**用户画像（User Profiles）：** 为了个性化，我们把用户人口统计信息与近期收听历史作为上下文提供给 LLM。人口统计信息包括用户 ID、类型、年龄组与性别。用户 ID 作为推理时的上下文信息，以便正确激活 “User-to-Item” 工具。对于近期收听历史，我们纳入用户收听会话中最近五首曲目的元数据，每首曲目的信息包括元数据、属性与语义 ID。

**先前对话历史（Previous Conversation History）：** 我们把先前对话状态作为上下文提供给 LLM。对话状态包括用户查询、被推荐的音乐以及 LLM 的回复。为纳入音乐的多模态信息，上下文中不仅包含曲目 ID，也包含元数据、属性与语义 ID。
