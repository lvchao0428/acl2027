## Abstract 摘要

推荐系统（RecSys）被广泛用于各种现代数字平台，并受到大量关注。传统推荐系统通常只关注固定而简单的推荐场景，因此难以泛化到交互范式中新的、未见过的推荐任务。近来，大语言模型（large language models, LLMs）的进展变革了 RecSys 的基础架构，推动其演进为更智能、可交互的个性化推荐助手。然而，多数现有研究依赖固定的、特定于任务的提示模板来生成推荐并评估个性化助手的性能，这限制了对它们能力的全面评估。原因是常用数据集缺少反映真实推荐场景的高质量文本用户查询，因而不适合评估基于 LLM 的个性化推荐助手。为填补这一差距，我们提出 RecBench+，一个新的数据集基准，用于评估 LLM 在 LLM 时代处理复杂用户推荐需求的能力。RecBench+ 包含多样的查询，同时覆盖硬条件与软偏好，并具有不同难度。我们在 RecBench+ 上评估了常用 LLM，并得到如下发现：1）LLM 已初步表现出充当推荐助手的能力；2）LLM 更擅长处理条件被显式陈述的查询，而在需要推理或包含误导信息的查询上面临挑战。数据集已发布于 https://github.com/jiani-huang/RecBenchPlus 。

## 1 The RecBench+ Benchmark RecBench+ 基准

在本节中，我们首先概述 RecBench+ 基准。然后，我们给出所提出数据集中每种数据类型的构建方法。

### 1.1 Overview 概述

在实际应用中，用户需求大体可分为两类，每一类都要求基于 LLM 的推荐助手具备专门能力。第一类由具体条件或约束驱动，例如按某位导演或某种类型要电影。这一场景要求推荐助手具有强推理能力，因为它需要准确解释并应用给定约束来生成合适的推荐。第二类不涉及指定条件，而是要求推荐助手基于对用户画像的理解来生成推荐（例如用户兴趣、职业、性别），这强调助手解释画像并提供个性化建议的能力。鉴于这两种场景对推荐助手的能力要求不同，我们构建两种不同的查询类型来评估其性能：基于条件的（Condition-based）与基于用户画像的（User Profile-based）。如表 1 所示，我们的基准使用 Amazon-Book 与 Movielens-1M。下面详述基于这些来源构建 Condition-based 与 User Profile-based 查询的方法。

脚注：与 10M/20M 版本不同，MovieLens-1M 包含必要的用户人口统计数据。

#### 1.1.1 Condition-based Query 基于条件的查询

Condition-based Query 模拟用户施加具体约束的场景（例如特定导演或类型）。核心挑战在于准确满足这些条件。为评估推理能力，我们把这类查询分为三种：显式条件查询（Explicit Condition Query，直接陈述的约束）、隐式条件查询（Implicit Condition Query，需要多跳推理的含糊输入）以及误导条件查询（Misinformed Condition Query，包含错误或拼写错误）。

- **显式条件查询：** 这些查询以自然语言形式显式指定被推荐物品应当满足的条件。例如查询 “Can you recommend movies featuring Gwyneth Paltrow?” 直接陈述推荐必须满足的条件（“featured by Gwyneth Paltrow”）。显式条件查询相对直接，因为约束被清楚表述。
- **隐式条件查询：** 与显式条件查询不同，隐式条件查询涉及不完整的说明，需要多跳推理才能推出目标条件。例如，请求 “movies with the same cinematographer as Stay Hungry and Beethoven” 需要先推断出未说出的名字（David Worth）。这一类别是对推理能力更具挑战的基准。
- **误导条件查询：** 用户有时会在查询中提供关于物品的不正确或误导性信息。例如查询 “I like ‘Avatar’ directed by Spielberg. Please recommend similar movies directed by him.” 错误地把电影 Avatar 归于 Steven Spielberg。期望推荐助手能够先识别并纠正这一错误信息——认识到 Avatar 并非 Spielberg 执导——再生成相关推荐。这一子类对推荐助手的稳健性构成显著挑战，要求它准确识别用户查询中的不准确信息。

#### 1.1.2 User Profile-based Query 基于用户画像的查询

在许多真实场景中，用户可能不提供过滤物品的具体条件，而是期望根据其画像信息得到个性化结果，例如兴趣（如对特效的兴趣）或人口统计属性（如性别、职业）。这是因为用户往往对自己的需求缺乏清晰理解，转而寻求与其背景或偏好直观一致的推荐。为应对这一常见情况，我们引入 User Profile-based Query，通过要求推荐助手基于用户画像信息生成个性化建议来模拟这些场景。我们进一步把 User Profile-based Query 分为基于兴趣的（Interest-Based）与基于人口统计的（Demographics-Based）查询，因为兴趣反映用户的动态偏好，而人口统计捕捉性别或职业等更稳定、并影响其需求的属性。

- **基于兴趣的查询：** 这些查询反映无法用具体条件清楚定义的用户兴趣。例如，历史上看过 “The Tree of Life” 和 “2046” 的用户可能偏好具有独特叙事与视觉美感的电影。为捕捉这类兴趣，我们构造诸如 “I just watched ‘The Tree of Life’ and loved its poetic storytelling and visual design. Can you recommend other movies with a similar tone?” 的查询。这类查询没有显式条件，但要求个性化推荐助手理解并基于用户的个人兴趣建议物品。
- **基于人口统计的查询：** 这些查询关注用户的人口统计属性如何影响推荐。不同用户基于年龄、性别或职业，可能有不同的偏好与需求。例如，哲学教授可能对探讨道德困境的电影感兴趣。利用这些模式，我们可以构造如下查询：“I’m a philosophy professor looking for movies with complex themes and moral dilemmas. Can you recommend any?” 通过与真实世界的人口统计行为对齐，这些查询可以反映个性化推荐助手应当提供的个性化推荐，确保建议与用户的背景和身份相关并量身定制。

### 1.2 Condition-based Query Construction 基于条件的查询的构建

用户查询常常通过对应于物品属性的条件来表达偏好，例如按类型、导演或演员过滤电影。然而，由于物品与其属性之间关系复杂，生成反映用户如何组合这些属性的真实、多样查询是困难的。值得注意的是，知识图谱（Knowledge Graph, KG）作为一种结构化表示，显式地把物品（例如电影）连接到其属性（例如导演），并捕捉它们之间的相互依赖（例如 “导演 X 经常与演员 Y 合作”）。因此，我们提议利用 KG 抽取有意义的条件，并生成与真实用户行为对齐的查询。具体而言，我们的方法包含三个关键步骤：物品知识图谱（Item KG）构建、共享关系抽取，以及查询生成，如图 2 所示。我们首先构建 Item KG，把物品链接到其属性。接下来，我们从用户交互历史中识别共享相同属性的物品集合（例如由 Christopher Nolan 执导的电影），形成查询的条件。最后，我们采用 LLM 模拟用户，并基于这些抽取到的条件生成查询。满足条件的物品集合可以作为评估的真实答案。

#### 1.2.1 Item KG Construction 物品知识图谱构建

Item KG 是在 RecBench+ 中生成真实 Condition-based Query 的基础。我们针对电影与图书领域利用不同的 KG：

- **电影：** 我们从维基百科抽取数据，聚焦导演、演员、作曲者与类型等 7 个关键属性。每部电影节点都链接到这些属性。
- **图书：** 我们使用 Amazon Book Dataset 的元数据，把作者与类别等属性连接到图书节点。

KG 建成后，我们把它们与传统推荐数据集 Movielens-1M 和 Amazon-Book 结合起来，逐步生成条件与查询。

#### 1.2.2 Shared Relation Extraction 共享关系抽取

共享关系是用户交互历史中的物品之间共有的属性。例如，若用户看过多部同一导演或同一主演的电影，这些共享属性有助于生成 Condition-based Query。给定用户 \(u\) 及其交互历史 \(H_u = \{i_1, i_2, \ldots, i_k\}\)，我们使用 KG 检索函数 \(R\)，在 \(H_u\) 的物品子集上识别共享属性（关系）。每个共享关系定义为元组 \((r, t)\)，其中 \(r\) 是关系类型（例如 “directed by”、“starring”），\(t\) 是目标值（例如导演姓名）。抽取过程产生多组共享关系及其对应的物品子集，可表示为：

\[
R(H_u, KG) = \{(G_{\mathrm{sub}}, C_{\mathrm{shared}}) \mid G_{\mathrm{sub}} \subseteq H_u,\ C_{\mathrm{shared}} = \{(r_1, t_1), (r_2, t_2), \ldots\}\}. \quad (1)
\]

这里 \(G_{\mathrm{sub}}\) 表示共享同一组关系 \(C_{\mathrm{shared}}\) 的物品子集。抽取到的共享关系随后将作为查询生成的条件。

#### 1.2.3 Query Generation 查询生成

从用户交互历史中抽取共享关系之后，我们生成三类 Condition-based Query：显式、隐式与误导。生成这些条件与最终查询的步骤如下：

- **显式条件构造：** 对于显式条件，我们直接采用从用户交互历史中抽取的共享关系。具体地，我们设显式条件 \(C_{\mathrm{explicit}} = C_{\mathrm{shared}}\)。这意味着条件直接来自用户交互过的物品所关联的共享属性（例如导演、类型）。
- **隐式条件构造：** 对于隐式条件，我们不直接陈述具体取值（例如导演姓名），而是利用 KG 通过相关物品间接描述它们。例如，不直接提及 James Cameron，我们可能使用 “the director of ‘The Abyss’”。具体地，对于共享关系 \((r_m, t_m) \in C_{\mathrm{shared}}\)（例如 (director, Cameron)），我们把需要被推断的值 \(t_m\)（例如 Cameron）替换为描述 \(t_m\) 与 KG 中另一物品 \(i_k\)（例如 The Abyss）之关系的间接指称。这可以表示为：

\[
i_k \in \{ i \in \mathcal{I} \mid (t_m) \xrightarrow{r_m} (i)\ \text{in KG} \}, \quad (2)
\]

其中 \(\mathcal{I}\) 是 KG 中全部物品的集合。（箭头在抽取中因换行断开，按从 \(t_m\) 经关系 \(r_m\) 指向物品 \(i\) 读出。）得到的隐式条件为：

\[
C_{\mathrm{implicit}} = (r_i,\ \mathrm{ref}(i_k)), \quad (3)
\]

其中 \(\mathrm{ref}(i_k)\) 表示对 \(i_k\) 的文本指称。例如，共享关系 (director, Cameron) 可以变换为隐式条件 (director, “the director of ‘The Abyss’”)，其中 “The Abyss”（\(i_k\)）从 KG 中检索得到，经由 “director” 关系（\(r_0\)）与 “Cameron”（\(t_0\)）相连。

- **误导条件构造：** 对于误导条件，我们有意在条件中引入事实错误，模拟真实用户可能错误引用属性或关系的情形。为生成误导条件，对于共享关系 \((r_i, t_i) \in C_{\mathrm{shared}}\)，我们从 KG 中随机选择一个或多个与 \(t_i\) 不具有指定关系 \(r_i\) 的物品 \(\{i_1, i_2, \ldots, i_m\} \in \mathcal{I}\)（即对每个 \(i_k \in \{i_1, \ldots, i_m\}\)，\(i_k \not\rightarrow t_i\)）。然后我们用“错误信息”构造条件，虚假地声称这些物品通过 \(r_i\) 与 \(t_i\) 相关：

\[
C_{\mathrm{misinformed}} = (r_i,\ t_i,\ \text{error info: } \{i_1, i_2, \ldots, i_m\} \xrightarrow{r_i} t_i), \quad (4)
\]

其中集合 \(\{i_1, \ldots, i_m\}\) 包含 KG 中实际上并不与 \(t_i\) 共享关系 \(r_i\) 的物品。例如，一条误导条件可以是 (director, Cameron, error info: Cameron is the director of ‘Startreck’)。

- **查询生成：** 对每种条件类型，我们应用 GPT-4o [11] 生成相应查询：

\[
q = \mathrm{LLM}(C, P), \quad (5)
\]

其中 \(P\) 是提示。对每条生成的查询 \(q\)，我们构造一个样本，由下式组成：

\[
(q,\ H'_u,\ G_q),\quad \text{where } H'_u = H_u \setminus G_q, \quad (6)
\]

\[
G_q = \{ i \in \mathrm{KG} \mid C_{\mathrm{shared}} \subseteq A_i \}. \quad (7)
\]

这里 \(H'_u\) 是排除了 \(G_q\) 中物品之后的用户交互历史，\(G_q\) 包含满足查询条件的真实物品。\(A_i\) 表示物品 \(i\) 在 KG 中的属性。

### 1.3 User Profile-based Query Construction 基于用户画像的查询的构建

除了提供具体约束，用户可能只提供观看历史或人口统计属性（例如年龄、职业）等基本个人信息。为评估 LLM 推荐助手处理这类场景的能力，我们引入 User Profile-based Query，其目标是在不要求具体过滤条件的情况下，基于用户画像信息生成个性化推荐。如第 1.1.2 节所述，User Profile-based Query 包含两个子类：Interest-based Query 与 Demographics-based Query。构建过程见图 3。

#### 1.3.1 Interest-based Query 基于兴趣的查询

这些查询旨在捕捉并非由具体条件显式定义、而是从用户交互中推断出的用户兴趣。为有效模拟真实场景，我们聚焦于捕捉从多名用户的共享行为中涌现的集体兴趣，它们更能代表一般偏好与趋势。例如，若许多看过 “The Dark Knight” 的用户也看了 “Inception”，这表明对动作与悬疑有明确兴趣。这样，我们可以构造反映由共享行为导出的集体用户兴趣的查询。具体地，我们首先识别共同兴趣集合（Common Interest Set），即被多名用户频繁连续交互的物品集合。令 \(H_u\) 表示用户 \(u\) 的交互历史，\(H = \{H_u \mid u \in U\}\) 表示全部用户的交互历史集合。共同兴趣集合可定义为：

\[
S = \{ s \mid \exists u \in U,\ s \subseteq H_u,\ f(s) \ge \theta \}, \quad (8)
\]

其中 \(f(s)\) 是序列 \(s\) 在全部用户历史中的频率，\(\theta\) 是预定义的频率阈值。

一旦识别出共同兴趣集合，我们进而抽取前序物品序列，即通常出现在共同兴趣集合中的物品之前的物品序列。令 \(P(s)\) 表示目标序列 \(s\) 的前序物品序列集合。前序序列可定义为：

\[
P(s) = \{ p \mid \exists u \in U,\ p \prec s \subseteq H_u \}, \quad (9)
\]

其中 \(p \prec s\) 表示序列 \(p\) 在交互历史 \(H_u\) 中紧接出现在序列 \(s\) 之前。

基于所识别的共同兴趣集合与前序物品序列，我们使用 LLM 分析模式，并推断多名用户共同兴趣背后的理由。生成的查询旨在同时反映物品的上下文特征与用户的共同兴趣。

#### 1.3.2 Demographics-based Query 基于人口统计的查询

人口统计相似的个体常常共享偏好；例如，儿童通常偏爱动画电影（如 Disney），而青少年可能偏爱动作片或超级英雄电影。利用这一点，我们按属性排列对用户分组（例如 18–24 岁的学生），并识别他们消费最多的物品。然后我们把这些人口统计信息与物品列表输入 LLM，以合成捕捉群体特定模式的查询。所识别的热门物品作为评估的真实答案。

### 1.4 Data Filtering and Selection 数据过滤与选择

对于 Condition-based Query，我们用字符串匹配检查所提供的信息（例如演员、导演）是否出现在查询中，并滤除省略了该信息的查询。对于 User Profile-based Query，我们人工核验查询，并滤除过于宽泛或不合理的查询。

## 2 Experiments 实验

### 2.1 Experiments Settings 实验设置

#### 2.1.1 Baselines 基线

我们评估若干广泛使用的模型，包括 GPT-4o（2024-08-06）[11]、GPT-4o-mini（2024-07-18）[11]、Llama（Llama-3.1-70B-Instruct）[6]、Gemini（gemini-1.5-pro-002）[30]、Claude（claude-3-5-sonnet-20241022）、DeepSeek-V3 [17] 与 DeepSeek-R1 [8]。然而，我们未能测试 GPT-o1 [12]，因为它把我们的提示标记为违反使用政策。此外，我们进一步在 Qwen-2.5-3B-Instruct 与 LLaMA-3.2-3B-Instruct 上进行全参数监督微调（supervised fine-tuning, SFT）以及基于 GRPO [27] 算法的强化微调（reinforcement fine-tuning, RFT），以探索它们在任务特定优化下的潜在性能增益。

#### 2.1.2 Evaluation Metrics 评估指标

我们使用下列指标评估 LLM 的性能。为模拟用户通常不预先规定所需推荐数量的真实场景，我们不在测试提示中指定固定的推荐数量 \(K\)；不过，我们也在第 2.2 节中纳入若干固定 \(K\) 的实验作为参照。

- **Precision：** 被推荐物品中实际与用户查询相关的比例。
- **Recall [10]：** 在全部可用相关物品中被成功推荐的相关物品比例。
- **条件匹配率（Condition Match Rate, CMR）：** 满足指定条件的被推荐物品百分比。对于 Condition-based Query，检查模型的推荐是否严格与给定条件对齐很重要，因为不满足这些条件的物品很可能不能令人满意。Precision 与 Recall 等传统指标不足以评估这一对齐。因此，我们提出 CMR 来达到这一目的。
- **未能推荐（Fail to Recommend, FTR）：** 该指标度量模型未能生成推荐物品的查询比例。较低的 FTR 更可取，表示模型能够生成物品列表。然而，在误导条件查询中，较高的 FTR 表明模型识别不正确信息、从而避免错误推荐的能力。

### 2.2 Results on Condition-based Query 基于条件的查询上的结果

**观察 1。** 就不同 LLM 而言，GPT-4o 与 DeepSeek-R1 优于其他模型。如表 2 所示，GPT-4o 在电影与图书数据集上取得最高的 Precision 以及第二高的平均 CMR，而 DeepSeek-R1 在 Recall 上排名第一、在 Precision 上排名第二。值得注意的是，具有高级推理能力的模型，例如 DeepSeek-R1，在处理需要推理的查询类型时表现出色。例如，在隐式条件查询中，当从显式条件过渡到隐式条件时，DeepSeek-R1 的性能下降显著小于其他模型。这使它在隐式条件查询性能上处于领先。这表明高级推理能力使基于 LLM 的助手能够推断条件中未显式提及的隐含属性，从而产生更准确的推荐。附录 B 中有一个案例研究。

**观察 2。** 就不同查询类型而言，模型性能随查询难度增加而下降。在电影与图书数据集上，多数 LLM 在显式条件查询上表现最好，优于另外两种查询类型。这表明 LLM 更擅长处理清楚陈述条件的查询。相比之下，隐式条件带来更大挑战，因为模型必须推断关于物品的、未被显式陈述的约束。值得注意的是，像 DeepSeek-R1 这样具有强推理能力的模型保持强性能，说明受益于其推理能力。此外，误导条件被证明最困难，Recall 与 CMR 最低，表明当查询包含误导信息时，在提供个性化推荐上经常失败。而且，这一条件下较高的 FTR 表明，基于 LLM 的助手可能利用一般知识来检测查询中的错误信息，并避免直接生成不准确的推荐。

**观察 3。** 就查询中条件数量的影响而言，Precision 与 Recall 随条件增多而提高，而 CMR 在显式条件查询上下降、在其他类型上上升。如图 4 所示，我们以电影数据集为例，研究改变查询中条件数量对模型性能的影响。我们注意到，额外条件收窄推荐范围，从而提高推荐准确率。例如，“Action movies by Nolan released after 2010” 的候选集合远小于 “movies by Nolan”，从而减少歧义并提高推荐的相关性。条件数量对 CMR 的影响因查询类型而异。在显式条件查询中，单一条件时 CMR 最高，因为增加更多条件会提高满足全部约束的难度，导致覆盖下降。相比之下，对于隐式与误导条件查询，额外条件提供更多上下文，使模型能更好地推断隐式条件，并减轻条件中事实错误的影响。因此，在这些查询类型中，CMR 随条件增多而提高。

**观察 4。** 就用户–物品交互历史的影响而言，纳入它们从两个关键方面提升推荐质量。纳入用户–物品交互历史的效果见图 5。第一，纳入用户–物品历史通过生成更个性化的推荐列表，在全部查询类型上提高 Precision。原因可能是条件有限的查询（例如 “movies directed by Nolan”）往往产生很大的候选池。通过利用历史交互，模型可以优先选择既符合用户偏好又满足查询条件的物品，从而有效过滤不相关候选。

第二，纳入用户历史并不总是提高 CMR。通过分析 LLM 助手的输出，我们注意到加入历史也可能引入降低严格条件遵循的“干扰”物品。例如，由于用户历史中的奇幻类型偏向，LLM 助手可能为 “Nolan films” 推荐 “The Prestige”。这表明纳入历史可能转移模型的注意力，使严格遵循给定条件变得更困难。这些结果突出一个重要权衡：虽然纳入历史可以增强模型对用户偏好的理解，它也可能妨碍模型与查询中具体要求的紧密对齐。因此，平衡历史数据的影响与精确遵循条件的需要，对于优化推荐助手的性能至关重要。

**观察 5。** 要求 LLM 生成 \(K\) 个推荐与先前观察一致。对于 Condition-based Query，存在样本中满足查询条件的物品数量可能少于 \(K\)。在这种情况下，要求模型输出 \(K\) 个推荐可能导致次优结果。因此，在表 2 的主实验中，我们没有要求模型生成 \(K\) 个推荐。然而，为进一步探索这一点，我们也进行了额外实验，指示 LLM 输出 \(K\) 个物品。结果见表 3，基于电影数据集，并与先前发现一致：LLM 在显式条件查询上表现最好，性能在隐式条件与误导条件查询上逐渐下降。

**观察 6。** 就微调的性能而言，SFT 与 RFT 都显著增强模型的推荐性能。鉴于近来使用 RFT 改进模型推理能力的兴趣 [27, 34]，我们希望探索它在这一场景中的潜力。我们对 Qwen-2.5-3B-Instruct 与 LLaMA-3.2-3B-Instruct 应用全参数 SFT 与基于 GRPO [27] 的 RFT，并评估不同查询类型上的 recall。如表 4 所示，两种微调范式都显著提高了模型的推荐性能。然而，仅用 RFT 训练的模型差于用 SFT 训练的模型。这一性能差距可能归因于缺少对推理的预热阶段，而预热对强化学习期间的有效探索是必要的 [1]。为验证这一点，我们进一步把训练过程分为两个阶段：先用 SFT 作为预热，再进行 RFT 训练。实验结果表明，这一两阶段方法进一步提高了 LLM 的性能。例如，在电影的显式条件查询上，SFT+RFT 模型取得 0.410 的 recall，优于仅 SFT 的模型（0.391）和仅 RFT 的模型（0.178）。

### 2.3 Results on User Profile-based Query 基于用户画像的查询上的结果

**观察 7。** 就不同 LLM 而言，Gemini-1.5 Pro 与 DeepSeek-R1 相比其他模型表现更好。如表 5 所示，更大、更先进的模型，例如 DeepSeek-R1 与 Gemini-1.5-Pro，一致地取得更高的 Precision 与 Recall。相比之下，GPT-4o-mini 等较小模型往往落后。从 FTR（未能推荐）指标看，多数模型失败率较低，表明它们能够有效遵循指令并按要求的格式生成推荐列表。

**观察 8。** 就不同查询类型而言，基于人口统计的查询的 Recall 低于基于兴趣的查询，但 Precision 相近。在全部模型上，基于人口统计的查询的 Recall 总体上低于基于兴趣的查询。这表明当依赖用户人口统计时，LLM 难以识别相关推荐。Recall 的差异可归因于这些查询的构建方式不同。基于兴趣的查询利用清楚的兴趣，使模型更容易生成相关推荐。相比之下，基于人口统计的查询要求推荐助手从更广泛的人口统计与行为趋势中推断偏好，从而引入更多变异与歧义。

**观察 9。** 对于基于兴趣的查询，由较不普遍的兴趣构造的查询往往更具挑战。如图 6 所示，我们按流行度把查询分为四组，并在电影与图书数据集上进行实验。可以观察到，被更多用户共享的兴趣往往产生更高的 Precision 与 Recall。这很可能是因为被广泛共享的兴趣更容易被 LLM 识别和解释，从而导致更好的性能。相比之下，图书领域呈现出相反趋势。这是由于图书数据的性质与评估过程。图书常常有多个版本或出版社，流行书名往往有更多变体。因此，流行图书（例如 “Dune”）可能因为 LLM 混淆版本/出版社（例如 “Dune: 1965” 与 “2021 adaptation”）而得到更低的指标。对于较不流行的图书，变体更少，LLM 更容易给出精确匹配，从而导致更高的性能指标。
