## 第 1 节 Introduction

引言先从问题分解写起。无论微调还是上下文学习，显式生成中间步骤都被证明能提高复杂问题的准确率。Nye 等人的 Scratchpad 表明，微调语言模型去生成执行结果时，若让它预测完整的执行轨迹，结果更好。后续工作则提示大模型先把难题拆成较小的推理步骤，再给出最终答案。作者认为这些方法的中间表示本质上仍是自然语言，而自然语言作为推理媒介天生有损耗、也有歧义。BLENDSQL 改用类似 SQL 的写法来分解问题，借助关系代数的组合性，使推理更确定，中间步骤也更容易解释。

第二块是智能体。已有框架把主任务拆给若干专家，专家可以是 Python 脚本、API、工具或语言模型，并由路由器或规划器决定如何拆分。基于规则的路由器很常见；大模型能处理复杂文本之后，也被用作规划器。规划器读入任务，输出子任务列表、该用哪一个专家、专家的输入是什么、期望它返回什么。由于单个专家的职责很窄，近期工作把精力主要放在规划器上，做法要么利用规划器的上下文学习，要么微调规划器。还有工作用上下文学习来构造数据。BLENDSQL 里的解析器就扮演规划器，决定回答问题时要调用哪些 API，文中称为 Ingredients。差别在于，它超出“用单一字符串表示复杂分解”的做法，用稳健、结构更完整的抽象语法树简化智能体框架，再把这棵树编码成单一字符串。作者还强调，BLENDSQL 不只是把原句改写成形式结构：它会利用参照数据库、输入提示和语言模型的内部知识，往查询里补充信息。

第三块把 SQL 当作已经有效的中间表示。在 Spider 上，已有系统在少样本或零样本设置里取得了很强的 text-to-SQL 结果。即便任务本身不是 text-to-SQL，SQL 也适合充当其他推理的中间语言。Hu 等人把对话状态跟踪改写成 text-to-SQL：把 MultiWOZ 的领域和槽位编码成序列化的数据库，用 SQL 代替传统的键值预测，并报告了明显提升。

第四块进入混合问答。与 text-to-SQL 不同，混合问答要隐含地决定去查表格、查非结构化数据，还是两者都查。Li 等人把这个决定做显式，在端到端模型和生成中间 SQL 的解析器之间路由，但两个系统彼此隔离，信息传不过去。本文把混合问答定义为：利用一份同时包含表格和非结构化多模态内容的语料来回答问题。多模态可以包括文本、图像、音频和视频，本文的主要对象是非结构化文本加上表格；扩展到图像的讨论放在附录。UniK-QA 的方向相反，它把结构化表格转成非结构化文本，并用知识库到文本的预处理模型，在若干知识库问答基准上得到提升。作者指出，那种预处理常把关系假定成简单的三元组，谓词来自表名；而主语和宾语之间的关系往往嵌在异构来源里，例如音频、文档或列名，于是还得再开发专门的转换模型。BLENDSQL 选择把非结构化文本收进表格，而不是把表格摊成文本。

和本文最接近的是 BINDER，它把大模型推理嵌进 SQL、Python 等符号语言。作者承认框架上受其启发，并列出三点差别。第一，BLENDSQL 做的是专门服务 SQL 的 API，能在含有非结构化内容的多表数据库上推理，并能执行和优化带 JOIN、别名、条件表表达式以及大多数其他 SQLite 操作的查询。第二，解码可以按数据库 schema 施加约束。第三，用户可以自己添加任意多个自定义函数，放进 BLENDSQL 脚本使用。

贡献概括为三条。据作者所知，这是第一次把混合问答的上下文整体看成一个关系数据库。他们发布开源查询语言 BLENDSQL，用来编排并优化横跨 SQL 逻辑与大模型推理的混合函数。实验主张是：只需少量上下文范例，BLENDSQL 就能超过端到端方法，同时少用 35% 的 token，并且不直接把非结构化上下文放进提示。

## 第 2 节 BLENDSQL: Overview

BLENDSQL 被实现为 SQLite 的超集。脚本执行后返回一个称为 smoothie 的对象，里面既有最终结果，也保留中间推理步骤。两个部件分别称为原料 ingredients 和搅拌机 blender。

### 2.1 Blender 与 Parser

blender 指那个真正执行原料函数的语言模型：BLENDSQL 脚本里每次调用原料，都由它接收相应提示并完成计算。parser 出现在执行之前，拿到一组少样本例子，再根据问题和数据库上下文生成一条 BLENDSQL 查询。核心实验里，blender 和 parser 都使用 GPT-4-0613。

### 2.2 Ingredients

原料是脚本的核心，是一些子程序，用来把特定逻辑操作交给基于大模型的函数。句法上用双花括号标出。整个 BLENDSQL 语法是一套解析表达式文法，用 PyParsing 实现。和普通 SQL 一样，原料调用可以完全递归，一次调用的上下文里可以再包含其他原料。

LLMMap 是一元标量函数，地位类似 SQLite 中的 LENGTH 或 ABS。它接受形如“表名::列名”的字符串参数，对目标列里的每个值做映射，再把映射结果写成临时表中的新列，供外层查询使用。作者用“这是不是团队项目”来说明其必要性：同一语义在列里会写成 team event、4x100 medley relay 等不同字符串，纯字符串规则很难覆盖整张表。LLMMap 按语义所指做变换，从而得到一个可泛化的列。

LLMQA 是聚合函数，把表的一个子集收成单个标量。它可以用 options 参数限制输出：结果必须是某一指定列里已经存在的值。这一约束解码在脚注中说明，是用 guidance 调整 OpenAI API 的 logit bias 来实现的。文中的例子让 LLMQA 同时接收一段非结构化文档、问题“哪一个 NBA 赛季因 COVID-19 而停赛”，以及一组用来约束生成的列值。事实核验使用变体 LLMValidate，返回值只有布尔真或假。

LLMJoin 在两组值之间建立自定义对应，再根据这个对应生成辅助表，以便执行 SQL 的 INNER JOIN。它针对的情形是：没有合格的外键，但两边在语义上仍能对齐。例子是 joshua fields 和 josh fields (pitcher) 指向同一个人。用 LLMJoin 把这两种写法对齐，完成的是一种实体链接。示例库来自 HybridQA：结构化表存放维基百科页面上的表格，另一张文档表存放条目正文，并用 SQLite 的 FTS5 做全文索引。这个库同时支撑上面的连接例子和下一小节的过滤例子。

### 2.3 Query Optimizations

能先做的 SQL 谓词会放进子查询，结果写入本次会话的临时表。原生 SQLite 操作相对便宜，因此昂贵的大模型原料只会看到生成可靠结果所需要的那一份数据，既不多也不少。文中的演示是：只把结构化表中学校等于 university of georgia 的那些行传给后续的大模型原料。这些优化由一套较完整的测试套件验证。
