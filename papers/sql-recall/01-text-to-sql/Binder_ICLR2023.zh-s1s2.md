## ABSTRACT 摘要

尽管端到端神经方法近来在性能和易用性上主导了 NLP 任务，但它们缺乏可解释性与稳健性。我们提出 BINDER，一个免训练的神经–符号框架，把任务输入映射为一个程序。该程序：（1）允许把语言模型（language model, LM）功能的统一 API 绑定到某种编程语言（例如 SQL、Python）上，以扩展其语法覆盖，从而处理更多样的问题；（2）在执行期间，既把 LM 用作程序解析器，也把它用作 API 所调用的底层模型；（3）只需要少量上下文示例标注。具体而言，我们采用 GPT-3 Codex 作为 LM。在解析阶段，仅凭少量上下文示例，Codex 就能识别出任务输入中无法由原编程语言回答的部分，正确生成 API 调用来提示 Codex 解决这些无法回答的部分，并确定把 API 调用放在何处，同时与原语法兼容。在执行阶段，只要 API 调用中的提示得当，Codex 就可以完成多种功能（例如常识问答、信息抽取）。BINDER 在 WIKITABLEQUESTIONS 和 TABFACT 数据集上取得了最先进的结果，并给出显式的输出程序，有助于人工调试。需要指出，此前最好的系统都在数万条任务特定样本上做了微调，而 BINDER 只把数十条标注用作上下文示例，不做任何训练。代码见 https://github.com/hkunlp/binder 。

## 1 INTRODUCTION 引言

自然语言处理任务上的性能，目前由直接把输入映射到输出的神经端到端系统主导（Devlin et al., 2019; Liu et al., 2019; Lewis et al., 2020; Raffel et al., 2020, i.a.）。这些端到端方法灵活、易用，但缺乏可解释性与稳健性。这与符号方法形成对照：符号方法产生显式的中间表示，例如逻辑形式、推理路径或程序代码，随后可以执行以得到最终输出（Zettlemoyer & Collins, 2005; Gulwani et al., 2017; Chen et al., 2019b, i.a.）。【抽取不清】The intermediate form produced by these the resulting execution makes them more robust to input changes. 然而，其语义覆盖受所选符号语言之语法能力的限制（例如无法处理图 1 中的 “North America?”），因而在真实世界的多样问题上会失败；中间形式的标注也需要专家知识与研究者的劳动。已有一些工作（Andreas et al., 2016; Gupta et al., 2019; Khot et al., 2021; Zhu et al., 2022, i.a.）试图把神经模块与符号语言结合起来（神经–符号，neural-symbolic），以同时利用两类方法的优点。然而，它们需要精心的人工符号语言设计，并校准相应的神经模块，才能在特定领域、借助大量训练数据来解决问题。更具体地说，这些工作大多提出任务特定的符号语言及相应模块，只覆盖特定任务和领域中有限的语义现象。因此，把它们适配到新任务和新领域时，必须引入新的语言和神经模块。其覆盖范围仍然受定制符号语言和神经模块的限制。此外，它们需要多样且大规模的训练数据，才能保证所有模块都得到充分训练。因此，我们期望一种神经–符号系统：它支持灵活的神经模块调用，从而提高符号语言的覆盖，同时只需要少量标注。

我们提出 BINDER，一个免训练的神经–符号框架。它把任务输入映射为某种编程语言（例如 SQL、Python）中的可执行程序，并通过统一 API 调用语言模型（LMs; Brown et al., 2020; Chen et al., 2021）来完成多种功能，即 BINDER 程序（例如图 1 中的 Binder-SQL、Binder-Python）；所需的上下文示例只是少量“输入–BINDER 程序”标注。更具体地说，BINDER 首先提示 Codex——GPT-3 的代码预训练版本——把问题输入解析为 BINDER 程序。在此过程中，Codex 必须决定：（1）输入中哪些部分可以转换成目标编程语言（图 1 中以灰色标出的问题部分）；（2）相应的任务 API 调用（例如 `f(“North America?”; Made_in)`），用以提示 Codex 解决其余部分；（3）把这些 API 调用插入 BINDER 程序的何处。接下来，BINDER 再次提示 Codex，为任务 API 调用生成答案（给定已生成的任务提示），并把生成结果整合回编程语言。具体如图 1：API 调用中的提示（例如 “North America?”）和数据（例如列 `Made_in`）被送入 Codex，输出是一个新列，根据输入数据回答该提示（即 `Made_in` 列中的国家是否属于北美洲，回答为 yes/no）。最后，使用标准编程语言写成的程序被执行，从而得到最终答案。总之，BINDER 把灵活的功能集成进编程语言以提高其覆盖，并且只需要少量标注。BINDER 程序用对 Codex 的统一提示 API 调用取代定制神经模块，用通用编程语言取代任务特定语言，从而在开放领域中处理远为多样的任务输入，而无需复杂的语言与神经模块设计。BINDER 建立在语言模型上下文学习的进展之上，不需要任何训练，也不需要大规模标注。

我们在 WIKITABLEQUESTIONS（WIKITQ; Pasupat & Liang, 2015）和 TABFACT（Chen et al., 2019a）这两个需要在表格上进行复杂推理的结构化知识定位数据集上，展示了 BINDER 框架的有效性。以 Codex（Chen et al., 2021）作为 LM，BINDER 在 WIKITQ 和 TABFACT 上取得了最先进的结果。需要指出，此前的最先进方法都需要在超过 10K 条标注训练样本上微调，甚至需要大量任务相关的预训练数据，而我们的方法只需要大约十几条标注，且不做训练。在进一步分析中，我们发现 BINDER 在原语言语法（SQL 和 Python）无法支持的问题上增益最大，表明 BINDER 有效提高了编程语言的覆盖。我们还展示 BINDER 可以应用于多模态知识源（文本、表格、图像及其组合），所用数据集为 MULTIMODALQA（Talmor et al., 2021）。此外，与端到端方法相比，BINDER 在调试模型时更可解释，对非常大的输入更具可扩展性，对噪声输入也更稳健。

图 1 的版面为示意图，单元格、示例代码与箭头在抽取文本中相互粘连，图中表格内容【抽取不清】。可可靠阅读的图注如下。图 1：BINDER 流水线概览，分为解析与执行两个阶段。（1）在解析阶段，语言模型根据问题以及（可选的）知识源，把输入映射为 BINDER 程序。程序中以蓝色背景标出的表达式是用于获取外部结果的 API 调用。（2）在执行阶段，由语言模型根据提示实现这些 API 调用，返回值回填到原来的编程语言中。确定性的程序解释器执行不含 API 调用的程序，得到最终答案。

## 2 APPROACH 方法

**任务定义。** 给定一个 NLP 任务，其输入为自然语言问题或陈述 Q，以及可选的上下文 D（例如段落、表格、图像，或上述内容的组合），目标是基于输入输出答案 A，从而正确回应 Q。例如，在段落问答中，Q 是关于段落 D 的问题；在表格事实验证中，Q 是关于表格 D 的陈述。

### 2.1 BINDER FRAMEWORK BINDER 框架

**概述。** 用于求解 NLP 任务的 BINDER 框架定义如下：给定自然语言输入 Q 和可选上下文 D，生成一个可执行的 BINDER 程序 Z。最后，用 BINDER 解释器执行 Z，得到输出答案 A。

**BINDER 解析。** 在解析阶段，输入的自然语言 Q 被解析为 BINDER 程序 Z。BINDER 程序是符号语言中的一个表达式，可以在核心符号语言无法提供所需功能之处，可选地包含 API 调用。我们把程序中的 API 调用定义为函数 `f(Q̂; D̂)`，它接受待回答的问题 `Q̂`，以及被查询的上下文 `D̂`。这里 `Q̂` 是仅用编程语言无法回答的那一部分 Q，`D̂` 是 D 中用于回答 `Q̂` 的相关上下文。例如，图 1 中的 “North America?” 是一个 `Q̂`，回答它所对应的上下文 `D̂` 是列 `Made_in`。注意，`Q̂ = Q` 或 `D̂ = D` 也是允许的（若 `Q̂ = Q` 且 `D̂ = D`，该程序等价于用 LM 以端到端方式求解问题）。API 调用 `f(Q̂; D̂)` 的输出是对 `Q̂` 的回答，并表示为一个与符号语言语法兼容的变量，从而使程序可以执行。

**BINDER 执行。** 在执行阶段，程序 Z 由 BINDER 解释器执行，以得到答案 A。BINDER 解释器由一个标准符号语言解释器，以及实现 API 调用的模型组成。执行阶段包括词法分析、语法分析和程序求值。在词法和语法分析中，`f(Q̂; D̂)` 被加入语法，作为一个新的标识符，程序据此扩展语法被解析为抽象语法树（abstract syntax tree, AST）。在程序求值中，API 调用通过调用底层神经模型来求值。API 调用的输出被保存为与标准符号语言语法兼容的变量，因此程序最终可以由现成的符号语言解释器执行，得到输出。具体而言，BINDER 扩展了符号语言的产生式规则，以便解析 BINDER 程序的 AST。AST 按自底向上的顺序求值，因此也支持嵌套 API 调用，从而允许对复杂问题作不同程度的分解，并自由组合语言模型。语法扩展以及 BINDER 程序 AST 的更多细节见附录 A.4。

### 2.2 IN-CONTEXT LEARNING FOR BINDER 面向 BINDER 的上下文学习

近期许多工作使用大语言模型做上下文学习（Brown et al., 2020; Chen et al., 2021; Chowdhery et al., 2022b）。与微调相比，上下文学习（1）只把少量标注或演示作为提示，（2）在不训练模型参数的情况下进行推理。这两者都是传统语义解析的长期问题。我们把 BINDER 的实验建立在 Codex 之上。Codex 是 GPT-3 的代码预训练版本，已被证明在代码生成任务上表现熟练（Rajkumar et al., 2022; Chen et al., 2022），甚至在对话状态跟踪等弱相关任务上也是如此（Hu et al., 2022）。我们把 Codex 既用作语义解析器，也用作执行 API 调用功能的模型。在解析阶段，生成 BINDER 程序具有挑战性，因为插入 API 调用后，其语法不同于原编程语言的语法。因此，我们利用 Codex 的少样本泛化能力，并发现只需少量上下文示例，它就能有效学会这种修改后的语法。在执行阶段，Codex 作为底层 LM，把 API 调用的输入 `Q̂` 与 `D̂` 拼接为语言模型提示（提示风格见第 3.1 节），从而给出 API 调用的输出。Codex 的输出结果被存为标准编程语言中的变量，以便编程语言解释器在这些变量与程序其余部分的组合上执行。

具体而言，我们按如下方式对 BINDER 应用上下文学习：输入是 k 个上下文示例 `{(Q_i, D_i, Z_i)}_{i=1}^{k}` 以及推理实例 `(Q, D)`。这 k 个示例应在问题类型的多样性与模型最大输入容量之间取得平衡；它们可以人工选定（固定），也可以根据推理实例自动检索（动态）。模型输出 n 个候选 BINDER 程序 `Z = {Z_1, ..., Z_n}`，旨在解决推理问题 Q。接着，这些程序 Z 由 BINDER 解释器执行，产生 n 个答案 `A = {A_1, ..., A_n}`。最后，通过对所产生答案集合 A 的多数投票得到输出答案 A（投票方法类似于 MBR-EXEC（Shi et al., 2022）所用的方法，我们在附录 A.3 中详述）。上述过程中，k 和 n 是超参数。

### 2.3 BINDER IMPLEMENTATION BINDER 的实现

本节以在结构化知识上用 SQL 和 Python 实现 BINDER 作为演示。由于 BINDER 被设计为可扩展到多种编程语言和 API 调用功能，我们在附录 D 中介绍一条流水线，供用户把 BINDER 快速适配到新领域。我们实现两个 API：`f_col(Q̂; D̂)` 和 `f_val(Q̂; D̂)`。其中 `D̂ = {c_1, ..., c_{|D̂|}}` 是一组表列构成的（子）表，`c = {v_i, ..., v_{|c|}}` 是填有单元格值的一列。基于 `Q̂`，`f_col` 把 `D̂` 映射为一列，`f_val` 把 `D̂` 映射为一个值。由于两种返回类型——列和值——都与 SQL 以及 Python（配合 Pandas 包）的语法兼容，`f_col` 和 `f_val` 被插入以替换列和值，从而构成合法的 BINDER 程序。

以图 1 中的问题 “which is the best-selling shirt made in North America and with no chemicals?” 为例。`Made_in` 列中的国名本身不足以表明它们所属的大洲，因此纯 SQL 无法（凭该表的数据）解决这个问题。然而，对一个（大）语言模型来说，回答某个国家是否属于北美洲很容易，这由标准 SQL 中列名位置上的表达式 `f_col(“North America?”; Made_in)` 表示。类似地，表达式 `f_col(“No chemicals?”; Shirt)` 调用（大）语言模型，根据 `Shirt` 列中的文本细节，判断这些衬衫是否不含化学成分（在此例中即纯棉）。当某个（子）问题过于复杂，或无法通过用 `f_col` 创建中间新列来解决时，我们转而使用 `f_val` 直接得到答案。例如，给定图 1 表格上的问题 “which shirt is the most suitable for a formal event?”，很难把 `Shirt` 映射为一个“正式程度”新列，再接一条 SQL 的 “ORDER BY” 子句。因此，表达式将是 `f_val(“The most formal?”; Shirt)`，它输出一个值作为答案。`f_val` 看起来更像端到端问答，但有两个重要区别：（1）它的结果可以作为值，被集成到组合性更强的 SQL 查询中；（2）它输入的是子表而不是整张表，从而可以缓解输入容量方面的挑战。
