## 1 引言

Text-to-SQL 把自然语言问题变成可执行的 SQL，从而让不熟悉 SQL 的人也能以低代码方式操作关系数据库。论文认为这件事在金融分析里尤其要紧：投资顾问等从业人员要频繁查询数据库，但通常并不擅长写 SQL。作者同时指出两个空缺。其一，当时还没有面向金融分析的实用 Text-to-SQL 基准。其二，已有方法没有处理金融库的特有形态，例如库里表很多、表又很宽。

为此，作者基于恒生电子智能投顾产品中的真实业务构造了基准 BULL。该产品服务五十余家金融机构（文中举例包括支付宝、招商银行）以及数百万个人用户。BULL 含三个库，分别对应基金、股票和宏观经济，并有 4,966 对由恒生的金融从业人员、数据科学家和软件工程师标注的自然语言问题与 SQL。数据同时提供英文和中文版本。

和 Spider、BIRD 相比，BULL 每个库的表更多，每张表的列也更多。表 1 用样本数、每库表数和每库列数把差距写出来：WikiSQL 为 80,654 条、每库 1 张表、每库 6.3 列；Spider 为 10,181 条、5.1 张表、27.1 列；BIRD 为 12,751 条、7.3 张表、54.2 列；BULL 为 4,966 条、26 张表、390 列。BULL 的样本数更少，但模式宽出一个数量级。表名和列名还经常是缩写或含糊说法。作者由此认为，金融 Text-to-SQL 必须吃得下很长的上下文，并且真正读懂这些上下文。基于大模型的 Text-to-SQL 在这两点上做得到，也已经有若干方法，但当时领先的做法通常调用 OpenAI 的接口，例如 GPT-3.5-turbo 或 GPT-4。论文认为这既贵，又有信息泄露风险，不能用在把隐私看得极重的金融场景里。

改用开源大模型（文中举例 LLaMA 和 Baichuan）并在私有域训练，可以避开泄露，但作者列出三道障碍。第一是模式链接和数据稀缺：金融库的列和表很多，问题和模式项很难对上；标注又贵，带标的问题—SQL 对数量有限、样式也不够多样。两件事合在一起，就写不出既短又多样的提示，模型效果受阻。第二是微调和跨库迁移的成本：在下游任务上微调大模型往往要多块 GPU 跑若干天，更新和迭代都贵；换到一个新库还要再付一次很高的成本，跨库迁移因此难以进行。第三是输出不稳定：采样解码本身带有随机性，模型会给出前后不一致的结果，SQL 因此出现句法错误或根本无法执行。

FinSQL 是针对这三件事提出的、与具体底座模型无关的训练和推理框架，可以套在任意开源大模型上。它由三块组成，分别对应上面的三个障碍。提示构造包含一种并行的模式链接方法和一种混合数据增强：前者把提示写得更短，后者把提示写得更多样，从输入侧提高效果。参数高效微调使用 LoRA，只更新不到 1% 的参数，为不同业务场景得到权重插件，并用插件库管理这些插件；有了插件库，针对特定库的模型就可以做少样本的跨库迁移。输出校正对生成的 SQL 做后处理，以提高正确性。概述图把训练和推理分成两段：训练时先做混合数据增强，再用增强后的数据训练负责不同 Text-to-SQL 任务的 LoRA 插件，插件放进插件库；图中的冰与火分别表示冻结权重和更新权重。推理时先做模式链接以得到简短提示，再送入“底座模型加上由若干插件合并而成的 LoRA 模块”，最后校正输出。

贡献也是三条。作者提出金融 Text-to-SQL 基准 BULL；提出与底座无关的大模型框架 FinSQL；并在 BULL 上报告实验结论：FinSQL 不绑定某一种模型，能够达到当时的最优表现，而且在需要少样本跨库迁移的情形下，最高能带来 36.64% 的性能提升。这两节只给出这一概括，没有展开具体的迁移配对和实验设置。

## 2 相关工作

### 2.1 Text-to-SQL 数据集

论文先用数据集的演进说明：现有数据离真实金融场景仍有距离。高质量数据决定 Text-to-SQL 系统能不能被开发和评测。早期的 GeoQuery 和 Scholar 提供了有用的观察，但查询数量有限，基本是单库，SQL 也相对简单。WikiSQL 和 Spider 则各自提供上万条 SQL，支持跨库迁移，并引入复杂的多表查询。

作者认为，即便有了这些改进，和真实应用仍有明显差距。真实库往往更大，还会提供外部知识来帮助用户理解模式。KaggleDBQA 在八个库上构造了 272 条 SQL，并用外部知识解释列的含义。BIRD 进一步增加了 SQL 样本和库的规模，还把问题和库内容之间的外部知识写进数据，使 Text-to-SQL 数据更接近真实情况。

尽管如此，论文认为这些数据仍满足不了工业场景。工业场景更复杂，也更难。表 1 表明，真实业务库的表数和列数远超当时的开源数据集。已有方法很难把这么大的模式放进模型，因此在这种场景里难以真正工作。

### 2.2 Text-to-SQL 模型

模型部分按技术路线写，每一代都在补上一代的短处，同时也留下金融场景仍然在意的成本、隐私和可迁移性问题。早期规则方法靠手工模板生成 SQL，有一定效果，但严重依赖人工规则，换一个场景就难以使用，也缺乏可扩展性和泛化能力。

随后的工作改用序列到序列结构。IRNet 用编码器表示问题和模式。RAT-SQL、LGESQL 和 S2SQL 用图神经网络刻画问题与模式之间的对齐，再由解码器生成 SQL。

预训练模型出现后，T5、mT5、LLaMA 等展示出更强的语言理解和泛化，基于它们做微调的方法在 Text-to-SQL 上取得更好结果。Graphix 让 T5 具备多跳推理。Picard 用受约束的解码器提高生成 SQL 的质量。RESDSQL 分成两阶段，先检索与问题相关的模式元素，再生成对应 SQL；论文称它是当时 Spider 榜上基于微调的最优方法。

更大的模型则把路线带到上下文学习：模型读懂指令后可以直接做任务，不必为该任务重新训练。论文称 Spider 榜上当时领先的方法都基于 GPT 的上下文学习，例如 C3、DIN-SQL 和 DAIL-SQL。这些方法要调用 OpenAI 接口，既有费用，也有隐私风险；换一个场景时，指令模板还得重新设计。这一节停在对现有路线的这一判断上，FinSQL 如何实现提示、微调和校正，正文留到后面的方法部分。
