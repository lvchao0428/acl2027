# Text2SQL is Not Enough: Unifying AI and Databases with TAG

## Abstract 摘要

面向数据库服务自然语言问题的 AI 系统有望释放巨大价值。这类系统将使用户能够同时借助语言模型（language models, LMs）强大的推理与知识能力，以及数据管理系统可扩展的计算能力。这些组合能力将使用户能够针对自定义数据源提出任意自然语言问题。然而，现有方法与基准对这一设定的探索并不充分。Text2SQL 方法只关注能够用关系代数表达的自然语言问题，而这只是真实用户希望提出的问题中的一小部分。同样，检索增强生成（Retrieval-Augmented Generation, RAG）只考虑能够通过对数据库中一条或少数几条数据记录做点查找（point lookup）来回答的有限查询子集。我们提出表增强生成（Table-Augmented Generation, TAG），一种在数据库上回答自然语言问题的统一且通用的范式。TAG 模型刻画了 LM 与数据库之间此前未被探索的广泛交互，并为在数据上利用 LM 的世界知识与推理能力创造了新的研究机会。我们系统地构建基准以研究 TAG 问题，发现标准方法正确回答的查询不超过 20%，从而确认该领域需要进一步研究。我们在 https://github.com/TAG-Research/TAG-Bench 发布基准代码。

## 1 Introduction 引言

语言模型有望通过让用户以自然语言对数据提问来变革数据管理，这已催生大量关于 Text2SQL 与检索增强生成（Retrieval-Augmented Generation, RAG）方法的研究。然而，根据我们的经验（包括 Databricks 的内部工作负载与客户），用户的问题常常超出这些范式的能力，因而需要新的研究投入，以构建把数据库系统的逻辑推理能力与现代语言模型（language models, LMs）的自然语言推理能力结合起来的系统。

具体而言，我们发现真实业务用户的问题常常需要领域知识、世界知识、精确计算与语义推理的复杂组合。数据库系统通过其所存储的最新数据提供领域知识来源，并提供大规模精确计算（而这正是 LM 不擅长的）。

LM 以两种关键方式扩展数据库的现有能力。第一，LM 具备对文本数据的语义推理能力，而这是许多自然语言用户查询的核心要素。例如，一项 Databricks 客户调查显示，用户希望提出诸如“产品 X 的哪些客户评论是正面的？”（which customer reviews of product X are positive?），或“为什么我的销售额在这一时期下降了？”（why did my sales drop during this period?）之类的问题。这些问题呈现基于推理的复杂任务，例如对自由文本字段做情感分析，或对趋势做摘要。LM 很适合这些任务，而传统数据库系统中的精确计算或关系原语无法对它们建模。

第二，LM 利用模型训练期间学到的、并隐式存储在模型权重中的知识，可以用数据库表模式未能显式捕获的世界知识来增强用户数据。例如，一位 Databricks 内部 AI 用户针对一张包含账户名称、产品与收入属性的表提问：“‘零售’（retail）垂直领域的 QoQ 趋势是什么？”（what are the QoQ trends for the "retail" vertical?）。要回答该查询，系统必须理解业务如何定义 QoQ（quarter over quarter，例如从上一季度到当前季度的季度环比趋势，或从去年本季度到今年本季度），以及哪些公司被视为属于零售垂直领域。这一任务适合利用预训练或微调 LM 所持有的知识。

能够高效地联合利用数据库与 LM、以完全一般的方式服务自然语言查询的系统，有潜力改变用户理解其数据的方式。遗憾的是，这些问如今无法由 Text2SQL 与 RAG 等常见方法回答。虽然 Text2SQL 方法 [26, 28, 31, 32] 适用于具有直接关系等价物的自然语言查询子集，但它们无法处理需要语义推理或世界知识的大量用户查询。例如，前述询问哪些客户评论为正面的用户查询，可能需要对评论做逐行的逻辑 LM 推理，把每条分类为正面或负面。类似地，询问销售额为何下降的问题，是一个必须跨许多表项聚合信息的推理问题。

另一方面，RAG 模型局限于对少数数据记录做基于相关性的简单点查找，随后只调用一次 LM。该模型只服务可由点查找回答的查询子集，也未能利用许多数据库系统更丰富的查询执行能力，从而把计算任务（例如计数、数学运算与过滤）留给单次、且易出错的 LM 调用。除了在计算任务上易出错且低效之外，已有工作表明 LM 在长上下文提示上表现不佳，这限制了它们在 RAG 生成阶段对大规模数据进行推理的能力。

我们转而提出表增强生成（table-augmented generation, TAG），作为在数据库上回答自然语言问题的系统的统一范式。具体而言，TAG 定义三个关键步骤，如图 1 所示。首先，查询合成（query synthesis）步骤 syn 把用户的任意自然语言请求 \(R\) 翻译为可执行的数据库查询 \(Q\)。然后，查询执行（query execution）步骤 exec 在数据库系统上执行 \(Q\)，以高效计算出相关数据 \(T\)。最后，答案生成（answer generation）步骤 gen 利用 \(R\) 与 \(T\)；其中 LM 被编排，可能以迭代或递归模式作用于数据，以生成最终自然语言答案 \(A\)。TAG 模型简单而有力：它由如下三个方程定义，但刻画了 LM 与数据库之间此前研究不足的广泛交互。

Query Synthesis: \(\mathrm{syn}(R)\rightarrow Q\) (1)

Query Execution: \(\mathrm{exec}(Q)\rightarrow T\) (2)

Answer Generation: \(\mathrm{gen}(R, T)\rightarrow A\) (3)

值得注意的是，TAG 模型统一了先前方法，包括 Text2SQL 与 RAG；它们都是 TAG 的特例，并且只服务有限的用户问题子集。

虽然若干先前工作处理 TAG 的这些特例，我们提供了首个端到端 TAG 基准，它由一组广泛的、需要 LM 推理与知识能力的真实查询组成。我们展示这类问题所带来的重大研究挑战，以及高效 TAG 实现的前景。我们的评测分析了朴素（vanilla）Text2SQL 与 RAG 基线，以及两个更强的基线：带 LM 生成的 Text2SQL，以及带基于 LM 重排序的检索。在各类查询类型上，我们发现每种基线方法都始终无法取得高准确率，在该基准上的精确匹配（exact match）从未超过 20%。另一方面，我们在近期的 LOTUS 运行时 [21] 之上实现手写 TAG 流水线，发现它们相对基线的准确率高出至多 20−65%。这一显著性能差距展示了构建高效 TAG 系统的前景。

## 2 The TAG Model TAG 模型

我们现在描述 TAG 模型。它接受自然语言请求 \(R\)，并返回以数据源为依据的自然语言答案 \(A\)。我们概述 TAG 系统实现的三个主要步骤：查询合成、查询执行与答案生成。为使定义可处理，我们把 TAG 定义为这些步骤的单次迭代，但也可以考虑以多跳（multi-hop）方式扩展 TAG。

### 2.1 Query Synthesis 查询合成

syn 函数接受自然语言请求 \(R\)，并生成由数据库系统执行的查询 \(Q\)。给定用户请求，该步骤负责 (a) 推断哪些数据与回答该请求相关（例如利用表模式），以及 (b) 执行语义解析，把用户请求翻译为数据库系统可以执行的查询。该查询可以是任何查询语言，但在我们的例子中使用 SQL。

图 1 展示了针对用户查询 “Summarize the reviews of the highest grossing romance movie considered a ‘classic’”（对被视为 “classic” 的票房最高爱情电影的评论进行摘要）的一个 TAG 实例。这里，数据源包含每部电影的标题、收入、类型，以及一条关联评论。在这一步，系统利用 LM 的语义推理能力生成一条 SQL 查询，该查询使用数据源中的 movie_title、review、revenue 与 genre 属性。注意，在这个例子中，数据库 API 能够在 SQL 查询内执行 LM 用户自定义函数（user-defined functions, UDFs），因此该步骤还在查询中为每一行引入对 LM 的调用，以识别经典电影。

### 2.2 Query Execution 查询执行

在查询执行步骤中，exec 函数在数据库系统中执行查询 \(Q\)，以获得表 \(T\)。该步骤利用数据库查询引擎，在大量已存储数据上高效执行查询。数据库 API 可以由多种多样的系统提供，我们将在 Section 3 探讨。一些 API 可能允许基于 LM 的算子 [18–21]，从而使数据库引擎能够在 exec 内部利用 LM 的世界知识与推理能力。

在图 1 所示例子中，数据库查询是用 SQL 写成的选择与排序查询，返回包含相关行的表。该查询使用 LM 根据 movie_title 评估哪些电影是经典作品来执行选择，并对 genre 施加标准过滤以找到爱情片（romance）。该查询还根据 revenue 对结果排序，以找到票房最高的电影。如图所示，所得表包含电影 “Titanic” 的评论。

### 2.3 Answer Generation 答案生成

TAG 中的答案生成步骤与 RAG 中的生成步骤相对应。在这一步，gen 函数使用 LM，利用计算出的数据 \(T\)，针对用户的自然语言请求 \(R\) 生成答案 \(A\)。

图 1 展示该示例 TAG 流水线的最后阶段：输出对 “Titanic” 评论的摘要，作为对原始用户请求的答案。在该例子中，相关数据 \(T\) 被编码为字符串供模型处理。编码后的表与原始用户请求 \(R\) 一起被传给 LM。为得到答案，该步骤利用模型对 review 列的语义推理能力来摘要这些评论。
