## 引言（Introduction）

这篇短文关心的是基准本身，而不是再提出一种写 SQL 的方法。用大语言模型做 text-to-SQL，可以让不具备专家知识的人访问结构化数据库。开发这类模型依赖高质量的公开数据和基准，多年来已经积累了不少。早期的 WikiSQL 场景简单，问句常常只涉及一张表。随后的数据更靠近真实使用：跨多张表、带连接的复杂查询，训练时没有见过的领域数据，以及带噪声的问句。较新的 BIRD-Bench 想把学术研究与真实应用之间的缺口再缩小一些，例如包含又大又脏的数据库取值，并要求使用外部知识。

BIRD-Bench 并没有明确往问句里加入噪声。作者指出，建数据时的人为失误仍可能把噪声带进去。真实使用中噪声同样躲不开，因为人的输入经常含糊，也经常有语法错误。可是，基准若要用来判断模型是否会处理噪声、以及应该在哪一方面改进，数据必须有效，并且能指出模型的短板。本文延续检查公开数据和基准是否适用、限度在哪里的传统，专门看 BIRD-Bench 的问句和查询如何体现噪声。做法是先定性分析数据里有哪些噪声、在具体领域中如何分布，再考察噪声对不同模型和提示技术的影响；比较时同时使用较强的基线和当时的先进方法。

引言中的图 1 说明，错误的金标准 SQL 会生成错误的参考答案。例子问的是男性借款人的平均贷款额。错误查询按地区标识把客户和账户连在一起。同一地区可以同时有多名客户和多个账户，账户就会配到错误的人身上。改正后的查询改为沿着账户与客户的正确关联，再按性别筛选。用来判分的 SQL 把人连错了，参考答案也随之错误。

引言概括的发现有四层。问句和金标准 SQL 中的噪声很常见。噪声在不同领域之间分布不均，各类噪声所占比例也不均衡。错误的金标准 SQL 同样常见，并降低 BIRD-Bench 的可靠性。若改用修正后的金标准查询来评测，零样本基线与先进提示方法之间的性能差距会被抹平，因此需要重新思考该如何解读模型在这一基准上的表现。这些是第 1 节对全文结果的概述。各领域的具体比例、每一类噪声的条数，以及修正数据之后各个模型的名次，都在第 3 节以后才展开。

## 相关工作（Related Work）

相关工作从数据集、建模路线和已有的噪声研究三条线，说明本文相对前人多做了什么。

数据集方面，WikiSQL 规模大，但只有简单的 SELECT 和 WHERE，没有嵌套查询，也没有 JOIN。SPIDER 更接近真实场景，要求模型构造复杂查询并理解数据库模式。复杂度固然重要，后来又出现两类变体：一类专门包含噪声问句，一类包含特定领域的问题。BIRD-Bench 则通过又大又脏的数据库取值、需要外部知识的问题，以及优化 SQL 执行效率，试图缩小学术评测和真实应用的距离。引言里的「多表连接、未见领域、噪声问句」在这里被落到具体数据集上：复杂查询对应 SPIDER，噪声问句和领域问题是它的变体，BIRD-Bench 则把脏数据和外部知识也纳入。

方法方面，作者用公开榜单上的差距说明任务远未解决。截至 2024 年 2 月 16 日，BIRD-Bench 上自动系统的准确率是 65.45%，人类专家是 92.96%。较传统的做法是在 text-to-SQL 样本上微调大语言模型。这些模型已有不错结果，但与用提示工程适配到该任务的指令微调模型之间仍有差距，其中特别提到 GPT-4。提示常常串成一条链，每一步处理一个子问题，例如模式链接、把查询拆开，以及修正模型已经生成的内容。相关工作因此把当时的性能瓶颈分成两处：自动系统离人类仍差一截；在大语言模型内部，微调路线又落后于以 GPT-4 为代表的提示工程。

噪声方面，几乎同时发表的 Wang 等人（2023）和 Sun 等人（2024）已经表明，BIRD-Bench 里存在含糊问句和错误 SQL。与本文不同，他们没有研究噪声如何随领域变化，也没有研究这些噪声和错误如何影响模型表现。Pourreza 与 Rafiei（2023b）对错误 SQL 做了更细的分析，也提到本文会覆盖的一类噪声，即自然语言问题与数据库模式对不上。本文把更细的分析放在自然语言问句上，例如语法错误、同义词和含糊问句各自带来的影响。Katsogiannis-Meimarakis 与 Koutrika（2023）则指出，数据库模式经常与数据实体错位，由此产生的词汇歧义或句法歧义会影响 text-to-SQL。第 2 节据此把本文的增量收成两点：噪声要按领域分开看，也要看它如何改变模型比较的结论；对问句侧噪声的区分，比只分析错误 SQL 更细。语法错误、同义词、含糊问句，以及自然语言问题与数据库模式不匹配，都是这一节点名的分析对象。版面中另有题目难度图和两张按领域统计噪声的表，插在第 1、2 节的页码之间，但正文要到第 3 节以后才引用，表内计数不属于这两节。
