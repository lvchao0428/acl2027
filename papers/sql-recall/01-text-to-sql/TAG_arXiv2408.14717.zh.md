## 1 INTRODUCTION

语言模型让用户用自然语言直接询问数据，这件事带动了大量 Text2SQL 和检索增强生成（RAG）研究。作者结合自身经验，包括 Databricks 的内部负载和客户，认为真实问题经常超出这两种范式。他们主张新的系统要把数据库的逻辑推理和现代语言模型的自然语言推理放在一起。

业务问题往往同时要求四种能力：领域知识、世界知识、精确计算和语义推理。数据库提供领域知识，因为表中数据是最新的；它也提供大规模上的精确计算，而语言模型不擅长这件事。语言模型则从两个方向补上数据库的缺口。第一是对文本做语义推理。Databricks 的客户调查显示，用户想问某产品的哪些评论是正面的，或者某一时期销售额为什么下降。前者要对自由文本做情感判断，后者要概括趋势。这些任务无法写成传统数据库里的精确计算或关系运算。第二是用训练进模型权重的世界知识，补上表结构没有写明的概念。一名内部用户对着含有账户名、产品和收入的表，询问“零售”行业的季度环比。系统既要知道业务上的环比指什么，例如上一季度到本季度，或去年同一季度到今年同一季度，也要判断哪些公司属于零售。这适合预训练或经过微调的语言模型。

能把两边一起用好的系统，有可能改变用户理解数据的方式。上面这类问题，今天的 Text2SQL 和 RAG 答不了。Text2SQL 适合能直接对应到关系查询的自然语言问题，处理不了语义推理或世界知识。判断评论是否正面，需要按行用语言模型做分类；追问销售额为何下降，则要把许多行的信息合起来再推理。RAG 的限制在另一端：它按相关性做点查，取出一条或少数几条记录，再做一次模型调用。只有点查能够回答的问题才落在它的范围内。计数、数学和过滤这些数据库擅长的计算，被留给了同一次容易出错的模型调用。语言模型在长上下文上表现也不好，因此 RAG 的生成阶段很难对大规模数据做推理。

作者提出表增强生成（Table-Augmented Generation，TAG），作为在数据库上回答自然语言问题的统一范式。如图 1，它分成三步。\(R\) 是用户的任意自然语言请求，\(Q\) 是可执行的数据库查询，\(T\) 是执行后得到的相关数据，\(A\) 是最终的自然语言答案。\(\operatorname{syn}\)、\(\operatorname{exec}\)、\(\operatorname{gen}\) 分别表示查询合成、查询执行和答案生成。

查询合成把请求译成查询：

\[
\operatorname{syn}(R) \rightarrow Q \tag{1}
\]

查询执行在数据库中算出相关数据：

\[
\operatorname{exec}(Q) \rightarrow T \tag{2}
\]

答案生成同时读取原请求和这份数据。语言模型可以按迭代或递归的方式扫过数据，得到最终答案：

\[
\operatorname{gen}(R, T) \rightarrow A \tag{3}
\]

这个模型很简单，但覆盖了此前研究不足的一大类语言模型与数据库的交互。Text2SQL 和 RAG 都是 TAG 的特例，而且只覆盖用户问题中的有限子集。已有工作处理过这些特例。本文给出第一个端到端的 TAG 评测，题目是一批需要语言模型推理和知识的现实查询，用来展示这类问题的研究难度，以及高效 TAG 实现的潜力。评测比较普通 Text2SQL、普通 RAG，以及两个更强的基线：带语言模型生成的 Text2SQL，和带语言模型重排序的检索。在多种查询类型上，每种基线的精确匹配都没有超过 20%。作者在 LOTUS 运行时上实现了手工编写的 TAG 流水线，准确率比这些基线高出 20% 至 65%。这个差距被用来说明，值得去构建高效的 TAG 系统。

## 2 THE TAG MODEL

TAG 接收自然语言请求 \(R\)，返回锚定在数据源上的自然语言答案 \(A\)。系统要实现的就是式 (1)–(3) 的三步：查询合成、查询执行和答案生成。为了把模型定义得可处理，这里先规定三步只走一轮；也可以考虑按多跳方式扩展。

### 2.1 Query Synthesis

\(\operatorname{syn}\) 接收 \(R\)，生成交给数据库执行的查询 \(Q\)。这一步负责两件事：判断哪些数据与请求相关，例如依据表模式；再做语义解析，把请求译成数据库能够执行的查询。查询语言并不限定，文中例子使用 SQL。

图 1 的请求是：总结票房最高、且被看作经典的那部爱情电影的评论。数据源包含每部电影的片名、票房、类型以及关联评论。合成步骤利用语言模型的语义推理，生成使用片名、评论、票房和类型这些属性的 SQL。该例中的数据库接口可以在 SQL 里执行语言模型用户自定义函数，因此这一步还会把按行调用模型写进查询，用来判断每部电影是不是经典。

### 2.2 Query Execution

\(\operatorname{exec}\) 在数据库中执行 \(Q\)，得到表 \(T\)。大规模存储上的高效执行交给数据库查询引擎。数据库接口可以由多种系统提供；有的接口允许基于语言模型的算子，从而在执行过程中使用模型的世界知识和推理能力。

图 1 中的查询是 SQL 里的选择加排序。选择分两路：用语言模型根据片名判断哪些电影是经典，用普通条件把类型滤成爱情片；然后再按票房排序，找出票房最高的一部。执行结果是《泰坦尼克号》的评论行，类型为爱情，票房为 2257.8。动作片等其他行在这一步被排除。

### 2.3 Answer Generation

答案生成与 RAG 的生成步骤对应。\(\operatorname{gen}\) 用语言模型，依据请求 \(R\) 和已经算出的数据 \(T\)，生成答案 \(A\)。图 1 的最后阶段输出对《泰坦尼克号》评论的摘要，作为对原请求的回答。相关表 \(T\) 被编码成字符串，与原始请求一起交给模型。这一步使用模型对评论列的语义推理，把评论概括成一段话，内容涉及银幕上的化学反应。
