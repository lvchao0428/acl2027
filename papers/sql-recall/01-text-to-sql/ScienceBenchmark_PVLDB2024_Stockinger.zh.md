## 第 1 节　引言

作者把用自然语言查询结构化数据视为数据民主化的关键。这类接口在二十世纪七十年代已经出现。早期系统大致分两条路：SODA、Precis 依据库模式把问句组装成 SQL；ATHENA、NaLIR 先分析问句结构，再映射到 SQL。1995 年的综述已经指出，当时没有标准评测，对进展只能作印象式判断。WikiSQL 与 Spider 改变了这一局面：自然语言到 SQL 被写成神经机器翻译，系统在大量问句–SQL 配对上训练，再放到统一基准上比较。

最早的深度学习方法只能处理单表，跨表、嵌套和复杂子句都会失败。后来的系统可以面向完整数据库，Spider 上的最高准确率大约到 85%。开源系统里，带约束解码 Picard 的 T5-Large、SmBoP，以及结合 NatSQL 的 RESDSQL，都已超过 70%。引言认为这些分数不能代表真实部署。Spider 的多数库是为基准建造的，表、列和记录都不多，题材以常识为主。把在 Spider 上训练的系统直接用于天体物理或癌症研究，效果会明显变差。

两份旧基准的限度不同。WikiSQL 的每条问题只指向一张表，查询简单，对真实关系数据库的参考有限。Spider 大约有 200 个关系数据库、138 个领域、一万条以上自然语言问题和五千条以上复杂 SQL，并用含新库的开发集考察迁移。可其中多数库仍然简单，内容是常识而不是专门知识。科学领域需要自己的基准，手工编写却同时受数据量和学科专长限制。作者因此把自动生成，也就是数据增强，看作可行出路。

ScienceBenchmark 覆盖三个高度领域化的科学库，由 SQL 专家与科研政策、天体物理、癌症研究的研究者共同建造。少量人工配对提供领域语义，自动流程再把样本补到可训练的规模。系统从种子查询抽出 SQL 模板，结合库模式和内容生成新 SQL，再用 GPT-3 回译成自然语言。作者比较多种 Transformer 预训练模型后选用 GPT-3，因为它只需很少种子就能泛化到新领域。回译问句再经判别模型筛选，留下与 SQL 最相关的问句，扩充后的配对可送入任何 NL-to-SQL 系统。同页的图把流水线分成种子、SQL 生成、回译和判别四段，细节留在后文。

贡献有三项。一是发布含六千条以上 NL/SQL 配对的 ScienceBenchmark，用来评估流行基准较少覆盖的复杂科学库。二是在训练数据极少或缺失时自动生成样本；对象是复杂科学库，而不是以往工作里较简单的库，流行系统在这里失效，主要因为缺少领域知识和配对。三是评估三个当时领先的 NL-to-SQL 系统以及两个大语言模型。它们在 Spider 排行榜上的准确率高于 82%，在新基准上只有大约 25% 到 60%，并且随领域变化。这个落差用来说明新基准更难。

## 第 2 节　为何需要新基准：以天体物理为例

第 2 节用一个科学库说明新基准为什么必要。问句可能含糊，指代难断，用词也常与库不一致；SQL 则必须同时符合语法和模式。科学库再叠加上学科本身的困难。Spider 虽包含复杂 SQL，库本身并不复杂：题材如宠物和演出，而且多数由学生专门编写，不能代表真实库。

贯穿例子是天体物理。它数据密集、高度复杂，使用关系数据库的传统很长。作者写明，这些困难也适用于实验中的癌症研究。运行库是斯隆数字巡天 SDSS，记录恒星和星系在天空中的位置及相关观测。三条问句表明，Spider 的难度标签抓不住真正的障碍。

第一条被标为容易。它只在光谱对象表上把子类滤为星暴，取出光谱对象标识。结构简单，难在领域词：星暴是光谱子类，不是日常用语。第二条被标为中等，仍然是单表。问句要求从光谱观测的星系中取出对象标识，以及赤经 $ra$、赤纬 $dec$ 和红移 $z$，且 $0.5 < z < 1$。这些物理量在库里是极短列名，系统必须把名词对齐到缩写。第三条被标为超难。它连接测光对象表与光谱对象表，连接键是光谱侧的最佳对象标识和测光侧的对象标识；筛选光谱类别为星系，并且紫外星等 $u$ 与红外星等 $r$ 之差满足 $1 < u - r < 2.22$，返回两侧标识。这里的难点不只是连接，而是过滤条件变成属性之间的算术关系。

三类挑战由此出现。未见领域：有意义的问句和 SQL 依赖天体物理知识，在常识数据上预训练的神经翻译系统会因题材差距失败。模式隐晦：科学库的属性可以多到数百个，列名短到几个字母，例如 $ra$ 表示赤经、$z$ 表示红移，或者列中直接存放数值测量。解释这些属性还需要本体，其中既有数学关系，也有文字说明，所以把问句里的一个词映射到正确列并不容易。查询精细：领域分析会在属性之间使用函数和运算，例如紫外与红外滤光的星等差要小于 2.22。

这些现象说明，专门基准必须同时覆盖领域语义和真实查询类型。再加上所需规模，纯手工构造不可行。大而复杂的模式即使专家也难以完全掌握，于是问题变成基准应当如何建造。第 2 节的回答是数据增强，并立刻列出它自己的三个困难：如何为新库生成有代表性的 SQL，如何配上自然语言描述，以及如何把人工参与降到很少甚至没有。本节停在这组问题上。
