# OmniSQL: Synthesizing High-quality Text-to-SQL Data at Scale

## Abstract 摘要

Text-to-SQL，即将自然语言问题翻译为 SQL 查询的任务，在使非专业用户能够与数据库交互方面起着关键作用。尽管近期大语言模型（large language models, LLMs）的进展显著提升了 text-to-SQL 性能，现有方法在真实世界的 text-to-SQL 应用中仍面临明显局限。基于提示（prompting-based）的方法往往依赖闭源 LLM，成本高昂，引发隐私顾虑，且缺乏可定制性。基于微调（fine-tuning-based）的方法则因公开可用训练数据覆盖有限而泛化能力较差。为克服这些挑战，我们提出一种新颖且可扩展的 text-to-SQL 数据合成框架，可在无需大量人工干预的情况下，自动合成大规模、高质量且多样的数据集。借助该框架，我们引入 SynSQL-2.5M，首个百万规模的 text-to-SQL 数据集，包含 2.5 million 条样本，跨越超过 16,000 个合成数据库。每个样本包括一个数据库、一条 SQL 查询、一个自然语言问题，以及一份思维链（chain-of-thought, CoT）解答。利用 SynSQL-2.5M，我们开发了 OmniSQL，一个强大的开源 text-to-SQL 模型，提供三种规模：7B、14B 与 32B。在九个数据集上的广泛评测表明，OmniSQL 取得了当前最优性能，尽管规模更小，仍能匹配或超过包括 GPT-4o 与 DeepSeek-V3 在内的领先闭源与开源 LLM。我们发布全部代码、数据集与模型，以支持后续研究。

## 1 INTRODUCTION 引言

Text-to-SQL 将自然语言（natural language, NL）问题翻译为可执行的 SQL 查询，使非专业用户能够有效地与数据库交互 [1, 40, 47]。这一能力支撑着广泛的以数据为中心的应用，并已引起自然语言处理（natural language processing, NLP）与数据库两个社区的大量研究兴趣 [18, 21, 24, 42–44, 59]。

**State-of-the-Art: Strengths and Limitations. 当前最优：优势与局限。** 大语言模型的近期进展推动了 text-to-SQL 领域的显著进步。当前最优（state-of-the-art, SOTA）方案 [22, 58] 常常采用多智能体协作框架，由专门的智能体处理不同子任务，例如模式链接（schema linking）、text-to-SQL 生成、SQL 精炼与 SQL 选择。其中，text-to-SQL 生成仍是核心组件。当前针对该组件的方法主要依赖 LLM，并可大致分为两类范式：基于提示与基于微调。

基于提示的方法通过精心设计的提示利用强大的 LLM，往往依赖经由 API 访问的闭源模型。相比之下，基于微调的方法聚焦于在现有 text-to-SQL 数据集（如 Spider [87] 与 BIRD [45]）上训练 LLM，使其适配该任务。尽管两种方法都在基准上展现了令人印象深刻的性能，它们在真实应用中仍面临明显局限。基于提示的方法因依赖调用 API，存在使用成本高、数据隐私顾虑，以及对模型行为控制有限等挑战。另一方面，基于微调的方法往往难以泛化到复杂问题或领域特定数据库，因为公开可用数据集对真实场景的覆盖有限。例如，实验表明，在 Spider 与 BIRD 训练集上微调的 Qwen2.5-Coder-7B-Instruct [30]，在二者的开发集上表现良好（开发集与训练数据分布相似），但在域外数据集 ScienceBenchmark [88] 与 EHRSQL [38] 上的执行准确率（execution accuracy）分别仅为 43.8% 与 31.4%。作为对照，零样本提示 GPT-4-Turbo [54] 取得了显著更高的执行准确率，分别为 59.2% 与 43.1%，凸显了当前微调方法泛化能力有限。

为应对这些局限，通过大规模、多样、高质量的训练数据来增强开源 LLM 的 text-to-SQL 能力，是一个有前景的方向。此类努力有望同时提升开源模型的性能与泛化能力。此外，开源模型可以本地部署，使 text-to-SQL 系统更具成本效益、数据更安全，且更便于修改，从而克服与闭源 LLM 相关的挑战。然而，通过人工标注获取大规模数据往往不可行。为缓解这一问题，若干早期数据增强方法 [28, 76, 80, 83] 被提出，用以扩充现有 text-to-SQL 数据集。遗憾的是，这些方法大多聚焦于生成符合现有数据集分布的数据样本，因而多样性、质量与可扩展性有限。此外，许多方法需要大量人工来定义复杂模板或文法，进一步制约了其实用性。

**Our Proposal. 我们的方案。** 为克服这些局限，我们提出一种新颖的 text-to-SQL 数据合成框架。它与现有数据增强方法的区别在于以下关键优势：（1）自动（Automatic）：整个合成过程只需极少乃至无需人工干预。（2）可扩展（Scalable）：该框架能够生成大规模、多样、高质量的数据样本，确保覆盖广泛领域。（3）贴近真实（Realistic）：合成数据与真实用户需求及场景相一致。

**Challenges and Solutions. 挑战与解决方案。** 设计一个自动、可扩展且贴近真实的数据合成框架并非易事。首要挑战在于，在保证自动化与可扩展性的同时，维持所生成数据的质量与多样性。为此，我们引入一条渐进式流水线，把合成过程解耦为若干更简单、可管理的步骤。每一步都用 LLM 自动化，从而把人工干预降到最低。（1）流水线首先利用网页表格（web tables）来合成贴近真实的数据库。具体而言，给定一张网页表格，提示 LLM 推断与该表相关联的、合理的数据库业务场景，并生成相应的数据库。该合成数据库包含多张具有主键与外键关系的关系表。每张关系表包含元数据，如表名、描述、列名、数据类型、列描述，以及两行示例数据。网上有数以百万计的网页表格可供使用 [17]，这一做法确保了跨广泛领域的可扩展性。（2）接下来，我们向 LLM 提供数据库信息，基于合成数据库生成有意义的 SQL 查询。（3）然后，我们采用回译（back-translation）技术，把这些 SQL 查询转换为语义等价的自然语言问题。该技术在先前研究中被广泛采用 [4, 25, 28, 76, 80, 88, 91]，能够保证合成的 <question, SQL query> 对的质量，因为把 SQL 查询转换为自然语言，本质上比反向转换更准确、歧义更少。（4）最后，为弥合问题与 SQL 查询之间的差距，我们从思维链推理 [35, 78] 中获得启发。对每条合成的 text-to-SQL 数据，我们生成一份逐步的 CoT 解答，详述从问题与数据库构造 SQL 查询所需的中间推理步骤。这不仅增强了合成数据的可解释性，也为 text-to-SQL 模型提供了高质量的训练信号。

第二个挑战是确保合成数据与真实用户需求及场景相一致。一个稳健的 text-to-SQL 模型必须能够容纳从简单到高度复杂的广泛 SQL 查询，既反映基本的数据检索，也反映高级的数据分析需求。为满足这一需求，我们定义四个 SQL 复杂度级别：simple、moderate、complex 与 highly complex。在 SQL 合成过程中，我们选择一个复杂度级别，并指示 LLM 生成与该级别对应的 SQL 查询。此外，真实用户往往以多样的语言风格表达问题，从正式、明确到含糊、隐喻不等。为应对这种变异，我们识别出九种常见的自然语言风格：formal、colloquial、imperative、interrogative、descriptive、concise、vague、metaphorical 与 conversational。在把 SQL 查询翻译为自然语言问题时，我们采用一种特定风格，并引导 LLM 生成与该风格一致的问题。这一做法确保合成数据能够准确捕捉用户在真实场景中表达问题的各种方式。

**Validation. 验证。** 为验证所提出框架的有效性，我们引入 SynSQL-2.5M，首个百万规模的 text-to-SQL 数据集。具体而言，SynSQL-2.5M 包含 2,544,390 条 text-to-SQL 数据样本，每条表示为四元组 <database, question, SQL query, CoT solution>，跨越 16,583 个不同的合成数据库。大量统计表明，与现有 text-to-SQL 数据集相比，SynSQL-2.5M 展现出高度的多样性与复杂性。我们进一步从四个维度评估其质量：数据库、问题、SQL 查询与数据样本。与被广泛采用的人工标注数据集 BIRD [45] 相比，SynSQL-2.5M 在几乎所有标准上都更优，凸显了我们数据合成流水线的可靠性与有效性。

在 SynSQL-2.5M 之上，我们开发了 OmniSQL，一个强大的开源 text-to-SQL 模型，提供三种规模：7B、14B 与 32B。我们在九个数据集上评测 OmniSQL，包括三个标准数据集（Spider 开发集与测试集 [87]，以及 BIRD 开发集 [45]）、三个领域特定数据集（Spider2.0-SQLite [39]、ScienceBenchmark [88] 与 EHRSQL [38]），以及三个稳健性数据集（Spider-DK [20]、Spider-Syn [19] 与 Spider-Realistic [12]）。结果表明，OmniSQL 在这些数据集上取得了当前最优的平均性能，尽管模型规模更小，仍能匹配或超过领先的开源 LLM（例如 DeepSeek-V3 [10] 与 Qwen2.5-72B-Instruct [81]）以及先进的闭源模型（例如 GPT-4-Turbo [54] 与 GPT-4o [56]）。我们的贡献概括如下：

- **Data Synthesis Framework. 数据合成框架。** 我们提出一个自动且可扩展的 text-to-SQL 数据合成框架，涵盖贴近真实的数据库、复杂度感知的 SQL 查询、风格化的自然语言问题，以及可靠的思维链解答的生成。
- **Synthetic Dataset and Fine-tuned Multi-scale Model. 合成数据集与微调的多规模模型。** 我们引入 SynSQL-2.5M，首个百万规模的 text-to-SQL 数据集，包含 2,544,390 条多样且高质量的数据样本。利用 SynSQL-2.5M，我们微调得到 OmniSQL，一个新的 text-to-SQL 模型，提供三种规模：7B、14B 与 32B。
- **New SOTA Text-to-SQL Performance. 新的当前最优 text-to-SQL 性能。** 广泛实验表明，OmniSQL 在 text-to-SQL 任务上取得了新的当前最优性能，以显著更少的参数超越领先的开源与闭源 LLM，凸显了我们数据合成框架的有效性。我们已在 GitHub¹ 上开源代码、数据集与模型，以促进 text-to-SQL 的进一步研究。

## 2 RELATED WORK 相关工作

### 2.1 Text-to-SQL 文本到 SQL

在 text-to-SQL 领域，早期研究通常采用显式的编码器-解码器（encoder-decoder）架构。编码器对数据库模式与问题进行编码，解码器则基于编码信息生成相应的 SQL 查询。一些研究通过纳入图关系信息 [6, 7, 44, 75]，或利用预训练技术 [12, 84, 85]，来增强编码器。另一些方法聚焦于改进解码器，引入文法约束，以帮助减少所生成 SQL 查询中的语法错误，从而提高模型准确率 [69, 77]。

随着序列到序列（sequence-to-sequence, seq2seq）模型的快速进展，text-to-SQL 任务被迁移为 seq2seq 建模任务。许多研究聚焦于微调 T5 [62] 以完成这一任务 [42, 44, 60, 63, 69]。近期，GPT-4 [53, 56] 与 Gemini [2, 66] 等大语言模型的出现再次改变了 text-to-SQL 领域。借助这些强大的 LLM，研究者可以把复杂的 text-to-SQL 任务分解为更简单的子任务，包括模式链接、text-to-SQL 生成、SQL 精炼与 SQL 选择 [21, 22, 58, 59, 74]。每个子任务可由一个基于 LLM 的智能体通过提示工程或微调技术来管理。与设计复杂多智能体框架的先前研究不同，本文聚焦于利用大规模合成数据，提升这些框架的核心能力——text-to-SQL 生成。

### 2.2 Data Augmentation for Text-to-SQL 面向 Text-to-SQL 的数据增强

为应对公开可用数据集覆盖有限的问题，大量研究提出了数据增强方法，以生成额外的训练数据（即 <question, SQL query> 对），使之与现有数据集的分布对齐。许多方法 [25, 34, 43, 76, 80, 88, 91] 采用 “SQL-to-question” 流水线：用 SQL 模板或文法生成 SQL 查询，再用神经网络模型将其翻译为自然语言问题。由于自然语言的灵活性，把 SQL 转换为自然语言通常更容易，因此该方法能确保高质量的合成 <question, SQL> 对。在这些方法中，SQL 模板往往从现有数据集中抽取 [25, 28, 43, 91]，而抽象语法树（abstract syntax tree）文法通常需要专家设计 [76, 80, 88]。然而，SQL 模板限制了多样性，基于文法的方法又耗费人工，二者都难以扩展。

另一些研究采用 “question-to-SQL” 流水线：先生成问题，再用现成的 text-to-SQL 模型将其翻译为 SQL 查询 [83]。然而，所用 text-to-SQL 模型的不准确往往导致噪声数据。其他方法使用 question-to-SQL 模板对（人工编写或从数据集中抽取），通过填充槽位映射来生成新样本 [79, 85, 86]。这些方法虽然有效，但多样性有限，且生成的问题不自然。

关系最密切的工作是 Sense [82]。它通过精心设计的提示，用 GPT-4 直接合成新的数据样本。具体而言，Sense 指示 GPT-4 先生成一个数据库，再基于该数据库拟定一个问题，最后为该问题生成相应的 SQL 查询。然而，Sense 对昂贵的 GPT-4 的依赖限制了其可扩展性与成本效益。相比之下，我们的框架把合成过程解耦为更简单、更可控的步骤，从而能够使用能力较弱但开源的 LLM。因此，我们的方法具有很高的成本效益，尤其是在扩展到百万级或更大规模的合成需求时。此外，Sense 的 “question-to-SQL” 设计有可能为先前合成的问题生成不正确的 SQL 查询，而我们采用的 “SQL-to-question” 策略能确保更高质量的合成数据。除这些优势之外，我们的方法还合成 CoT 解答，进一步增强所生成数据的可解释性。
