# Query Carefully: Detecting the Unanswerables in Text-to-SQL Tasks

> 版权声明：本文档为同目录英文论文「摘要与正文前两节」的中文译文，仅供论文快速阅读与选题使用。译文不替代原文，不用于发表、再分发或商业用途。版权归原作者及出版方所有。原文件：`QueryCarefully_arXiv2512.21345.pdf`。

## Abstract 摘要

Text-to-SQL 系统使非 SQL 专家能够用自然语言与关系数据库交互。然而，这类系统倾向于为含糊、超出范围或无法回答的查询生成可执行 SQL，从而引入一种隐蔽风险：输出可能被误认为是正确的。这一风险在生物医学场景中尤为严重，因为精度至关重要。因此，我们提出 Query Carefully，一条把基于大语言模型（large language model, LLM）的 SQL 生成与对无法回答输入的显式检测和处理结合起来的流水线。在 ScienceBenchmark 的 OncoMX 组件之上，我们构建 OncoMX-NAQ（No-Answer Questions，无答案问题），共 80 道无答案问题，覆盖 8 个类别（non-SQL、超出模式/领域（out-of-schema/domain），以及多种歧义类型）。我们的方法使用 llama3.3:70b，配合模式感知提示、显式的无答案规则（No-Answer Rules, NAR），以及同时取自可回答问题与无法回答问题的少样本示例。我们评测 SQL 精确匹配（SQL exact match）、结果准确率（result accuracy），以及无法回答检测准确率（unanswerable-detection accuracy）。在 OncoMX 的开发集（dev）划分上，使用可回答示例的少样本提示提高了结果准确率，加入无法回答示例并未降低性能。在 OncoMX-NAQ 上，平衡提示取得最高的无法回答检测准确率（0.8）：对结构上可界定的类别（non-SQL、缺失列（missing columns）、超出领域（out-of-domain））接近完美，但对缺失值查询（missing-value queries）（0.5）和列歧义（column ambiguity）（0.3）仍持续困难。一个轻量用户界面呈现中间 SQL、执行结果与弃答（abstentions），以支持生物医学应用中透明、可靠的 text-to-SQL。

关键词：text-to-SQL · Unanswerable Question Detection · OncoMX。

## 1 Introduction 引言

关系数据库是管理和查询结构化数据的基本工具，应用遍及包括医疗与科学研究在内的众多领域。这类系统通常要求用户用领域特定的编程语言（例如 SQL（Structured Query Language））来表述查询，这会构成显著障碍，并把关系数据库中所存储知识的访问限制在数据库专家之内。

自然语言到 SQL（Natural Language to SQL, text-to-SQL）系统试图弥合这一差距：把自然语言问题翻译成可执行 SQL 查询，使用户无需掌握查询语言，也能用日常语言与数据库交互 [5]。深度学习模型的进展，尤其是基于大语言模型（Large Language Models, LLM）的方法，已使 text-to-SQL 在 Spider 等简单基准数据集上显著改进；这些数据集提供自然语言问题与对应 SQL 查询的标注对 [6, 9]。

尽管潜力很大，text-to-SQL 仍然困难，在医疗等敏感领域尤其如此，因为错误可能对患者造成严重后果。三个关键挑战包括：

- 为大型领域特定关系数据库中的复杂问题生成准确且语义正确的查询。[7]
- 避免输出误导性或不正确的 SQL 语句。[7]
- 处理含糊、不完整或无法回答的用户查询 [11]。

本文聚焦第三个挑战：识别无法回答的问题。text-to-SQL 系统的真实用户通常不是数据库专家。因此，他们可能提出含糊的问题，引用并不存在的模式（schema）元素，或提出超出数据库领域的问题。面对这类问题，基于 LLM 的 text-to-SQL 系统仍可能尝试生成 SQL 查询，从而产生错误输出或误导性结果。因此，text-to-SQL 系统必须能够检测无法回答的问题并作出恰当回应，例如返回 “not answerable” 消息或请求澄清。检测无法回答的问题不仅有助于避免错误结果，也能揭示系统局限，从而提升真实应用中 text-to-SQL 界面的稳健性与可靠性 [1,8,11,12]。

本文通过扩展已有 text-to-SQL 数据集（ScienceBenchmark [10]）来应对这一挑战：基于包含癌症生物标志物信息的 OncoMX 生物医学数据库，加入无法回答的问题。随后我们提出一条流水线，把基于 LLM 的 SQL 生成与检测、处理无法回答输入的机制结合起来，并通过直观的对话式界面呈现。

## 2 Related Work 相关工作

本项目基于 ScienceBenchmark 数据集。该数据集包含三个复杂、领域特定数据库的标注问题–SQL 对：科研政策制定（CORDIS）、天体物理（SDSS）与癌症研究（OncoMX）[10]。我们特别关注 OncoMX 数据库（https://www.oncomx.org/），因为它具有高度领域特定的生物医学信息与术语。ScienceBenchmark 所使用的 OncoMX 版本包含 25 张表，每张表 2 到 14 列，共计 106 列，每张表平均 2,636,771 行。OncoMX 由美国国立卫生研究院（U.S. National Institutes of Health, NIH）资助，整合了来自多个来源的癌症生物标志物、癌症样本中的差异基因表达，以及已知癌症突变数据，因而与 ScienceBenchmark 中的问题–SQL 对一起，成为真实生物医学 text-to-SQL 应用的理想测试数据库。

现有 text-to-SQL 研究大多假定用户查询在给定模式内有效且可回答，很少有研究处理检测无法回答或含糊用户问题这一关键问题。

Zhang 等人 [11] 提出 TriageSQL，一个把用户问题分类为五种意图类型的基准，其中包括四类无法回答的查询（例如含糊、不当、需要外部知识，以及 non-SQL）。他们训练了一个基于 RoBERTa 的分类器，根据输入问题与数据库模式预测问题类型，从而强调在 SQL 生成之前需要一个意图分类步骤。Wang 等人 [8] 研究了一款商用 text-to-SQL 产品的真实使用，发现用户提交的问题中有 20% 存在问题，揭示了仅依赖只包含可回答问题的精选数据集的局限。他们收集了超过 3,000 条失败的用户查询，并人工归为六类无法回答的问题。这些类别——聚焦歧义、超出范围的查询以及模式不匹配等问题——构成了本研究分类框架的基础，方法部分将进一步说明。Wang 等人 [8] 认为，无法回答查询的高频率来自三个关键因素：(1) 用户不熟悉数据库模式，(2) 自然语言固有的歧义与变异性，(3) 数据库中存在语义相近的概念，容易造成混淆。Wang 等人进一步聚焦两类——列歧义（column ambiguity）与列无法回答（column unanswerable）——并提出通过修改已有表来生成无法回答问题，而不是新造无法回答问题，使过程更可控，但也更不真实。

在生物医学领域，EHRSQL 2024 共享任务（Shared Task）针对为电子健康记录（electronic health records, EHR）构建可靠 text-to-SQL 系统这一挑战 [3]。该任务的独特之处在于有意纳入无法回答的问题，鼓励系统不仅为可回答输入生成正确 SQL，也在查询很可能无法回答时弃答。评价指标奖励系统对无法回答问题不产出 SQL，并同时惩罚不正确的 SQL 以及在问题无法回答时仍尝试作答。在此基础上，我们把该方法应用到生物医学数据集 OncoMx，并引入对无法回答问题的分类。这使我们能够按不同的不可回答类型分析系统性能，目标是进一步提升 text-to-SQL 系统在医疗与生物医学研究等敏感领域中的可靠性与安全性。
