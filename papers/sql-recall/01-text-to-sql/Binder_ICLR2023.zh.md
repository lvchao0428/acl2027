## 第 1 节 INTRODUCTION

作者从两条已经分叉的技术路线起笔。端到端神经网络直接把输入映射到输出，在性能和易用性上主导了当时的自然语言处理，但缺少可解释性，稳健性也不足。符号方法走另一条路：先产生逻辑形式、推理路径或程序代码这类显式中间表示，再执行得到最终输出。作者认为，这种中间形式及其执行让系统对输入变化更稳健。紧接着的限制是：语义覆盖受所选符号语言的语法能力约束。图中的例子是，纯 SQL 处理不了“是否属于 North America”这类需要外部知识的判断。面对多样的真实问题，符号系统就会失败；中间表示本身还要专家来标注，研究成本很高。

已有的神经符号工作试图兼取两边，把神经模块和符号语言接在一起。作者认为它们的代价是，符号语言要由人精细设计，对应的神经模块也要针对特定领域校准，并且依赖大量训练数据。更具体地说，这些语言和模块通常只覆盖某一任务、某一领域里有限的语义现象。换任务或换领域，就要再引入新语言和新模块。覆盖范围因此仍被定制语言和定制模块卡住，而且还需要多样、大规模的数据才能把每个模块训练好。作者想要的系统是：神经模块的调用足够灵活，从而抬高符号语言的覆盖，同时只需要很少的标注。

BINDER 被提出来满足这个要求。它不训练参数，把任务输入映射成一段可执行程序。宿主语言可以是 SQL 或 Python，程序里再绑定一套统一的 API，用来调用语言模型完成宿主语言本身做不到的功能。这样的程序称为 BINDER 程序。标注只需要少量“输入与 BINDER 程序”的配对，当作上下文范例。解析阶段使用代码预训练的 GPT-3，也就是 Codex。给定少量范例，Codex 要同时决定三件事：输入里哪些部分能直接写成目标编程语言，哪些部分要变成调用 Codex 的 API，以及这些 API 应该插在程序的什么位置才能继续符合原有语法。执行阶段再次使用 Codex。API 里的提示若合适，它可以完成常识问答、信息抽取等多种功能。

引言用一张衬衫销量的表把流程说具体。问题询问北美制造、且不含化学品的最畅销衬衫。产地列只有国名，成分信息藏在非结构化的商品详情里，标准 SQL 写不出这两项条件。BINDER 在对应位置插入 API：一项询问某国是否属于 North America，一项询问某件衬衫是否不含化学品。Codex 根据提示和列数据返回新的判断结果，这些结果被填回原编程语言，再由确定的程序解释器算出最终答案。作者把这个设计概括为：用统一的 Codex 提示 API 替换定制神经模块，用通用编程语言替换任务专用语言，从而在开放领域处理更多样的输入，而不必为每个领域重做语言和模块。整个方法站在上下文学习上，不训练，也不需要大规模标注。

在需要复杂表格推理的 WIKITABLEQUESTIONS（WIKITQ）和 TABFACT 上，以 Codex 为语言模型的 BINDER 达到当时的最佳结果。此前的最佳系统都要在一万条以上的任务标注上微调，或者还使用大量任务相关的预训练数据；BINDER 只用大约十几条标注，且不做训练。进一步分析里，增益最大的是原 SQL 或 Python 语法覆盖不到的问题，作者据此认为 BINDER 确实扩大了编程语言的覆盖。同一框架还被用到 MultiModalQA，知识来源可以是文本、表格、图像及其组合。相对端到端系统，中间程序在排错时看得见，因而更好解释；面对很大的输入更能扩展；对带噪声的输入更稳健。

## 第 2 节 APPROACH

### 任务定义

任务接受自然语言的问题或陈述 Q，以及可选上下文 D。D 可以是段落、表格、图像，或几者的组合。目标是给出能正确回应 Q 的答案 A。段落问答里，Q 是关于段落的问题；表格事实验证里，Q 是关于表格的陈述。

### 2.1 BINDER 框架

框架分成生成和执行。给定 Q 和可选的 D，先生成可执行的 BINDER 程序 Z，再由 BINDER 解释器执行 Z，得到 A。

解析阶段把 Q 写成 Z。BINDER 程序仍是符号语言中的表达式，只在宿主语言提供不了所需功能的地方插入 API。API 写成函数调用，接受两段输入：一段是仅靠编程语言回答不了的子问题，一段是 D 中与该回答相关的上下文。衬衫例子里，子问题是 “North America?”，相关上下文是产地列 Made_in。两段输入也可以就是完整的 Q 和 D；若两者都取全文，程序就等价于用语言模型做端到端求解。API 的返回值必须是宿主语法能够接受的变量，这样含有 API 的程序才执行得下去。

执行阶段的解释器由两部分组成：标准的符号语言解释器，以及真正实现 API 的模型。过程包括词法分析、语法分析和程序求值。扩展后的语法把 API 调用登记为新的标识符，并据此把程序解析成抽象语法树。求值时，API 交给底层神经模型，输出存成符合标准语法的变量，其余部分再交给现成的符号解释器。语法的产生式被扩展，以便解析这种树。求值按自底向上进行，因此 API 可以嵌套。作者认为，嵌套带来的是不同程度的问题分解，以及多个语言模型调用的自由组合。语法扩展和语法树的进一步细节放在附录。

### 2.2 用于 BINDER 的上下文学习

作者把 BINDER 放在大模型的上下文学习上，并与微调对照：上下文学习只把少量标注当作提示，推理时也不更新参数。这两点被写成传统语义解析的长期困难。实验中的模型是 Codex。它在代码生成上已经表现熟练，即便在对话状态跟踪这类关系较弱的任务上也能工作。Codex 在这里担任两个角色：语义解析器，以及 API 所调用的功能模型。

解析的难点在于，插入 API 之后，程序语法已经不同于原来的编程语言。作者依靠 Codex 的少样本泛化，认为少量上下文例子就足以让它学会这套修改过的语法。执行时，Codex 把 API 中的子问题和相关上下文拼成提示，生成结果；提示的具体样式留到后文实验设置。生成结果存为标准编程语言中的变量，解释器再把这些变量和程序的其余部分一起执行。

具体流程是：输入包括 k 个上下文范例，每个范例含问题、上下文和对应的 BINDER 程序，再加上当前要推断的问题与上下文。k 要在问题类型的多样性和模型输入长度之间取平衡。范例可以人工固定挑选，也可以按当前样本自动检索。模型一次产生 n 个候选程序，解释器得到 n 个答案，再对这些答案做多数投票，得到最终答案。投票方式与 MBR-EXEC 类似，细节在附录。k 和 n 都是该流程的超参数。

### 2.3 BINDER 的一种实现

本节用结构化知识上的 SQL 和 Python 作演示。框架打算扩展到其他编程语言和 API 功能，迁移到新领域的流程放在附录。

实现提供两个 API，记为 f_col 与 f_val。相关上下文是一张子表，由若干列组成，每列是单元格的值。f_col 根据子问题把子表映射成一列，f_val 把子表映射成一个值。列和值都能进入 SQL 以及带 Pandas 的 Python，因此这两个调用可以替换原来写列名或写值的位置，使整段程序在语法上仍然成立。

仍用“北美制造且不含化学品的最畅销衬衫”。产地列里的国名本身说明不了所属大洲，单靠这张表的数据，纯 SQL 解不了。语言模型容易判断一个国家是否在北美，于是在标准 SQL 该写列名的位置放入 f_col，子问题是 “North America?”，上下文是产地列 Made_in。另一处 f_col 的子问题是 “No chemicals?”，上下文是衬衫列，利用列中的文本细节判断是否为纯棉，也就是此例中的不含化学品。

当子问题复杂到不适合先造出一个中间列时，就改用 f_val 直接得到答案。例如询问哪件衬衫最适合正式场合：很难先把衬衫映射成“正式程度”列，再写排序子句。此时 f_val 以衬衫列为上下文，直接输出一个值作为答案。它表面上接近端到端问答，作者强调两点差别。其一，返回值可以嵌进更组合的 SQL，当作普通的值来用。其二，送进模型的是子表而不是整张表，从而减轻输入长度的压力。
