## 第 1 节 Introduction

Text-to-SQL 把自然语言问题写成可执行的 SQL，让不熟悉查询语言的人也能使用数据库，并支撑多种以数据为中心的应用。自然语言处理和数据库两个社区都在研究这一问题。

大语言模型把这个领域明显往前推了一步。文中概括的领先系统常把流程分给多个智能体，分别处理 schema 关联、SQL 生成、SQL 修正和候选选择；生成 SQL 仍是核心。围绕这一核心，现有路线分成提示和微调。提示方法用精心编写的提示调用模型，实际中多通过 API 使用闭源模型。微调方法在 Spider、BIRD 等已有数据上训练，使模型适应该任务。两类方法的基准成绩可以很强，真实应用仍有明确限制：提示方法费用高，存在数据隐私问题，调用方也难以控制模型行为；微调方法面对复杂问题或特定领域数据库时泛化不足，公开数据对真实场景的覆盖有限。

文中用一组数字说明这个泛化差距。Qwen2.5-Coder-7B-Instruct 在 Spider 和 BIRD 的训练集上微调后，在与训练分布相近的开发集上表现良好；到域外的 ScienceBenchmark 和 EHRSQL，执行准确率只有 43.8% 和 31.4%。零样本提示的 GPT-4-Turbo 在这两个集合上达到 59.2% 和 43.1%。作者用这组差距说明，只靠现有公开数据微调，泛化仍然偏弱。

出路因此放在开源模型上：用大规模、多样、高质量的训练数据同时补上性能和泛化。开源模型可以本地部署，费用、数据安全和后续修改都更可控。这样的规模无法靠人工标注。早期增强大多只顺着已有数据的分布扩充样本，多样性、质量和规模有限，还常依赖人工模板或文法。

本文的合成框架对应三个目标。过程自动，人工介入极少。它能扩展出多样、高质量、覆盖广泛领域的样本。内容还要贴近真实用户的需求和场景。为了在自动、可扩展的同时保住质量与多样性，合成被拆成几步，每步交给大模型。第一步从网络表格推断合理的业务场景，并生成带主外键的多表数据库，写明表名、表描述、列名、类型、列描述和两行示例。网上表格以百万计，领域覆盖由此得到规模。第二步依据库信息生成有意义的 SQL。第三步把 SQL 回译成语义等价的自然语言问题。作者沿用已有判断：由 SQL 写成自然语言，比反向生成更准确、歧义更少，因而更能保证问题与 SQL 的配对质量。第四步借鉴思维链，为每条样本写出由问题和数据库构造 SQL 的中间推理，以提高可解释性，并提供训练信号。

为同时覆盖基本检索和更深入的分析，SQL 分成简单、中等、复杂、高度复杂四档，生成时先指定一档。提问风格归纳为九种：正式、口语、祈使、疑问、描述、简练、含糊、隐喻和对话式。回译时指定其中一种，让问句覆盖用户在实际场景中的不同说法。

用来检验框架的是 SynSQL-2.5M，作者称为第一个百万级 Text-to-SQL 数据集。它有 2,544,390 条样本，每条是数据库、问题、SQL 和思维链四元组，分布在 16,583 个合成库上。统计显示，相对已有数据集，它的多样性和复杂度都更高。质量从数据库、问题、SQL 和整条样本四个维度检查，并与人工标注的 BIRD 比较；作者报告几乎所有标准上都更好，据此认为合成流程可靠、有效。

在这批数据上得到开源模型 OmniSQL，尺寸为 7B、14B 和 32B。评测覆盖九个数据集：标准集是 Spider 开发集、Spider 测试集和 BIRD 开发集；领域集是 Spider2.0-SQLite、ScienceBenchmark 和 EHRSQL；稳健性集是 Spider-DK、Spider-Syn 和 Spider-Realistic。OmniSQL 在这些集合上的平均表现达到新的领先水平。尽管参数更少，它仍追平或超过 DeepSeek-V3、Qwen2.5-72B-Instruct 等开源模型，以及 GPT-4-Turbo 和 GPT-4o。代码、数据和模型已经公开。

## 第 2 节 Related Work

相关工作沿着建模方式和数据增强两条线回顾 Text-to-SQL。

### 2.1 Text-to-SQL

早期研究通常采用显式的编码器—解码器。编码器编码数据库模式和问题，解码器依据编码结果生成 SQL。随后的改进分两侧：编码器引入图关系信息，或借助预训练加强表示；解码器加入文法约束，以减少生成 SQL 的语法错误，从而提高准确率。序列到序列模型快速发展之后，该任务被转成序列生成，许多研究专门微调 T5。GPT-4 和 Gemini 出现后，研究者把复杂任务拆成 schema 关联、SQL 生成、SQL 修正和 SQL 选择，每个子任务由大模型智能体通过提示工程或微调处理。本文把工作集中在这些框架的核心环节，用大规模合成数据改进 SQL 生成。

### 2.2 Data Augmentation for Text-to-SQL

公开数据集覆盖有限，增强方法因而要生成额外的问题与 SQL 配对，并使其贴近已有数据的分布。许多方法先用模板或文法产生 SQL，再用神经网络写成自然语言。自然语言更灵活，这个方向更容易得到质量较高的配对。模板多从已有数据抽取，抽象语法树文法则常要专家设计。作者指出，模板限制多样性，文法耗费人工，两者都难以扩展。另一类方法先生成问题，再用现成的 Text-to-SQL 模型译成 SQL；所用模型一旦不准确，数据就会带上噪声。还有方法使用成对的问题模板和 SQL 模板，模板由人工编写或从数据集抽取，再通过填槽生成新样本。这类方法能够工作，但多样性有限，生成的问题也不自然。

与本文最接近的工作是 Sense。它通过精心设计的提示，让 GPT-4 先生成数据库，再基于该库提出问题，最后为问题写出 SQL。作者认为，依赖昂贵的 GPT-4 限制了规模和成本效益。本文把合成拆成更简单、更可控的步骤，因此可以使用能力较弱但开源的模型；在百万级或更大规模上，这一路线更具成本优势。Sense 先写问题再生成 SQL，有可能为已经写好的问题配上错误查询。本文采用由 SQL 到问题的回译来提高配对质量，并进一步合成思维链，使生成数据的推理过程可以被直接读出。
