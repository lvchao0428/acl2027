## 引言（Introduction）

Text-to-SQL 是把自然语言问题写成 SQL。这项任务已经持续几十年，而且不限于机器学习本身：医学、金融、零售和电信都依赖数据库。领域专家若能用自然语言取出其中的结构化数据，才更有机会从大数据里得到新的定量发现。

真正使用时，用户必须先知道模型能答对哪类问题、能看到什么信息，以及哪些操作 SQL 做得到。许多潜在用户并不掌握这些边界，提出的问题经常落在模型能力之外。部署场景比常规评测更宽：问题里既有做得到的，也有做不到的，例如所需知识超出库的内容，或所需功能超出 SQL。现有模型又大多不会弃答，于是可行题上的错误 SQL 和不可行题上硬生成的 SQL 都可能悄悄被当成答案，模型带来的好处可能被这些未察觉的错误抵消。作者认为，若模型只在有把握时给出正确 SQL，其余情况拒绝生成，用户才会更信任输出，也更愿意使用它。

TrustSQL 把可靠性定义为：任何输入都能被正确处理，可行问题生成正确 SQL，不可行问题弃答。不可行的原因包括模式不兼容和功能超出 SQL。图 1 对比三种画面。部署同时有可行与不可行区域。常规任务只在可行区域内追求更多正确 SQL，错误输出容易被忽略，而各模型能答对的范围不同，使用门槛高。可靠任务则增加可行区域内的正确 SQL，并用弃答减少两类错误：可行题上的错误 SQL，以及不可行题上仍生成 SQL。五个区域中，可行题的正确 SQL 与不可行题的正确弃答可取；可行题上的弃答是中性的；两类错误 SQL 都不可取。错误区域缩小后，中性弃答也会收缩，用户才会信任输出。这五种情形计入后文的惩罚式评分，其公式不在前两节。

基准由三个领域数据集和一个跨领域数据集构成：航班 ATIS、教育 Advising、医疗 EHRSQL，以及跨库的 Spider。构造时用数据划分，并加入多种不可行问题，把会损害可靠性的常见错误收进来，做法接近红队测试。引言对实验只给出方向性结论：无惩罚时，多数先进方法看起来不错；惩罚很重时，高分仍然很难。从重惩罚的角度看，知道何时该弃答，比贸然生成 SQL 更重要。要让输出值得信任，还需要大量额外工作。

## 数据集构建（Dataset Construction）

第 2 节先确认哪些常见错误会把答案推进图 1 的错误区域，再逐一写入数据。领域专家的问题常常过难，难在查询本身，也难在模型没见过的库内说法和实体；此时若不能弃答，信任就会受损。查询难度记为 P1，熟悉程度记为 P2，都放在可行数据中。问句还常在指称列或记录时含糊不清。澄清意图需要多轮对话，作者把这一点放在本文之外，不为歧义单独立样。不熟悉模式的用户会索取现有列中没有的信息。先前工作用删列或扰动列来构造这类样本，本文则在 P3 中分成三种，以便细看模型。用户也可能不清楚 SQL 的边界，提出复杂数值运算、数据分析或预约等标准 SQL 做不到的请求，记为 P4。外部知识分两种：完全落在库外的问题，如询问某地有什么机场，记为 P5 并做成不可行题；只部分依赖外部知识的问题，如按某一历史事件筛选出生时间，则排除。

### 2.1 可行数据

可行问题来自三个复杂的领域数据集，即 ATIS（航班）、Advising（教育）和 EHRSQL（医疗），再加上跨领域的 Spider。领域设定与跨领域设定的差别，以及各数据集的复杂度，放在补充材料中。初步分析表明，ATIS 和 Advising 需要大量清理：查询重复多、数据不一致、自然语言问句质量差。处理包括用 GPT-4 为全部输入问句生成新释义，再由作者人工复核。清理后的数据库及问句–SQL 对，构成可行区域。四个数据集都采用既有工作的 SQL hardness 标准来体现查询难度，各难度等级的条数见补充材料。熟悉度留到 2.3 的划分中实现。

### 2.2 不可行数据

真实请求常常落在不可行区域：超出库内容或 SQL 功能，因而没有对应 SQL。作者手工标注问句，纳入三类不可行情形。

模式不兼容不采用随机删列，而使用假设列。问题写得好像存在对应 SQL，但那些列并不在库中。三类按表面形式和语义上与已有列的相似或相异来区分。column-surface 指假设列像其他表里的已有列，或写法相近，例如在 dog_kennels 库的 Professionals 表上虚构 age，去贴近 Dogs 表已有的 age。column-related 指假设列可以自然接入现有模式，例如在 song 表上虚构 duration；作者把它看作 ADVETA 中 ADD 扰动的手工版本。column-unrelated 指假设列从别的库随机抽来，多数很不自然，例如把 product_category 放进 battles 库。

超出 SQL 的问题称为 non-sql。作者先整理自然语言处理与数据分析任务，再用 GPT-4 设想：若允许任意工具，AI 助手面对该库还能做什么。清单有 27 项任务，例子包括异常检测、可视化和网页搜索。标注按库进行：问句要与该库已有的列相关或直接指向这些列，用来模拟用户期待模型做不能只靠 SQL 完成的事。外部知识问题称为 ext-know，由 GPT-4 生成需要领域专长、定性认识或因果理解的问句，一直生成到与其他不可行类型的样本量大致相当。手工标注后，作者再用 GPT-4 反复复查，确认这些问题确实不可行。

表 1 以 Spider 的 orchestra 库为例，该库有 4 张表、23 列，领域库样例从略。注释写的是并不存在的假设列，或标注所用的任务名。五个例子依次覆盖表面相近的容纳人数列、可以自然加入的成员人数列、从其他库搬来的飞行器列、要求做特征重要性分析的非 SQL 请求，以及询问多样性有何好处这种没有对应列的库外问题。

### 2.3 数据划分

划分的原则是：可行数据要有不同的查询熟悉度，不可行数据对模型而言应当是意外遇到的。SQL 结构指 SQL 成分与具体表、列的组合，不含实际取值。seen SQL 指该结构已出现在训练集，但验证集和测试集换了释义后的问句；unseen SQL 指训练集中没有该结构。这对概念只用于可行数据，并用来分析验证集和测试集上的表现。

领域数据集分三步。先按问句把可行数据以 6:2:2 分成训练、验证和测试，各份 SQL 结构相同、问句不同；再从验证集和测试集去掉 20% 互不重叠的 SQL 结构；然后把这合计 40% 的结构从训练集删除。于是各划分中有 60% 属于 seen SQL，验证集和测试集则保留 80% 的 SQL 结构，其中 60% 为 seen SQL、20% 为 unseen SQL。Spider 单独处理：把原开发集对半切开，作为新的验证集和测试集，各 10 个数据库，全部是 unseen SQL，与训练集不重叠。

column-surface、column-related、column-unrelated、non-sql 和 ext-know 全部只放入测试集，比例大体均衡，用来模拟部署中突然出现的不可行请求。
