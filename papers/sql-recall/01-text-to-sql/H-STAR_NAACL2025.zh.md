## 1 引言

表格是现实应用里存放结构化信息的常见格式。表格推理要同时对付非结构化的自然语言问题和结构化的表，并且把逻辑推理、数学推理和文本推理合在一起，因此本身就难。论文把理解并推断表格看成自然语言处理里的一个重要方向。此前已经有大量工作研究基于表的问答，以及基于表的事实验证。图 1 用同一张关于 NY Americans 赛季成绩的表，说明三类任务的答案形态不同：事实验证要对一条陈述给出真或假，短答案问答要给出简短答案，长答案问答要写成一句完整的话。每个例子都配有作答所需的列和行，也就是证据。作者想强调的是，答题并不需要整张表，而需要先找到和问题对应的那一小块单元格。

大模型靠仔细设计的提示，已经在许多任务上表现更好。表格推理里，符号路线以 Program of Thought 为代表，文本路线以 Chain of Thought 为代表。论文认为，两条路线单独使用都会栽在表格特有的复杂性上：格子里混着数值、时间和文本，表的结构本身也不规整。文本推理擅长理解自然语言，却容易读错表结构，也做不好定量计算。基于 SQL 的方法定量问题更强，但一遇到噪声或不规则的输入就变差。只走文本或只走符号的近期方法，因此带着同样的短板。图 2 用这张赛季表把两种失败画出来。面对“1936 年 NY Americans 有没有赢得全国杯”这类是否题，符号推理会返回单元格里的值，而不是是否。面对“1936 年之后过了多久才再赢全国杯”这类要计算的问题，纯文本推理会算错。引言把要解决的问题收成一句：怎样把符号方法和文本方法合成一种混合流程，用上各自的长处，并压低各自的短处。

H-STAR 就是这个混合流程。它把表格推理拆成两步：表抽取，以及自适应推理。抽取采用逐步的“多视图”链。先利用原表和它的转置确定相关列，再在滤掉无关列之后的表上抽取行。这和另一些方法不同：那些方法在原表上同时选行和选列。作者认为，把上下文收束到真正相关的单元格，能减少推理时的幻觉。抽取阶段本身就混用 SQL 和文本。自适应推理阶段则利用大模型的语言理解，并用少样本例子教会模型：什么时候只做语义推理，什么时候要给语义推理再配上符号推理。语义推理始终使用；直接查找、常识问题和复杂的词汇问题只走语义；定量、数学和逻辑问题再加一步 SQL。论文认为，按问题类型切换，才能在不同问题上都取得较好表现，并在需要计算时用计算撑住文本理解。

引言报告，这一流程在三个表格基准上做了验证，任务覆盖表格问答和表格事实验证。多视图抽取加上自适应推理之后，结果超过此前只使用符号或只使用语义的方法。分析还表明，H-STAR 对所使用的大模型是稳的，也能跨任务保持推理能力。贡献写成三条。其一，提出把表抽取和自适应推理连在一起的两步方法，把 SQL 所代表的符号逻辑和文本所代表的语义方法合到一个流程里。其二，实验表明，这种混合在更大的表上尤其优于单用一种推理的已有方法。其三，消融和分析说明，抽取和推理两个阶段各自都对最终表现有贡献，而且这一点跨模型和跨数据集都成立。代码与补充材料的入口包括 https://github.com/nikhilsab/H-STAR 和 https://hstar-llm.github.io/ 。具体数据集名称、分数和消融数字不在这两节里。

## 2 H-STAR 方法

第 2 节把上述分解写成可执行的流程。输入是原表 T 和问题 Q，输出是预测答案。表抽取的产物是一张只和当前问题有关的表 TCR，算法 1 给出对应步骤，图 3 用“1936 年之后 NY Americans 过了多久赢得全国杯”贯穿整条流水线。作者把 H-STAR 和两种只走一条路的方法对照：DATER 用文本推理做抽取，TabQSLify 用 text-to-SQL 做抽取；H-STAR 在抽取阶段就把两种推理配成互补，而不是二选一。推理阶段则只在定量问题上把符号方法和语义方法叠在一起，用来越过纯文本推理的上限。整节分成表抽取和自适应推理。提示词、输入表的格式和超参数放在附录 C 和 D，这里不转述附录中的提示词。

### 2.1 表抽取

二维表由列和行组成，所以抽取是一条两步链：先列、后行。作者强调顺序。先把列收窄，过滤后的表比原表短，更容易落进上下文长度之内，后面的行抽取才做得动，也更省。

列抽取使用多视图。算法先在原表 T 上调用 colsql，由模型写出 SQL 来选列，得到列集合 C1；再把表转置成 TT，在转置表上调用文本步骤 coltext，得到列集合 C2。换一个视图被写成核对：表的排布会让某一路漏掉信息，另一路负责补上。论文称这种核对能提高整体表现，具体分析放在附录 A.3。图 3 的例子里，问题要求计算 1936 年之后再夺杯所间隔的时间。colsql 只抽出 year，也就是 C1；coltext 在转置表上同时返回 year 和 national cup，也就是 C2。全国杯这一列是回答所必需的，却被 SQL 那一路漏掉。两路取并集得到 C′，再按 C′ 过滤原表，得到只含这些列的 TC。概述图在剪列时还保留 row_id，后面的行号才指得回去。

行抽取接在 TC 之后，目标是 TCR。因为列已经减少，TC 的词元数少于 T，行抽取因此更有效。例子中，rowsql 在 TC 上生成 SQL，抽出 row 18，记为 R1。这一行本身选得对，但还不够回答问题。文本验证 rowtext 接着补行；算法把 TC、问题 Q 和已经选出的 R1 一起交给 rowtext，因此文本这一步看得到 SQL 的结果，而不是另起炉灶。rowtext 得到的 R2 包含 row 1 和 row 18。R1 与 R2 取并集得到 R′，再按这些行过滤 TC，得到最终的 TCR。就这个例子而言，回答所需的两行分别对应 1936/37 赛季和后来再次夺杯的赛季，单留 row 18 会把参照年份所在的行丢掉。

这一节的主张可以收成三点。列和行都不是只靠 SQL 或只靠文本决定的：SQL 先提出候选，文本再补上被漏掉的部分。列的文本核对看的是转置后的表，用来对付原表排布造成的遗漏。行的文本核对则显式依赖 SQL 已经选出的行，并且发生在列过滤之后，以便把上下文控制在相关单元格上。

### 2.2 自适应推理

自适应推理要保留文本推理的语义能力，同时用符号推理补上它不擅长的定量部分。作者先让大模型凭语言理解判断这个问题需要什么。需要定量分析时，才启用符号推理；符号步骤的输出 Ev 和表 TCR 一起，成为最后那次文本推理的输入。不需要定量分析时，最后一步只看 TCR。

算法把分支写成对 math(Q) 的判断。若为真，先调用 fsql(TCR, Q)，在 SQL 引擎上执行生成的查询，从 TCR 得到精确结果，这份结果就是证据 Ev；再调用 ftext(TCR, Q, Ev)，由文本推理给出最终答案。若为假，则直接调用 ftext(TCR, Q)，输入里没有这份 SQL 证据。语义推理因此始终负责最后作答，SQL 只在被判定为数学类的问题上提供附加证据。引言里的类型划分比这个布尔条件写得更细：直接查找、常识和复杂词汇问题只用语义；定量、数学和逻辑问题再加 SQL。第 2 节的算法本身把开关写成 math(Q)，并把“定量分析”作为启用 fsql 的条件。

图 3 仍用“夺杯花了多久”说明这条分支。该问题需要计算，流水线因此优先走 fsql，在 TCR 上执行 SQL，再把执行结果当作附加证据送进 ftext。概述图把这份证据画进最终推理的输入。作者的推论是：把定量步骤显式接进文本推理，针对的就是大模型处理定量推理时的弱点，从而提高需要数值推理的问题的准确性和稳健性。

把两节连起来看，H-STAR 的方法主张是一条固定顺序，而不是让模型在整张原表上自由选择推理工具。先用 SQL 与转置文本互补地确定列，再在缩短后的表上用 SQL 与文本互补地确定行，得到 TCR；然后始终用文本给出答案，只在问题被判断为需要数学或定量分析时，把 TCR 上的 SQL 执行结果当作证据一并送入。符号方法负责可执行的定位和计算，文本方法负责核对遗漏并组织最终答案。引言中的实验结论声称，这条顺序在三个表格基准上优于单用一种推理的方法，并在大表上更明显；那些比较的具体数字不在第 2 节。
