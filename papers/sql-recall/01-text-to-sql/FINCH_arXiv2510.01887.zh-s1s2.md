# FINCH: Financial Intelligence using Natural language for Contextualized SQL Handling

## Abstract 摘要

Text-to-SQL，即把自然语言问题翻译成 SQL 查询的任务，长期以来一直是 NLP 的核心挑战。尽管进展显著，将其应用于金融领域仍然特别困难，原因在于复杂的模式（schema）、领域特定术语，以及错误的高代价。尽管如此，目前还没有专门的大规模金融数据集来推进研究，形成了一个关键空白。为此，我们引入一个经过整理的金融数据集 FINCH，包含 292 张表和 75,725 个自然语言–SQL 对，既能用于微调，也能用于严格评测。在这一资源之上，我们对不同规模的推理模型和语言模型进行基准测试，系统分析它们在金融 Text-to-SQL 任务中的优势与局限。最后，我们提出一个面向金融的评测指标 FINCH Score，它捕捉现有指标所忽略的细微差别，从而更忠实地评估模型性能。关键词：Text-to-SQL、金融中的大语言模型（Large Language Models in Finance）、金融基准数据集、面向金融的 text-to-SQL 评测指标。

## 1 Introduction 引言

把自然语言问题翻译成 SQL 查询的任务，通常称为 Text-to-SQL，自关系数据库早期以来一直是核心研究挑战 [28]。早期方法以基于规则的语法和符号解析为主，但神经方法的出现从根本上重塑了该领域。Seq2SQL (2017) [37] 的提出表明，强化学习可以用来生成可执行查询，并超越基于模板的系统。不久之后，SQLNet [29] 用基于草图的解码策略取代强化学习，在保持强性能的同时降低了复杂度。Spider (2018) [33] 作为第一个大规模跨领域数据集发布，为在多样模式上评测泛化提供了基础，并迅速成为首选基准。后续数据集如 CoSQL 和 SParC (2019) [32, 34] 把该任务扩展到对话式和依赖上下文的设定。模型层面的进展随之而来：RAT-SQL (2020) [24] 引入关系感知 Transformer 做模式链接，PICARD (2021) [20] 对大型预训练语言模型实施约束解码。更近一些，BIRD 基准 (2023) [14] 把评测扩展到数十亿级查询，成为迄今衡量大规模稳健性的最全面资源。

尽管有这条进展轨迹，显著挑战仍然存在。许多最先进系统在基准上取得高表现，却在与训练语料偏离的模式上失利 [13, 22]。虽然 Spider [33] 和 BIRD [14] 强调跨领域泛化，它们的模式大多反映百科式或开放领域知识，而不是行业特定设定。RAT-SQL [24] 和 DCG-SQL (2025) [25] 等模式链接方法改善了上下文对齐，但对噪声描述和宽列空间仍然敏感——这些条件在企业数据库中很常见 [4, 18, 20]。更近的方法，如 NL2PY2SQL (2024) [16]，探索 Python 到 SQL 的中间表示，但它们在高风险领域中的效率与可解释性仍有疑问。最后，评测方法继续依赖精确匹配（exact match）[33] 和执行准确率（execution accuracy）[37]，这些指标常常无法捕捉微妙但有意义的结构差异。这些局限共同暴露出：由基准驱动的进展与真实世界部署的需求之间存在差距。

与此同时，金融领域对可执行推理任务的兴趣日益增长。这些任务虽然并不总是以 SQL 为中心，但处理的挑战与数据库查询直接相关 [12, 19]。FinQA (2021) [1] 引入一个在公司财务报告上做数值推理的基准，把文本输入与操作程序（program-of-operations）监督配对，以促进神经–符号整合。类似地，TAT-QA (2021) [39] 结合表格与文本信息，反映金融数据的多模态性质。ConvFinQA (2022) [2] 进一步把它扩展到多轮推理，模拟分析师工作流中查询迭代演化的情形。除数据集之外，模块化方法也已出现。例如，Nye et al. [17] 提出一个系统：一个智能体从申报文件中抽取关键绩效指标，另一个把它们翻译成 SQL 查询，从而把推理分布到专门组件上。伴随这些进展，评测指标已从僵硬的精确匹配转向树编辑距离 [36] 和结构感知的相似度度量 [38]，更符合分析师的期望。

近期工作已开始专门处理金融中的 Text-to-SQL，不过与开放领域研究相比，该领域仍处于初期。FinSQL (2024) [35] 做出了第一次专门尝试，发布了 BULL 数据集，由为跨数据库泛化而设计的宽模式金融表组成。其结果表明，领域特定调优相对通用基线可以带来高达 36% 的相对改进，但也凸显了在更大模式上性能的陡降。BookSQL (2024) [11] 对此作了补充，在会计领域提供 75k 个自然语言–SQL 对，暴露出大型预训练模型在处理细微商业语义和复杂连接时的局限。在方法方面，NL2PY2SQL (2024) [6] 引入两步的自然语言–Python–SQL 流水线，更好地捕捉领域逻辑；DCG-SQL (2025) [15] 利用深度上下文图表示，增强宽表和关系复杂表中的模式链接。在准确率之外，可靠 Text-to-SQL（Reliable Text-to-SQL, RTS, 2025）[26] 纳入自适应弃答和人在回路中的修正，强调可靠性是银行、审计和投资情境中的核心要求。

综合来看，这些发展凸显出一个关键空白：尽管基准性能稳步提高，当前系统仍然不适合金融部署 [3, 21, 30]。金融数据库提出独特挑战——宽且不断演化的模式、严格的领域约束、监管合规，以及对错误的更高敏感性。应对这些挑战需要领域特定数据集、明确针对金融模式定制的架构，以及超越精确匹配、能够捕捉语义保真和操作安全的评测方法。弥合这一差距不只是通用 Text-to-SQL 研究的增量一步，而是转向构建实用系统的必要转变，使这些系统能够在关键决策中支持分析师、审计者和政策制定者。

尽管金融 QA 和领域特定 Text-to-SQL 已有相当进展，大多数先前工作仍然以文档中心或表格–文本混合推理为中心，而不是直接查询金融 SQL 数据库。因此，专门面向金融的 Text-to-SQL 基准稀缺，社区仍然缺少一种资源，能够忠实地捕捉真实世界金融应用所要求的复杂性、术语和精度。填补这一空白既需要大规模、领域特定的数据集，也需要反映金融环境独特挑战的评测方法。

受这些挑战推动，本工作为推进金融领域的 Text-to-SQL 做出三项关键贡献：

- **大规模金融数据集整理。** 我们把 BIRD [14]、Spider [33]、FinSQL [35] 和 BookSQL [11] 等现有资源整合并扩展为一个统一数据集。所有 SQL 查询都经过规范化，以与 SQLite 兼容，从而保证在开源社区中的广泛可用性。最终数据集 FINCH 跨越 33 个数据库，领域包括零售、银行交易、贷款、保险、销售、市场营销、金融、电子商务、基金、股票和会计。总计包含 292 张表、2233 列、177 个关系，以及 75,725 个 NL–SQL 对——提供了最大的面向金融的基准，既适合评测也适合微调。
- **全面的模型基准测试。** 我们评测四类模型：大规模 LLM（Qwen3-235B-A22B）、中小规模开源模型（GPT-OSS-120B、GPT-OSS-20B、Qwen3-8B），以及以推理为中心的模型（Phi-4-mini-reasoning 和 Arctic-Text2SQL-R1-7B）。结果表明，GPT-OSS-120B 取得最强的总体性能，甚至超过 Qwen3-235B-A22B 等更大的模型；而 Arctic-Text2SQL-R1-7B 尽管参数规模不大，成为表现第三好的模型。这些发现表明，以推理为中心的架构在经过仔细适配后，可以在金融 Text-to-SQL 任务上媲美甚至超过大得多的通用 LLM。
- **金融特定的评测指标。** 我们提出一个定制评测指标 FINCH Score，它把成分匹配和执行准确率与加权评分及容差阈值结合起来。这一设计减轻对微小浮点不匹配的不成比例惩罚，同时强调结构保真——优先考虑列名、表引用和条件的正确性。实验表明，该指标对金融设定中的性能提供更忠实的评估，比传统的精确匹配度量更好地对齐实际要求。

## 2 FINCH Dataset Construction FINCH 数据集构建

为应对对大规模、面向金融的 Text-to-SQL 基准的迫切需求，我们通过有意识地整合并精炼四个公开资源来整理 FINCH 数据集：BIRD [14]、Spider [33]、BULL [35] 和 BookSQL [11]。尽管 Spider 和 BIRD 是 Text-to-SQL 社区广泛认可的基准，它们最初并非针对金融应用而设计。它们的数据库跨越广泛领域——从体育和教育到娱乐和地理——其中许多与金融系统几乎无关。相比之下，使用金融数据的从业者和研究者面临高度专门的挑战，例如解释银行记录、分析银行卡交易、管理零售和销售数据，或处理贷款和保险查询 [1, 39]。使用通用基准有稀释模型焦点的风险，并限制其在真实金融设定中的适用性。为弥合这一差距，我们进行了仔细的筛选，只保留与金融情境对齐的数据库。具体而言，我们识别并保留覆盖零售销售、银行卡交易、银行服务、贷款处理、保险和电子商务的领域。由此，我们确保 FINCH 不只是 Text-to-SQL 数据的又一次聚合，而是对金融相关应用具有直接效用的基准。表 1 把 FINCH 与四个广泛使用的 Text-to-SQL 数据集进行比较。与先前要么强调规模（例如 BookSQL）、要么强调跨领域泛化（例如 Spider、BIRD）的基准不同，FINCH 在规模、模式多样性和金融相关性之间取得平衡。特别是，它提供 33 个金融特定数据库，平均表–数据库比高于更早的资源，因而特别适合评测金融中的模式链接和组合推理。

### 2.1 Dataset Curation 数据集整理

FINCH 的整理经过若干审慎而有条理的步骤。从 Spider 中，我们选择了 22 个具有明确金融相关性的数据库；从 BIRD 中，我们保留了 7 个这样的数据库。对于 BULL 和 BookSQL，它们在设计上已经以金融为重点，我们保留了所有同时具有自然语言问题及其对应 SQL 语句的可用样本。由此得到一个多样但仍领域特定的数据集，结构如下：

- BIRD：1,139 个样本
- Spider：1,100 个样本
- BULL：4,966 个样本
- BookSQL：78,433 个样本

在此过程中，我们观察到 BookSQL 的测试划分缺少对应的 SQL 查询，因此把这一部分排除在 FINCH 之外，以保持完整性与可用性。为进一步确保数据完整性，每条 SQL 查询都在其关联的 SQLite 数据库上执行。这一验证步骤被证明至关重要，揭示出大量异常；若置之不理，将损害数据集的可靠性。具体而言，我们发现：

- 在 BIRD 中，1,139 条查询里有 327 条失败，其中包括 198 条列名不正确，以及 129 条无效的表引用。
- 在 BULL 中，4,966 条查询里有 60 条有问题，其中 43 条语法错误、10 条错误的表引用、1 条列错误、4 条不完整查询，以及 2 个无法识别的词元。
- 在 BookSQL 中，78,433 条查询里有 9,526 条出现错误：7,018 条列名不正确、1,494 条无效表引用，以及 1,014 条语法错误。
- 有趣的是，Spider 子集没有检测到异常，因而显得突出。

识别、编目并纠正这些错误的过程并不纯粹是机械的。它需要反复执行查询、仔细检查数据库模式，并对每个问题背后的意图作上下文推理。这种认真确保 FINCH 不仅在规模上聚合数据，也保持金融特定 Text-to-SQL 研究所需的精度与稳健性。

FINCH 的最终版本由 33 个数据库组成，涵盖 292 张表、2,233 列和 177 个关系，NL–SQL 对总计超过 75,725。在难度分布上，FINCH 包括 9,358 个简单、33,780 个中等和 32,587 个困难示例。另外 7,035 个原本未标注的样本，按照 [11] 中提出的模式复杂度指南进行了标注。这一设计确保覆盖多样的金融操作、模式复杂度和 SQL 构造。此外，FINCH 大量使用 ORDER BY、GROUP BY 和嵌套查询等 SQL 操作，这些对在金融环境中建模复杂推理至关重要。图 1 提供 FINCH 的高层概览，说明来自多个来源的数据库如何被合并为一个统一基准。该图也突出数据库模式的多样性，以及通过这一整合所达到的领域覆盖广度。图中具体图形【抽取不清】。

概括而言，FINCH 是第一个大规模、金融特定的 Text-to-SQL 数据集，它结合了广度（多个领域）、深度（丰富的模式复杂度）和难度（非平凡的 SQL 构造）。我们相信 FINCH 将成为在金融应用中评测和微调大语言模型以及以推理为中心的架构的基石资源。
