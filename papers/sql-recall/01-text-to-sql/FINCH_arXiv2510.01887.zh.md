## 1 引言

把自然语言问题译成 SQL，也就是 Text-to-SQL，从关系数据库的早期起就是核心研究问题。早期方法以规则文法和符号解析为主。神经网络改写了这个领域的做法。Seq2SQL（2017）表明，可以用强化学习生成可执行查询，并且超过基于模板的系统。随后 SQLNet 用基于草图的解码代替强化学习，复杂度下降，成绩仍然较强。Spider（2018）是第一个大规模跨领域数据，用来评估模型在不同数据库模式上的泛化，并很快成为主要基准。CoSQL 和 SParC（2019）把任务延伸到对话、以及依赖上下文的设定。模型一侧，RAT-SQL（2020）用关系感知的 Transformer 做模式链接；PICARD（2021）为大型预训练语言模型加上约束解码。论文称，BIRD（2023）把评测规模扩到十亿级查询，成为当时衡量大规模稳健性最全面的资源。

作者认为，成绩沿这条线提高之后，困难仍然明显。许多最优系统在基准上分数高，一旦模式偏离训练语料就会失手。Spider 和 BIRD 强调跨领域泛化，它们的模式大多对应百科或开放域知识，行业现场的库不在这个范围里。RAT-SQL 和 DCG-SQL（2025）改善了上下文对齐，但对噪声描述和很宽的列空间仍然敏感，而企业数据库常常就是这种条件。NL2PY2SQL（2024）探索先落到 Python、再生成 SQL 的中间表示；在高风险领域里，它的效率和可解释性仍被写成尚未解决的问题。评价则继续依赖精确匹配和执行准确率。论文认为，这两种指标常常抓不住细小但有意义的结构差异。上述限制合在一起，构成基准进展和真实部署之间的缺口。

金融领域并行出现了一批可执行推理工作。它们不一定以 SQL 为中心，但和查库直接相关。FinQA（2021）做的是公司财报上的数值推理，把文本输入和「操作程序」的监督配在一起，用来推动神经方法与符号方法的结合。TAT-QA（2021）同时使用表格和文本，对应金融数据既有表又有正文的形态。ConvFinQA（2022）再延伸到多轮推理，模拟分析师逐步改写问题的工作过程。模块化系统也出现了。文中的例子是 Nye 等人的设计：一个智能体从申报文件中抽取关键绩效指标，另一个智能体把这些指标译成 SQL，推理被分到不同部件上。评价指标也从严格的精确匹配，转向树编辑距离和感知结构的相似度，论文认为这更接近分析师的预期。

专门做金融 Text-to-SQL 的工作被写成仍处于早期，和开放域研究相比刚刚起步。FinSQL（2024）放出 BULL，被论文称为第一次专门尝试：宽模式的金融表，目标是跨库泛化。其结果是，领域专用调优相对通用基线最多可以有 36% 的相对提升，同时在更大的模式上成绩下降很陡。BookSQL（2024）在引言里被概括为会计领域约 7.5 万条自然语言–SQL 对；作者用它说明，大型预训练模型在处理细微的商业语义和复杂连接时仍然有限。第 2 节给出的 BookSQL 计数与这个约数不同，见下节。方法上，NL2PY2SQL（2024）用「自然语言—Python—SQL」两步流程来抓住领域逻辑；DCG-SQL（2025）用深层上下文图加强模式链接，对象是又宽、关系又复杂的表。可靠 Text-to-SQL（RTS，2025）加入自适应弃权，以及人在回路中的修正，把可靠性写成银行、审计和投资场景的核心要求。

将这些线索合在一起，论文的判断是：基准分数在提高，现有系统仍然不适合部署到金融场景。金融库的困难包括模式宽而且会演变、领域约束严格、需要满足监管，以及对错误更敏感。应对方式被写成三件套：领域专用的数据，明确针对金融模式来设计的架构，以及超出精确匹配、能够反映语义忠实度和操作安全性的评价。作者认为，补上这个缺口是从通用 Text-to-SQL 转向实用系统，服务对象是分析师、审计师和政策制定者的关键决策。

引言后半进一步收窄缺口的位置：金融问答和领域专用 Text-to-SQL 已有不少进展，但多数工作仍集中在以文档为中心的推理，或表格与文本混合的推理，直接对金融 SQL 数据库发问的基准很少。社区缺少一份能呈现真实金融应用所要求的复杂度、术语和精度的资源。因此既需要大规模的领域数据，也需要能反映金融环境特有困难的评价方法。

本文的三项贡献如下。

- 整理大规模金融数据。作者把 BIRD、Spider、FinSQL 和 BookSQL 合并并扩展成一份数据，全部 SQL 被规范化到与 SQLite 兼容，以便开源社区使用。最终的 FINCH 跨 33 个数据库，领域包括零售、银行交易、贷款、保险、销售、营销、金融、电子商务、基金、股票和会计。合计 292 张表、2233 列、177 个关系、75,725 条自然语言–SQL 对。论文称之为当时最大的面向金融的基准，既可以评测，也可以用于微调。
- 对模型做系统评测。论文说评测覆盖四类模型，正文点名的是：大规模语言模型 Qwen3-235B-A22B；中小规模开源模型 GPT-OSS-120B、GPT-OSS-20B 和 Qwen3-8B；以及以推理为中心的 Phi-4-mini-reasoning 和 Arctic-Text2SQL-R1-7B。引言给出的排序是：GPT-OSS-120B 整体最强，超过规模更大的 Qwen3-235B-A22B；Arctic-Text2SQL-R1-7B 参数量不大，排在第三。由此推出的结论是，经过认真适配的推理型架构，在金融 Text-to-SQL 上可以比肩甚至超过大得多的通用大语言模型。前两节没有列出各模型的分数表。
- 提出面向金融的 FINCH Score。它把组件匹配和执行准确率合在一起，使用加权计分和容差阈值。设计目的是减轻浮点数的微小不一致所带来的过重惩罚，同时强调结构是否忠实，优先看列名、表引用和条件是否正确。作者写道，实验表明在金融设定里，这一指标比传统精确匹配更贴近实际要求。编号公式不在前两节。

## 2 FINCH 数据集的构建

为做出大规模、面向金融的 Text-to-SQL 基准，FINCH 由四个公开资源合并并修订而成：BIRD、Spider、BULL 和 BookSQL。

Spider 和 BIRD 是 Text-to-SQL 社区的常用基准，原本并不是为金融应用设计的。它们的库覆盖体育、教育、娱乐、地理等诸多领域，其中很多与金融系统关系不大。金融场景里的实际工作是解读银行记录、分析卡交易、管理零售和销售数据，或处理贷款与保险查询。作者认为，继续用通用基准会稀释模型的关注点，并限制它们在真实金融场景中的适用性。

因此筛选只保留与金融情境对齐的库，保留下来的领域包括零售销售、卡交易、银行服务、贷款处理、保险和电子商务。论文把这一步的结果说成：FINCH 直接服务金融相关应用，目的不是再做一次无差别的数据汇集。

表 1 将 FINCH 与 Spider、BIRD、BULL、BookSQL 对照。比较结论是：已有基准或者强调规模，文中的例子是 BookSQL；或者强调跨领域泛化，例子是 Spider 和 BIRD。FINCH 要同时兼顾规模、模式多样性和金融相关性。它提供 33 个金融专用数据库，平均每库表数高于先前资源，因而更适合评估金融场景中的模式链接和组合推理。

表中各列包括全量规模、全量库数、筛选后的库数、筛选后的样本数，以及平均表库比。可读出的数字是：Spider 全量 10,181 条、200 个库，筛进 FINCH 的是 22 个库、1,100 条，表库比 5.1；BIRD 全量 12,751 条、95 个库，保留 7 个库、812 条，表库比 7.3；BULL 全量即保留量，4,966 条、3 个库，表库比 26.0；BookSQL 全量 78,433 条、1 个库，表中保留 68,907 条，表库比 7.0；FINCH 为 33 个库、75,725 条，表库比 8.85。引言里把 BookSQL 概括为约 7.5 万对，与本节的 78,433 和 68,907 不是同一个数字。

### 2.1 数据整理

整理是按来源筛选，并要求自然语言问题和对应 SQL 同时存在。从 Spider 选出 22 个有明确金融相关性的库，从 BIRD 保留 7 个这样的库。BULL 和 BookSQL 本身就是金融向的，满足「问题与 SQL 都在」的样本全部保留。正文列出的纳入规模是：BIRD 1,139 条，Spider 1,100 条，BULL 4,966 条，BookSQL 78,433 条。Spider 的 22 个库、BIRD 的 7 个库，加上 BULL 的 3 个库和 BookSQL 的 1 个库，与后文 33 个库的总数一致。

BookSQL 的测试划分没有配套 SQL。为了数据完整、可用，这一部分被排除出 FINCH。其后每条 SQL 都在对应的 SQLite 库上执行。作者认为这一步很关键，因为它暴露出大量异常；若不处理，数据的可靠性会受损害。分来源的清点如下。

- BIRD：1,139 条中有 327 条执行失败，其中 198 条列名错误，129 条表引用无效。表 1 里 BIRD 的保留样本 812，与 1,139 减去这 327 条之后的差数相同。
- BULL：4,966 条中有 60 条有问题，包括 43 条语法错误、10 条错误的表引用、1 条列错误、4 条不完整查询，以及 2 条无法识别的记号。表 1 中 BULL 的保留样本仍是 4,966。
- BookSQL：78,433 条中有 9,526 条出错，其中 7,018 条列名错误，1,494 条表引用无效，1,014 条语法错误。表中的 68,907 与 78,433 减去 9,526 之后的差数相同。正文同时写了两件事：排除缺少 SQL 的测试划分，以及对错误进行改正。
- Spider 的子集没有发现异常，1,100 条原样保留。

识别、登记和改正这些错误被写成不是机械替换。需要反复执行查询、对照数据库模式，并根据每个问题背后的意图做判断。作者认为，经过这一步，FINCH 在按规模汇集数据的同时，保持了金融 Text-to-SQL 研究所需要的精度和稳健性。

最终版本是 33 个数据库、292 张表、2,233 列、177 个关系，自然语言–SQL 对超过 75,725 条。难度分布为易 9,358、中 33,780、难 32,587，三档相加为 75,725。另有 7,035 条样本原先没有难度标签，作者按 BookSQL 一文提出的模式复杂度指南做了标注。从这组数字看，这 7,035 条落在上述三档之内，因为三档已经加总到全部 75,725 条。设计目标是覆盖不同的金融操作、不同的模式复杂度和不同的 SQL 结构。FINCH 大量使用 ORDER BY、GROUP BY 和嵌套查询，论文把这些结构视为在金融环境中做复杂推理所需要的成分。

图 1 是合并过程的总览：多个来源的库如何进入同一个基准，并用来显示模式的多样性，以及这次合并所覆盖的领域范围。

本节的收束是：FINCH 是第一个大规模、专门面向金融的 Text-to-SQL 数据，同时具有广度（多个领域）、深度（丰富的模式复杂度）和难度（并不简单的 SQL 结构）。作者预期，它可以成为在金融应用中评测和微调大语言模型以及推理型架构的基础资源。
