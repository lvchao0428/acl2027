## Abstract 摘要

推荐带有 kids 标签的视频等真实任务，可以归结为寻找与硬谓词（hard predicates）相关联的相似向量。这一任务称为过滤向量搜索（filtered vector search）。它具有挑战性，因为先前最先进的、基于图的（未过滤）相似性搜索技术在考虑硬约束时会发生退化：有效的基于图的过滤相似性搜索，依赖于足够的连通性，以便在少数几跳内到达相似物品。为了考虑谓词，近期工作提出修改图遍历，只访问满足谓词的物品。然而，它们无法对广泛的谓词提供「少跳可达」（just-a-few-hops）性质：它们必须显著限制谓词，否则在只有很少物品满足谓词时就会失去效率。

我们提出相反的做法：不去约束遍历，而是构建许多索引，每个索引服务不同形式的谓词。为了有效构建，我们设计了一个三维分析模型，刻画索引大小、搜索时间与召回率（recall）之间的关系，并据此采用负载感知（workload-aware）的方法，把尽可能多的有用索引装进一个集合。查询时再次使用该分析模型，从中辨认出在给定召回率下搜索最快的那一个。我们在选择率（selectivity）与形式各不相同的数据集上展示了更优的性能与支持：相对其他索引，本方法最高获得 8.06× 加速，构建时间最低可至其他索引的 1%，内存不到标准 HNSW 图的 2.15×，并且只需要对历史负载有适度了解。

## 1 INTRODUCTION 引言

寻找满足硬约束的语义相似物品是一项常见任务。妈妈们可能搜索带有 “safe-for-kids” 标签（硬约束）的视频（语义）。在线购物者可能搜索处于特定价格区间（硬约束）的服装（语义）[75]。这一任务称为过滤向量搜索：我们查询与硬谓词相关联的相似向量，这些向量编码语义。随着现代机器学习模型提供高质量向量嵌入，该问题受到越来越多的研究 [15, 16, 21, 23, 31, 39, 44, 48, 51, 61, 66, 75]；这些模型见 [35, 36, 43]。

一些工作通过约束原本用于未过滤向量搜索的、基于图的近似最近邻（approximate nearest neighbor, ANN）索引来处理过滤向量搜索 [17, 27, 33]：FilteredVamana 把图遍历与过滤器求值交错进行；ACORN [44] 只访问通过谓词的节点，从而在查询时诱导出子图。这些工作优于预过滤（pre-filtering）这类朴素方法；预过滤使用（缓慢的）线性扫描来做相似度计算。基于图的方法经由边在物品之间导航，以少数几跳到达目标。有效的过滤向量搜索旨在用紧凑的图来服务查询；一旦小世界（small-world）这一性质丢失，图遍历就会失去效率。

不幸的是，现有基于图的方法无法为低选择率谓词提供小世界性质，因而性能更差。而且，我们也不能简单地使用预过滤，因为除非选择率过低，线性扫描仍然太贵。这一选择率区间被称为 “unhappy middle” [23]。FilteredVamana 试图通过把共享属性的向量连接成局部、稠密、按过滤器划分的子图来缓解这一点，但需要限制过滤器形式 [21]。ACORN [44] 以一定代价支持一般谓词：如果诱导子图变得过于稀疏，它可以证明地失去小世界性质 [4, 29, 33]。我们推测，单一图不足以处理全部谓词，这些谓词的支持集可能以复杂方式相互重叠。我们可能需要多张图，每张图专门面向不同的谓词集合。

**Our Goal.** 我们的目标是通过构建一个索引集合，为几乎所有选择率或形式各异的过滤查询提供紧凑的图。集合比单一索引更具表达力。利用真实过滤向量搜索负载中的过滤器稳定性 [39, 53]，我们可以按观察到的负载定制索引，以最大化期望的搜索质量。每个索引可以服务多个谓词：例如，为 stars=1–3 构建的图，如果对子谓词足够稠密，也可以服务 stars=1。索引集合比单一索引需要更多内存；然而，相对原始数据（即高维向量），索引比较小。在我们的实验中，数百个（小的）附加索引所占内存只相当于一个覆盖全数据集的索引，同时相对只依赖一个索引显著提升性能。只要我们提出的索引集合能为几乎所有查询提供高质量的过滤搜索，每个查询都有一张紧凑的图，并且内存高效，它就能成功。

**Challenge.** 构建有效的索引集合具有挑战性，因为目标相互冲突。在构建时，图可以用召回率换取更小的体积（Fig 1a），从而允许更多索引和更大覆盖。然而，图必须足够稠密才能获得高召回率。同样，在查询时，我们可以用搜索速度换取更高召回率（Fig 1b）。必须量化这一关系，才能为给定查询找到该使用哪个索引。这些独特性质使本任务区别于已有问题 [49, 52]。例如，物化视图选择（materialized view selection）针对的是精确查询，而 ANN 是近似的，并带有速度/召回率权衡。

**Our Approach.** 我们的框架称为 SIEVE（Set of Indexes for Efficient Vector Exploration），构建一个针对已观察查询负载定制的索引集合，以在内存预算和指定召回率下最大化期望吞吐。每个候选索引被赋予收益——把它加入集合时的边际性能增益——以及内存成本，我们据此构建集合。这一思路本身并不新；新的是（1）如何估计收益/成本，以及（2）如何用索引集合服务查询。

首先，我们设计一个分析性的、与谓词形式无关的收益/成本模型，刻画索引大小、搜索时间与召回率之间的三维关系，从而找到满足特定召回率的最小（即最稀疏）图。由于每个索引更小，在内存预算内就允许更多索引，从而为更多谓词加速搜索。我们的模型基于经验观察以及已有的小世界网络理论 [4]。

其次，查询服务在给定特定召回率时动态选择搜索最快的索引。查询时的这一选择是必要的，因为我们的索引可能重叠：一个查询可能可以由多个索引服务。为了最优选择，我们再次使用该模型来确定（1）使用哪个索引，以及（2）它的搜索参数化。

**Difference from Existing Work.** SIEVE 与现有向量搜索工作显著不同（Table 1）。相对于面向精确查询的物化视图选择 [2, 71]、划分 [53, 68] 和查询重写 [19, 20]，SIEVE 的优化明确考虑召回率，并进行理论驱动的索引调参（§4.2）以及动态的、感知召回率的服务（§5.2），以获得所需的内存/速度/召回率权衡。

**Contributions.** 我们提出 SIEVE，一种面向过滤向量搜索的索引框架（§3），贡献如下：

## 2 MOTIVATION 动机

SIEVE 建立在 HNSW [33] 之上，后者是一种高性能的未过滤向量索引 [12, 74]。我们描述 HNSW（§2.1）、已有工作如何（低效地）把它扩展到过滤搜索（§2.2），以及我们为有效过滤搜索构建并使用 HNSW 索引集合的想法（§2.3）。

### 2.1 HNSW Graph HNSW 图

HNSW 是一种基于图的向量索引 [33]，它结合小世界图 [4] 与跳表（skip-lists）[65] 的思想，形成多层图结构，以便在向量数据集上进行有效的相似性搜索。

**HNSW Graph Structure.** HNSW 图由多个分层的小世界图组成 [4]。最顶层（入口层）包含最少的向量，并具有较长的边，便于在向量空间中做长程移动；底层（基层）包含全部向量，并具有较短的边，表示局部邻域。HNSW 图通过增量插入向量来构建：每个向量在每一层连接到若干邻居，由构建参数 \(M\) 控制。\(M\) 作为出度上限，并确保向量在每一层连接到其他相似向量。

**HNSW Search.** 给定查询向量，图的各层自顶向下遍历：先用高层的长链接走到具有相似数据向量的邻域，再用低层的短链接找出 top-k 选择。Alg. 1 给出逐层搜索算法。

### 2.2 Existing Filtering Methods Underperform 现有过滤方法表现不佳

尽管最初的 HNSW 图方案并未考虑执行过滤向量搜索，已有若干基于 HNSW 的过滤搜索方法被提出。本节概述这些方法。

**Post-Search Filtering.** 对于选择率为 \(sel\) 的过滤 top-\(k\) 查询，可以在图上过度搜索 top-\(k/sel\) 个向量。不匹配的结果被丢弃，并期望 top-\(k/sel\) 的结果中仍保留 \(k\) 个；若不是，则再做一次 top-\(2k/sel\) 搜索，依此类推。

**Result-Set-Filtering.** hnswlib [40] 在 HNSW 搜索过程中、把候选加入 top-k 结果集之前评估查询过滤器（Alg. 1 第 13 行）。这相对搜索后过滤有所改进，因为一次遍历就能返回 \(k\) 个满足条件的结果，但每个候选仍有 \((1-sel)\) 的概率被过滤器从 top-k 集合中拒绝。因此，召回率几乎不受影响，但搜索时间与选择率成反比（Fig 2a），在 \(sel\) 较低、却又有许多点可供预过滤搜索时（例如大规模数据集 [8]）仍然表现不佳。

脚注 1：具体而言，hnswlib、ACORN（以及我们的工作）都通过一种常用的基于位图（bitmap）的过滤方法实现过滤，该方法原则上可以处理任意谓词：它为插入的向量分配 ID，然后根据通过过滤器的向量 ID，相对于标量属性计算一个二元的 ID→{0,1} 映射（例如经由外部关系数据库管理系统 RDBMS，§6）。

**Other Filter Application Methods.** ACORN [44] 在邻居扩展时应用过滤（Alg. 1 第 6 行），实际上是在 HNSW 图中满足条件的向量所诱导的子图里搜索。然而，子图诱导等价于删除边和节点，子图可能失去小世界性质，尤其是有效搜索所需的连通性 [67]；若子图过于稀疏 [41]，按 Alg. 1 原样搜索可能导致过早停止和低召回率。因此，ACORN 同时修改 HNSW 的构建与搜索，特别是扩展到 2 跳邻居，以避免子图稀疏。然而，即使 2 跳子图稀疏，ACORN 仍可能表现不佳。我们将通过实验表明（§7.2），结果集过滤有时优于 ACORN，反之亦然。

SIEVE 在其 HNSW 索引中使用结果集过滤，因为它无需专门的图构建即可应用；专门的图构建可能带来过高的索引构建时间（time-to-index, TTI，§7.3）。因此后文的讨论限于结果集过滤。不过，只要做少量调整，SIEVE 也可以改用 ACORN 的过滤。

Alg. 1 的步骤可读。注释位置按抽取保留：第 8 行注明 ACORN 在此过滤，第 15 行注明 hnswlib 在此过滤。正文所说的行号（ACORN 为第 6 行，hnswlib 为第 13 行）与算法注释所在行不完全一致，行号对应关系【抽取不清】。

```
Algorithm 1: HNSW_SEARCH_LAYER
Input: query vector q, enter points ep, exploration factor ef, layer lc
Output: ef closest vectors to q
Initialize visited set V, candidate set C, top-ef set W to ep
while |C| > 0 do
    c ← extract nearest vector in C to q
    f ← furthest vector in W to q
    if dist(c, q) > dist(f, q): break
    nbrs ← neighborhood(c) at layer lc    // ACORN filters here
    for each e ∈ nbrs do
        if e ∈ V: continue
        V ← V ∪ e
        f ← furthest vector from W to q
        if dist(e, q) < dist(f, q) or |W| < ef: then
            C ← C ∪ e
            W ← W ∪ e    // hnswlib filters here
        If |W| > ef: remove furthest vector from W to q
Return W
```

### 2.3 SIEVE’s Intuition for Faster Search SIEVE 加速搜索的直觉

现有基于 HNSW 的过滤方法在 “unhappy middle” 选择率上表现不佳。SIEVE 旨在通过负载驱动的拟合来缓解这一点：在数据子集上拟合一个 HNSW（子）索引集合，使这些查询能够被有效服务，因为它们的匹配点在子索引中是稠密的。如 §1 所述，构建和使用 HNSW 图涉及速度/召回率/内存权衡（Fig 1）；因此，SIEVE 应当同时决定构建和使用索引集合的对象与方式。本节描述我们的直觉。

图 2 位于本小节前部，图注可读。图 2：SIEVE 旨在构建相对加速高、且适用于许多查询的子索引（例如 attr=AorB）。(a) 在 100K 向量数据集上，QPS 与选择率的关系。横轴 Filter Selectivity，可见刻度 0.01、0.2、0.4、0.6、0.8、1；纵轴 QPS @ 0.9+ recall，可见刻度 0、10,000、20,000、30,000、40,000。图例包括 Filtered Search in base HNSW、Brute-force Pre-Filter Search、Subindex Search (our goal)，并标有 attr=D、attr=C、attr=AorB。三条曲线的具体形状【抽取不清】。(b) 候选子索引示例。可读文字包括 Vectors、attr、A、B、C、D、100K vectors、10K vecs.、30K vecs.、50K vecs.、attr=AorB、attr=C、attr=D。各属性块与 10K/30K/50K 向量组的对应排布【抽取不清】。

**Three-Dimensional Modeling.** 不失一般性，SIEVE 把召回率和内存当作约束，并优化速度，因为用户通常 ① 对索引有有界内存 [32, 53, 54]，② 有目标召回率（例如服务等级目标 SLO [49, 52]）。这不同于面向（精确）查询的物化视图选择，后者通常只受内存约束。SIEVE 的直觉是：借助理论驱动的建模，召回率这一维可以通过推理索引应当如何构建（稍后说明）来针对不同目标召回率加以归约。然后，SIEVE 可以使用已有方法，在有界内存下选择构建哪些索引，以最大化服务速度。最后，在服务时，SIEVE 可以用类似的建模，在可能不同于构建时的新目标召回率下，确定使用哪些已构建索引以及如何使用，以获得最快搜索。

**How to Build Indexes?** 每个子索引的内存大小与（1）被索引的向量数量以及（2）控制密度的构建参数 \(M\)（§2.1）成线性关系。\(M\) 可以针对不同的内存/召回率权衡进行调节：更高的 \(M\) 同时增加内存大小和召回率（因为密度增加），反之亦然（Fig 3a）。目标召回率实际上决定了每个索引构建时所能使用的最低 \(M\) 值。

脚注 2：SIEVE 优化的是平均召回率，因为据我们所知，不存在能保证绝对的、逐查询召回率的方法，查询难度可以变化 [62]。

直观上，较小的索引需要较低的 \(M\) 值就能达到相同的目标召回率（例如，Fig 2 中的 attr=C 相对 attr=D 需要更低的 \(M\)，才能以平均 \(x\) 召回率服务查询，Fig 3b）。我们在 §4.2 中描述这一点。

**What Indexes to Build?** SIEVE 旨在构建这样的子索引：它们能高效服务（已观察到的）查询，而这些查询用其他方法（例如暴力 KNN）服务时是低效的，也就是具有边际收益。假设我们有 Fig 2b 中的基础 HNSW 索引：虽然构建子索引（attr=D）对其对应的过滤查询有益，但 attr=D 的选择率很高（50%），基础索引通过结果集过滤就已经足够快地服务它。相比之下，子索引（attr=AorB）具有高边际收益：它服务（attr=AorB）显著快于基础索引（Fig 2）。子索引也可以服务并非精确匹配的过滤查询：例如，（attr=AorB）也可以有效服务（attr=A），后者在该子索引中的选择率足够高（50%）。这使得 (attr=AorB) 这类子索引的效用，进一步来自它们对其他过滤器的适用性。我们在 §4.3 描述 SIEVE 的索引选择。

**How to Serve Queries?** 当用已构建的索引集合服务查询时，SIEVE 在索引搜索与暴力 KNN 之间做决定。控制 HNSW 索引搜索速度/召回率权衡的一个关键参数是搜索探索因子 \(sef\)（Alg. 1）：更高的 \(sef\)（对图过度搜索）用更低的速度换取更高的召回率（Fig 3c）。如果服务时的目标召回率高于构建时所假设的召回率，SIEVE 就需要调节 \(sef\)。与 \(M\) 类似，SIEVE 希望对索引搜索使用最低的 \(sef\)，较小的子索引达到同一目标也需要较小的 \(sef\)（Fig 3d）。然后，在找到最佳索引和 \(sef\) 之后，SIEVE 评估回退到暴力 KNN 是否更快（例如 \(sef > 30\)，Fig 3c）；暴力 KNN 也始终具有完美召回率。我们在 §5.2 描述 SIEVE 的服务策略。
