## 摘要

现实任务可以收成 filtered vector search：向量表示语义，硬谓词表示必须满足的约束，例如找带有 “kids” 标签的相似视频。已有的图近似最近邻方法靠 small-world 性质，用很少几跳到达相似点。一旦遍历时只访问满足谓词的点，谓词一多、命中向量一少，这张图就不再“几跳可达”。近期工作改的是遍历本身，只走通过谓词的物品；作者认为这条路要么把谓词限制得很死，要么在命中很少时失去效率。

SIEVE 反过来：不为一次遍历去约束图，而是建很多索引，每张索引服务不同形态的谓词。建索引靠一个三维分析模型，把索引大小、搜索时间和 recall 连起来，再按负载在预算里尽量塞进有用的索引。查询时仍用这个模型，在指定 recall 下挑出搜索最快的一张。摘要给出的量级是：相对其他索引最高 8.06× 加速，建索引时间可低到对方的 1%，内存不到一张标准 HNSW 图的 2.15 倍，并且只需要有限的历史负载知识。数据集的选择率和谓词形式都有变化。

## 1 INTRODUCTION

问题被定义成：在硬约束下找语义相近的物品。例子包括母亲找标了 “safe-for-kids” 的视频，以及网购时在某个价格区间里找戏服。向量来自现代机器学习模型，因此 filtered vector search 被越来越多地研究。已有图方法把无过滤的近似最近邻索引改成带过滤：FilteredVamana 把图遍历和谓词判断交错进行；ACORN 在查询时只访问通过谓词的节点，诱导出子图。它们优于先过滤再线性扫描这种朴素做法，因为图方法本来就是靠边在少数几跳内到达目标。作者把失败点放在低选择率：现有图方法维持不住 small-world，性能变差；选择率又没有低到可以接受线性扫描，这条带被称作 “unhappy middle”。FilteredVamana 把共享属性的向量连成按过滤器划分的局部稠密子图，但要限制谓词形式。ACORN 能处理一般谓词，可是诱导子图太稀时会失去 small-world。作者由此认为一张图覆盖不了彼此重叠方式很复杂的全部谓词，需要多张各管一批谓词的图。

目标是用一个 index collection，让不同选择率、不同形式的过滤查询几乎都能落到一张紧凑的图上。集合比单索引表达力更强。作者借助真实过滤向量负载里过滤器相对稳定这一点，按观察到的负载来定制索引。一张图可以服务多个谓词：为 stars=1–3 建的图，如果对子谓词仍然够密，也可以服务 stars=1。多索引更占内存，但索引相对高维原始向量仍然较小。引言里的实验说法是：数百个较小的附加索引，所占内存大约只相当于一个覆盖全数据集的索引，性能提升却很明显。困难在于几个目标互相牵制。Figure 1 用 10 万条随机向量说明两笔交换：建索引时可以用更低 recall 换更小的索引，从而在同样内存里放进更多索引；查询时可以搜得更慢来换更高 recall。因此必须把索引大小、搜索时间和 recall 的关系量化，才能决定某条查询该用哪张索引。作者把这件事和物化视图选择区分开：物化视图针对的是精确查询，近似最近邻则带有速度和 recall 的交换。

框架名叫 SIEVE（Set of Indexes for Efficient Vector Exploration）。它按观察到的查询负载建索引集合，在内存预算和指定 recall 下尽量提高期望吞吐。每个候选索引有一份收益（加入集合后的边际性能增益）和一份内存代价。作者认为“建一组索引”这个想法本身并不新，新在两处：如何估计收益和代价，以及查询时如何使用这组索引。收益/代价模型不依赖具体谓词形式，依据是经验观察和已有的 small-world 网络理论；它要找出达到指定 recall 的最稀疏图，这样每张索引更小，预算内容纳的索引更多。查询阶段索引之间可能重叠，同一条查询可能被多张索引服务，因此要再次用模型决定用哪张、以及搜索参数怎么设。Table 1 把 SIEVE 和四类已有索引对比，列的是高、中、低三种 Query Selectivity 以及是否支持 Complex Filters：

| 方法 | 高 / 中 / 低选择率 | 复杂谓词 | 文中列出的弱点 |
|---|---|---|---|
| Partition-Based | × / ✓ / ✓ | × | 谓词形式受限 |
| Data Attr.-aware Graphs | ✓ / ✓ / × | × | 要求数据属性基数有限（<200） |

贡献对应后文三块，引言只作宣布：三维代价模型同时做索引选择和参数设定；用同一模型在任意目标 recall 下选服务方式和参数；实验上在多种谓词格式下达到最高 8.06× 加速，内存小于标准 HNSW 的 2.15 倍，并只使用有限的历史负载知识。后两节不展开这些实验和形式化。

## 2 MOTIVATION

SIEVE 建在 HNSW 上。这一节先交代 HNSW，再说明现有过滤改法为什么慢，最后给出用一组 HNSW 子索引加速的直觉。形式化的建索引和查询策略留在后文。

### 2.1 HNSW Graph

HNSW 把 small-world 图和 skip-list 合成多层图。顶层向量最少、边更长，用来在向量空间里做长距离跳跃；底层包含全部向量、边更短，表示局部邻域。建图时向量逐个插入，每一层连多少邻居由构造参数 M 控制，M 同时是出度上限，并促使向量连向同层中相似的向量。查询从顶层走到下层：先用长边进入相近区域，再用短边找出 top-k。Algorithm 1（HNSW_SEARCH_LAYER）描述单层搜索，输入是查询向量、入口点、探索因子 ef 和层号，输出是离查询最近的 ef 个向量。

### 2.2 Existing Filtering Methods Underperform

原始 HNSW 并不做过滤搜索。后过滤（post-search filtering）对选择率为 sel 的 filtered top-k，先过度搜索 top-k/sel，丢掉不匹配的结果，指望剩下至少 k 个；不够就再搜 top-2k/sel，依此类推。hnswlib 的 result-set-filtering 改在搜索过程中、候选进入 top-k 结果集之前判断谓词（正文标为 Algorithm 1 的 line 13）。一次遍历就能返回 k 个满足谓词的结果，但每个候选仍有 (1−sel) 的概率被滤掉。recall 几乎不受影响，搜索时间却大致与选择率成反比（Figure 2a），所以选择率低、数据又大、预过滤仍然要扫很多点时，这种方法仍然慢。

ACORN 把过滤放在邻域展开（正文标为 Algorithm 1 的 line 6），等于在满足谓词的诱导子图上搜索。删边删点会破坏连通性等 small-world 性质，子图太稀时按原算法搜索会过早停止、recall 下降。ACORN 因此同时改建设和搜索，特别是扩展到 2-hop 邻居来缓解稀疏。即便如此，2-hop 子图仍然稀疏时它还是会变慢；正文说实验里 result-set-filtering 和 ACORN 会互有胜负。SIEVE 自己的 HNSW 索引采用 result-set-filtering，因为不必做专门的图构建，避免过长的 time-to-index。后文讨论也限定在这种方式上，但作者说稍作调整也可以换成 ACORN 的过滤。脚注说明 hnswlib、ACORN 和本文都用常见的 bitmap：给插入向量分配 ID，再根据标量属性算出哪些 ID 通过谓词；属性侧可以交给外部关系数据库。

### 2.3 SIEVE’s Intuition for Faster Search

现有 HNSW 过滤在 “unhappy middle” 的选择率上表现不好。SIEVE 按负载，在数据子集上拟合一组 HNSW 子索引，让这些查询的命中点在子索引里足够密。recall 和内存被当成约束，优化目标是速度：用户通常有索引内存上限，也有目标 recall（例如 SLO）。这和只受内存约束的精确查询物化视图选择不同。作者的直觉是，用理论模型先决定“为了某个目标 recall，索引应该建成什么样”，recall 这一维就可以先消掉，然后在内存上限内选择能提高服务速度的索引；服务时如果目标 recall 变了，再用类似模型决定用哪张已建成的索引、怎么搜。脚注强调优化的是平均 recall，因为据作者所知还没有方法能保证每条查询的绝对 recall，查询难度本身会变。

建多大：子索引内存与索引向量数、以及控制密度的 M 成线性关系。M 越高，图越密，内存和 recall 一起上升（Figure 3a，10 万向量）。目标 recall 决定每张索引能用的最低 M；更小的索引达到同一 recall 所需的 M 更低（Figure 3b 画的是达到 0.9 平均 recall 所需的 M）。建哪些：要建的是那些相对暴力 KNN 等替代方法收益明显的子索引。Figure 2b 在 10 万向量上举了候选子索引：属性 A、B 各 1 万向量，合成 attr=AorB；C 为 3 万；D 为 5 万。正文说 attr=D 的选择率有 50%，基索引用 result-set-filtering 已经够快，单独为它建子索引的边际收益不高。attr=AorB 则明显快于基索引，而且还能服务并非精确匹配的 attr=A：A 在这个子索引里的选择率达到 50%。查询怎么走：在索引搜索和暴力 KNN 之间选择。控制搜索速度与 recall 的是探索因子 sef，sef 越大越慢、recall 越高（Figure 3c：10 万向量、选择率 0.2）。若服务时的目标 recall 高于建索引时的假设，就要调高 sef；和 M 一样，SIEVE 希望用能达到目标的最低 sef，更小的子索引所需 sef 也更小（Figure 3d，同样是达到 0.9 平均 recall）。选定索引和 sef 之后，再判断退回暴力 KNN 是否更快；正文举例 sef > 30（Figure 3c）时暴力搜索可能更快，而且暴力搜索的 recall 是完全的。
