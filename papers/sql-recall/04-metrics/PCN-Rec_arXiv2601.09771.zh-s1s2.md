# PCN-Rec: Agentic Proof-Carrying Negotiation for Reliable Governance-Constrained Recommendation

## Abstract 摘要

现代基于大语言模型（LLM）的推荐系统可以生成有说服力的排序列表，但难以可靠满足治理约束，例如最低长尾曝光或多样性要求。我们提出 PCN-Rec，一条携带证明的协商（proof-carrying negotiation）流水线，把自然语言推理与确定性强制执行分开。基础推荐器（MF/CF）产生大小为 \(W\) 的候选窗口，由两个智能体协商：User Advocate 优化相关性，Policy Agent 强制执行约束。一个调解 LLM 综合出 Top-\(N\) 推荐列表（slate），并给出结构化证书（JSON），描述所声称的约束满足情况。确定性验证器根据列表重新计算全部约束，只接受通过验证器检查的证书；若验证失败，确定性的约束贪心修复会生成合规列表并再次验证，从而留下可审计轨迹。在带治理约束的 MovieLens-100K 上，相对没有验证/修复的一次性（one-shot）单 LLM 基线，PCN-Rec 在可行用户上达到 98.55% 的通过率（\(n=551\)，\(W=80\)），同时保持效用，NDCG@10 仅绝对下降 0.021（0.403 对 0.424）；差异具有统计显著性（\(p<0.05\)）。

## 1 Introduction 引言

部署在真实平台上的推荐系统受硬约束支配，这些约束超出纯相关性，例如最低长尾曝光、体裁多样性，或每个推荐列表的策略上限 [10, 12, 19]。这些约束往往有法律或合同动机，并且必须可审计：平台必须能够解释为何投放该列表，并证明策略检查确实被满足。近期基于 LLM 的推荐器可以用自然语言产生有说服力的排序，但在被要求可靠满足严格组合约束时很脆弱 [1, 2, 7, 14, 21]。实践中，单个 LLM 可能输出看似合理的理由，同时仍然违反约束，而且其推理不能直接执行或验证。现有单体 LLM 方法存在 “lost-in-the-middle” 推理问题，也无法在组合约束上维持全局状态 [23]。通过把推荐任务分解为智能体之间的竞争，我们允许专门的推理路径：User Advocate 对策略保持“盲视”以最大化效用，而 Policy Agent 提供聚焦的“对抗性”检查。

我们提出 PCN-Rec，把 LLM 当作提议者（proposer）而不是权威。核心想法是携带证明的交互：LLM 参与协商，但每一份推荐列表都必须通过用代码实现的确定性验证器。PCN-Rec 从标准候选生成器（例如 MF/CF）开始，生成排序列表，并从中取大小为 \(W\) 的候选窗口。在该窗口内，两个智能体代表相互竞争的目标：User Advocate 推动与用户偏好相关的项目，Policy Agent 推动治理约束的满足（例如头部/尾部平衡与体裁多样性）。调解 LLM 随后提出 Top-\(N\) 列表，并发出结构化证书（JSON），描述哪些项目满足哪些约束。关键在于，确定性验证器根据所提议的列表重新计算全部约束函数，要么接受证书，要么拒绝。被拒绝时，我们应用确定性的约束贪心修复以产生合规列表，再次验证，并记录轨迹以供审计。与单体 LLM 推荐器不同，我们的智能体方法把推荐任务分解为专门角色，使“有创造性的”提议者与“严格的”验证器解耦。

**贡献。** 我们有三项贡献：

- 面向推荐的携带证明的协商：一种智能体式 fram【抽取不清】，由 LLM 提出推荐列表与结构化证书，但正确性由确定性验证强制保证 [6, 20]。
- 可行性分析：基于窗口大小的方法，把不可满足的用户历史（在 \(W\) 内不存在可行列表）与方法失败（存在可行列表，但方法失败）区分开。
- 强治理且效用损失很小的经验证据：在 MovieLens-100K 上，相对单 LLM 基线，PCN-Rec 在可行用户上达到近乎完美的通过率，NDCG@10 仅有很小下降 [8, 11]。

## 2 Method: Proof-Carrying Negotiation for Recommendation 方法：面向推荐的携带证明的协商

设 \(u\) 表示用户，基础推荐器（例如 MF/CF）产生带预测相关性分数的排序候选列表 \(C(u)=\langle i_1,i_2,\ldots\rangle\)。我们只关注包含前 \(W\) 个项目的候选窗口 \(C_W(u)\)，目标是输出列表 \(S\subseteq C_W(u)\)，且 \(|S|=N\)，使其既有用又合规。

我们考虑必须对每个列表成立的治理约束 [4, 8, 12]。实验中包括：（i）头部/尾部曝光约束，要求最低的长尾代表，并可选地限制头部项目；（ii）体裁多样性约束，要求列表中不同体裁的最少数量。每个项目 \(i\) 带有元数据（例如流行度桶 head/tail、体裁标签），约束由这些标签与列表内容确定性地计算。

图 1：PCN-Rec 携带证明的协商流水线。基础推荐器产生候选窗口（\(W\)）。两个智能体协商（User Advocate 负责相关性；Policy Agent 负责治理），调解 LLM 提出 Top-\(N\) 列表以及结构化证书。确定性验证器根据列表重新计算约束，只接受通过验证器检查的证书；失败则触发确定性约束贪心修复并再次验证，产生可审计轨迹。

### 2.1 PCN-Rec Framework PCN-Rec 框架

图 1 给出概览。PCN-Rec 把自然语言推理与强制执行分开：把 LLM 当作提议者，把全部正确性保证放在确定性代码中 [1, 2, 7, 14, 21]。

**候选窗口。** 基础推荐器提供排序后的 \(C_W(u)\)，它定义所有下游步骤的可行搜索空间。这种“有界”视角对可审计性与可行性分析很重要：若 \(C_W(u)\) 内不存在合规列表，则失败属于不可满足的约束，而不是方法错误。

**协商智能体。** PCN-Rec 使用目标互补的两个智能体 [9, 22]：

- User Advocate：主张能最大化与用户历史和偏好相关性的项目。
- Policy Agent：主张满足治理约束的项目（例如最小尾部、最大头部、体裁多样性）。

两个智能体都只在 \(C_W(u)\) 中的候选上操作。

**调解者（LLM）+ 证书。** 调解 LLM 综合两个智能体的论证，提出 Top-\(N\) 列表 \(S\)，以及结构化证书 \(c\)（JSON）[3, 15, 16, 20]。证书包含（a）所选项目 ID，以及（b）验证治理约束所需的显式字段（例如哪些项目被计为尾部、覆盖了哪些体裁），从而支持机器可检查的审计。

**确定性验证。** 用代码实现的验证器 \(V\) 直接根据 \(S\)（及项目元数据）重新计算全部约束函数，仅当每条约束都被满足时才接受输出 [6, 13]。关键是，验证器不信任 LLM 文本；它只信任确定性检查。这产生携带证明的接口：仅当 \(V(S,c)=1\) 时系统才返回 \((S,c)\)。

**确定性修复（故障安全）。** 若验证失败，PCN-Rec 运行确定性的约束贪心修复过程，在可能时从 \(C_W(u)\) 构造合规列表（例如先满足硬约束，再在剩余名额中最大化相关性）[5, 10, 18]。修复后的列表再被验证，并连同审计轨迹一并返回。这保证在可行用户上稳健合规，并把约束不可行与 LLM 提议失败干净地分开。

### 2.2 Feasibility vs. Method Failure 可行性与方法失败

由于约束是按列表强制执行的，在给定窗口大小 \(W\) 下，有些用户可能不可行。因此我们报告两类结果：（i）全部用户；（ii）可行用户子集，即 \(C_W(u)\) 内存在合规列表的用户。这一区分对公平评价至关重要：不可行情形不应被算作算法失败。在第 3 节中，我们量化可行性如何随 \(W\) 变化，并用它选择运行点 \(W=80\)。
