# Text2SQL is Not Enough: Unifying AI and Databases with TAG

## Abstract 摘要

能够针对数据库回答自然语言问题的人工智能系统，有望释放出巨大价值。这样的系统将使用户得以同时利用语言模型（language models, LMs）强大的推理与知识能力，以及数据管理系统可扩展的计算能力。这些能力结合起来，将使用户能够针对自定义数据源提出任意的自然语言问题。然而，现有方法与基准对这一设定的探索并不充分。Text2SQL 方法只关注那些能够用关系代数表达的自然语言问题，而这只是真实用户希望提出的问题中的一小部分。同样，检索增强生成（Retrieval-Augmented Generation, RAG）只考虑有限的查询子集，即那些通过对数据库中一条或少数几条数据记录做点查找（point lookup）就能回答的查询。我们提出表增强生成（Table-Augmented Generation, TAG），一种用于针对数据库回答自然语言问题的统一且通用的范式。TAG 模型涵盖了语言模型与数据库之间一大类此前尚未探索的交互，也为在数据上利用语言模型的世界知识与推理能力带来了新的研究机会。我们系统地构建基准来研究 TAG 问题，并发现标准方法正确回答的查询不超过 20%，从而确认这一方向仍需进一步研究。我们将该基准的代码发布于 https://github.com/TAG-Research/TAG-Bench。

## 1 INTRODUCTION 引言

语言模型有望让用户以自然语言对数据提问，从而改变数据管理的方式；这已经催生了大量关于 Text2SQL 与 RAG 方法的研究。然而根据我们的经验（包括 Databricks 的内部工作负载与客户），用户的问题常常超出这些范式的能力，因此需要新的研究投入，去构建把数据库系统的逻辑推理能力与现代语言模型的自然语言推理能力结合起来的系统。

具体而言，我们发现真实业务用户的问题往往需要领域知识、世界知识、精确计算与语义推理的复杂组合。数据库系统显然提供了领域知识的来源，即它们所存储的最新数据，以及大规模的精确计算（语言模型并不擅长后者）。

语言模型从两个关键方面扩展数据库的现有能力。第一，语言模型具备针对文本数据的语义推理能力，而这正是许多自然语言用户查询的核心要素。例如，Databricks 的一项客户调查显示，用户希望提出这样的问题：which customer reviews of product X are positive?，或者 why did my sales drop during this period?。这些问题构成基于推理的复杂任务，例如对自由文本字段做情感分析，或对趋势做摘要。语言模型很适合这些任务，而传统数据库系统中的精确计算或关系原语无法刻画它们。

第二，语言模型可以利用在训练期间学到的、并由模型权重隐式存储的知识，用数据库表模式并未显式捕获的世界知识来有力地扩充用户的数据。例如，Databricks 的一名内部人工智能用户针对一张包含账户名称、产品与收入等属性的表，提出了 what are the QoQ trends for the "retail" vertical?。要回答该查询，系统必须理解业务如何定义 QoQ（例如从上一季度到当前季度的季度环比趋势，或者从去年同一季度到今年同一季度的趋势），以及哪些公司被视为属于 retail 这一垂直领域。这一任务适合利用预训练或微调后的语言模型所掌握的知识。

能够高效地同时利用数据库与语言模型、并以完整一般性来服务自然语言查询的系统，有潜力改变用户理解其数据的方式。遗憾的是，这些问题今天还无法由 Text2SQL 和 RAG 这类常见方法回答。尽管 Text2SQL 方法 [26, 28, 31, 32] 适用于那些具有直接关系等价形式的自然语言查询子集，但它们无法处理大量需要语义推理或世界知识的用户查询。例如，前面询问 which customer reviews are positive 的用户查询，可能需要对评论逐行进行语言模型的逻辑推理，以便把每条评论分类为正面或负面。类似地，询问 why sales dropped 的问题是一个推理问题，必须跨许多表项聚合信息。

另一方面，RAG 模型仅限于基于相关性、对少数数据记录进行的简单点查找，随后只调用一次语言模型。该模型只服务那些能够由点查找回答的查询子集，也未能利用许多数据库系统更丰富的查询执行能力，从而把计算任务（例如计数、数学运算与过滤）留给一次容易出错的语言模型调用。除了在计算任务上容易出错且效率不高之外，语言模型在长上下文提示上的表现也已被证明较差，这限制了它们在 RAG 的生成阶段对大规模数据进行推理的能力。

我们因此提出表增强生成（table-augmented generation, TAG），作为那些针对数据库回答自然语言问题的系统的统一范式。具体而言，TAG 定义了三个关键步骤，如图 1 所示。首先，查询合成步骤 syn 把用户任意的自然语言请求 𝑅 翻译为可执行的数据库查询 𝑄。然后，查询执行步骤 exec 在数据库系统上执行 𝑄，以高效计算出相关数据 𝑇。最后，答案生成步骤 gen 使用 𝑅 与 𝑇；在此过程中，语言模型被编排起来，可能以迭代或递归的模式作用于数据，以生成最终的自然语言答案 𝐴。TAG 模型简单而有力：它由下面三个方程定义，却覆盖了语言模型与数据库之间一大类此前研究不足的交互。

Query Synthesis: syn(𝑅) → 𝑄 (1)

Query Execution: exec(𝑄) → 𝑇 (2)

Answer Generation: gen(𝑅, 𝑇) → 𝐴 (3)

值得注意的是，TAG 模型统一了先前的方法，包括 Text2SQL 与 RAG。它们是 TAG 的特例，并且只服务于用户问题中的一个有限子集。

尽管已有若干工作处理 TAG 的这些特例，我们提供了首个端到端的 TAG 基准，它由一大类需要语言模型推理能力与知识能力的真实查询组成。我们展示了这类问题所带来的重大研究挑战，以及高效 TAG 实现的前景。我们的评估分析了原始的 Text2SQL 与 RAG 基线，以及两个更强的基线：带语言模型生成的 Text2SQL，以及带基于语言模型重排序的检索。在多种查询类型上，我们发现每一种基线方法都始终无法达到高准确率，在该基准上的 exact match 从不超过 20%。另一方面，我们在近期的 LOTUS 运行时 [21] 之上实现了手写的 TAG 流水线，发现它们相对基线的准确率高出至多 20–65%。这一显著的性能差距表明，构建高效的 TAG 系统是有前景的。

## 2 THE TAG MODEL TAG 模型

我们现在描述 TAG 模型。它接收自然语言请求 𝑅，并返回锚定于数据源的自然语言答案 𝐴。我们概述 TAG 系统所实现的三个主要步骤：查询合成、查询执行与答案生成。为使问题可处理，我们把 TAG 定义为这些步骤的单次迭代，但也可以考虑以多跳（multi-hop）方式扩展 TAG。

### 2.1 Query Synthesis 查询合成

syn 函数接收自然语言请求 𝑅，并生成将由数据库系统执行的查询 𝑄。给定用户请求，这一步负责 (a) 推断哪些数据与回答该请求相关（例如利用表模式），以及 (b) 进行语义解析，把用户请求翻译成数据库系统可以执行的查询。该查询可以使用任何查询语言，但在我们的示例中使用 SQL。

图 1 给出了一个 TAG 实例，对应用户查询 “Summarize the reviews of the highest grossing romance movie considered a ‘classic’”。此处的数据源包含每部电影的标题、收入、类型，以及与之关联的评论。在这一步，系统利用语言模型的语义推理能力生成一条 SQL 查询，该查询使用数据源中的 movie_title、review、revenue 与 genre 属性。需要注意的是，在这个例子中，数据库 API 能够在 SQL 查询内部执行 LM UDF（user-defined functions，用户定义函数），因此这一步还会在查询中对每一行调用语言模型，以识别经典影片。

图 1：一个 TAG 实现示例，用于回答用户针对一张电影表提出的自然语言问题。TAG 流水线分三个阶段进行：查询合成、查询执行与答案生成。图中查询为 “Summarize the reviews of the highest grossing romance movie considered a ‘classic’.”。查询执行阶段的表含列 genre、review、revenue、movie_title。可辨认的行包括：Action，“solid film…”，432.2，Shang-Chi；Romance，“still best…”，2257.8，Titanic；Romance，“a guilty…”，2257.8，Titanic；其余行以省略号表示。过滤之后保留 Romance / Titanic 的行，包括 “still best…” 与 “a guilty…”，收入均为 2257.8。答案生成阶段同时给出原查询以及编码后的记录 “{movie_title: “Titanic”, revenue: 2257.8, review: “still best…”, genre: “Romance”}…”。答案开头为 “The reviews of Titanic discuss the on screen chemistry…”，其后在图中省略。图中 “screenchemistry” 按换行粘连还原为 “screen chemistry”。三个阶段编号为 1、2、3。

### 2.2 Query Execution 查询执行

在查询执行步骤中，exec 函数在数据库系统中执行查询 𝑄，以得到表 𝑇。这一步利用数据库查询引擎，在海量已存储数据上高效执行该查询。数据库 API 可以由多种多样的系统来提供，我们将在第 3 节讨论。有些 API 可能允许基于语言模型的算子 [18–21]，从而使数据库引擎能够在 exec 内部利用语言模型的世界知识与推理能力。

在图 1 所示的例子中，该数据库查询是用 SQL 写成的选择与排序查询，返回一张包含相关行的表。该查询利用语言模型根据 movie_title 判断哪些电影是经典影片，从而完成选择，并用 genre 上的标准过滤找出爱情电影。该查询还按 revenue 对结果排序，以找出票房最高的影片。如图所示，所得表中包含电影 “Titanic” 的评论。

### 2.3 Answer Generation 答案生成

TAG 中的答案生成步骤与 RAG 中的生成步骤相对应。在这一步，gen 函数使用语言模型，依据计算出的数据 𝑇，为用户的自然语言请求 𝑅 生成答案 𝐴。

图 1 展示了该示例 TAG 流水线的最后阶段：它输出对 “Titanic” 评论的摘要，作为对原始用户请求的回答。在这个例子中，相关数据 𝑇 被编码为字符串，供模型处理。编码后的表与原始用户请求 𝑅 一起被传给语言模型。为得到答案，这一步利用模型在 review 列上的语义推理能力来摘要这些评论。
