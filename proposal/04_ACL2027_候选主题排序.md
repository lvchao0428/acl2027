| 排名 | 主题 | 建议 |

| 2 | 模拟器当训练信号的 Goodhart（推荐 / CRS） | **备选**；主线在决策点失败时切换 |

## 1. 单人约束：选题的硬条件

可用资源：作者一人、RTX 5090（32GB）、公开数据集、可选的少量 API 与租卡预算。

| 条件 | 含义 | 不满足的例子 |
|---|---|---|
| **真人信号来自已公开日志** | 「真实用户」= 别人已经采集并公开的行为记录（购买、评分、对话），不是本文新招募的人 | Sim2Real（arXiv 2603.11245）自己招了 451 人跑 τ-bench；本文**只引用其结论**，不复刻 |
| **不做用户研究** | 无问卷、无众包、无伦理审批；不报告 inter-annotator agreement | 02 号文档里「300 条人工校验，自己 + 1 位同学」改为下文的自动检查 + 作者自查 |
| **不需要线上平台** | 不声称线上收益；全部是离线评测 | 双受众推荐、A/B 测试、AlignUSER 那种 55 个线上实验的相关性 |
| **单卡能训** | 训练限于 4B–8B LoRA SFT / DPO；RL 可选、且必须有不用 RL 的退路 | 集群级 GRPO 训练生成式推荐 |
| **数据今天就能拿到** | 公开、免申请，或已核实下载路径 | 只在论文里提到、未发布的数据 |

**作者自查的边界**：作者本人抽看 50–100 条样本，确认构造没有明显错误，属于数据检查，不是人工评测。论文里写成「作者人工检查了 N 条，发现 X 类问题并修正」，不作为结论依据。所有需要判断的指标都用自动规则或两个不同家族的 LLM judge，报告两者一致率。

**审稿人可能问的「真实性」**：本文回答是离线代理。真实购买 + 事后评分是公开数据里最接近「这个用户是否满意」的信号；局限写进 Limitations：评分是噪声代理，未评论的购买不可见，离线结论不等于线上收益。

## 3. 逐个主题

### 3.1 个性化受托差距（排名 1）

**问题**：agent 替**这个用户**选商品时，是否命中其满意的购买、避开其后悔的购买。

**2026-09 之后的新邻居**

| 工作 | 做了什么 | 和本题的距离 |
|---|---|---|
| *Personalization Matters*（arXiv 2610.11375，2026-10-08） | Amazon Reviews 2023 上的多 agent RAG 购物对话；轨迹级 LLM 打分；真人研究 n=5 | 方法论文，评测是 LLM 打分的偏好一致性，**没有真实购买与满意度作 ground truth** |
| *From Product Search to Preference Articulation*（arXiv 2608.08395） | 经济学理论：消费者需投入精力让 agent 形成偏好表示 | 纯理论，**给本题提供动机**，可引用 |
| ACES（arXiv 2508.02630） | 无个人偏好时 agent 的决策面；作者把「人类基线」和「偏好引出」留作未来工作 | 已在 03 号文档降级处理 |

**为什么排第一**：问题新（Spotify position paper 只有议程）；ground truth 来自公开的真实购买与评分，单人可构造；有一个可证伪的主张（模拟器在后悔型上会忠实踩雷，因此不是好受托人）。训练部分不显著时，「测量 + 对照」仍可投 Findings。

**单人版本的构造**（替换 02 号文档 2.4 节）：

1. **两类 episode 用同一个改写器**：从 Amazon Reviews 2023 选 verified、≥100 字的评论；5 星作满意型，1–2 星作后悔型。同一 prompt 只保留「购前需求」。用 C4 校验改写器：对 C4 原评论重新改写，与 C4 query 比较风格与长度。
2. **泄漏检查全自动**：关键词规则（坏了、退货、失望等）+ 两个不同家族的 LLM 判断「是否透露了使用结果」，两者都通过才保留；报告两者一致率与剔除率。作者自查 50 条。
3. **候选集自建**：同细分品类，embedding 检索 + LLM 判断「满足 query 的硬约束」，\(K=10\)，含 \(i^\*\)；均分与评论数按目标时间戳之前重算。
4. **规模**：满意型 3,000 + 后悔型 1,500 评测；训练集另构造约 30k。

**评测指标**（不需要人）：满意型 Hit@1 / MRR；后悔型 Regret-Avoidance（不选 \(i^\*\)）与「所选商品在该时间点前的均分」；硬约束满足率用 LLM judge（两家族一致率）。

**主要风险**：后悔型改写泄漏结果；query 太好猜。见 03 号文档第 5 节的停止条件。

### 3.2 模拟器当训练信号的 Goodhart（排名 2）

**问题**：用 LLM 用户模拟器 A 训练出的推荐 / 对话推荐 agent，换到模拟器 B，或放到留出的真实对话上，掉多少；学到了哪些讨好模拟器的行为。

**现状**

- 用模拟器当训练信号的工作继续增加：SMTPO（arXiv 2604.03671，SFT + GRPO）、TRACER（arXiv 2609.28690，训练多轮模拟器）、ShopSimulator RL、ECPO/AILO。
- 指出模拟器不可靠的工作也在增加，但**都不在推荐训练闭环里**：
  - *Mind the Sim2Real Gap*（arXiv 2603.11245）：作者自己招募 451 名真人，在 τ-bench 上对照 31 个模拟器，发现模拟器过度合作、抬高 agent 成功率。领域是客服任务，也不测训练后的分叉。**本文不复刻这类真人实验**，真人锚点改用已公开的对话日志。
  - SimEval-IR（SIGIR'26）：「像人」与「能给系统正确排序」几乎不相关。领域是搜索会话。
  - Turing-RL（arXiv 2606.19336）：在聊天域观察到 reward hacking 并截断奖励。
- **没人做**：推荐域里「训练模拟器 ≠ 评测模拟器」的分叉曲线与 hacking 行为分类。

**单人版本**：

- 真人锚点 = ReDial / INSPIRED / Reddit-Movie 的留出对话，按标准离线协议评测：给定真实对话上下文，预测真人最终接受的电影（Recall@k）。
- 优化强度旋钮 = best-of-n 重排（\(n=1,4,16,64\)）+ 2–3 轮迭代 DPO，不做完整 GRPO，单卡可跑。
- hacking 行为分类用规则 + LLM judge：回复长度、奉承、复述用户原话、诱导式提问的比例随优化强度的变化。

### 3.3 推荐场景的模拟器效度（排名 3）

**问题**：在推荐 / CRS 里，模拟器的「行为像人」分数能否预测「用它给系统排序是否正确」。

**为什么只排第三**：SimEval-IR 在搜索里已经给出答案，Sim2Real 在 agent 任务里也给出答案，推荐版本容易被说成移植。它的价值是当主题 2 的第一章：先证明模拟器排名不可靠，再证明拿它当训练信号会被利用。纯推理、无训练。

### 3.4 不建议单独做的三个方向

| 方向 | 已有工作 | 不做的理由 |
|---|---|---|
| 偏好澄清 / 何时问 | DECISIVE（ACL'26 主会，2026.acl-long.1465）、InPE（arXiv 2607.06765）、IDSS（AAAI-SS'26）、信息增益澄清（arXiv 2606.03135） | 一年内至少四篇，方法空间（熵触发、信息增益）已被占满 |
| GEO / 操纵推荐 agent | SafeGEO（arXiv 2606.28356，22 种攻击、600 例、utility 标签与硬约束违背）、GEO-Bench（arXiv 2605.29107）、CORE（arXiv 2602.03608）、ACES | 攻击分类学与 agent 侧防御都已有人做；本题只保留「操纵不变性」作训练正则，并引用 SafeGEO |
| 面向 agent 的商品表示 / 双受众 | AgenticTagger（arXiv 2602.05945）、DENIM（RecSys'26 workshop）、行业 schema 文章 | 没有平台就没有真实下游信号，违反第 1 节「不需要线上平台」 |

## 5. 时间表

一个人 250h 只够一篇扎实的长文，不并行两篇。

| 周 | 日期 | 主线（主题 1） | 决策点 |
|---|---|---|---|
| 1–2 | 10/12–10/25 | 选 3–4 个品类；同一改写器生成满意型 / 后悔型；自动泄漏检查 + 作者自查 50 条；按时间重算均分与评论数；检索基线 | **10/25**：检索基线接近前沿 LLM，或泄漏剔除后后悔型不足 1,000 条 → 切到主题 2 |
| 3–5 | 10/26–11/15 | 四角色对照（受托人 / 模拟器 / 无条件买家 / 历史排序器）× 3–4 个模型；有无该用户历史 | **11/15**：模拟器与受托人在后悔型上无显著差 → 切到主题 2，已建数据放附录 |
| 6–8 | 11/16–12/6 | 满意度加权 DPO（Qwen3-4B/8B LoRA）；一个操纵探针作正则 | 不显著则定位为 benchmark + 分析 |
