3. 温度 0 的字符串一致用的是不是 Atil 的 TARr，结果集用的是不是 ReproRAG 的 Jaccard？15% 和 70% 是不是这篇 SQL 生成器已经测过的晃动？
4. mFAR 表 1 的 BM25 和 STaRK 表 6 的 BM25 是不是同一格？网格写不是。官方全测试集信任 03 的表 6；本窗口只核对 mFAR 自己的表。
5. 已经落到列上的数值和否定，网格交给数据库。NumConQ、ExcluIR、NevIR、LIMIT 的失败，是列上的谓词，还是自由文本、改写句，或 46 篇文档的两两组合？

## 不要做的事

- 不要写「LIMIT 是推荐器的结果」，也不要写 “who likes Apples?” 证明嵌入搞不定推荐式查询。相关集是 46 篇文档的全部两两组合；小集合上 BM25 的 Recall@2 是 97.8。
- 不要写「SQL 后过滤一般会丢掉 30% 以上的正确结果」。原文只有 ClickHouse 上 UniVectorSQL-7B 从 Non-integration 的召回 0.6 到 JOIN-integration 的 0.4。WHERE 没有这个数。
- 不要写「SQL 是忠实解释」。Faithful CoT 的忠实等于答案由求解器执行链得到，翻译阶段不在保证里。PCN-Rec 写明解释声明本身不被验证，就不保证解释忠实。
- 不要写「只发 Cypher 或 SQL 就能打过 BM25」。
- 不要写「约束抽取和过滤合计占 SPARK 错误的 30%–36%」。只留表 7 的 Constraint 行。
- 不要捡回这些句子：BRIGHT 的 +12.2 来自对候选做推理；QUEST 的 0.142 是宏召回；Atil 等的 15% 或 70% 是这篇 SQL 生成器的预期晃动；PCN-Rec 的 0.000 是大模型在约束推荐上的普遍通过率；ACORN 的倍速是向量约束失败的证据。

## 交给这个窗口的写法

对上表每一篇按五步写完，不要跳步：（1）逐段提取核心论点和论据（2）论点之间的因果、递进、转折、并列（3）未明说的隐含假设（4）证据强度和推理漏洞（5）最终结论。数字从 PDF 抄。输出写到 `proposal/sql-recall/deep/reanalysis/window-04.md`。不要重析 SUQL、TAG、RecBench+、STaRK 基准论文本身、InteRecAgent、SIEVE，也不要重析归 05 的论文。STaRK 表 6 的官方全测试集以 03 为准；本窗口只在 mFAR、MoR、KAR、AvaTaR、SPARK 自己的表上核对他们印出的 BM25。
