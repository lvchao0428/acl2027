# 混合检索与指标：批判

> 2026-11-11。PDF 在 `papers/sql-recall/04-metrics/`，21 份。CMR 的定义另核对了 RecBench+（arXiv 2503.09382），该 PDF 不在这个目录里。
> 不改 [04_混合检索与指标](../04_混合检索与指标.md)。下面凡是和笔记不一致的地方，以这里的引文为准。
> 判定只用三档：站得住 / 只在该设置下成立 / 不成立。

总判：文献支持的是分工。显式谓词交给数据库，语义留给检索或模型谓词。用这些论文支撑「LLM 写的 SQL 应当替换向量召回」不成立。用它们支撑「列或边上的谓词先精确取出超集，再让检索排序」只在该设置下成立。执行结果等于 SQL 结果，是流水线审计，不是可解释性分数。不新造可解释性指数，这个决定站得住；把「忠实解释」写进贡献句，审稿人会要用户研究，现有预算撑不住。

## 五个必答问题

### 1. LIMIT 证明的是推荐式查询，还是 SQL 也不会被拿去解的组合 qrel？

不成立，如果拿它证明「嵌入搞不定推荐式查询，所以该换成 SQL」。

查询表面是偏好查找。正文写的例子是 “who likes Apples?” 和 “Jon likes Apples, ...”。构造约束写明每条查询只问一件事，即 “who likes X”。文档是随机姓名加上「某人喜欢某属性」。

难的不是这个句式。第 5.2 节写他们故意用很简单的查询和文档，好让难度落在 top-k 集合本身，而不是落在 QUEST、BrowseComp 那种算子上。相关矩阵取的是 46 篇文档的全部两两组合：\(\binom{46}{2}=1035\)，再配上 1000 条查询、每条恰好 2 个相关文档。全库另有约 5 万篇对任何查询都不相关的干扰文档。附录表 2 里，LIMIT 的 qrel 图密度是 0.085481，平均查询强度 28.4653；FollowIR 的 Core17 是 0.025641 和 0.5912，NQ 两个都是 0。这是一张被刻意填满的组合相关矩阵，不是购物或观影请求。

嵌入失败是真的，而且是容量失败。小集合（46 篇）上，表 4 的 Recall@2：BM25 97.8，GTE-ModernColBERT 83.5，最好的单向量 Promptriever（4096 维）54.3，GritLM 38.4。全文说最好的嵌入 Recall@2 不到 60%，Gemini-2.5-Pro 把 46 篇和 1000 条查询一次给进去可以做对 100%。全库表 5：BM25 的 Recall@2 / @10 / @100 是 85.7 / 90.4 / 93.6；最好的单向量 Promptriever-4096 的 Recall@100 是 18.9。正文说全库上模型连 20% 的 Recall@100 都难达到。自由向量实验里，46 篇理论上 12 维就嵌得下，训练好的模型仍然做不到。所以单向量表示不了全部 top-k 组合，这个主张在 LIMIT 上站得住。

SQL 不会被拿来解这个容量问题。属性字符串还在文档里时，词法匹配已经接近做对：BM25 小集合 Recall@2 是 97.8。同义词版把语料里的属性换成不重叠的说法之后，正文写 BM25 掉了 89% 以上，Qwen3 掉 38.9%，词法模型反过来差于多数单向量。一条 `WHERE liked = 'apples'` 只有在「喜欢」已经是列的时候才精确；属性只活在句子里、又被换成同义词时，SQL 和 BM25 一起失效。论文自己给出的出路是交叉编码器、多向量和高维稀疏，不是查询语言。

推荐召回也不会被要求「把 46 个物品的全部两两相关集都表示进一个固定维向量」。STaRK 和 RecBench+ 的相关集来自模板或知识图谱，稀疏得多。LIMIT 不能当这条动机的证据。

### 2. 「SQL 后过滤丢掉 30% 以上正确结果」是原文数字，还是转述？

数字在论文里。笔记把它的对照对象写宽了。只在该设置下成立。

引言原句：post-filtering（先向量、再把 SQL 谓词套到向量结果上）比传统的过滤向量搜索漏掉更多正确结果；“For instance, in complex queries involving ‘JOIN’ operations, post-filtering can silently discard over 30% of the correct results.”

正文唯一给出的一对数字不是「后过滤对过滤向量搜索」。第 IV 节：ClickHouse 上，UniVectorSQL-7B 的召回 “degrades by more than 30% (from Non-integration’s 0.6 to JOIN-integration’s 0.4)”。0.6 到 0.4 是相对下降三分之一，绝对下降 0.2。对照的是同一套后过滤后端上的查询类别，不是同一批查询的预过滤对后过滤。

三类集成，论文第 III-A2 节：

- Non-integration：向量搜索单独做，主键再通过 `WHERE IN` 或一次 JOIN 接回主查询。
- WHERE-integration：向量搜索发生在已经被 `WHERE` 滤过的子集上。
- JOIN-integration：向量搜索发生在表已经和其他表连接之后，过滤条件来自相关表。论文写这一档最容易让后过滤失败。

所以「尤其是连接」对得上 JOIN-integration，对不上任意一条带 JOIN 的 SQL。WHERE 是中间那一档，正文说召回从 Non 落到 WHERE，再在 JOIN 上陡降，但没有给 WHERE 的数字。PostgreSQL 因为 pgvector 的迭代索引扫描，退化「much less severe」。30% 是 ClickHouse、UniVectorSQL-7B、Non-integration 对 JOIN-integration。数据是 VectorSQLBench（BIRD、Spider、arXiv、Wikipedia 上的向量列），不是推荐 qrel。

笔记里「相对过滤向量搜索可以丢掉 30% 以上的正确结果」把引言的定性比较和正文的 0.6→0.4 焊在了一起。方向可以留：两种顺序都要报，连接比单表 `WHERE` 更危险，后过滤会静默漏结果。不能把 30% 写成推荐召回上的预期跌幅，也不能写成已经对着预过滤基线量过。

### 3. STaRK 后继是靠结构打过稠密检索吗？有没有「只发出 Cypher/SQL」打过 BM25？

前半句只在该设置下成立：打过 ada-002 的方法都还在检索。后半句不成立。没有一篇给出「只执行 Cypher 或 SQL、不再做向量或 BM25」并且在 STaRK-Amazon 上打过 BM25。

合成 Amazon 的 Recall@20，SAGE 表 2（Human 在前，Synthetic 在后；Amazon 合成查询 n=1638）：

| 方法 | 合成 Amazon R@20 |
|---|---|
| ada-002 | 53.29 |
| BM25 | 53.77 |
| SPARK | 53.95 |
| multi-ada-002 | 55.12 |
| KAR（此表） | 57.29 |
| mFAR | 58.50 |
| SPARK+SAGE−Edge | 58.28 |
| MoR（此表四舍五入） | 59.90 |
| AvaTaR | 60.57 |

笔记里的 53.95 对 53.77 就是这一格，打平成立。同一格里 multi-ada-002 是 55.12，SPARK 没有打过稠密检索。人工 Amazon（n=81）同一张表：BM25 15.23，SPARK 33.56，ada-002 35.46，multi-ada-002 40.22。人工分割上 SPARK 明显高于 BM25，低于 ada-002。SPARK 的大头在 MAG 和 PRIME，不在 Amazon。

SPARK 不是「写出 Cypher 再执行」。第 2.2 节：代理交替使用两样工具，（1）HNSW 语义候选，（2）Neo4j 里按类型和关系约束的 Cypher。计划无结果时回退到 BM25 加余弦。附录 C.7 把同一步写成 “a Cypher/HNSW query”。论文标题是 SAGE（arXiv 2602.16964v1，2026-02-18）；SPARK 是种子检索器。图扩展（SPARK+SAGE−Edge）在合成 Amazon 把 R@20 抬到 58.28，那是邻居扩展再加 BM25 与稠密重排，仍然不是裸查询。

错误分析可以沿用，不要加总。表 7 的 Cypher Constraint 一行是 Amazon 36、MAG 30、PRIME 31。局限性写 “constraint extraction and filtering (30 to 36 percent of errors)”。Over-Retrieval 是另一行（23 / 18 / 22）。30%–36% 只覆盖约束抽取这一类，不是约束加过滤的合计。

各方法实际在做什么：

- AvaTaR（arXiv 2406.11200）。优化工具调用的提示。KAR 表 2 转引的合成 Amazon：Hit@1 49.87，R@20 60.57；同表 ada-002（Base）Hit@1 39.16，R@20 53.29。输出仍按检索指标打分。PDF 里没有「只执行 SQL」的一臂。
- KAR（arXiv 2410.13765）。知识图谱邻居进查询扩展，最后仍用检索器。自己的表 2，合成 Amazon、ada-002：Base 的 Hit@1 39.16，KAR 54.20；R@20 从 53.29 到 57.24。表 3 人工留出集 Amazon：Base Hit@1 39.50，KAR 61.73。笔记里的 54.20 和 61.73 都是 Amazon 的 Hit@1，前者合成测试集，后者人工留出集。表 4 把检索器换成 BM25、只报人工查询：Base Hit@1 34.57，KAR 45.06。这是「扩展之后的 BM25」打过「原查询的 BM25」，查询文本变了，引擎仍是 BM25。
- MoR（arXiv 2502.20317v4）。结构遍历和文本匹配混合。Amazon 上文本臂用 BM25。表 1：BM25 的 Hit@1 / R@20 是 44.94 / 53.77，ada-002 是 39.16 / 53.29，MoR 是 52.19 / 59.92。同表纯结构的 QAGNN 在 Amazon 上 Hit@1 只有 26.56，低于 BM25。结构单独并不打过 BM25；打过的是仍带着 BM25 的混合。
- mFAR（ICLR 2025）。多字段打分，不是图查询。Amazon 上 BM25 的 Hit@1 0.483 高于 ada-002 的 0.392。作者写：只看词法时，Amazon 和 MAG 上 BM25 已经很强，多字段词法没有稳定超过它。这支持「字段要分开打分」，不支持「生成 SQL 替换 BM25」。
- HybGRAG（ACL 2025）。脚注写明法律原因只用 STARK-MAG 和 STARK-PRIME，没有 Amazon。表 5：相对 Hit@1 提升 MAG 47.4%、PRIME 54.9%；摘要里的平均相对提升 51% 是这两份的平均。检索器银行加评论模块，解释指的是路由修正路径。不是 SQL。

SAGE 表 2 里 KAR 的合成 Amazon R@20 写成 57.29，KAR 自己的表是 57.24；MoR 的 59.92 被收成 59.90。引用时用各篇自己的表。

### 4. 哪些指标不用用户研究就定义得清，哪些套到 SQL 推荐器上是范畴错误？

| 指标 | 判定 | 原因 |
|---|---|---|
| CMR | 站得住，限于显式、可判定的条件 | RecBench+ 第 2.1.2 节只有一句：推荐物品里满足所述条件的百分比。没有公式。物品级「全部条件都满足」还是逐谓词微平均，论文没写死，实验里要自己写死。显式条件、属性在目录里、校验器确定时，不需要用户。隐式条件他们仍对着隐藏的知识图谱标签打分，那是生成协议，不是用户判断。 |
| TARr@N、TARa@N | 定义站得住；15% 和 70% 不能搬过来 | Atil 等：TARr 是 N 次运行的原始字符串全部相同的题目比例；TARa 是解析后的答案全部相同的比例。温度 0、top-p 1、固定种子。他们写明可以出现准确率 100%、TARa 100%、TARr 0。摘要里的 “accuracy variations up to 15%” 是各次运行准确率的起伏；“gap of best possible performance to worst possible performance up to 70%” 是 BestAcc 对 WorstAcc（一道题只要有一次对就算进最好，只要有一次错就算进最差）。两件事不是同一个差。SQL 上的合理改写：TARr 看 SQL 字符串，TARa 看执行结果集或规范化后的语法树。 |
| Jaccard | 站得住，对象是集合 | ReproRAG 第 3.3 节：两次取回文档集合的 \(\lvert A\cap B\rvert/\lvert A\cup B\rvert\)，忽略名次。用在两次生成的 SQL 结果集上，定义是清楚的。ReproRAG 量的是向量索引跨次运行的漂移，不是生成器。同一条 SQL、同一个库，Jaccard 应当为 1；方差来自生成，不来自执行。 |
| Kendall's tau | 只在有排序时成立 | 同一节：两条结果列表的秩相关，只比较两边都出现的文档。SQL 没有 `ORDER BY` 时，结果是集合。这时算 tau 是范畴错误。交集上的 tau 还可以在集合已经变了的时候看起来很稳，所以稳定性以 Jaccard 为主。 |
| why-provenance / 见证行 | 算出来不需要用户；当成分数是范畴错误 | 选择查询的见证就是该行自己，连接查询的见证是参与连接的输入行。系统若直接返回 SQL 结果，「每个返回物品都有见证行」恒为真。过滤式推荐器上这个比例不是实验结果。自连接的共现路径可以作为例子展示，仍然不是主表里的分数。 |
| Faithful CoT 式的「执行即忠实」 | 审计项站得住；解释质量不成立 | 原文：最终答案是确定性求解器执行符号链的结果，因此这条链是模型预测的忠实解释。他们同时写明，主实验不约束自然语言片段和符号片段彼此一致。忠实在这里等于「答案由程序算出来」，不等于「程序正确表达了用户的话」，也不等于「人觉得这是好解释」。返回行恰好是 SQL 结果，只说明展示层没有私自增删。生成器写出错误的 `WHERE` 时，这个等式仍然成立。 |

CMR 的一个现成数字不要用错格。RecBench+ 表 2，电影、显式条件、GPT-4o：Precision 0.308，Recall 0.408，CMR 0.714。同一行的平均 CMR 是 0.374，隐式条件的 CMR 是 0.301。0.714 只属于显式条件。这些系统没有检索目录。

PCN-Rec 的 PassRate 定义清楚，场景不是这条论文。式 (8)：用户级，验证器接受证书的比例；PassRate_feas 把分母收成窗口内存在可行名单的用户。表 1，MovieLens-100K，可行用户 n=551，窗口 80：一次生成的 LLM 是 0.000，校验过的系统是 0.985；NDCG@10 从 0.424 到 0.403。摘要写绝对下降 0.021，正文又写 \(\Delta=-0.022\)。0.424−0.403=0.021，正文多写了 0.001。约束是长尾占比、头部上限和类型多样性，候选来自 MF/CF 的窗口，不是自然语言 SQL。可借鉴的是「提议和确定性校验分开」，数字不要横移。

### 5. 「不新造可解释性指数」对不对？主表和附录各放什么？

这个决定站得住。审稿人会要用户研究，当且仅当贡献句声称解释质量。一个人、公开数据、有限 API，做不了有统计效力的用户研究。塞一个几个人的试测，比不报更容易被写成证据不足。

Faithful CoT 把忠实定义成计算因果，把可模拟性留在外面。笔记里引用的 ACL 2024 长文 2024.acl-long.753 是人能读、能改画像。那类主张的标准证据是人。本篇若写「SQL 文本是忠实解释」，审稿人会要有用性、可模拟性或至少一次受控阅读。预算不够，就把句子改成：SQL 是可执行的审计轨迹，本文不声称用户觉得它是好解释。

主表只放自动指标：

- Hit@1、Hit@5、Recall@20、MRR、NDCG、延迟。协议写在格子里。
- 显式、已经落到列或边上的条件匹配率。定义写成：一件返回物品算匹配，当且仅当每个已落地的原子谓词都成立。隐式和主观条件（「不要太甜」「适合家庭」）不进这列。
- 温度 0、固定种子、N 次：SQL 字符串的 TARr，结果集的 Jaccard。有 `ORDER BY` 才加 Kendall。
- 一条审计列：展示给排序器或用户的行，是否恰好是这条 SQL 的执行结果。SQL 超集再排序时，这列应当为真。先向量再 SQL 过滤时，这列用来区分「展示的是过滤后的向量命中」和「展示的是 SQL 结果」。不要把它标成忠实度得分。

附录：

- 错误计数，沿用 SAGE 表 7 的分法：约束没写对、图结构或连接没写对、执行失败、滤完为空、滤完过大。这是诊断，不是新指数。
- 几条自连接的见证路径，当例子。
- 一段局限性：可模拟性和用户判断不在本篇范围内。不要做 n 很小的用户研究来填这个洞。

两种顺序都留在主表，但 30% 只作为 Text2VectorSQL 的文献警告，并带上 ClickHouse、JOIN-integration、0.6 到 0.4 的条件。先导实验自己的漏召回用自己的 qrel 算。

## 逐项主张

| 主张 | 判定 |
|---|---|
| 嵌入在精确约束上失败，所以 SQL 应替换推荐召回里的向量 | 不成立 |
| 列或边上的谓词先交给数据库，语义留给检索 | 站得住 |
| 每条难查询都路由到 SQL | 不成立 |
| 先向量再 SQL 过滤，相对过滤向量搜索会掉 30% 以上正确命中 | 只在该设置下成立 |
| LIMIT 的 “who likes apples” 是推荐召回的反例 | 不成立 |
| STaRK 上打过 ada-002 的系统仍在检索 | 站得住 |
| 只发出 Cypher 或 SQL 就能打过 BM25 | 不成立 |
| 合成 Amazon 上 SPARK 的 R@20 与 BM25 打平 | 站得住，仅这一格 |
| 约束抽取占 SPARK 错误的 30%–36% | 站得住，仅 Constraint 那一行 |
| 返回行等于 SQL 结果，故解释忠实 | 不成立 |
| 不新造可解释性指数 | 站得住 |
| CMR、TARr/TARa、结果集 Jaccard 可以没有用户研究 | 站得住，定义要按上面收窄 |
| 见证覆盖率、无序结果上的 Kendall、执行等式的百分比，当作解释分数 | 不成立 |

## 分篇

### LIMIT（arXiv 2508.21038v2，ICLR 2026）

主张：固定维的单向量表示不了全部带间隔的 top-k 组合；LIMIT 用自然语言把这个极限做成了可测数据集。容量主张站得住。转到推荐 SQL 上不成立。见问题 1。词法版 BM25 已经接近做对，同义词版词法崩溃。论文要的是更有表达力的检索结构，不是数据库。

### Text2VectorSQL（arXiv 2506.23071v2）

主张：自然语言到向量 SQL 是一个任务；后过滤会静默漏召回，JOIN-integration 最重。任务定义和「两种执行策略都要测」站得住。30% 的外推不成立。见问题 2。他们的金标准是混合查询的执行结果，不是推荐相关性。预过滤被写成高保真、可能换来全表扫描；这和「SQL 超集再排序」同向，和「用 SQL 换掉向量」反向。

### NevIR（arXiv 2305.07614）

主张：双编码器不懂否定。站得住。表 2：随机成对准确率 25%；没有一个双编码器超过 12%，多数在 5%–10%（表内从 DPR 6.8% 到 multi-qa-mpnet 11.1%）。正文原句：“No bi-encoder architecture scores higher than 12% paired accuracy ... with most models performing in the 5-10% range.” 稀疏模型也差：TF-IDF 2.0%，SPLADEv2 约 8%。交叉编码器可以高于随机，MonoT5-3B 50.6%。标注禁止使用只出现在一段里的词，所以关键词 `NOT` 也做不对。否定活在自由文本里时，SQL 没有可执行的谓词。能用 `WHERE NOT` 的，是类型、品牌这种已经成列的排除。

### ExcluIR（arXiv 2404.17288）

主张：排除性查询（要 A 不要 B）是独立于一般否定的检索失败。只在该设置下成立。语料是生成的排除性查询，3,452 条有人工标注。模型把排除短语当普通关键词。若被排除的属性是列，`NOT IN` 或差集可以精确做；若排除的是评论里的感官描述，就回到 SUQL 的 `ANSWER`，SQL 谓词写不出来。不能把这篇的失败直接记成 SQL 的胜利。

### NumConQ（BDMA 2026，DOI 10.26599/BDMA.2025.9020047）

主张：稠密检索器满足不了文本里的数值约束。站得住，对象是文本化之后的记录。摘要写数值约束满足的准确率只有 16.3%。正文把 16.3% 收成身高、体重、年龄的一致性平均；非数值属性（性别、国家、项目、奖牌）平均 73.64%。总表里 BGE-M3 的 Recall@10 是 40.37%，Precision@10 是 10.45%。四位数字那一档，同一模型的 Recall@10 是 62.8%，不要和 40.37% 混用。文档是从结构化条目改写来的。原表还在时，数值比较是 SQL 的工作，不该交给嵌入。作者的补救是 NC-Retriever，仍是稠密检索器。这篇支持「数值谓词不要交给嵌入」，不支持「整个召回换成 SQL」。

### QUEST（ACL 2023）

主张：隐式交、并、差让双编码器的穷尽召回很差。只在该设置下成立。表 4：T5-Large 双编码器平均 Recall@100 是 0.476。MRecall 的定义是「候选集包含全部相关文档的查询所占比例」，@100 是 0.142。笔记里的「宏召回」容易听成宏平均召回；论文的平均召回是 0.476 那一列，0.142 是完全召回的查询比例。查询是维基实体上的集合描述，不是推荐。文档是正文。SQL 要能做这些运算，先得有实体—属性表。双编码器在表 3 里仍然高于 BM25，所以这篇也不是「词法或 SQL 全面胜出」。

### FollowIR（NAACL 2025）

主张：检索模型把指令当关键词。站得住，有明确的模型范围。正文：“current models generally fail to follow instructions in retrieval unless they are 3B+ parameters or have not been trained for retrieval.” 表 2 说明：一般只有 3B 以上，或没有按检索任务训练过的指令模型，p-MRR 才为正。无指令模型的平均 p-MRR 多为负，MonoT5-3B 是例外（平均 +2.5）。失败原因他们写成两条：不习惯长指令，以及把指令拿去当关键词。TREC 叙事指令不是列谓词。SQL 解析不了「在这种叙事下什么算相关」。这篇限制的是「把所有指令都编译成 `WHERE`」。

### BRIGHT（ICLR 2025，arXiv 2407.12883）

主张：相关关系需要推理时，现有检索器都很差；对查询做思维链再检索，最多提高 12.2 个点。检索很差，站得住。表 2 的 BM25 十二个数据集平均 nDCG@10 是 14.5。表注、第 4.2 节和结论都写最好模型的平均只有 24.3。抽出的表 2 各行里，最高平均是 Qwen 的 22.5，没有一行的平均数等于 24.3；24.3 以作者正文为准，不指派给某个抽不出来的模型名。SFR-Embedding-Mistral 的平均是 18.3，同时在 MTEB 检索子集上是 59.0。

+12.2 是查询侧的思维链，不是对候选做推理。第 1 节：“generate chain of thought reasoning steps about the query before retrieval, resulting in average improvements of up to 12.2 points.” 第 4.2 节把这些步骤当作新查询。图 3 显示换成 GPT-4 写的推理后，BM25 涨得最多。笔记里「提升来自对候选做推理」和这篇的 12.2 对不上。另有一张重排小表，BM25 从 14.3 到 GPT-4 重排的 17.4，不是 12.2。

对本文的用法：LeetCode 子任务、定理、堆叠溢出帖都没有可执行的关系谓词。不能把每条难查询都路由到 SQL。BRIGHT 同时说明，这种缺口上 BM25 也差，SQL 不会因为「嵌入不行」就自动赢。

### ACORN（SIGMOD 2024，arXiv 2403.04871）

主张：谓词无关的混合搜索可以在 0.9 召回下比先前方法高 2–1,000 倍的 QPS。速度主张站得住。摘要和结论都是 throughput / QPS，不是效果失败。它扩展 HNSW，让向量索引和结构化谓词一起走。用它证明「向量在约束上失败，所以换成 SQL」不成立。它证明的是系统和算法可以把谓词留在向量搜索里面。效果上的过滤近似搜索失败要到召回基线那一份笔记里找，不要引 ACORN 的倍速。

### SUQL（NAACL 2024 Findings）

主张：SQL 加上自由文本上的 `SUMMARY` 和 `ANSWER`，才能覆盖结构化加非结构化的查询。分工站得住，替换不成立。Yelp：满足全部用户要求的对话轮，SUQL 90.3%，把表线性化后塞进模型是 63.4%；单轮 93.8%。`ANSWER(reviews, 'is parking easy?')` 被用作过滤器。作者写，停车难不难这种信息在评论文本里，纯 SQL 不够。餐馆搜索，1,828 家，指标是约束是否全满足，没有排序指标。这是公开文献里最接近「结构化约束下找店」的系统，也是「SQL 替换向量」的反例：去不掉的正是模型谓词。

### TAG（CIDR 2025）

主张：能写成关系代数的问题只是用户问题的一小部分；RAG 又只覆盖点查。标准方法在他们的基准上正确率不超过 20%。分工站得住。三步是查询合成、数据库执行、语言模型生成答案。摘要原句：“standard methods answer no more than 20% of queries correctly.” 正文把 20% 说成精确匹配或准确率的上限，不是推荐的 Recall。没有排序器。这篇直接反对「Text-to-SQL 够用」，也反对「只做向量点查够用」。

### AvaTaR、KAR、MoR、mFAR、HybGRAG、SAGE/SPARK

见问题 3。合在一起的主张「加了结构就能打过稠密检索，因此发出查询语言就能打过 BM25」：前半只在检索器还在的混合系统上成立，后半不成立。Amazon 上纯结构的 QAGNN 低于 BM25。SPARK 在合成 Amazon 的 R@20 上与 BM25 打平，并低于 multi-ada-002。

### PCN-Rec（arXiv 2601.09771）

主张：LLM 只提议名单和证书，确定性验证器决定接受；做不到就用约束贪心修补。验证器和效用要分开报，这个实验设计站得住。数字只在 MovieLens-100K 的治理约束、窗口 80、551 个可行用户上成立。见问题 4。它不是 SQL，也不是自然语言推荐请求。一次生成的 0.000 说明他们的验证器很严，不能写成「大模型在约束推荐上的通过率普遍是 0」。

### Faithful CoT（IJCNLP-AACL 2023）

主张：符号链交给确定性求解器，链就是答案的忠实解释，并且在 10 个基准的 9 个上优于普通思维链。忠实的操作定义在他们的任务上站得住。摘要里的相对准确率提升（数学应用题 6.3%，规划 3.4%，多跳问答 5.5%，关系推理 21.4%）是问答和推理，不是推荐。转到 SQL 推荐器：执行等式可以当审计，不能当解释贡献。见问题 4。他们自己把「自然语言是否像那么回事」和「符号链是否决定答案」拆开，主实验不约束两者一致。

### Atil 等（arXiv 2408.04667）

主张：温度 0 仍不稳定；用 TARr@N 和 TARa@N 分开量原始字符串和解析答案。定义站得住。五个模型、八个任务、10 次运行、零样本和少样本。15% 是运行准确率的起伏上限，70% 是 BestAcc 与 WorstAcc 的差距上限。不要写成「SQL 准确率会晃 15% 或 70%」。本地 7B 和闭源 API 要分开报，他们的数字来自 GPT-3.5、GPT-4o、Llama-3-8B/70B 和 Mixtral。

### ReproRAG（arXiv 2509.18869）

主张：向量 RAG 的跨次运行要用集合重叠和秩相关来量，不能假设索引不变。指标定义站得住，见问题 4。论文页眉是 workshop。它量的是嵌入、FAISS、数据插入带来的检索漂移。精确 SQL 执行不在这个失败模式里。把他们的 Jaccard 拿来量两次生成的结果集，是借用定义；把他们的实验结论写成「SQL 结果集会自己漂」不成立。

## 笔记里建议改口、本篇没有改原文的几处

- LIMIT 不要出现在「推荐约束上嵌入失败」那一栏。可以出现在「单向量表示不了任意相关组合；词法匹配在原字符串上反而很强」的相关工作里。
- Text2VectorSQL 的 30% 改成：ClickHouse 上，UniVectorSQL-7B 从 Non-integration 的召回 0.6 降到 JOIN-integration 的 0.4；引言把后过滤在 JOIN 上的静默漏检概括为丢掉 30% 以上正确结果。WHERE 没有这个数字。PostgreSQL 的迭代扫描轻得多。
- SPARK 改称 SAGE 论文中的 SPARK 代理。写明 HNSW、Cypher、BM25/余弦回退。53.95 对 53.77 只标注合成 Amazon 的 Recall@20。同一格补上 multi-ada-002 的 55.12。人工 Amazon 另报。
- 30%–36% 标明是表 7 的 Cypher Constraint（36 / 30 / 31），不要加上 Over-Retrieval。
- BRIGHT 的 +12.2 改成查询侧思维链。BM25 平均 14.5 保留。24.3 是作者对最好模型平均 nDCG@10 的陈述。
- QUEST 的 0.142 改称 MRecall@100，即完全召回的查询比例。
- RecBench+ 的 0.308 / 0.714 标明电影、显式条件。平均 CMR 是 0.374。
- HybGRAG 没有 Amazon，是作者写明的法律原因，不是没做完。
- PCN-Rec 的效用差用 0.021（0.424 到 0.403）。正文的 −0.022 是论文自己的算术误差。
