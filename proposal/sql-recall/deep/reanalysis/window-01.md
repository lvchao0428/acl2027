# 窗口 01：Text-to-SQL 五步重析

日期：2026-11-11。范围是大纲点名的 22 篇。数字从 PDF 正文、表和图注抄，不从旧笔记转写。SUQL 的两份 PDF（`01-text-to-sql/SUQL_NAACL2024_Findings.pdf` 与 `04-metrics/SUQL_NAACL2024.pdf`）MD5 同为 `e6f3a96e950c64f4f0db7d2900a44fdf`，只析前一份。TAG 析 `04-metrics/TAG_CIDR2025.pdf`（页眉 CIDR’25），不把 `TAG_arXiv2408.14717.pdf` 另算一篇。QUEST、InteRecAgent、SIEVE、RecBench+、RelBench 不在本窗口。

全文检索 `NDCG`、`nDCG`、`Hit@`、`Recall@`、`MRR`：22 篇加 TAG 的 CIDR 版均为零命中。唯一的 `recall@k` 在 FinSQL 表 7，对象是表和列，不是物品。

## 选题：这一窗口能定下来的部分

### 五个问题的答案

1. **用户、物品、交互表上由模型写 SQL，执行结果当候选，用留出交互的 Recall 或 NDCG 打分，并单独报告错误 SQL 被执行的代价。** 这 22 篇里没有。SQL 的执行结果被当成答案、返回的餐馆、或表问答的单元格，打分停在执行是否匹配、人工集合精度、或可靠性分。空位还在。

2. **再报一个域内执行准确率，或把拒答、不可答令牌、错答更贵的可靠性分写成主创新，已经挤满。** 域内执行准确率被 ScienceBenchmark、SM3、BiomedSQL、BookSQL、BULL、FINCH、OMOP 占住。拒答主创新被 EHRSQL、EHRSQL 2024、TrustSQL、OMOP 的 RS、Query Carefully 占住。这一格没有空位。

3. **换库会让在 Spider 上训练或成名的系统变差，但必须带配置。没有「同一系统、同一配置从 82% 掉到 25%–60%」。** ScienceBenchmark 的 “above 82%” 是 Spider 榜上别的系统；“25-60%” 把他们自己跑通的微调和提示结果并进一句。40 个模板和专家 90.0 **还在 BiomedSQL 的 PDF 里**：40 个专家种子题生成约 6.8 万对；90.0 是两名分析员各做 20 题的执行准确率均值，作者写 95% 区间约 [68%, 99%]，并标明是近似参照。不能把贡献列表里的「25–30 个百分点」写成已经测稳的科学推理差距。

4. **执行准确率会把错查询判对、把对查询判错，金 SQL 会改名次。证据停在 SQL 对错。** 没有一篇把主指标写成推荐的 Recall、NDCG 或 Hit。若推荐标签由一条 SQL 算出，Recall 会退回执行匹配；这是从 FLEX、Jin、Wretblad、Arctic、TrustSQL 推到推荐上的设计约束，不是这 22 篇已经证明「主指标必须是推荐效果」。

5. **纯 SQL 盖不住外部知识或自由文本。** SUQL 占住的是 Yelp 餐馆、最多返回 3 家、作者判定的集合精度（单轮 93.8%，对话 90.3%）。这不是 STaRK 上的检索，也不是交互表上的留出推荐分。TAG 的 0.55 是 80 道 BIRD 改写题上的手写流水线精确匹配，不是可复用自动系统，也不是 Recall。

### 论文可以做的那一格

在用户、物品、交互表上，模型写出 SQL，数据库执行，执行结果就是候选，主指标用留出交互的 Recall 或 NDCG，另外一列报告错误 SQL 一旦执行要付的代价。相关集必须是留出的交互，不能是这条 SQL 自己的结果集，否则 Recall 退回执行匹配。

自由文本、评论、问句里没有落到列上的语义，仍交给检索或模型谓词。Binder、SUQL、TAG、BlendSQL 已经说明纯 SQL 盖不住这部分；它们的分数不能挪来当推荐涨幅。

生成器可以借用 Arctic-Text2SQL-R1-7B 或 OmniSQL-7B。借用的是检查点，不是它们的执行准确率。同一张表里，Arctic-7B 在 Spider 测试上是 88.8，在 Spider2.0-SQLite 上是 15.6；OmniSQL-7B 贪心在 Spider 测试上是 87.9，在它自己的 135 条 Spider2.0-SQLite 上是 10.4。高 Spider 分不会自动搬到另一套库。

### 这一窗口明确不写的句子

- 领域 text-to-SQL 完全不值得做。挤满的是再报一个域内执行准确率。
- 拒答、不可答令牌或可靠性分是这篇的主创新。
- 同一系统从 82% 掉到 25%–60%。
- 执行准确率、作者判定的集合精度、或可靠性分，就是 Recall、NDCG 或 Hit。
- 原文已经证明主指标必须是推荐效果。

## 1. ScienceBenchmark（PVLDB 17(4): 685–698, 2023）

文件：`papers/sql-recall/01-text-to-sql/ScienceBenchmark_PVLDB2024_Stockinger.pdf`。文件名写 2024，正文卷期是 2023。读了第 1–5 节和表 5。

### 第 1 步

1. 引言：Spider 上顶尖系统 “reach accuracies up to 85%”；开源的 T5-Large（带 Picard）、SmBoP、RESDSQL with NatSQL “already achieving over 70%”。这是转述榜单，不是本文复现。
2. 贡献段写：Spider 榜上 82% 以上的系统，到科学库 “only in the range of 25-60% accuracy depending on the domain”。
3. 三个库。CORDIS：19 表、82 列。SDSS 全库 10 张表，列数从 3 到 804；因输入 token 限制，实验库裁成 5 张原表加 1 张光度表，表 1 记 61 列。OncoMX：25 表、106 列。每域手工 100 条训练、100 条后来称为 Dev 的评测题，由领域和 SQL 专家写。合成查询由种子抽模板、只换叶子、GPT-3 回译。
4. 实际跑通的系统写在第 5 节和表 5：ValueNet、T5-Large、SmBoP+GraPPa，外加 GPT-3.5 与 LLaMA2-70B。脚注：Picard 的 Haskell 解码器编译失败，T5-Large 是无约束解码。NatSQL 转换代码不可用，集成 NatSQL 的系统（含 RESDSQL）被排除。
5. 表 5，指标是执行准确率，评测集是每库 Dev。零样本（只在 Spider 上训练）：CORDIS 上 ValueNet 0.12、T5 0.16、SmBoP 0.16；SDSS 上 0.08、0.05、0.06；OncoMX 上 0.13、0.11、0.19。种子加合成之后最高是 OncoMX 上 T5-Large 0.56（相对零样本 +0.45），CORDIS 上 ValueNet 0.35。提示侧：GPT-3.5 在 CORDIS 一点提示 0.60、零样本和五点都是 0.57；SDSS 五点 0.33；OncoMX 五点 0.55。LLaMA2-70B 全面更低，SDSS 零样本是 0。
6. 正文把 T5 的 +45 个点收成 “maximum execution accuracy of 56%”，把 GPT-3.5 的 CORDIS 收成 60%、SDSS 收成 33%。没有推荐 Recall、NDCG 或 Hit。没有把空结果单独分析成「错 SQL 被判对」。

### 第 2 步

「Spider 库简单」递进到「需要科学库」。基准并列成手工对和模板合成对。难度主张接在表 5 上，但 “above 82%” 与 “25-60%” 不是同一批系统、同一配置的前后测：82% 是榜单上没在这里跑通的系统，25–60 把微调后的 0.56 和提示模型的 0.33–0.60 并成一个区间。

### 第 3 步

未写出的依赖：执行结果相同即问句被正确回答；每库 100 条 Dev 代表该科学库；裁到 61 列的 SDSS 仍是「复杂真实科学库」；模板换叶子后的问句是新问法。他们没有说空结果会让错误 SQL 判对。

### 第 4 步

「在这三个裁过的库、每库 100 条 Dev 上，当时能跑通的微调模型零样本执行准确率在 0.05–0.19，加上种子和合成数据后最高到 OncoMX 的 0.56，GPT-3.5 在 CORDIS 一点提示到 0.60、在 SDSS 五点提示到 0.33」：强，表 5 直接支持，外推停在这三库。

「同一批系统从 82% 掉到 25%–60%」：弱。表 5 没有那些榜单系统的同配置 Spider 分，Picard 和 RESDSQL 没跑。

「第一个复杂真实科学库」：弱到中等。相关工作自己列出 MIMICSQL；SDSS 不是全库。

### 第 5 步

可以相信的是任务在这三库上当时没被跑通的模型解决，评测就是执行准确率。不能写成同一系统从 Spider 的 82% 掉到 25%–60%，也不能写成全库 SDSS 已被这个基准代表。没有推荐指标。

## 2. SM3-Text-to-Query（NeurIPS 2024 Datasets and Benchmarks）

文件：`papers/sql-recall/01-text-to-sql/SM3-Text-to-Query_NeurIPS2024.pdf`。读了第 1–6 节和表 3、表 4。

### 第 1 步

1. 同一批 Synthea 合成病人上的四种查询语言：SQL、SPARQL、Cypher、MQL。默认配置是 100 名在世加 10 名已故，不是医院导出。408 个模板，每种语言 1 万对（6K/2K/2K）。局限节写模板 “only created with guidance from health professionals, but not directly formulated by them”。
2. 表 3 是测试集执行准确率（%）。带 schema、零样本 SQL：Llama3-70b 47.05，GPT-3.5 42.20，Gemini 1.0 Pro 38.60，Llama3-8b 22.55。带 schema、五点：Llama3-70b 57.50（±2.91），GPT-3.5 56.30（±2.36）。SPARQL 带 schema 零样本最高是 GPT-3.5 的 3.30，Llama3-70b 只有 1.00；五点 Llama3-70b 到 30.49。
3. 他们用 Stack Overflow 帖子数解释语言差距，随即承认 MQL 是反例：帖子多于 Cypher，零样本却更低（Llama3-70b 的 MQL 21.55 对 Cypher 34.45）。
4. 表 4：BM25 从训练集抽 5 个相似问句，GPT-3.5 带 schema，SQL 88.55，相对固定五点 +32.25；SPARQL 75.75，Cypher 78.30，MQL 78.70。
5. 局限：SQL 和 Cypher 平均不到 10 个 token，可能太容易。没有推荐指标。

### 第 2 步

「四种语言还没放在同一批医学数据上」递进到建库。语言差距的因果解释被他们自己的 MQL 反例转折掉。88.55 不否定 47.05，它依赖另一种例题选择。

### 第 3 步

未写出的依赖：408 个模板填槽后互相独立；训练集里 BM25 抽到的相似问句不是同一骨架的金查询；执行结果相同即语义相同；Synthea 加 SNOMED 命名等于临床原话。

### 第 4 步

「在他们划定的范围内，这是四种语言放在同一批合成数据上的基准」：中等。范围声明站得住。

「47.05 是医学 text-to-SQL 的上限」：弱。换 BM25 例题就到 88.55。模板填槽后，相似例很容易把同一骨架的金查询放进提示。

「临床真实问句」：弱。局限节自己写医生没有直接出题，数据是合成的。

### 第 5 步

可以相信的是：同义问句在四种语言上的零样本差距很大；按问句相似度取例之后，GPT-3.5 的 SQL 从固定五点的 56.30 升到 88.55。不能把 47% 写成医学上限，也不能把模板实例写成医院原话。没有推荐指标。

## 3. BiomedSQL（COLM 2026；arXiv:2505.20321v6）

文件：`papers/sql-recall/01-text-to-sql/BiomedSQL_arXiv2505.20321.pdf`。页眉 COLM 2026。读了第 1–7 节和表 3、表 4、表 5。

### 第 1 步

1. 40 道专家种子题，程序填入疾病、基因和 SNP，得到表 1 的 68,227 对。库是公开 BigQuery，十张表，单表最多约 7200 万行、31 列。金 SQL 避免 `SELECT *`，结果帽在 100 行。评测集是按模板分布抽出的 546 条，不是 6.8 万条全评。
2. 科学推理在文中指问句不写、SQL 必须写的惯例。例子是 GWAS 的 `p < 5e-08`，以及问句没提却要查的试验阶段。作者把这写成 schema 里看不见的领域惯例。
3. 表 3，基线提示：Gemini-3-Pro 的 EX 58.1（±4.3）、JAC 62.4、RQR 81.8。领域专家一行是 90.0、90.0、95.0。正文写明：两名分析员各做从 546 里抽的 20 题，报均值；EX 的 95% 区间约 [68%, 99%]，“should be read as an approximate reference”。两人答案没有裁决，没有标注者一致率。
4. 贡献列表写 “a 25-30 percentage point gap”。这是 90 减 58.1 或 62.6 的算术，不是区间下界上的差距。
5. 表 4：BMSQL-GPT-o3-mini 的 EX 62.6（±4.1）、JAC 69.2。DAIL-SQL-GPT-o3-mini 61.2，正文写差距落在置信区间内。10-shot 对 GPT-o3-mini 的 ΔEX 是 +7.8；把 40 个模板全放进提示，收益很小。错误分析：最常见的是选错表，其次是漏掉或用错阈值。BMSQL 的优势之一是把阈值写进了后续步骤，所以「模型必须自己推断惯例」只对基线提示成立。
6. 表 5：BMSQL-GPT-o3-mini 从 1-pass 到 3-pass，EX 从 62.6 到 61.7，RQR 从 83.2 到 85.5。没有推荐指标。

### 第 2 步

「schema 看不见统计惯例」递进到新基准，再递进到「专家 90、模型 58–63，所以差 25–30 个点」。后半段被作者自己转折：评测在 546 条，专家在 20 条，区间下界约 68。阈值写进提示或写进 BMSQL 之后，「必须自己推断惯例」这条因果对那个系统不再成立。

### 第 3 步

未写出的依赖：40 个骨架填槽后仍是 6.8 万道独立科学问题；100 行帽下的 UUID 或数值集合相等不会让两条不同过滤撞车；GPT-4o 对 100 条回答的 RQR 与专家的 Spearman 0.89 足以代表科学正确；BigQuery 方言上的失败可以外推到一般 SQL。

### 第 4 步

「问句不写、SQL 必须写上的统计阈值」：强，作为现象。这和 ScienceBenchmark 的领域词表不是同一件事。

「40 个模板和专家 90.0 还在 PDF 里」：在。模板属于种子构造；90.0 属于 20 题子集，并带 [68%, 99%] 的区间。旧笔记若写这两格没有留下，以这份 PDF 为准，两格都在。

「专家比模型高 25–30 个点」：弱。点估计是 90.0 对 58.1 或 62.6；区间下界约 68 对 62.6 只剩大约五个点，模型区间半宽是 4.1。作者写方向仍在，贡献列表里的 25–30 不能当稳定差距。

### 第 5 步

可以相信的是：在这 546 条、这个 BigQuery 库、基线提示下，Gemini-3-Pro 的执行准确率是 58.1；BMSQL-GPT-o3-mini 是 62.6；失败里有一批是漏掉 schema 里没有的统计阈值。不能把 40 个模板的域内规模、或 20 条上的专家 90.0，写成科学推理已被测量到差 25–30 个点。没有推荐指标。

## 4. BookSQL（NAACL 2024 长文，页 497–516）

文件：`papers/sql-recall/01-text-to-sql/BookSQL_NAACL2024.pdf`。读了第 1–5 节和表 1、表 3、表 5、表 6。

### 第 1 步

1. 摘要：会计库，100k 问句–SQL 对，约 100 万行。表 2：1 个库、1 个域、7 张表。表 3：27 家企业，Easy 10,000，Medium 45,000，Hard 45,000。第 3.4 节又写 “BookSQL consists of 7,193 Hard SQL queries”。两句都在正文，规模不要收成一个数。
2. 问句来自两名财务专家列出的 183 道典型问题，再模板化。划分按模板 70/10/20，测试模板不在训练里。测试集难度是 easy 14.37%、medium 78.43%、hard 7.2%。测试集的难度分布和表 3 的全库分布不是同一张饼。
3. 表 1 是精确匹配，标题写预训练 SOTA 在 Spider 和 BookSQL 上的表现，正文说明是 Spider 上训好的模型直接测 BookSQL：UniSAr 70% 对 3.8%，SEDE 63.2% 对 0.0%，RESDSQL 80.5% 对 10.8%。这是迁移，不是在 BookSQL 上微调。
4. 表 5 是微调或提示之后。RESDSQL 在 BookSQL 上精确匹配 51.5%、执行准确率 54.4%，对照栏写它在 Spider 上 80.5% / 84.1%。DIN-SQL+GPT-4 执行准确率 7.6%，动态十例加 GPT-4 是 67.2%。GPT-4 只跑了测试集随机 10%（附录写明是 API 调用次数限制）。表 6 的 GPT4 列：Easy 100、Medium 71.35、Hard 22.08。正文没有写这列是 DIN-SQL 还是动态少样本。
5. 第 3.3 节自称第一份有大量多步嵌套和时间过滤的 text-to-SQL。表 2 自己列出 Spider 的 NESTED 是 844，BookSQL 的 NESTED 是 4,456。没有推荐指标。

### 第 2 步

「会计人员不会写 SQL」递进到「需要会计库」，再并列成「Spider 模型迁过来很差」和「微调之后仍有缺口」。表 1 的 10.8 和表 5 的 54.4 是两种训练状态，不能接成一条落差。7,193 与 45,000 是同一篇里的转折，不是两篇文献。

### 第 3 步

未写出的依赖：183 个专家模板的填槽等于会计人员的问句分布；按模板划分就挡住了同骨架泄漏；Spider 上的 80.5/84.1 与 BookSQL 微调是同一配置，只换了库。

### 第 4 步

「Spider 上训好的 UniSAr、SEDE、RESDSQL 直接测 BookSQL，精确匹配是 3.8、0.0、10.8」：强，表 1 支持。这是精确匹配迁移，不是执行准确率，也不是 82 到 25–60。

「微调后的 RESDSQL 在 BookSQL 上执行准确率 54.4，对照它公布的 Spider 执行准确率 84.1」：中等。数字在表 5，但是否同配置、同解码，表没有写死。

「100k 与 7,193 道 Hard 可以收成一个规模」：不成立。表 3 的 Hard 是 45,000。

### 第 5 步

可以相信的是：会计模板库上，Spider 训练的模型不做微调时精确匹配很低；微调之后 RESDSQL 的执行准确率到 54.4，GPT-4 的数字只覆盖测试集的随机 10%。问句分布是 183 个专家模板的填槽。没有推荐指标。

## 5. FinSQL / BULL（arXiv:2401.10506v1）

文件：`papers/sql-recall/01-text-to-sql/FinSQL-BULL_arXiv2401.10506.pdf`。页眉仍是 Conference’17 占位，不写成已出版会议。读了第 5、9 节和表 4–9。

### 第 1 步

1. BULL：基金、股票、宏观经济三个库，4,966 对，中英两套问句共用库结构。正文写三库分别 31、28、19 张表。图 2 的最大列数是 30、29、30。多数表超过十列。这不是 Spider 2.0 那种每库数百列的企业库。

## 9. TrustSQL（arXiv:2403.15879v6，2024-07-02）

文件：`papers/sql-recall/01-text-to-sql/TrustSQL_arXiv2403.15879.pdf`。页眉没有会议名。读了第 1–3 节、表 3、表 4 的表头和公式，以及附录里关于执行假阳性的段落。

### 第 1 步

1. 可靠性定义为：可行题写出执行正确的 SQL，不可行题拒绝。不可行题包括假设列（surface / related / unrelated）、非 SQL 功能、外部知识。假设列是作者构造的，不是从真实用户日志抽的含糊问法。正文把真实歧义明确排除在范围外，理由是消歧需要多轮。
2. 公式 (1)，记 ϕc(x)：可行且作答且执行正确得 1；可行且拒答得 0；可行且作答但执行错误得 −c；不可行且作答得 −c；不可行且拒答得 1。聚合是样本均值。
3. 正文对 c=0 的原句：“This does not penalize any mistakes made by the model. If we only handle feasible questions, this score is equivalent to the standard text-to-SQL accuracy.” 表 4 标题重复：只看可行题时，ϕ0 等于标准 text-to-SQL 的执行准确率。数学上，拒答得 0，答错在 c=0 时也得 0，所以均值等于「做对的可行题 / 全部可行题」。模型若总是作答，它就退化成执行准确率。
4. 表 3 是可行加不可行、各约一半，所以全拒答是 50.0。ϕ0 下若干系统在 70–88，ϕN 下同一行落到 −10^3 到 −10^4 的量级。例如开放统一模型 T5[MAXENT] 在 EHRSQL 上 ϕ0 是 85.3、ϕ10 是 36.1、ϕN 是 −9.1K。API 管道 CLSP→SQLPROMPT 在 ATIS 上 ϕ0 是 88.9、ϕ10 是 −2.5。
5. 附录写执行准确率的假阳性：金 SQL 返回 Null 或空列表时，错误 SQL 也可能被判对；问句要名字、SQL 选了 ID，执行结果仍可能碰巧相同。他们预处理时删掉一批空结果，并改写问句。主表没有推荐分。这篇追问的是：执行匹配把「结果碰巧相同」和「空结果撞车」算成成功，c=0 时答错又不比拒答更贵。

### 第 2 步

「部署时既有可行题也有不可行题」递进到五区打分。c=0 只看可行题时，打分退回执行准确率，这是他们自己写出的转折。表 3 再转折一次：无惩罚看起来高，严惩罚下几乎全负。

### 第 3 步

未写出的依赖：假设列等于真实用户的含糊问法。正文明确不这样写，只把假设列当成红队式的 schema 不兼容。也不能把删掉空结果之后的执行准确率当成已经消除假阳性。

### 第 4 步

「c=0 且只看可行题时，可靠性分退化成执行准确率」：强，正文和表 4 标题都这样写。前提是拒答和答错都记 0。

「高 ϕ0 等于可以部署」：弱。同一张表的 ϕN 列是很大的负数。

「假设列代表真实含糊问法」：弱。作者把歧义排除在数据构造之外。

### 第 5 步

可以相信的是：错答不加罚时，可靠性分会退回执行准确率；一旦错答比拒答更贵，高分可以变成很大的负数。执行匹配会把空结果撞车和列含义不同但结果碰巧相同算成成功。拒答主创新被这篇占住。主表没有推荐分。

## 这一窗口留给选题的边界

空着、并且这 22 篇没有占住的，是：模型在用户、物品、交互表上写 SQL，数据库执行，候选就是执行结果，主指标是留出交互的 Recall 或 NDCG，错误 SQL 被执行的代价单独一列。相关集不能是这条 SQL 自己的结果，否则指标退回执行匹配。FLEX、Jin、Wretblad、Arctic 和 TrustSQL 已经表明执行匹配会把错查询判对、把对查询判错，金 SQL 还会改名次。

挤满的是两件事。一是专家模板或合成问句上再报一个域内执行准确率。二是拒答、不可答令牌和错答更贵的可靠性分。EHRSQL 2024 的第一名可以同时是 RS(0) 88.17 和 RS(N) −711.83。TrustSQL 写明 c=0 且只看可行题时，可靠性分退回执行准确率。

换库的句子要带配置。ScienceBenchmark 的 82% 和 25%–60% 不是同一批系统。能写成同一检查点、同一贪心协议的，是 Arctic-7B 从 Spider 测试 88.8 到 Spider2.0-SQLite 15.6，以及 OmniSQL-7B 从 Spider 测试 87.9 到 135 条上的 10.4。这不是「从 82% 掉到 25%–60%」，也不能用来给几张窄交互表背书。

自由文本仍在 SQL 外面。SUQL 的 93.8 / 90.3 是餐馆、最多 3 家、作者判定的集合精度。TAG 的 0.55 是 80 题上的手写精确匹配。Binder 的 64.6 是 WikiTQ。三篇都说明纯 SQL 盖不住外部知识或自由文本，三篇都不是留出推荐分。

所以这篇如果做，数字是推荐任务上的留出指标，加上错误 SQL 被执行之后的代价。生成器可以用 7B 检查点。域内执行准确率和拒答不再作为主创新。
