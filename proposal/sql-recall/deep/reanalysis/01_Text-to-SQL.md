## 1. ScienceBenchmark（PVLDB 17(4): 685–698, 2023）

文件：`papers/sql-recall/01-text-to-sql/ScienceBenchmark_PVLDB2024_Stockinger.pdf`。文件名写 2024，PDF 自署 2023。读了第 1–7 节至结论；参考文献未逐条当论点。

### 第 1 步

1. Spider 上已有系统超过 80%，但 Spider 库简单、多为学生所造，换到科学库会差。引言写 “top NL-to-SQL systems reach accuracies up to 85% on Spider”，又写开源系统 T5-Large（带 Picard）、SmBoP、RESDSQL with NatSQL “already achieving over 70%”。证据是转述榜单，不是本文复现。
2. 贡献一：三个科学库、六千多对，是 “the first NL-to-SQL benchmark designed with complex real-world scientific databases”。Table 1：CORDIS 19 表 / 82 列，手工 200 + 合成 1306；SDSS 6 表 / 61 列，200 + 2061；OncoMX 25 表 / 106 列，200 + 1065。第 3.1 节写明 SDSS 全库有表多至 804 列，实验库因 “limitation of the input tokens” 裁成 5 张原表加 1 张附加表。第 3.2 节：每库手工 seed 100、另 100 条他们先称 test、后文称 Dev，由 INODE 项目里 SQL 专家和领域专家写。Table 2：OncoMX 合成集 Hard 与 Extra Hard 都是 0。相关工作自己列出 MIMICSQL。
3. 贡献二：种子抽 SemQL 模板，只换叶子，GPT-3 把 SQL 回译成问句。第 4.1 节 Table 3，Spider dev 上人工正确率：微调 GPT-3 0.731，零样本 GPT-3 0.765；他们仍选微调版，因为 SacreBLEU 38.55 对 30.36、SentenceBERT 0.888 对 0.870。领域 dev 上 SQL 到问句的人工正确率：CORDIS 82%、OncoMX 73%、SDSS 53%。Table 4 抽查每库 100 条合成对：正文把第二列解释成 SQL 有意义，范围 91%–97%（抽出的单元格是 CORDIS 97%、SDSS 97%、OncoMX 91%），问句与 SQL 语义等价 75%–83%（83%、76%、75%）。他们写明不滤掉不等价对，理由是银标可以有噪声，并引 Honovich 等说噪声银标可以胜过精标。
4. 贡献三：Spider 榜上 82% 以上的系统，到这里 “only in the range of 25-60%”。Table 5 的实际对照不是这批榜单系统。脚注：Picard 因 Haskell 编译失败，T5-Large 是无约束解码；NatSQL 转换代码不可用，RESDSQL 被排除。零样本执行准确率：T5-Large 在 SDSS 上 0.05，ValueNet / T5 / SmBoP 在三库上从 0.05 到 0.19。加上 seed 和合成数据后，T5-Large 在 OncoMX 上 0.56（相对零样本 +0.45）。GPT-3.5 一点提示在 CORDIS 上 0.60，五点在 SDSS 上 0.33。评测集是每库 100 条手工 dev，指标是执行准确率。没有空结果或同结果异查询的分析。

### 第 2 步

「Spider 简单」递进到「需要科学库基准」。基准又并列分成手工对与合成对：合成流程因果地依赖种子模板，模板只换叶子。质量论证是转折：人工正确率零样本 GPT-3 更高，他们改用自动指标选定微调版，再主张银标不必过滤。难度主张依赖 Table 5，但 25%–60% 把微调后的 0.56 和提示模型的 0.33–0.60 并到一句，82% 来自别的系统在 Spider 上的分数，这两段不是同一实验的因果链。

### 第 3 步

未写出的依赖：执行结果相同即问句被正确回答；100 条 dev 足以代表该科学库；裁过的 SDSS 仍可支撑「复杂真实科学库」；模板换叶子后的问句仍是新问法；领域专家看过输出就等于金 SQL 无歧义。他们没有说空结果会让错误 SQL 判对。

### 第 4 步

「这三个裁过的库、每库 100 条 dev 上，Spider 上训的开源模型零样本很差，加种子和合成数据后仍远低于他们口中的 Spider 高分」：强，Table 5 直接支持，但外推停在这三库。

「82% 掉到 25%–60% 是同一批系统的落差」：弱。Table 5 没有那些榜单系统的同配置 Spider 分，也没跑 Picard 和 RESDSQL。

「合成数据质量高所以不用过滤」：中等偏弱。只在每库 100 条抽查和随后的涨点上成立；等价率最低 75%，他们主动留下噪声。

「第一个复杂真实科学库基准」：弱到中等。范围声明可引用，但相关工作已列 MIMICSQL，SDSS 不是全库。

### 第 5 步

可以相信的是：在 CORDIS、裁过的 SDSS、OncoMX 上，当时能跑通的微调模型零样本执行准确率很低，种子加模板合成能把分抬起来，OncoMX 上 T5-Large 到 0.56，GPT-3.5 在 CORDIS 一点提示到 0.60、在 SDSS 五点提示到 0.33，任务仍未解决。不能写成同一系统从 Spider 的 82% 掉到 25%–60%，也不能写成全库 SDSS 或「真实科学问句」已被这个基准代表。评测就是执行准确率，没有推荐指标。

## 2. SM3-Text-to-Query（NeurIPS 2024 Datasets and Benchmarks）

文件：`papers/sql-recall/01-text-to-sql/SM3-Text-to-Query_NeurIPS2024.pdf`。读了第 1–7 节至结论。附录 A（模式图、提示、模板例）未逐段走。

### 第 1 步

1. 摘要与第 1 节：第一份同时覆盖关系、文档、图，以及 SQL、MQL、Cypher、SPARQL 的医学 Text-to-Query 基准。近亲是 FootballDB（单库内多 schema）和一份 SQL/SPARQL 对照；他们把「四种语言、同一批数据」当成空位。数据是 Synthea 合成病人，默认配置 100 名在世加 10 名已故，不是医院导出。
2. 第 3 节：项目和两家大学医院的人做了一年以上；查询主要由两名本科生和一名博士生写、两名教员核对。第 6 节又写模板 “only created with guidance from health professionals, but not directly formulated by them”。两句都在正文。408 个模板，每种语言 10K 对（6K/2K/2K，按实体分层）。槽值从库里抽病人名、过敏等。Table 2：SQL 平均 9.93 token，Cypher 7.28 token。局限节承认 SQL 和 Cypher 平均不到 10 个 token，可能太容易。
3. Table 3，带 schema 的零样本：SQL 最高是 Llama3-70b 的 47.05；SPARQL 零样本最高是 GPT-3.5 的 3.30。同一张表，SQL 五点提示 Llama3-70b 57.50，GPT-3.5 56.30。他们用 Stack Overflow 帖子数解释语言差距（SQL 673K、MQL 相关 176K、Cypher 33K、SPARQL 6K），并承认 MQL 是反例：帖子多于 Cypher，零样本却更低（Llama3-70b 的 MQL 21.55 对 Cypher 34.45）。
4. 第 5.4 节 Table 4：BM25 从训练集抽 5 个相似问句，GPT-3.5 带 schema，SQL 执行准确率 88.55，比固定五点的 56.30 高 32.25；SPARQL 75.75，Cypher 78.30，MQL 78.70。

### 第 2 步

「四种语言还没有人放在同一批医学数据上」递进到「所以建 SM3」。数据构造与实验是并列：合成库和模板决定了后面的准确率能被相似例抬上去。语言差距的解释是因果尝试（训练语料多少），随即被他们自己用 MQL 转折掉。88.55 不否定 47.05，它依赖另一种例题选择。

### 第 3 步

未写出的依赖：408 个模板的填槽题相互独立；训练集里的相似问句不是同一骨架的金查询；执行结果相同即语义相同；Synthea 加 SNOMED 命名就等于临床问句；四种语言的金查询彼此语义对齐，因此准确率差只来自语言而不是标注难度。

### 第 4 步

「在他们划定的范围内，这是四种语言、三种数据模型的第一份」：中等。范围声明站得住，对照表没有穷尽同时期工作，但是他们点名的近亲确实更窄。

「临床真实问句」：弱。局限节自己否定了「医生直接写题」，数据是合成的。

「零样本 SQL 47.05、SPARQL 3.30 是医学推理上限」：弱。Table 4 换 BM25 例题就到 88.55 / 75.75。模板填槽后，相似例检索会把同一骨架的金查询放进提示。这是泄漏式的高分，不是模型突然学会了医学。

### 第 5 步

可以相信的是：数据模型是一个独立变量，同义问句在四种查询语言上的零样本差距很大；一旦按问句相似度从训练集取例，SQL 可以从固定五点附近的 56.30 升到 88.55。不能把 47% 写成医学 text-to-SQL 的上限，也不能把这批模板实例写成医院里的原话。没有推荐指标。

## 3. BiomedSQL（COLM 2026；arXiv:2505.20321v6，2026-08-12）

文件：`papers/sql-recall/01-text-to-sql/BiomedSQL_arXiv2505.20321.pdf`。页眉是 COLM 2026。读了第 1–8 节至结论。附录中的提示、Table 8 的逐点 few-shot、Table 9 的错误计数没有逐格抄；正文已经给出下面用到的数。

### 第 1 步

1. 摘要与贡献：第一份专门评「科学推理」的生物医学 text-to-SQL，约 68,000 对。Table 1 写 68,227。来源是 40 道专家题，程序填入疾病、基因和 SNP。金 SQL 由一名领域专家写，两名分析员审；审前标注没留下，没有标注者一致率。金 SQL 避免 `SELECT *`，结果帽在 100 行。推理指问句里不出现、SQL 里出现的惯例，例如 `p < 5e-08`。Table 1 的对照是 MIMICSQL、EHRSQL、SM3、BIRD，没有 WikiSQL 或 BookSQL。
2. 评测集是按模板分布抽出的 546 条，不是 6.8 万条全评。Table 3：Gemini-3-Pro 的 EX 58.1（±4.3）、JAC 62.4、RQR 81.8。Table 4：BMSQL-GPT-o3-mini 的 EX 62.6（±4.1）；DAIL-SQL-GPT-o3-mini 61.2，正文写 “margin ... falls within confidence intervals”。专家是两名分析员各做从 546 里抽的 20 条，EX 均值 90.0，JAC 90.0，RQR 95.0。他们写 EX 的 95% 置信区间约 [68%, 99%]，“should be read as an approximate reference”，并写差距在区间下界仍有方向。贡献列表的「25–30 个百分点」用的是 90 减 58.1 或 62.6。
3. EX 被改成 UUID 集合或数值集合相等。JAC 对多返回或少返回仍给分。`stat-instruct` 把统计阈值写进提示；分析节写 BMSQL 的优势之一是应用这些阈值。因此「模型必须自己推断惯例」只对基线提示成立。错误分析：最常见的是选错表，其次是漏掉或用错阈值。10-shot 对 GPT-o3-mini 的 ΔEX 是 +7.8；把 40 个模板全放进提示，收益很小。

### 第 2 步

「schema 看不见统计惯例」递进到「所以要新基准」，再递进到「所以 68,227 对和专家 90% 说明缺口有 25–30 个点」。后半段是转折：评测只在 546 条上，专家只在 20 条上，而且作者自己把专家分标成近似参照。JAC 与 EX 并列，用来承认多条 SQL 可以接近同一答案。阈值写进提示之后，「必须推断惯例」这条因果对 BMSQL 不再成立。

### 第 3 步

未写出的依赖：40 个骨架被填槽后仍是 6.8 万道独立科学问题；100 行帽下的集合相等不会让两条不同过滤撞车；GPT-4o 的 RQR 与专家判断的 Spearman 0.89（100 条回答）足以让 RQR 代表科学正确；BigQuery 方言上的失败可以外推到一般 SQL。

### 第 4 步

「问句不写、SQL 必须写上的统计阈值和试验阶段」：强，作为现象。这和 ScienceBenchmark 的领域词表不是同一件事。

「68,227 与第一」：中等。数字在 Table 1；「最大」「第一」只在该表的对照里成立。

「专家比模型高 25–30 个点」：弱。20 条的点估计是 90.0，区间下界约 68；62.6 对 68 只剩大约五个点，而且模型区间半宽是 4.1。作者写方向仍在，但贡献列表里的 25–30 不能当稳定差距。

### 第 5 步

可以相信的是：在这 546 条、这个 BigQuery 库上，基线提示下 Gemini-3-Pro 的执行准确率是 58.1，BMSQL-GPT-o3-mini 是 62.6，失败里有一批是漏掉 schema 里没有的统计阈值。不能把 40 个模板的域内高分、或 20 条上的专家 90.0，写成科学推理已被测量到差 25–30 个点。没有推荐指标。

## 4. BookSQL（NAACL 2024 长文，页 497–516）

文件：`papers/sql-recall/01-text-to-sql/BookSQL_NAACL2024.pdf`。读了第 1–7 节、局限和伦理声明。附录的库表样本和提示未逐段走。

### 第 1 步

1. 摘要与 Table 2、Table 3：会计库，100k 对，约 100 万行，1 个库、7 张表、27 家企业。第 3.4 节又写 “BookSQL consists of 7,193 Hard SQL queries”，而 Table 3 写 Hard 45,000。两句冲突。问题来自两名财务专家列出的 183 道典型问句，再模板化。划分按模板 70/10/20，测试模板不在训练里。测试集难度是 easy 14.37%、medium 78.43%、hard 7.2%。库按复式记账约束造过，名字被匿名化。
2. Table 1：Spider 上训好的模型直接测 BookSQL 的精确匹配，UniSAr 3.8%，SEDE 0.0%，RESDSQL 10.8%。这是迁移，不是在 BookSQL 上微调。Table 5：微调之后 RESDSQL 精确匹配 51.5%、执行准确率 54.4%，对照它在 Spider 上的 80.5% / 84.1%。GPT-4 只跑了测试集的随机 10%。DIN-SQL+GPT-4 执行准确率 7.6%，动态十例提示加 GPT-4 是 67.2%。Table 6 的 GPT4 列是 Easy 100、Medium 71.35、Hard 22.08，正文没有写这列是 DIN-SQL 还是动态少样本。
3. 第 3.3 节自称第一份有多步嵌套、第一份有大量时间过滤的 text-to-SQL。Table 2 自己列出 Spider 的 NESTED 是 844，BookSQL 的 NESTED 是 4,456。

### 第 2 步

「会计库缺席」递进到「所以要 100k 对」。迁移实验因果地支持「Spider 模型不能直接用」；微调表是另一件事，和迁移表并列，不能串成「所以 GPT-4 仍明显更差」。动态少样本 67.2 高于微调 RESDSQL 的 54.4，这是转折，而且样本不是全测试集。「第一份嵌套」被他们自己的 Table 2 转折掉。

### 第 3 步

未写出的依赖：183 个专家模板的填槽等于会计人员的问句分布；一个 schema 上的分数可以写成会计领域；测试模板不可见就等于问法不可见（槽值和时间表达仍可能重合）；执行准确率等于账目正确。GPT-4 的 10% 子集被放进与全量微调同一张表，隐含这个子集代表全测试集。

### 第 4 步

「零样本迁移很差」：强，Table 1，指标是精确匹配。

「微调后 GPT-4 仍有明显差距」：弱。只对 DIN-SQL 的 7.6% 成立；动态少样本 67.2% 更高，且只评了 10% 测试题。Table 6 的 GPT4 列归属不明。

「100k 与 7,193 道 hard」：不能同时当精确规模。二者都印在论文里，彼此打架。

「第一份嵌套」：弱。Table 2 已列 Spider 844 条嵌套。时间过滤作为这个库的特征可以保留。

### 第 5 步

可以相信的是：Spider 上训好的三个模型，精确匹配迁移到 BookSQL 只有 0.0–10.8；划分按模板，测试骨架不在训练里。不能把 100k 和 7,193 道 hard 同时当成精确规模，也不能把 10% 子集上的 GPT-4 分数写成全测试集结论。没有推荐指标。FINCH 后文对这个库的金 SQL 做了执行检查，见第 6 篇。

## 5. FinSQL / BULL（读的是 arXiv:2401.10506v1；ACM 页眉在 PDF 里仍是 Conference’17 占位）

文件：`papers/sql-recall/01-text-to-sql/FinSQL-BULL_arXiv2401.10506.pdf`。读了引言、相关工作、问题定义、第 5 节数据、第 6 节前半的增强动机、第 9 节全部实验和结论。LoRA 合并公式和提示模板没有逐式推导。

### 第 1 步

1. 摘要：此前没有实用金融基准；BULL 有 4,966 对。第 5.1 节：基金、股票、宏观经济，表数分别为 31、28、19（对应 China A-Shares、公募基金、中国宏观经济）。Table 1 的平均数是每库 26 张表、390 列。图 2 注：单表平均列数约 14.0 与 14.4，最大列数 30 与 29。第 5.2 节：恒生的人 “work together for more than one week”，金融人员和数据科学家写 4,966 道中文问题，工程师写 SQL，三名实习生核对并译成英文。实验节划分：基金 1744/405，股票 1672/464，宏观 550/131，加总 4,966。
2. Table 4，英文执行准确率：FinSQL+LLaMA2 82.2，FinSQL+T5 81.5，Picard\*+T5 79.3，DAIL-SQL+GPT-4 75.0。GPT-4 方法只评了 20 条，ChatGPT 方法 100 条；DIN-SQL+GPT-4 因超过 8192 token 没有准确率，只估了价格。T5 系基线先被他们的交叉编码器裁到 3 张表、7 列，表上标了星号。Table 6：英文 schema 链接 AUC 表 0.9984、列 0.9979。Table 7：英文表 R@3 是 99.1%。
3. 摘要和贡献写跨库少样本最高提升 36.64%。第 9.5 节：基金和股票的 LoRA 平均合并，再在宏观经济上做 k-shot，对照从零训练的 LoRA。10-shot 时四个模型分别高 36.64%、35.87%、34.35%、21.37%。零样本合并相对从零 LoRA：LLaMA2 50.39%，Baichuan2 29.77%，T5 47.33%，mT5 24.57%。交叉编码器也用了 “varying amounts of macro data”。图 13 是曲线，正文没有给出各 k 的绝对执行准确率，这里不从图上读数。Table 9：去掉输出校准，英文从 82.2 到 80.7，差 1.5 个点。

### 第 2 步

「库又宽又缺基准」递进到「所以 BULL + FinSQL」。主表 82.2 与 36.64% 是并列的两套实验，不是同一张表的涨点。36.64% 因果地依赖「合并 LoRA 对从零 LoRA、宏观库、10-shot」。AUC 接近 1 与「宽表很难链接」形成转折：分类器是在这批库上训练的，高 AUC 说明这个划分容易，不能说明跨库链接。

### 第 3 步

## 20. Spider 2.0（ICLR 2025；arXiv:2411.07763v2，2025-03-17）

文件：`papers/sql-recall/01-text-to-sql/Spider2.0_arXiv2411.07763.pdf`。读了摘要、引言的任务定义、第 2.2–2.3 节的标注与 Table 2、Table 6 的成功率，以及结论里复述 21.3% 的句子。45 页里的改写示例附录和动作空间表没有逐条走。

### 第 1 步

1. 632 个企业工作流任务。Table 2 的列是测试题数、测试库数、每库列数、每条 SQL 的 token 数、每条 SQL 的函数数。Spider 2.0 全体是 632 题、213 个库、每库 743.5 列、每条金 SQL 148.3 token；lite 是 547 题、803.6 列、144.5 token；snow 是 547 题、812.1 列、161.8 token。正文写 “an average of 812 columns”，下一句写 “each ground-truth SQL query contains 144 tokens”。812 落在 snow 的列数上，144 更接近 lite 的 144.5，而不是 snow 的 161.8，也不是全体的 148.3。任务要读项目代码、方言文档和数据库接口，可以是多条 SQL，不只是「给 schema、写一条 SQL」。Table 3 里的 135（21.36%）是带 SQLite 的任务占比，不是做对的题数。标注节写第一轮校验发现 45% 的例子有错，第二轮之后剩 5%，然后他们说已全部改完。
2. 摘要：基于 o1-preview 的代码智能体只解决 21.3%，对照 Spider 1.0 的 91.2% 和 BIRD 的 73.0%。引言把 91.2 和 73.0 归给 “methods based on GPT-4” 在 Spider 1.0 和 BIRD 上的执行准确率，不是这个 o1-preview 智能体的同配置分数。Table 6：Spider-Agent 加 o1-preview 的成功率是 21.36%。

### 第 2 步

「企业库又大又方言化」递进到「所以现有执行准确率不够」。21.3% 与 91.2/73.0 被摘要放进一个比较，引言把后两个数的主语换成别的方法，这是转折，不是同一系统的落差。

### 第 3 步

未写出的依赖：「平均 812 列」和「平均 144 token」描述同一个子集；91.2 和 73.0 是这篇智能体在旧榜上的分数；企业工作流的难度可以背书给只有几张窄表的库。

### 第 4 步

「企业库大、方言多、任务含项目上下文」：强，以 Table 2 的分子集数字为准。单一的「812 列、144 token」不成立为同一个子集的一对平均数。Table 3 的 21.36% 是 SQLite 任务占比，不能写成做对率。

可以引用它说明 Spider 式的单条 SQL 执行准确率不是企业工作流的难度。物品-用户-交互库若只有几张窄表，不能用 Spider 2.0 的难度给自己背书。智能体设定还要读代码和文档。

## 21. Arctic-Text2SQL-R1（ACL 2026 Findings，页 26966–26995）

文件：`papers/sql-recall/01-text-to-sql/Arctic-Text2SQL-R1_ACL2026-Findings.pdf`。读了摘要、第 3 节奖励定义、Table 的列头与 7B 行、结论和局限全文。训练曲线和提示附录没有逐段走。

### 第 1 步

1. 奖励只看执行：结果与金标对齐得 1，SQL 可执行但结果不对得 0.1，否则得 0。相关工作说更碎的奖励会被钻空子。局限节明确写：因为只按执行结果打分，GRPO 仍可能奖给在某个库实例上碰巧结果相同的语义错误查询；他们用去掉空结果、无序结果的弹性比较、以及加厚合成库来降低这种偶然，并写完全避免假阳性仍是开放问题。
2. 正文与结论：32B 在 BIRD 测试榜上执行准确率 71.83%，自洽后 73.84%。表头把 BIRD 标成 (dev)、SPIDER 标成 (test)。Arctic-Text2SQL-R1-7B 一行是 BIRD 68.9、SPIDER 88.8、Spider2.0-SQLite 15.6、Spider-DK 81.5、EHRSQL 36.7、Science Benchmark 51.8、平均 57.2。同表 ExDPO-70B 的 BIRD（dev）是 68.5，不是 7B 的测试分。同表 OmniSQL-7B 的 Spider2.0-SQLite 是 13.3，Science Benchmark 是 50.2，平均 54.4。
3. 平均 57.2 高于同表 OmniSQL-7B 的 54.4，正文写也高于 DeepSeek-V3 的 55.6、GPT-4-Turbo 的 55.6 和 GPT-4o 的 55.9。这是六基准平均。Science Benchmark 的 51.8 是一列平均，不是 ScienceBenchmark 原论文里按库拆开的 0.60 或 0.33。

### 第 2 步

「碎奖励会投机」递进到「只用执行对错」。局限节转折了这条因果：执行对错本身也会把碰巧相同的错 SQL 写进策略。六基准平均高于同表的 GPT-4o，不递进到「每个科学库都已解决」，也不递进到「7B 的 68.9 是 BIRD 测试集」。

### 第 3 步

执行匹配等于语义等价这一点，局限节已经写明不成立，所以不能再算成未说出的假设。未写出的依赖是：去掉空结果和加厚合成库之后，榜单上的执行准确率仍然可以称为 “accurate SQL”；六基准平均的权重是均等且有意义的；同表里 OmniSQL 的 13.3 与 OmniSQL 论文自己的 10.4 可以不经说明地互换。后一个矛盾来自两篇 PDF，不是 Arctic 单独能消掉的。

### 第 4 步

「训练配方是 GRPO 加执行奖励」：强，作为方法事实。

「奖励等于 SQL 真的写对了」：弱。局限节自己否认了完全等同。

「7B 的 BIRD 68.9、Spider 测试 88.8、Spider 2.0-SQLite 15.6」：强，按他们的表，且 68.9 是开发集。把 68.9 写成 BIRD 测试 68.5 不成立；68.5 是同表另一行的开发集。

「六基准平均 57.2 高于同表若干大模型」：中等，限于这张表的平均。不能写成每个库都已解决。

### 第 5 步

本地 7B 生成器用这篇的检查点是工程选择，不是评测结论。论文主指标不能只用它的训练奖励。Spider 2.0-SQLite 的 15.6 说明这个 7B 一到多方言、大 schema 就不再是 BIRD 开发集上的 68.9。引用 OmniSQL 的 Spider 2.0 分数时要标明是 Arctic 表里的 13.3 还是 OmniSQL 表里的 10.4。

## 重新整理后的创新点

下面只留第 4 步里强或中等、而且范围没有被同一篇推翻的主张。

1. 换库会让在 Spider 上训练或成名的系统变差，但必须带配置。ScienceBenchmark 的 Table 5 是另一批开源模型的零样本和加数据后的执行准确率，不是「82% 掉到 25%–60%」。BookSQL 的 Table 1 是精确匹配迁移，0.0–10.8。Spider 2.0 的 21.3% 是企业工作流智能体，不是同一套 Spider 系统。
2. 问句里不写、SQL 里必须写的领域惯例是真实缺口。BiomedSQL 用 `p < 5e-08` 这类阈值把这件事从「领域词表」里分开。40 个模板和专家 90.0 没有留下来。
3. 执行准确率会把错查询判对，也会把对查询判错；金 SQL 也会错，而且会改名次。FLEX 的 Table 3：EX 对专家共识的 kappa 是 62.00。Jin 等：修正子集后 16 个系统的相对执行准确率从 −7% 到 31%，名次最多动 9 位。Wretblad 等：金融开发集 106 条里 22 条金 SQL 有错。21/17 的子集归属、Figure 3 的未抽出百分比，没有留下来。
4. 错答比拒答更贵时，排名会变，而且高执行分可以和很差的可靠性分同时出现。TrustSQL 的公式 (1) 把 c=0、只看可行题定义成执行准确率。EHRSQL 2024 第一名 RS(0) 88.17、RS(N) −711.83。OMOP 最好检查点执行准确率 93.55，RS(10) 只有 0.373。Query Carefully 在 80 题上把缺值和列歧义从「显然不可答」里分开，功效弱，只留现象。
5. 纯 SQL 盖不住需要外部知识或自由文本的问题，但现有分数不是推荐召回。Binder 在 WikiTQ 上相对 Codex SQL 从 61.1 到 64.6。SUQL 的 Table 5 是返回集合的人工精度。TAG 的 0.55 是 80 道改写题上的手写上界。H-STAR 和 BlendSQL 说明「不是每题都进 SQL」和「SQL 里调用模型」已经有人做，涨点不大或口径不可比。

没有留下来的，是把上述任何一篇的执行准确率、作者判定的约束满足、或可靠性分，写成推荐的 Recall、NDCG 或 Hit。抽取文本里这三个名字都没有出现。

## 这一路的结论

挤满的是三件事。第一，专家写几十到几百个模板，程序填槽或让模型改写，再报一个新领域上的执行准确率。ScienceBenchmark、SM3、BiomedSQL、BookSQL、FinSQL、EHRSQL、OMOP 都是这个骨架。OMOP 的域内 LoRA 已经把这种设定做到测试执行准确率 93.55，未微调的同一底座是 10.54。SM3 的 Table 4 说明，模板填槽之后用训练集里的相似例，还能把 SQL 从 56.30 抬到 88.55。只把推荐库说成又一个领域，并报域内执行准确率，写不进创新点。

第二，不可答题、拒答令牌、以及错答比拒答更贵的可靠性分。EHRSQL、TrustSQL、EHRSQL 2024、OMOP、Query Carefully 已经把「知道何时不写 SQL」占住。再把拒答写成主创新，没有空位。

第三，SQL 只是中间表示，分数看答案对不对或约束满不满足，纯 SQL 不够就在查询里调用模型。Binder、SUQL、TAG、H-STAR、BlendSQL 是这一组。SUQL 已经在公开餐馆表上做了「返回的物品是否满足话语里的每条约束」，指标是作者判定的集合精度，上限 3 家，对话还是在他们自己的代理上收集的。若主指标改成同一种人工判定，会被看成缩小复制。

空着的是：在用户、物品、交互表上，由模型写出 SQL，把执行结果当作候选，用留出交互上的 Recall 或 NDCG 打分，并单独报告错误 SQL 被执行的代价。这一路没有这篇。写的时候不能把空位说成「原文已经证明主指标必须是推荐效果」。原文证明的是执行匹配和金标都会排错名次，以及用户最终看到的不该只是 SQL 字符串。推荐指标是把「打用户任务」落到推荐上的推论。

还要防三件会被审稿人抓住的写发。标签若由一条 SQL 算出，Recall 就退回执行匹配，Jin、FLEX、Wretblad 都适用。模板、单库和相似例会制造高分，SM3、EHRSQL、BookSQL、BiomedSQL、OMOP 都适用。用执行对错训练的生成器会把碰巧相同的错 SQL 写进策略，Arctic 的局限节自己写了这件事；无约束子集上的召回不衡量缺值、列歧义和越权 SQL。
