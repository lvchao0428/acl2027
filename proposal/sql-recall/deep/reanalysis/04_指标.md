## 1. LIMIT（arXiv 2508.21038v2，ICLR 2026）

### 1. 逐段论点

摘要的主张是：单向量嵌入能表示的 top-k 文档组合数受维度限制；这个极限会在「极简单的查询」上出现，不需要不现实的查询。他们把已知的学习理论结果接到检索上：某个查询能返回的 top-k 子集个数，被嵌入维度卡住。

第 3 节把这件事写成定理。单位文档向量、单位查询、间隔 γ。一个 k-子集被间隔 γ 实现，当且仅当存在查询向量，使相关文档的内积比无关文档至少高出 2γ。若每个 k-子集都要被这样实现，则 \(\binom{n}{k} \le (1+1/\gamma)^d\)。表 1 用 γ=0.1（分数间隔 2γ=0.2）给出下界：n=100、k=2 时维度下界是 4。他们同时写明这是极端下界，梯度、分词、泛化都会把实际需要的维度抬高。

第 4 节用自由向量检验这个下界是不是只对「没训练好」成立。查询向量和文档向量直接对测试 qrel 做 Adam + InfoNCE，全数据当一个 batch，早停 1000 步无改进。k=2，把 n 加到优化不再能到 100% 准确率，称为 critical-n。拟合的三次多项式是 \(y=-10.5322+4.0309d+0.0520d^2+0.0037d^3\)（\(r^2=0.999\)）。外推：512 维约 50 万篇，768 维约 170 万，1024 维约 400 万，3072 维约 1.07 亿，4096 维约 2.5 亿。附录表 6：d=12 时 critical-n=47，d=18 时 critical-n=99。他们用这组对比表 1：n=100 的理论下界是 4，自由向量却要 d>18，大约 4.5 倍。这个实验故意在测试 qrel 上过拟合，作者写明不能泛化到新数据。

第 5.1 节把 QUEST 拿来当对照，说明现有评测只覆盖组合空间的一小块。QUEST 有 32.5 万篇文档、每条查询 20 个相关文档、3357 条查询；全部 top-20 组合是 \(\binom{325000}{20}=7.1\times 10^{91}\)。他们的结论是：评测集少采样，是标注成本，不是这些组合不存在。

第 5.2 节故意把难度从算子上拿开。原句：与 QUEST、BrowseComp 那种算子难度相反，他们选很简单的查询和文档，好让难度落在 top-k 集合本身。构造约束有两条：每个用户属性少于 50 个；每条查询只问一件事，即 “who likes X”。属性表由 Gemini 2.5 Pro 生成并清到 1850 项，并用 BM25 的失败检查避免词面重叠。语料 5 万篇、1000 条查询、每条恰好 2 个相关文档。相关矩阵取 46 篇文档的全部两两组合：\(\binom{46}{2}=1035\)，再配 1000 条查询。全库里这 46 篇之外约 4.995 万篇对任何查询都不相关。另做一个只有这 46 篇的 small 版。

全库表 5（图 3）：BM25 的 Recall@2 / @10 / @100 是 85.7 / 90.4 / 93.6。最好的单向量 Promptriever-4096 的 Recall@100 是 18.9。正文说全库上模型连 20% 的 Recall@100 都难达到。GTE-ModernColBERT 的 Recall@100 是 54.8。

46 篇小集合表 4（图 4）：BM25 的 Recall@2 / @10 / @20 是 97.8 / 100.0 / 100.0。GTE-ModernColBERT 是 83.5 / 97.6 / 99.1。Promptriever-4096 的 Recall@2 是 54.3，GritLM-4096 是 38.4，Qwen3-4096 是 19.0。正文说最好的嵌入 Recall@2 不到 60%。图 6 把这几个 Recall@2 印成 BM25 97.8、GTE 83.5、Promptriever 54.3、GritLM 38.4。

域偏移实验（表 3，图 5）：在训练集上微调，Recall@10 最高到 2.8（1024 维）；在测试集上过拟合可以到很高（1024 维 Recall@2 96.5）。作者写：自由向量实验说明 N=46 用 12 维就嵌得下，真实模型 64 维仍然做不完。

同义词版：把语料里的属性换成不重叠的说法。正文写 BM25 掉了 89% 以上，Qwen3 掉 38.9%。词法模型反过来差于多数单向量。同义词柱在 PDF 抽取里和原词柱串在一起，除这两句百分比外，不把单个柱子改派给某个模型。

交叉编码器：把 46 篇和 1000 条查询一次给 Gemini-2.5-Pro，1000 条全部做对（100%）。对照是最好嵌入的 Recall@2 不到 60%。

附录表 2 把 qrel 当成图。LIMIT 的图密度 0.085481，平均查询强度 28.4653。对照：NQ 两个都是 0；HotpotQA 0.000037 和 0.1104；SciFact 0.001449 和 0.4222；FollowIR 的 Core17 是 0.025641 和 0.5912。

结论把出路写成交叉编码器、多向量、高维稀疏，以及尚未出现的单向量结构。没有查询语言。

### 2. 逻辑关系

递进：维度下界 → 自由向量在测试 qrel 上仍然卡住 → 用自然语言把同一张满组合矩阵做成 LIMIT。转折在第 5.2 节：表面句式是 “who likes Apples?”，难度被作者从算子上挪到组合矩阵上。再一处转折是同义词：原字符串上 BM25 接近做对，换说法后词法崩溃。

这篇没有从「这张 qrel 上嵌入失败」滑到「推荐约束上嵌入失败」。滑的是我们若把 “who likes X” 当成购物或观影请求。作者自己把 LIMIT 和 QUEST、BrowseComp 分开：后者难在算子，LIMIT 难在被填满的相关组合。

### 3. 隐含假设

单向量、固定维、带间隔的最近邻，就是要被否定的检索器。一张穷尽的组合 qrel 被当成「任何用户都可能问到的相关集」。属性先写成不重叠的字符串，词法匹配才会接近完美；这个条件和「喜欢已经是一列」不是同一件事。自由向量能在 12 维嵌下 46 篇，只说明表示容量在无语言约束时够，不说明推荐系统会被要求把 46 个物品的全部两两相关集塞进一个向量。

### 4. 证据

容量主张是强的：定理、自由向量、46 篇和全库两张表、同义词对照、Gemini 一次看完全部文档能做对，条件都写在论文里。转到推荐 SQL 是弱的，而且是范畴错误。SQL 不会被拿来解这个容量问题。`WHERE liked = 'apples'` 只有在「喜欢」已经是列时才精确；属性只活在句子里、又被换成同义词时，SQL 和 BM25 一起失效。

### 5. 引用边界

允许：固定维单向量表示不了全部带间隔的 top-k 组合；LIMIT 的相关集是 46 篇的全部两两组合，图密度 0.085481、平均查询强度 28.4653，高于 FollowIR Core17 的 0.025641 和 0.5912；小集合上 BM25 Recall@2 是 97.8，最好的单向量 Promptriever-4096 是 54.3；全库 Promptriever-4096 的 Recall@100 是 18.9，BM25 是 85.7 / 90.4 / 93.6；同义词版作者写 BM25 掉 89% 以上。

不允许：LIMIT 说明嵌入搞不定推荐式查询；“who likes Apples?” 是推荐召回的反例；因此该换成 SQL。

## 2. Text2VectorSQL（arXiv 2506.23071v2）

### 1. 逐段论点

摘要把任务定义成：自然语言到同时含 SQL 谓词和向量检索的 VectorSQL。生态系统是合成数据、VectorSQLBench（3 个后端 × 4 个数据源 = 12 组），以及「召回退化」：SQL 过滤和向量搜索套在一起，会比传统过滤向量搜索漏掉更多正确结果。

第 II 节把执行分成两档，对照条件是顺序。预过滤：先用 SQL 得到子集，再在子集里做向量搜索。作者称为高保真，代价是可能让 ANN 索引失效、退成扫描。后过滤：先做 ANN，再把 SQL 谓词套到向量结果上。作者称为快，但真邻居可能不在先取出的候选里。

引言给出唯一一句百分比：复杂查询涉及 JOIN 时，后过滤可以静默丢掉 30% 以上的正确结果。这句的对照对象是「传统过滤向量搜索」，但没有在引言里给出那一对原始召回。

第 III-A2 节把向量和 SQL 的耦合分成三档，这是后面唯一的对照轴：

- Non-integration：向量搜索单独做，主键再通过 `WHERE IN` 或一次 JOIN 接回主查询。
- WHERE-integration：向量搜索发生在已经被 `WHERE` 滤过的子集上。
- JOIN-integration：向量搜索发生在表已经和其他表连接之后，过滤条件来自相关表。作者写这一档最容易让后过滤失败。

金标准故意不用后过滤。每条问题采五个 VectorSQL 变体，全部用预过滤执行，再用倒数排名融合得到 \(R_{gold}\)。作者写：对 VectorSQL，他们把预过滤的执行结果当作 ground truth。

VectorSQLBench 表 I：2997 条，来自 BIRD、Spider、arXiv、Wikipedia 上的向量列，不是推荐 qrel。向量耦合计数：Non 969、WHERE 1005、JOIN 1023。

第 IV 节唯一一对召回数字：ClickHouse 上，UniVectorSQL-7B 的召回 “degrades by more than 30% (from Non-integration’s 0.6 to JOIN-integration’s 0.4)”。0.6 到 0.4 是同一套后过滤后端上、不同查询类别之间的下降。相对下降是三分之一，绝对下降 0.2。对照不是同一批查询的预过滤对后过滤。WHERE 被说成从 Non 落到 WHERE、再在 JOIN 上陡降，正文没有给 WHERE 的数字。PostgreSQL 因为 pgvector 的迭代索引扫描，退化「much less severe」，也没有数字。图 5 的对象是 Claude-4-Sonnet、OmniSQL-32B、UniVectorSQL-7B，后端是 PostgreSQL 和 ClickHouse。

训练数字是另一件事，不能焊进 30%。表 III：纯 SynVecSQL 的 UniVectorSQL-7B 在 BIRD-dev 上执行准确率 58.2，VectorSQLBench 上 nDCG@k 39.3；OmniSQL-7B 对照是 63.9 和 22.5。表 IV：32B 带 CoT 的平均 nDCG@10 是 42.7，不带是 39.5。

### 2. 逻辑关系

递进：任务定义 → 两种执行顺序 → 三档耦合 → 用预过滤当金标准 → 在后过滤后端上按耦合档位看召回。转折在引言：从「后过滤比过滤向量搜索漏得更多」滑到「JOIN 上丢掉 30% 以上」，再被正文的 0.6→0.4 接住。接住的对照变了。WHERE 被放进叙述，但没有数字。

这篇没有把失败写成推荐约束。数据是 VectorSQLBench 的混合查询执行结果。

### 3. 隐含假设

金标准等于预过滤执行结果，所以「SQL 写对了」和「用户觉得相关」被当成同一件事。后过滤的 k′ 取多大、谓词选择率多高，正文的 0.6 和 0.4 没有分开报。把 ClickHouse 上的类别差写成一般的「SQL 后过滤」，等于假设后端、模型和 JOIN-integration 都可以拿掉。

### 4. 证据

「两种顺序都要测、JOIN 耦合比单表 WHERE 更危险、后过滤会静默漏结果」是中等偏强：定义、金标准协议和一对数字都在。把 30% 写成对预过滤基线已经量过的一般跌幅，是弱的，推理漏洞就在引言和第 IV 节的对照对象不一致。数据也不是推荐 qrel。

### 5. 引用边界

允许：ClickHouse 上，UniVectorSQL-7B 从 Non-integration 的召回 0.6 降到 JOIN-integration 的 0.4；引言把 JOIN 上的后过滤概括为丢掉 30% 以上正确结果；WHERE 没有这个数字；PostgreSQL 的迭代扫描轻得多；预过滤被写成高保真。先导实验两种顺序都报，漏召回用自己的 qrel 算。

不允许：SQL 后过滤相对过滤向量搜索会丢掉 30% 以上正确结果，当作推荐召回上的预期跌幅；任意一条带 JOIN 的 SQL 都有这个跌幅。

## 3. NevIR（arXiv 2305.07614v2）

### 1. 逐段论点

主张：神经检索不懂否定。数据是 2556 对只差一处关键否定的文档，众包查询使每条查询只和其中一篇相关。指标是成对准确率：两条查询都把对的那篇排在前面。随机基线是 25%，因为两对独立，期望是 \(\tfrac12\times\tfrac12\)。

表 2。没有一个双编码器超过 12%：从 DPR 6.8% 到 multi-qa-mpnet 11.1%，多数在 5%–10%。稀疏：TF-IDF 2.0%，SPLADEv2 ensemble-distill 8.0%、self-distill 8.7%。晚期交互：ColBERTv2 13.0%，ColBERTv1 19.7%。交叉编码器里 MonoT5-base 34.9%，MonoT5-3B 50.6%。正文原句：“No bi-encoder architecture scores higher than 12% paired accuracy ... with most models performing in the 5-10% range.”

TF-IDF 低是标注协议造成的：标注者不能使用只出现在一段里的词，所以关键词 `NOT` 也做不对。作者注明 2% 而不是 0%，是因为界面没有禁掉部分匹配（version / versions）。人类在 10 个随机测试实例上，三名标注者全部排对。继续在对比否定上微调能涨，离 100% 仍有大缺口。

### 2. 逻辑关系

并列：架构表达力越高，成对准确率越高，但几乎所有模型仍低于随机。转折：MS MARCO 上很强的模型，在这个对比对上失败。没有滑到推荐约束。否定活在自由文本的对比段里。

### 3. 隐含假设

「两篇只差否定、查询不能用独有词」代表用户的否定需求。这比「不要某品牌」更苛刻，也比「类型列上的 `NOT IN`」更不能写成谓词。

### 4. 证据

「双编码器在这种对比否定上低于随机」是强的，表 2 和随机 25% 的定义对齐。把它记成 SQL 的胜利是弱的：类型、品牌已经成列时，`WHERE NOT` 可以做；否定还在句子里时，SQL 没有可执行的谓词。

### 5. 引用边界

允许：这种对比否定上，没有一个双编码器的成对准确率超过 12%，多数在 5%–10%，随机是 25%；MonoT5-3B 是 50.6%。

不允许：推荐里的否定因此该交给 SQL；NevIR 的失败是嵌入在约束推荐上的失败。

## 4. ExcluIR（arXiv 2404.17288）

### 1. 逐段论点

主张：排除性查询（要 A 不要 B）是检索上被忽略的失败，而且独立于一般否定来研究。评测集 3452 条人工标注的排除性查询；训练集 70293 条，每条配一个正文档和一个负文档。例子是 “besides Avengers: Endgame”。

指标是 R@N、MRR，以及正负文档之差 ΔR@N、ΔMRR，再加 RR（正文档排在负文档前的比例）。随机 RR 是 50% 量级。

表 1（HotpotQA 上训练）：BM25 在 ExcluIR 上 R@1 49.68、MRR 65.17、ΔR@1 7.82、ΔMRR 4.66、RR 53.48。DPR 的 RR 54.02。表 2（NQ320k 上训练）：BM25 的 ExcluIR 格子与表 1 相同（稀疏模型不随训练集变）。Sentence-T5 的 RR 67.83、ΔR@1 32.90；GTR 的 RR 68.31、ΔR@1 34.85。正文写：几乎所有模型的 RR 只比随机高不到 10 个百分点；NQ 上最好的 Sentence-T5 和 GTR 仍远未理想，因为负文档被排得很高。BM25 和 DocT5Query 的 RR 是 53.48 和 53.85，只略高于随机。作者把原因写成词法匹配抓不住排除短语。

扩域（表 3）对双编码器有一点帮助，对 ColBERT 和 SEAL 不稳定。作者的补救是把排除性训练数据加进去，以及生成式检索；不是查询语言。

### 2. 逻辑关系

并列三种架构，再递进到训练数据。转折：标准问答集上好看，ExcluIR 上 RR 接近随机。没有滑到推荐约束。论文自己的电影例子是排除某部片子，被排除的是标题字符串，不是目录里的列。

### 3. 隐含假设

生成的「要 A 不要 B」代表用户排除。负文档和正文档共享大量词，所以词法系统会被负文档吸引。若被排除的属性已经是列，这个假设不成立。

### 4. 证据

「现有检索器在这批生成的排除查询上接近随机」是中等：RR 和 Δ 的定义清楚，但是语料是生成的，人工只标注了 3452 条评测。不能把这篇的失败直接记成 SQL 的胜利。列上的 `NOT IN` 或差集可以精确做；评论里的感官描述写不出谓词。

### 5. 引用边界

允许：在这批排除性查询上，BM25 的 RR 是 53.48，NQ320k 上训练的 GTR 是 68.31，作者认为仍远未理想。

不允许：排除性推荐约束因此该换成 SQL。

## 5. NumConQ（BDMA 2026，DOI 10.26599/BDMA.2025.9020047）

### 1. 逐段论点

摘要：稠密检索器在数值约束上只有 16.3% 的准确率；NC-Retriever 相对当时最好方法，Recall@10 相对提高 65.84%，Precision@10 提高 78.28%。数据集多于 6500 条查询，五个域。表前统计总数 6577 条查询、5362 篇文档。

第 3.2 节写明文档来自结构化条目：Diabetes、Leagues、QS、Olympics、IMDB。文档用模板把字段填进句子，例如联赛的年份、收入、观影人数、薪资。查询是 “哪位运动员身高 185cm” 这类。数值还在原表里。

16.3% 的正文位置在第 3.4.1 节，不是全基准、也不是全部检索器。实验是 Olympics 加上 Contriever，看 top-10 里约束一致的比例。身高、体重、年龄的一致性平均 16.3%；性别、国家、项目、奖牌等非数值属性平均 73.64%；混合的 Games（年份加赛季）是 59.42%。摘要把这句收成「最先进的稠密检索器只有 16.3%」。

表 3 是全 NumConQ、各检索器自己的 Recall 和 Precision，另一格。BGE-M3 的 Recall@10 是 40.37%，Precision@10 是 10.45%。BM25 的 Recall@10 是 28.93%。NC-Retriever 是 66.95% 和 18.63%。表内 Relative gain 的 Recall@10 是 +38.73，对的是最好基线 Contriever-finetuned（48.26），不是 BGE-M3。摘要的 65.84% 对得上相对 BGE-M3 的 Recall@10（40.37 到 66.95）；78.28% 对得上相对 BGE-M3 的 Precision@10（10.45 到 18.63）。两套分母不能混用。

四位数字是图 4 的切片。正文写 BGE-M3 在四位数字上 Recall@10 62.8%、Precision@10 12.4%。不要和表 3 的 40.37% 混用。

作者的补救是 NC-Retriever：两阶段对比学习加混合数字表示，仍然是稠密检索器。结论写数值差来自长数字的分词不一致，以及训练时不重视数值属性。BM25 差被归因于数字分词和缺少数量级。

### 2. 逻辑关系

递进：结构化记录改写成句子 → 稠密检索器在数值一致性上差 → 再训练一个稠密检索器。摘要把「Contriever、Olympics、身高体重年龄」滑成「最先进稠密检索器、数值约束满足」。这篇没有写推荐系统，但收入、薪资、身高、上映年就是推荐里常见的数值谓词。滑到「整个召回换成 SQL」是引用时才会发生的。

### 3. 隐含假设

把表填进模板句之后，检索器仍该从句子里读出比较关系。原表还在时，这个假设不必要：数值比较是 SQL 的工作。一致性是 top-10 文档里匹配约束的比例，不是「返回集合恰好是满足谓词的全集」。

### 4. 证据

「文本化之后的数值属性上，Contriever 的一致性远低于非数值属性」是强的，16.3% 对 73.64% 的条件写在第 3.4.1 节。摘要的外推是中等偏弱。NC-Retriever 的相对涨幅要看分母。支持「数值谓词不要交给嵌入」，不支持「整个召回换成 SQL」。

### 5. 引用边界

允许：Olympics 上 Contriever 对身高、体重、年龄的一致性平均 16.3%，非数值属性平均 73.64%；全表 BGE-M3 的 Recall@10 是 40.37%、Precision@10 是 10.45%；四位数字切片的 Recall@10 是 62.8%。文档由结构化条目改写而来。

不允许：所有稠密检索器在推荐数值约束上只有 16.3%；因此召回应全部换成 SQL。

## 6. QUEST（ACL 2023）

### 1. 逐段论点

主张：带隐式交、并、差的实体查询，现有检索器做不到穷尽召回。3357 条自然语言查询，映射到维基实体文档。查询由维基类别名按模板合成（例如 A 差 B 再交 C），再由众包改写。推理时不给类别图，强迫系统从正文里找证据。平均答案集大小 10.5。约 69% 的实体有完整证据，约 30% 只有部分证据。

任务是预测相关实体集合。主指标是逐例 F1 的平均。另报平均召回，以及 MRecall：候选集包含全部相关文档的查询所占比例。

表 4，检索器本身。T5-Large 双编码器平均 Recall@100 是 0.476，MRecall@100 是 0.142。T5-Base 双编码器是 0.455 和 0.127。BM25 是 0.197 和 0.037。双编码器高于 BM25。

表 3 是检索加分类器、只看 top-100 候选之后的集合指标。最好的一行是 T5-Large 双编码器加 T5-Large 分类器：平均 Precision 0.165，Recall 0.368，F1 0.192。BM25 加 T5-Large 分类器的 Recall 只有 0.168。正文写：检索器的 Recall@100 给整个系统封顶，0.476 再被分类器压到 0.368，而 Precision 只有 0.165。

错误分析：假阳性常来自忽略否定约束或忽略合取。查询例是 “shorebirds that are not sandpipers”、“science-fiction films shot in England”。

### 2. 逻辑关系

并列：检索和分类都难；合取和差集更难。转折：双编码器仍然高于 BM25，所以这篇不是词法全面胜出。0.142 是 MRecall，不是宏平均召回；宏平均召回是 0.476 那一列。没有滑到推荐，但电影、书是领域之一，相关集来自类别成员，不是观影反馈。

### 3. 隐含假设

维基类别的集合运算是用户查询。文档是正文。SQL 要做这些运算，先得有实体—属性表；论文故意不给这张表。

### 4. 证据

「隐式集合运算上，T5-Large 双编码器的穷尽召回差」是强的，表 4 的两个指标分开定义。外推到「SQL 应替换推荐召回」是弱的。

### 5. 引用边界

允许：T5-Large 双编码器平均 Recall@100 是 0.476，MRecall@100（候选集含全部相关文档的查询比例）是 0.142；同一张表上 BM25 的 Recall@100 是 0.197，双编码器更高。

不允许：把 0.142 叫成宏召回；把 QUEST 写成推荐约束上嵌入失败，或写成 SQL 已经胜出。

## 7. FollowIR（NAACL 2025）

### 1. 逐段论点

主张：检索模型把 TREC 的叙事指令当关键词，跟不住指令改写后的相关集变化。数据来自 TREC 给专业标注员的 narratives。新指标 p-MRR：同一查询配上改写后的指令，看相关文档的名次是否按新指令移动。范围从 −100 到 100，忽略指令时的中性变化记 0。nDCG 会被「根本不看指令」刷高，所以不够。

正文原句：“current models generally fail to follow instructions in retrieval unless they are 3B+ parameters or have not been trained for retrieval.” 表 2 的说明重复这一点：一般只有 3B 以上，或没有按检索任务训练过的指令模型，p-MRR 才为正。

表 2 的平均 p-MRR：BM25 −2.1；MonoT5-base −1.8；无指令模型里 MonoT5-3B 是例外，平均 +2.5。E5-mistral 平均 −3.5，GritLM-7B 平均 −0.0，OpenAI v3 Large −2.7。指令微调、且没按检索任务训练的模型为正，例如 Mistral-7B-instruct 平均 +10.1。他们自己的 FollowIR-7B 平均 p-MRR 是 +12.2。这个 +12.2 是本篇训练后的模型，不是 BRIGHT 的思维链涨幅。

失败原因写成两条：不习惯长指令；把指令拿去当关键词。图 3 和表 3：对跟不住的模型，把指令收成关键词往往不比全文更差，说明它们本来就在做关键词。

### 2. 逻辑关系

转折：标准 nDCG 可以很高，同时 p-MRR 为负。递进：长度和关键词用法两个原因，再用训练把 p-MRR 拉正。没有滑到推荐约束。TREC 叙事不是列谓词。

### 3. 隐含假设

标注员叙事等于用户指令，模型应该在指令改写后改变相关集。SQL 解析不了「在这种叙事下什么算相关」。

### 4. 证据

「小于 3B、以及按检索器训练的模型，在 p-MRR 上普遍失败」是强的，表 2 和正文的模型范围一致。MonoT5-3B 是明确例外。外推到「所有指令都应编译成 WHERE」是弱的。

### 5. 引用边界

允许：这批 TREC 叙事上，无指令或按检索训练的模型 p-MRR 多为负；MonoT5-3B 平均 +2.5；作者把失败写成不习惯长指令，以及把指令当关键词。

不允许：FollowIR 的 +12.2 当成 BRIGHT 的涨幅；把叙事指令写成可以交给 SQL 的列谓词。

## 8. BRIGHT（ICLR 2025，arXiv 2407.12883）

### 1. 逐段论点

主张：相关关系需要推理时，现有检索器都很差。十二个数据集，nDCG@10。相关性来自同一算法、同一技巧或同一定理，不是词面重叠。LeetCode、定理、Stack Overflow 都在里面。

表 2 印出的平均：BM25 14.5。大于 1B 的开源模型里，Qwen 22.5 是表内最高，GritLM 21.0，SFR-Embedding-Mistral 18.3。SFR 在 MTEB 检索子集上被摘要写成 59.0，同时在 BRIGHT 上是 18.3。专有模型里 Google 20.0。表注、第 4.2 节和结论都写「最好模型平均只有 24.3」。抽出来的 13 行里没有一行的平均数等于 24.3。SFR 的 TheoQ 列是 24.3，那一列不是平均。24.3 以作者正文为准，不派给某个抽不出来的模型名。

+12.2 在摘要和第 1 节，对照是查询侧思维链，不是对候选做推理。原句：“generate chain of thought reasoning steps about the query before retrieval, resulting in average improvements of up to 12.2 points.” 第 4.2 节把这些步骤当作新查询。提示是三步：认出问题、想相关文档该含什么、起草一个答案。图 3 写明换成 GPT-4 写的推理后，BM25 涨得最多。

附录把这个「新查询」拆开。表 38，GPT-4 写的推理当查询：BM25 平均 27.0。表 2 的原始 BM25 是 14.5。两格相减是 12.5，不是正文的 12.2。表 36，Llama3-70B 的推理当查询，BM25 平均 25.7。表 34，GritLM 写的推理，BM25 平均 19.4。正文说最好成绩仍低于 30，27.0 落在这句里面。12.2 和 27.0−14.5 对不齐，引用时两句都带上，不要把 12.2 改写成某一次相减。

另一张是重排，表 3 的平均：BM25 无重排 14.3，GPT-4 重排 top-10 是 17.4。不是 12.2。14.3 和表 2 的 14.5 也差 0.2，重排表自己的无重排基线是 14.3。

问答侧（表 4）是另一条线：Claude-3.5-sonnet，无检索平均 77.7，BM25 78.3，Qwen 79.6，oracle 81.8。Qwen 相对无检索是 1.9 个点，oracle 是 4.1 个点。

### 2. 逻辑关系

并列：词法、稠密、专有嵌入都低。递进：把推理写进查询再检索，BM25 涨得最多，最好仍低于 30。转折：推理发生在查询侧，重排是另一张小表。没有滑到推荐约束。定理和编程题没有可执行的关系谓词。

### 3. 隐含假设

「同一技巧」这种相关，是检索器该表示的相关性。SQL 不会因为嵌入在这上面差就自动赢；BM25 的 14.5 说明词法一样差。

### 4. 证据

「推理型相关上检索器差、BM25 平均 14.5」是强的，表 2 印得出来。24.3 是中等：作者三次写了这个数，但和印出的行平均不一致。+12.2 是中等：方向是查询侧思维链，和印出的 14.5→27.0 同向，差值不完全相等。

### 5. 引用边界

允许：表 2 的 BM25 十二个数据集平均 nDCG@10 是 14.5；作者写最好模型平均 24.3，同时印出的最高行平均是 Qwen 的 22.5；查询侧思维链最多提高 12.2 个点，附录里 GPT-4 推理查询下 BM25 平均是 27.0；重排表里 BM25 从 14.3 到 GPT-4 的 17.4。

不允许：+12.2 来自对候选做推理；每条难查询都该路由到 SQL；BRIGHT 上嵌入不行所以 SQL 会赢。

## 9. ACORN（SIGMOD 2024，arXiv 2403.04871）

### 1. 逐段论点

主张：谓词无关的混合搜索可以在固定召回下比先前方法快。ACORN 扩展 HNSW，让向量索引和结构化谓词一起走，而不是只支持大约 1000 个等值谓词的专用索引。摘要和结论都是吞吐：固定召回下吞吐高 2–1,000 倍。正文把同一句话写成：0.9 召回下，QPS 高 2–1000 倍。细分：先前基准上 2–10 倍，新基准上超过 30 倍，2500 万向量规模上超过 1000 倍。

数据是 SIFT1M、Paper、LAION、TripClick。SIFT1M 的谓词是随机整数上的等值，选择率 0.083。这是速度结果。效果上的过滤近似搜索失败不在这篇里。

### 2. 逻辑关系

因果：图更密、按选择率做邻居扩展，所以谓词子图仍近似 HNSW，QPS 在 0.9 召回下更高。没有效果失败的论点，也就没有滑到推荐。

### 3. 隐含假设

谓词选择率可以估计，低于阈值走索引，高于阈值可以退回预过滤。随机标签上的选择率和品牌、价格、排除已买不是同一分布。

### 4. 证据

速度主张是强的，指标是 QPS，不是召回失败。用它证明「向量在约束上失败，所以换成 SQL」不成立，方向相反：系统可以把谓词留在向量搜索里面。

### 5. 引用边界

允许：ACORN 在 0.9 召回下把 QPS 提高 2–1,000 倍，对象是谓词无关的 HNSW 混合搜索。

不允许：引用 ACORN 的倍速当作向量约束失败的证据。

## 10. SUQL（NAACL 2024 Findings）

`01-text-to-sql/SUQL_NAACL2024_Findings.pdf` 是同一份文件。

### 1. 逐段论点

主张：结构化列加自由文本，需要 SQL 再加上 `SUMMARY` 和 `ANSWER`。`ANSWER(reviews, 'is parking easy?') = 'Yes'` 被用作过滤器。作者写，停车难不难这种信息在评论文本里；检索器可能因为「parking」把「停车很难」排上来，所以纯关键词过滤不够，还得把原句谓词再跑一遍。`SUMMARY` 是 `ANSWER(t, 'what is the summary of this text?')` 的语法糖。

HybridQA 上，少样本 SUQL 的精确匹配离全监督 SOTA 差 8.9 个点、F1 差 7.1 个点；对方用了 6.2 万训练样本。开发集精确匹配 59.3%。作者抽查 100 个非精确匹配，认为只有 36% 是真错，因此「真实准确率可能到 85.3%」。这是抽查外推，不是官方指标。

餐馆实验：Yelp 上 1828 家，四个城市，每家最多 20 条评论和 20 道热门菜。检索器是现成的稠密模型，LLM 是 gpt-3.5-turbo-0613。单轮 100 问，对话 20 段、96 个回合，其中 62 个回合在找餐馆。表 4：单轮里 45 个只需要结构化字段，55 个要组合；对话侧 37 和 25。合计超过 49% 的用户问句同时要结构和自由文本。

表 5 的回合准确率：返回的餐馆里，满足用户全部条件的比例，由人工逐家判断真假阳性。SUQL 限制最多返回 3 家。单轮 93.8%，对话 90.3%。线性化后只取第 1 名：单轮 57.0%，对话 63.4%。线性化取前 3：49.7% 和 61.9%。没有排序指标，没有 Recall@K。

### 2. 逻辑关系

递进：SQL 覆盖结构化约束，`ANSWER` 覆盖评论里的谓词，两者可组合。转折：纯 SQL 不够，去不掉的正是模型谓词。并列：HybridQA 的精确匹配和 Yelp 的人工回合准确率不是同一个指标。没有从嵌入失败滑到「用 SQL 替换检索」。

### 3. 隐含假设

人工判断「这家店满足全部要求」等于系统成功。最多返回 3 家，所以这不是全库召回。`ANSWER` 的内部仍是检索加 LLM，不是数据库谓词。

### 4. 证据

分工是强的：评论里的停车、浪漫，作者明确说纯 SQL 不够，表 5 的对照是线性化。93.8% 和 90.3% 只在「最多 3 家、人工看是否全满足」上成立。这是公开文献里最接近「结构化约束下找店」的系统，也是「SQL 替换向量」的反例。

### 5. 引用边界

允许：Yelp 1828 家上，SUQL 回合准确率单轮 93.8%、对话 90.3%，线性化 @1 是 57.0% 和 63.4%；`ANSWER` 用来过滤评论文本，作者写纯 SQL 不够。

不允许：SUQL 证明 SQL 可以替换检索；93.8% 是排序指标。

## 11. TAG（CIDR 2025）

`01-text-to-sql/TAG_arXiv2408.14717.pdf` 是同一篇的 arXiv 版，这里只析 CIDR PDF。

### 1. 逐段论点

摘要：能写成关系代数的问题只是用户问题的一小部分；RAG 又只覆盖点查。标准方法在他们的基准上正确回答不超过 20% 的查询。三步是查询合成、数据库执行、语言模型生成答案。

第 4 节的基准从 BIRD 里抽五个领域，查询类型沿用 BIRD：匹配、比较、排序、聚合。准确率是精确匹配；聚合不进这个准确率（表 1 脚注）。模型是 Llama-3.1。RAG 用一个嵌入模型做点查。

表 1 的总体精确匹配和耗时：Text2SQL 0.17（5.63 秒），RAG 0.00（3.23 秒），Retrieval + LM Rank 0.02（4.82 秒），Text2SQL + LM 0.13（9.08 秒），手写 TAG 0.55（2.94 秒）。分类型：Text2SQL 在排序上是 0.10；Text2SQL + LM 在匹配和比较上是 0.10，排序上是 0.20。手写 TAG 匹配 0.60、比较 0.65、排序 0.40。正文写手写 TAG 总体做对 55%，比较最好是 65%，除排序外各类型超过 50%，相对标准基线的提升在 20% 到 65% 之间。20% 是非手写基线的上限，不是推荐的 Recall。手写 TAG 不是自动 Text-to-SQL。

RAG 在所有类型上是 0。作者用 Sepang 赛道的例子说明：RAG 只说到检索到的那几场，Text2SQL + LM 没用上库里的行，手写 TAG 把库内日期和模型知识合在一起。表 2 的知识型和推理型上，手写 TAG 都超过 50% 精确匹配；vanilla Text2SQL 在需要 LM 推理的查询上是 10%。

### 2. 逻辑关系

并列：Text2SQL 缺生成步，RAG 缺精确计算，两边都低。递进到手写的三步流水线。转折：20% 容易被听成「系统很差」，它是精确匹配，而且手写 TAG 到 0.55 靠的是人写的语义算子，不是模型突然学会了 SQL。没有推荐排序。

### 3. 隐含假设

BIRD 上改出来的问题代表「真实业务用户」。精确匹配等于答对。手写管道的分数可以用来说明框架有空间，不能用来说明模型已经能写出这条管道。

### 4. 证据

「标准 Text2SQL 和 RAG 在这批查询上精确匹配不超过 20%，RAG 是 0」是强的，表 1 对得上。用它支持「Text-to-SQL 不够，也不能只做向量点查」是中等偏强。用它支持「发出 SQL 就能做推荐召回」不成立：没有排序器，手写的是人。

### 5. 引用边界

允许：摘要「standard methods answer no more than 20% of queries correctly」；表 1 里 Text2SQL 总体精确匹配 0.17，RAG 0.00，手写 TAG 0.55；20% 是精确匹配上限，不是 Recall。

不允许：把 20% 写成推荐召回；把 0.55 写成自动 Text-to-SQL 的分数。

## 12. AvaTaR（arXiv 2406.11200）

### 1. 逐段论点

主张：用对比器改写工具调用的提示，让代理更会用工具。检索指标仍是 Hit@1、Hit@5、Recall@20、MRR。STaRK 的函数库是检索、抽属性、用 LLM 检查节点是否满足要求、再用 LLM 打分，最后 `FINISH`。没有「只执行 SQL」的一臂。

## 18. PCN-Rec（arXiv 2601.09771）

### 1. 逐段论点

主张：LLM 只提议名单和证书，确定性验证器决定接受；失败就用约束贪心修补。候选来自 MF/CF 的窗口，不是自然语言 SQL。约束是每份名单上的长尾占比、头部上限和类型多样性。公式里有 τ、κ、\(G_{min}\)，正文句子没有给出这三个数的取值，复现清单只要求实验者报告它们。

式 (8)：PassRate 是全体用户里验证器接受的比例；PassRate_feas 把分母收成窗口内存在可行名单的用户。W=80 时可行用户 551/943。

表 1，只在这 551 人上。一次生成、无验证器的 LLM：PassRate 0.000，NDCG@10 0.424。PCN-Rec：0.985，NDCG@10 0.403。确定性贪心上界的 NDCG@10 是 0.426。摘要写通过率 98.55%，以及 NDCG@10 绝对下降 0.021（0.403 对 0.424）。正文和表注写 \(\Delta=-0.022\)。0.424−0.403=0.021，和摘要一致，和正文的 −0.022 不一致。显著性写成 p<0.05，检验例子是按用户的配对 bootstrap，正文用了 “e.g.”。

作者在伦理节写明：系统避免的是静默的策略违反；除非解释声明本身也被验证，否则不自动保证解释忠实。

### 2. 逻辑关系

递进：先分出窗口内不可行，再把提议和校验分开。转折：摘要的 0.021 和正文的 −0.022 是同一对 NDCG 的两种写法。没有从嵌入 qrel 滑到推荐约束；这篇的约束本来就是名单级治理约束，不是嵌入实验。

### 3. 隐含假设

一次生成的 0.000 被看成「大模型不会守约束」。对照是他们自己的验证器，而且候选被限制在 MF/CF 的窗口里。验证器很严时，0.000 不能写成大模型在约束推荐上的普遍通过率。

### 4. 证据

「提议和确定性校验分开、两边都报」这个实验设计是强的，定义在式 (8) 和表 1。数字只在 MovieLens-100K、窗口 80、551 个可行用户、长尾和类型约束上成立。效用差用 0.021。它不是 SQL，也不是自然语言推荐请求。

### 5. 引用边界

允许：MovieLens-100K、可行用户 n=551、W=80，一次生成的 LLM 通过率 0.000、NDCG@10 0.424，校验过的系统 0.985、0.403；绝对差按 0.424−0.403 写成 0.021，并注明正文写了 −0.022。

不允许：大模型在约束推荐上的通过率普遍是 0；PCN-Rec 的通过率是 SQL 推荐器的通过率；证书文本是忠实解释。

## 19. Faithful CoT（IJCNLP-AACL 2023）

### 1. 逐段论点

主张：语言模型把问题译成自然语言和符号语言交织的链，确定性求解器执行这条链得到答案，因此这条链是最终答案的忠实解释。忠实的定义来自可解释性文献：解释应准确代表模型得出预测的过程。他们把它和「人觉得可信」分开。脚注写明：不声称翻译阶段本身可解释。

经验数字是问答和推理，不是推荐。Codex 上，相对普通思维链的准确率提升：数学应用题 6.3%，规划 3.4%，多跳问答 5.5%，关系推理 21.4%；10 个基准里 9 个更好。GPT-4 和 Codex 在 7 个数据集上达到少样本 SOTA，其中 6 个准确率 95.0 以上。

消融（第 6.1 节）：去掉求解器，准确率大掉；在 GSM8K、Date、SayCan 上，自然语言注释对准确率贡献很小，有时略有伤害；CLUTRR 上注释重要，nudge 那一行单独带来 31.3 个点。附录写：结构化自然语言注释有时不改变分数，但让链更容易被人看懂。这是性能和可读性拆开，不是「主实验强迫注释和程序一致」。

人工检查：答案正确时，链在多数情况下被判为可用；StrategyQA 上错误的链仍可能得到正确的是非答案。例子是 Karachi 那题，答案对，子问题里的国家知识是错的。作者写：最终答案正确，并且忠实于模型生成的链，但链里有错误知识。局限性：保证的是求解阶段忠实；翻译阶段仍是黑的。

### 2. 逻辑关系

因果：答案由求解器执行链得到，所以链在「答案从哪来」这个意义上忠实。并列：忠实不等于正确，也不等于人觉得像那么回事。转折：经验涨幅在推理基准上，不能递进成推荐解释质量。

### 3. 隐含假设

符号链被执行，就等于用户拿到了一份可用的解释。论文自己把翻译阶段排除在外，也承认链可以既忠实于执行、又含有错误知识。把「返回行恰好是 SQL 结果」当成忠实解释，重复的是这个假设，不是论文的定理。

### 4. 证据

操作定义在他们的任务上是强的：求解器是 Python、Datalog 或 PDDL 规划器，答案是执行结果。6.3% 等相对涨幅是中等，只属于那 10 个推理集。转到 SQL 推荐器，执行等式可以当审计，不能当解释贡献。生成器写出错误的 `WHERE` 时，等式仍然成立。他们做了链的合理性人工检查；本篇若声称解释质量，审稿人要的是同类证据，现有预算撑不住。

### 5. 引用边界

允许：答案由确定性求解器执行符号链得到，因此这条链是「答案如何算出」的忠实解释；翻译阶段不在这个保证里；相对涨幅是推理基准上的 6.3%、3.4%、5.5%、21.4%。

不允许：SQL 文本是用户可用的忠实解释；执行等式是解释质量分数。

### 1. 逐段论点

主张：温度 0、top-p 1、固定种子，输出仍然不稳定。五个模型（GPT-3.5 Turbo、GPT-4o、Llama-3-8B、Llama-3-70B、Mixtral-8x7B），八个任务，零样本和少样本，每个条件 10 次运行。

TARr@N：N 次运行的原始字符串全部相同的题目比例。TARa@N：解析后的答案全部相同的比例。他们写明可以出现准确率 100%、TARa 100%、TARr 0。

BestAcc：一道题只要有一次对，就算进最好。WorstAcc：只要有一次错，就算进最差。最大减最小准确率是各次运行准确率的差，论文写明它和 BestAcc、WorstAcc 不是同一个差。

摘要：“accuracy variations up to 15%” 是各次运行准确率的起伏；“gap of best possible performance to worst possible performance up to 70%” 是 BestAcc 对 WorstAcc。第 7.1 节把图 1 说成某些任务上 5%–15% 的运行间差异。表 2 少样本、college math、Mixtral：BestAcc 75.0，中位 31.5，WorstAcc 3.0。70% 是摘要给的上限，不要把某一格改写成唯一来源，也不要把它和 15% 加在一起。

### 2. 逻辑关系

并列：字符串一致、解析答案一致、运行准确率起伏、最好对最差，四件不同的事。转折：温度 0 仍不稳定。没有推荐，也没有 SQL。

### 3. 隐含假设

这五个模型和八个任务上的起伏，可以出现在别的解码栈上。SQL 执行器不在这个失败模式里。字符串抖动来自生成，不来自同一条 SQL 的重复执行。

### 4. 证据

定义是强的。15% 和 70% 是这批模型、这批任务、10 次运行上的上限，证据强，外推弱。不要写成「SQL 准确率会晃 15% 或 70%」。

### 5. 引用边界

允许：温度 0 下用 TARr 看原始字符串、TARa 看解析后的答案；15% 是运行准确率起伏的上限，70% 是 BestAcc 对 WorstAcc 的上限。SQL 上的合理改写是：TARr 看 SQL 字符串，TARa 看执行结果集或规范化后的语法树。

不允许：把 15 或 70 写成本篇 SQL 生成器的预期晃动。

## 21. ReproRAG（arXiv 2509.18869，页眉 Workshop ’25）

### 1. 逐段论点

主张：向量 RAG 的跨次运行不能假设索引和嵌入不变。度量分三层。嵌入：L2 和余弦。检索集合：Jaccard 是 \(|A\cap B|/|A\cup B|\)，忽略名次，1 表示两次返回同一集合。Kendall’s tau 只比较两边都出现的文档的名次，1 表示这些公共文档的顺序相同。另有分数标准差、重叠系数和 RBO。

场景 1，数据插入。MSMARCO 中等规模配置在总设置里是 10 万文档、1000 条查询；这一场景的初始索引约 7920 篇，100 条查询，top-50。HNSW、IVF、LSH 的平均重叠系数大约 0.80，RBO 大约 0.73。HNSW 的重叠系数中位 0.80，范围 0.64 到 0.92。作者写：新增数据造成结果更替，但留下来的文档的相对顺序在近似索引上保持稳定，Kendall 在该场景被说成完美。

场景 2，换嵌入模型，FAISS Flat_L2、FP32、5000 篇子集、100 条查询、top-50。BGE 对 E5 的重叠系数 0.540、RBO 0.570、Kendall 0.384；BGE 对 Qwen 0.454、0.486、0.338；E5 对 Qwen 0.432、0.474、0.322。Kendall 的范围被写成 0.32–0.38，p 值大于 0.05。

场景 4，固定缓存嵌入、固定种子，在 CPU 上重建 FAISS。表 6：Flat、IVF、HNSW、LSH 的精确匹配、Jaccard、Kendall 都是 1.00。作者写：在这个受控条件下，索引和 CPU 搜索本身可以完全复现。漂移来自数据插入、模型差异和数值精度，不来自「FAISS 在固定输入下必然随机」。

Jaccard 和 Kendall 的定义可以借走。论文量的是嵌入、FAISS 和数据插入。同一条 SQL、同一个库，结果集的 Jaccard 应当为 1；方差来自生成，不来自执行。无 `ORDER BY` 时结果是集合，这时算 tau 没有名次可排。tau 只看交集，集合已经变了仍可以看起来很稳，所以稳定性以 Jaccard 为主。

五编码器、2200 万到 80 亿参数、改写距离 32%–50% 不在这 21 份 PDF 里，本篇不引。

### 2. 逻辑关系

并列四种场景：插入、换模型、精度、固定种子重建。转折：固定种子下 Jaccard 和 Kendall 可以是 1，换模型或插入数据就不是。没有从嵌入失败滑到推荐约束，也没有滑到 SQL 结果集会自己漂。

### 3. 隐含假设

两次 top-k 的集合重叠代表系统可复现。SQL 结果集借用这个定义时，假设两次执行看到的是同一个库。这个假设对精确 SQL 成立，对向量索引不成立，论文自己把两者分开了。

### 4. 证据

指标定义是强的。实验结论「索引会漂」只在向量 RAG 的那些场景里是强的。写成「SQL 结果集会自己漂」不成立。

### 5. 引用边界

允许：两次取回集合的 Jaccard 是 \(|A\cap B|/|A\cup B|\)，忽略名次；Kendall 只比较两边都出现的文档；固定种子、缓存嵌入时，表 6 的 Jaccard 和 Kendall 是 1.00。

不允许：把他们的实验结论写成 SQL 执行不稳定；在没有 `ORDER BY` 的结果上把 Kendall 当主稳定性指标。

## 重新整理后的创新点

这 21 篇放在一起，站得住的只有分工，没有替换。

显式、已经落到列或边上的谓词，交给数据库。语义、评论、叙事、推理型相关，留给检索或模型谓词。SUQL 的 `ANSWER`、TAG 的生成步、BRIGHT 的查询侧推理、FollowIR 的叙事、NevIR 和 ExcluIR 的自由文本否定，都是 SQL 写不出来的那一块。NumConQ 的数值只有在原表还在时才该交给 SQL；属性被写进句子之后，他们自己的补救仍是稠密检索器。

STaRK 上打过 ada-002 的系统仍在检索。合成 Amazon 上，SPARK 的 Recall@20 是 53.95，BM25 是 53.77，multi-ada-002 是 55.12。人工 Amazon 上 SPARK 33.56，高于 BM25 的 15.23，低于 ada-002 的 35.46。MoR 打过 BM25 时文本臂就是 BM25；QAGNN 的 Hit@1 是 26.56，低于 BM25 的 44.94。没有任何一篇给出「只执行 Cypher 或 SQL、不再做向量或 BM25」并且在 STaRK-Amazon 上打过 BM25。

因此本篇还能写的创新，不是「用 SQL 换掉向量召回」。能写的是：模型只把已经落到关系上的片段写成 SQL，数据库取出超集，BM25 或小编码器在超集里排序；另一种顺序单独报。主表用自动指标。解释只做到审计：展示的行是否恰好是这条 SQL 的执行结果。不写「SQL 是忠实解释」。

LIMIT 可以留在相关工作里的一句是：单向量表示不了任意相关组合；在原字符串上，词法匹配反而接近做对。它不能留在「推荐约束上嵌入失败」那一栏。

## 这一路的结论

主表可以放、不必做用户研究的指标：

- Hit@1、Hit@5、Recall@20、MRR、NDCG、延迟。协议写在格子里。这些是检索指标，不是上面任何一篇的用户研究。
- 显式、已经落到列或边上的条件是否成立。一件返回物品算匹配，当且仅当每个已落地的原子谓词都成立。隐式和主观条件不进这列。NumConQ 的一致性只说明文本化数值不该交给嵌入，不把 16.3% 搬进这列。
- 温度 0、固定种子、N 次：SQL 字符串用 Atil 的 TARr 定义，结果集用 ReproRAG 的 Jaccard。有 `ORDER BY` 才加 Kendall，并且写明它只比较两边都出现的行。
- 一条审计列：展示给排序器或用户的行，是否恰好是这条 SQL 的执行结果。SQL 超集再排序时，这列应当为真。先向量再 SQL 过滤时，这列用来区分「展示的是过滤后的向量命中」和「展示的是 SQL 结果」。

必须丢掉的句子：

- LIMIT 是推荐器的结果，或 “who likes Apples?” 证明嵌入搞不定推荐式查询。相关集是 46 篇文档的全部两两组合；全库另有约 5 万篇干扰文档。小集合 BM25 的 Recall@2 是 97.8。
- SQL 后过滤一般会丢掉 30% 以上的正确结果。原文只有 ClickHouse、UniVectorSQL-7B、Non-integration 的召回 0.6 到 JOIN-integration 的 0.4。WHERE 没有这个数。两种顺序仍都要报，漏召回用自己的 qrel 算。
- SQL 是忠实解释。Faithful CoT 的忠实等于答案由求解器执行链得到，翻译阶段不在保证里，链可以既忠实于执行又含有错误知识。返回行等于 SQL 结果，只说明展示层没有私自增删。PCN-Rec 也写了：解释声明本身不被验证，就不保证解释忠实。这句写进贡献，审稿人会要用户研究。

一并丢掉、避免回写进主表的句子：只发 Cypher 或 SQL 就能打过 BM25；约束抽取和过滤合计占 SPARK 错误的 30%–36%（只引用表 7 的 Constraint 行 36 / 30 / 31）；BRIGHT 的 +12.2 来自对候选做推理；QUEST 的 0.142 是宏召回；Atil 的 15% 或 70% 是本篇 SQL 准确率的晃动；PCN-Rec 的 0.000 是大模型约束推荐的普遍通过率；ACORN 的倍速是效果失败。
