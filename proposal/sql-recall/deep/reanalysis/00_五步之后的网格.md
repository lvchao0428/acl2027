## 2. 每一路在五步之后还成立的结论

下面每段只使用该文件第 4 步留下、或最终节写出的句子。

**Text-to-SQL。** 还能做的是：在用户、物品、交互表上由模型写出 SQL，把执行结果当作候选，用留出交互上的 Recall 或 NDCG 打分，并单独报告错误 SQL 被执行的代价。这一路没有这篇。挤满的是三件事：专家模板填槽后再报域内执行准确率；不可答、拒答令牌和错答更贵的可靠性分；SQL 当中间表示，分数看答案对不对或约束满不满足。第 4 步留下的是：换库会使在 Spider 上训练或成名的系统变差，但必须带配置，不能写成同一系统从 82% 掉到 25%–60%；问句里不写、SQL 里必须写的领域惯例是缺口，40 个模板和专家 90.0 没有留下；执行准确率会把错查询判对、把对查询判错，金 SQL 也会改名次；错答比拒答更贵时，高执行分可以和很差的可靠性分同时出现；纯 SQL 盖不住外部知识或自由文本，Binder、SUQL、TAG 的现有分数不是推荐召回。不能把执行准确率、作者判定的约束满足或可靠性分写成 Recall、NDCG 或 Hit。推荐指标是把「打用户任务」落到推荐上的推论，不是原文已经证明的主指标。TAG 的强度两路用词不同：01 把「自动 Text2SQL 或 RAG 解不了这些改写题」标成中等，限于这 80 题和这个 70B，并把「可复用自动系统、准确率 55%」标成弱；04 把「表 1 上标准方法精确匹配不超过 20%、RAG 为 0」标成强。事实相同。外推范围信任 01，20% 不是 Recall、0.55 不是自动 Text-to-SQL，信任 04。

**召回。** 没有一篇已经占住「大模型写出一条协同 SQL 自连接，数据库执行，再用推荐的 Recall 或 NDCG 打分」。无约束的下一物品不要当主表。主表放带谓词的召回：序列臂用 Xu 的全量交叉熵，再套同一组谓词；平凡臂是同一条 SQL 写出来的、调过收缩的 ItemKNN；EASE 在内存放得下时另报，不能把 EASE 说成自连接；向量臂按 SIEVE 的大约 1/sel 多取。InteRecAgent 用来划界：属性 SQL 已经有人做，提示禁止用 SQL 找相似物品。不能写「SQL 自连接打不过调好的 SASRec 或 EASE」，因为这批 PDF 没有把三者放进同一张全库排序表。生成式检索主表里的 SASRec 是 S3-Rec 公开结果那一档，不能把「超过 SASRec」写成超过调好的序列模型。Hit、Recall、NDCG 不能横比。线上 CTR 不证明某个召回算子必要。SIEVE 和 Lim 的退化是近邻 recall，不是推荐 NDCG。02 的原句是「主表放带谓词的召回」。03 的原句是「主实验仍然是 STaRK-Amazon 的全库检索」。信任 02 回答协同自连接有没有被占住，信任 03 回答哪份基准能承载 SQL 返回的候选。不要收成一张主表。

**Benchmark。** 主实验是 STaRK-Amazon 的全库检索。模型只把关系片段写成 SQL，数据库返回关系候选，文本仍交给 BM25 或小编码器，在超集里排序；关系片段和整句分开报。要打的全库数字是表 6 的 BM25：Hit@1 44.94，Hit@5 67.42，Recall@20 53.77，MRR 55.30。人工 81 条另报。合成集上，只执行关系模板的集合召回或纯 SQL 的 Hit@1 不能当主结果；Recall@20 可以照官方协议报，不能按「完美系统应接近 1」来读。RecBench+ 的历史子集 Precision，以及表 2 的生成式 Precision 0.308 和 CMR 0.714，不能进检索主表；若做电影显式条件，相关集是式 (7)。Amazon-C4 只作负对照，论文没有 SQL 行，「精确 SQL 会输」还不是结论。EComAgentBench、REGEN、TalkPlay-Tools、AgentRecBench 不换到主实验的位置。InteRecAgent 已经把硬条件交给 SQL，并写明不许用 SQL 找相似物品；它的 Hit@5 来自知道目标的模拟器。04 的 MoR 一节把 BM25 写成 44.94 / 67.42 / 53.77 / 55.30，与 03 的表 6 一致。04 的 mFAR 表 1 另写 BM25 的 H@1 / R@20 / MRR 为 0.483 / 0.584 / 0.589。那是 mFAR 自己的表。官方全测试集信任 03 的表 6。

**指标。** 站得住的是分工，不是用 SQL 换掉向量召回。已经落到列或边上的谓词交给数据库；语义、评论、叙事、推理型相关和自由文本里的否定留给检索或模型谓词。没有任何一篇给出「只执行 Cypher 或 SQL、不再做向量或 BM25」并且在 STaRK-Amazon 上打过 BM25。还能写的是：模型只把已经落到关系上的片段写成 SQL，数据库取出超集，BM25 或小编码器在超集里排序，另一种顺序单独报。主表用自动指标：检索指标、显式谓词匹配、温度 0 的字符串一致和结果集 Jaccard，外加一条审计列。审计只说明展示的行是否恰好是这条 SQL 的执行结果。01 留下的空位是交互表上的留出推荐分。04 留下的能写的是 STaRK 上的关系片段加检索，并写明这不是替换向量。两句都留着。01 否定的是「原文已经证明主指标必须是推荐效果」。04 否定的是「用 SQL 换掉向量召回」。

**RelBench。** H&M 购买上成立的是：超过全局流行和自身历史的是 ID-GNN、NBFNet 和 ContextGNN，不是任意一个 GNN，也不是数据科学家的特征 SQL。因此「GNN 打败 SQL」不成立；成立的是「特定的成对 GNN 打败流行度和自身历史」。手写共现 SQL 是这组论文没报过的经典基线，不是新系统。它先要对照历史访问。超过历史访问不等于接近 ContextGNN。这组不能当 ACL 的语言实验。主实验若在带问句的检索基准上，RelBench 只保留为协同假设的健全性检查：一条带时间谓词的共现 SQL，在 H&M 购买上有没有超过历史访问。与 02 的分工：02 的 ItemKNN 是矩阵式 top-n 上调过的近邻，自连接写得出这一类 ItemKNN，写不出 EASE，也写不出序列模型；05 的历史访问数的是历史标签列表，不是交易表对自身的连接。RelBench 的 MAP 信任 05。推荐召回文献里的 ItemKNN 信任 02。

## 4. 必须丢掉的句子

- LIMIT 是推荐器的结果，或 “who likes Apples?” 证明嵌入搞不定推荐式查询。杀掉它的是 `04_指标.md`：相关集是 46 篇文档的全部两两组合，小集合上 BM25 的 Recall@2 是 97.8。
- SQL 后过滤一般会丢掉 30% 以上的正确结果。杀掉它的是 `04_指标.md`：原文只有 ClickHouse 上 UniVectorSQL-7B 从 Non-integration 的召回 0.6 到 JOIN-integration 的 0.4，WHERE 没有这个数。
- SQL 是忠实解释。杀掉它的是 `04_指标.md`：Faithful CoT 的忠实等于答案由求解器执行链得到，翻译阶段不在保证里；PCN-Rec 写明解释声明本身不被验证，就不保证解释忠实。
- GNN 打败 SQL。杀掉它的是 `05_RelBench.md`：H&M 上超过历史访问的是 ID-GNN、NBFNet 和 ContextGNN；两层 GraphSAGE、NGCF 和 MultiVAE 没有超过历史访问。
- SQL 自连接已经输给全量交叉熵 SASRec 和 EASE。杀掉它的是 `02_召回.md`：这张全库排序表不存在；EASE 的胜负不能说成自连接的胜负；用 Benigni 等证明「SQL 版 ItemKNN 没前途」，方向反了。
- Amazon-C4 上精确 SQL 一定会输给嵌入。杀掉它的是 `03_benchmark.md`：论文没有 SQL 或 BM25 的行，「会输」必须先测再写。
- 领域 text-to-SQL 完全不值得做。杀掉它的是 `01_Text-to-SQL.md`：挤满的是再报一个域内执行准确率；最终节仍留着空位，即用户、物品、交互表上由模型写 SQL，并用留出交互的 Recall 或 NDCG 打分。

`04_指标.md` 最终节还丢掉这些句子，写主表时一并不要捡回来：

- 只发 Cypher 或 SQL 就能打过 BM25。
- 约束抽取和过滤合计占 SPARK 错误的 30%–36%。04 只留表 7 的 Constraint 行。
- BRIGHT 的 +12.2 来自对候选做推理。04 写那是查询侧思维链。
- QUEST 的 0.142 是宏召回。04 写宏平均召回是另一列。
- Atil 等的 15% 或 70% 是这篇 SQL 生成器的预期晃动。
- PCN-Rec 的 0.000 是大模型在约束推荐上的普遍通过率。
- ACORN 的倍速是向量约束失败的证据。04 写方向相反：谓词可以留在向量搜索里面。
