## 本窗口的五个答案

1. **没有一篇是「只执行 Cypher 或 SQL、不再做向量或 BM25」，并且在 STaRK-Amazon 上打过 BM25。** SPARK 的工具是 HNSW 和 Cypher，空结果回退 BM25 加余弦，邻居再按 BM25 和稠密相似度裁剪。MoR 的文本臂在 Amazon 上就是 BM25。KAR 的引擎仍是 ada-002 或 BM25。AvaTaR 按检索指标打分。mFAR 把 BM25 的分数接进混合模型。HybGRAG 没有 Amazon 分割。Text2VectorSQL 的库是 VectorSQLBench，不是 STaRK。这一做法跨了「硬属性过滤」和「带文本的半结构化检索」两格，不被上面任何一篇单独占住。

2. **还能写、但这批 PDF 里没有测过的数，就是关系片段超集再排序。** 模型只把已经落到关系上的片段写成 SQL，数据库取出超集，BM25 或小编码器在超集里排序；另一种过滤顺序单独报；漏召回用这份 qrel 算；审计列只说明展示的行是否恰好是这条 SQL 的执行结果。Text2VectorSQL 讨论了预过滤和后过滤，金标准是预过滤执行结果，唯一一对召回是 ClickHouse 上 UniVectorSQL-7B 从 Non-integration 的 0.6 到 JOIN-integration 的 0.4，数据不是推荐 qrel。PCN-Rec 的校验对象是治理约束，候选来自 MF/CF 窗口。Faithful CoT 的等式是求解器执行符号链。四件事都还没在 STaRK 的 qrel 上测过。

3. **温度 0 的字符串一致用 Atil 的 TARr；结果集用 ReproRAG 的 Jaccard。15% 和 70% 是 Atil 那项研究的上限，不是这篇 SQL 生成器已经测过的晃动。** TARr@N 看 N 次原始字符串是否全部相同，TARa@N 看解析后的答案。他们写明可以出现准确率 100%、TARa 100%、TARr 0。摘要的 15% 是各次运行准确率起伏的上限；正文另写有些任务上十次运行的最低和最高相差 5%–15%。70% 是 BestAcc 对 WorstAcc 的上限。表 2 少样本、college math、Mixtral 印的是 75.0、31.5、03.0，这一格的最好对最差是 72 个点，不能改写成 70% 的唯一来源。同一条 SQL、同一个库，结果集的 Jaccard 应当为 1。ReproRAG 表 6 在固定缓存嵌入、固定种子、CPU 上重建时，Flat、IVF、HNSW、LSH 的精确匹配、Jaccard、Kendall 都是 1.00。没有 `ORDER BY` 时，Kendall 不当主稳定性指标。

4. **mFAR 表 1 的 BM25 和 STaRK 表 6 的 BM25 不是同一格。** mFAR 表 1 的 Amazon 列是 H@1、R@20、MRR，BM25 印成 0.483 / 0.584 / 0.589，ada-002 印成 0.392 / 0.533 / 0.542。MoR 在自己的表里把 Wu 等的 BM25 印成 H@1 44.94、H@5 67.42、R@20 53.77、MRR 55.30。两行对不上，列也不一样。官方全测试集仍信任 03 的表 6。本窗口不把 mFAR 的 0.483 挪去当那个基线。

5. **NumConQ、ExcluIR、NevIR、LIMIT 的失败都不是已经落到列上的谓词。** NumConQ 的文档由结构化条目用模板改写成句子，数值约束写在问句里。ExcluIR 的排除发生在自由文本查询和正负文档之间。NevIR 的否定是两篇自由文本只差一处对比否定。LIMIT 的相关集是 46 篇文档的全部两两组合，\(\binom{46}{2}=1035\)，再配 1000 条查询；“who likes X” 是故意选的简单句式。网格把已经落到列上的数值和否定交给数据库；这四篇供给的是自由文本、改写句，或一张被填满的组合矩阵。

选题收在文末。主实验仍是：STaRK-Amazon 上只把关系片段写成 SQL，数据库取超集，BM25 或小编码器在超集里排序。要打的 BM25 用 03 的表 6，也就是 MoR 转印的 44.94 / 67.42 / 53.77 / 55.30。这篇测的是超集再排序能不能高于这行，不是「只发 SQL」。

## 1. LIMIT（arXiv:2508.21038v2，ICLR 2026）

### 1. 论点与原文数字

摘要的主张是：单向量嵌入能表示的 top-k 文档组合数受维度限制，而且这个极限会在极简单的查询上出现。第 5.2 节把难度从算子上拿开：与 QUEST、BrowseComp 那种算子难度相反，他们选很简单的查询和文档，让难度落在 top-k 集合本身。构造约束有两条：每个用户属性少于 50 个；每条查询只问一件事，即 “who likes X”。属性表由 Gemini 2.5 Pro 生成并清到 1850 项，并用 BM25 的失败检查避免词面重叠。

语料 5 万篇、1000 条查询、每条恰好 2 个相关文档。相关矩阵取 46 篇文档的全部两两组合：\(\binom{46}{2}=1035\)，再配 1000 条查询。这 46 篇之外约 4.995 万篇对任何查询都不相关。另做一个只有这 46 篇的 small 版。

附录把图收成表。表 4（小集合，N=46）：BM25 的 Recall@2 / @10 / @20 是 97.8 / 100.0 / 100.0。GTE-ModernColBERT 是 83.5 / 97.6 / 99.1。Promptriever Llama3 8B、4096 维的 Recall@2 / @10 / @20 是 54.3 / 90.0 / 97.7。GritLM 7B、4096 维是 38.4 / 75.4 / 90.5。Qwen3 Embed、4096 维是 19.0 / 52.3 / 73.8。正文说最好的嵌入 Recall@2 不到 60%。

表 5（全库）：BM25 的 Recall@2 / @10 / @100 是 85.7 / 90.4 / 93.6。Promptriever Llama3 8B、4096 维是 3.0 / 6.8 / 18.9。GTE-ModernColBERT 的 Recall@100 是 54.8。正文说全库上模型连 20% 的 Recall@100 都难达到。

同义词版把语料里的属性换成不重叠的说法。正文只点名两句：BM25 掉了 89% 以上，Qwen3 embedding 掉 38.9%。图 6 的同义词柱和原词柱在版面上串在一起，除这两句外，不把单个柱子改派给某个模型。原词柱里已经由附录表印出的数，用表 4，不用图。

交叉编码器：把 46 篇和 1000 条查询一次给 Gemini-2.5-Pro，1000 条全部做对（100%）。对照是最好嵌入的 Recall@2 不到 60%。

附录表 2 把 qrel 当成图。LIMIT 的图密度 0.085481，平均查询强度 28.4653。对照：NQ 两个都是 0；HotpotQA 0.000037 和 0.1104；SciFact 0.001449 和 0.4222；FollowIR 的 Core17 是 0.025641 和 0.5912。

结论把出路写成交叉编码器、多向量、高维稀疏，以及尚未出现的单向量结构。没有查询语言。

### 2. 逻辑关系

递进：维度下界，自由向量在测试 qrel 上仍然卡住，再用自然语言把同一张满组合矩阵做成 LIMIT。转折在第 5.2 节：表面句式是 “who likes Apples?”，难度被作者从算子上挪到组合矩阵上。再一处转折是同义词：原字符串上 BM25 接近做对，换说法后词法掉 89% 以上。

### 3. 隐含假设

单向量、固定维、带间隔的最近邻，就是要被否定的检索器。一张穷尽的组合 qrel 被当成「任何用户都可能问到的相关集」。属性先写成不重叠的字符串，词法匹配才会接近完美。这个条件和「喜欢已经是一列」不是同一件事。

### 4. 证据强度

容量主张是强的：46 篇和全库两张表、同义词对照、Gemini 一次看完全部文档能做对，条件都写在论文里。转到推荐 SQL 是范畴错误。`WHERE liked = 'apples'` 只有在「喜欢」已经是列时才精确；属性只活在句子里、又被换成同义词时，SQL 和 BM25 一起失效。小集合上 BM25 的 Recall@2 已经是 97.8。

### 5. 结论

可以引用：固定维单向量表示不了全部带间隔的 top-k 组合；相关集是 46 篇的全部两两组合；小集合 BM25 Recall@2 是 97.8，Promptriever-4096 是 54.3；全库 Promptriever-4096 的 Recall@100 是 18.9，BM25 是 85.7 / 90.4 / 93.6；同义词版作者写 BM25 掉 89% 以上、Qwen3 掉 38.9%。

没有出处的句子：LIMIT 说明嵌入搞不定推荐式查询；“who likes Apples?” 是推荐召回的反例；因此该换成 SQL。

## 2. Text2VectorSQL（arXiv:2506.23071v2）

### 1. 论点与原文数字

任务是自然语言到同时含 SQL 谓词和向量检索的 VectorSQL。生态系统是合成数据、VectorSQLBench（SQLite、PostgreSQL、ClickHouse，乘 BIRD、Spider、arXiv、Wikipedia），以及「召回退化」：SQL 过滤和向量搜索套在一起，会比传统过滤向量搜索漏掉更多正确结果。

第 II 节把执行分成两档。预过滤：先用 SQL 得到子集，再在子集里做向量搜索。作者称为高保真，代价是可能让 ANN 索引失效、退成扫描。后过滤：先做 ANN，再把 SQL 谓词套到向量结果上。作者称为快，真邻居可能不在先取出的候选里。

引言的唯一一句百分比：复杂查询涉及 JOIN 时，后过滤可以静默丢掉 30% 以上的正确结果。这句的对照对象是「传统过滤向量搜索」，引言里没有给出那一对原始召回。

第 III-A2 节把耦合分成三档。Non-integration：向量搜索单独做，主键再通过 `WHERE IN` 或一次 JOIN 接回主查询。WHERE-integration：向量搜索发生在已经被 `WHERE` 滤过的子集上。JOIN-integration：向量搜索发生在表已经和其他表连接之后，过滤条件来自相关表。作者写这一档最容易让后过滤失败。

金标准故意不用后过滤。每条问题采五个 VectorSQL 变体，全部用预过滤执行，再用倒数排名融合得到 \(R_{gold}\)。作者写：对 VectorSQL，他们把预过滤的执行结果当作 ground truth。

第 IV 节唯一一对召回数字：ClickHouse 上，UniVectorSQL-7B 的召回 “degrades by more than 30% (from Non-integration’s 0.6 to JOIN-integration’s 0.4)”。0.6 到 0.4 是同一套后过滤后端上、不同查询类别之间的下降。对照不是同一批查询的预过滤对后过滤。正文说从 Non 落到 WHERE、再在 JOIN 上陡降，WHERE 没有数字。PostgreSQL 因为 pgvector 的迭代索引扫描，退化 “much less severe”，也没有数字。图 5 的对象是 Claude-4-Sonnet、OmniSQL-32B、UniVectorSQL-7B，后端是 PostgreSQL 和 ClickHouse。数据是 VectorSQLBench，不是推荐 qrel。

### 2. 逻辑关系

递进：任务定义，两种执行顺序，三档耦合，用预过滤当金标准，再在后过滤后端上按耦合档位看召回。转折在引言：从「后过滤比过滤向量搜索漏得更多」滑到「JOIN 上丢掉 30% 以上」，再被正文的 0.6 到 0.4 接住。接住的对照变了。WHERE 被放进叙述，没有数字。

### 3. 隐含假设

金标准等于预过滤执行结果，所以「SQL 写对了」和「用户觉得相关」被当成同一件事。后过滤的 \(k'\) 取多大、谓词选择率多高，正文的 0.6 和 0.4 没有分开报。把 ClickHouse 上的类别差写成一般的「SQL 后过滤」，等于假设后端、模型和 JOIN-integration 都可以拿掉。

### 4. 证据强度

「两种顺序都要测、JOIN 耦合比单表 WHERE 更危险、后过滤会静默漏结果」是中等偏强：定义、金标准协议和一对数字都在。把 30% 写成对预过滤基线已经量过的一般跌幅，是弱的。推理漏洞就在引言和第 IV 节的对照对象不一致。数据也不是推荐 qrel。

### 5. 结论

可以引用：ClickHouse 上，UniVectorSQL-7B 从 Non-integration 的召回 0.6 降到 JOIN-integration 的 0.4；引言把 JOIN 上的后过滤概括为丢掉 30% 以上正确结果；WHERE 没有这个数字；PostgreSQL 的迭代扫描轻得多，没有数字；预过滤被写成高保真。先导实验两种顺序都报，漏召回用自己的 qrel 算。这个数这批 PDF 里没有。

没有出处的句子：SQL 后过滤相对过滤向量搜索会丢掉 30% 以上正确结果，当作推荐召回上的预期跌幅；任意一条带 JOIN 的 SQL 都有这个跌幅。

## 3. NevIR（arXiv:2305.07614v2）

### 1. 论点与原文数字

主张：神经检索不懂否定。数据是成对文档，只差一处关键否定，众包查询使每条查询只和其中一篇相关。指标是成对准确率：两条查询都把对的那篇排在前面。随机基线是 25%，因为两对独立，期望是 \(\tfrac12\times\tfrac12\)。

表 2 的正文：“No bi-encoder architecture scores higher than 12% paired accuracy ... with most models performing in the 5-10% range.” MonoT5-base 是 34.9%，MonoT5-3B 是 50.6%。稀疏侧 TF-IDF 是 2%，作者写这是标注协议造成的：标注者不能使用只出现在一段里的词。他们不报 BM25，因为在这个小集合和词面相近的对上，BM25 的实现会接近 TF-IDF。否定活在自由文本的对比段里。

### 2. 逻辑关系

并列：架构表达力越高，成对准确率越高，但双编码器仍低于随机。转折：在 MS MARCO 上很强的模型，在这个对比对上失败。没有滑到推荐约束，也没有滑到列上的 `NOT`。

### 3. 隐含假设

「两篇只差否定、查询不能用独有词」代表用户的否定需求。这比「不要某品牌」更苛刻，也比「类型列上的 `NOT IN`」更不能写成谓词。

### 4. 证据强度

「双编码器在这种对比否定上低于随机」是强的，表 2 和随机 25% 的定义对齐。把它记成 SQL 的胜利是弱的：类型、品牌已经成列时，`WHERE NOT` 可以做；否定还在句子里时，SQL 没有可执行的谓词。

### 5. 结论

可以引用：这种对比否定上，没有一个双编码器的成对准确率超过 12%，多数在 5%–10%，随机是 25%；MonoT5-3B 是 50.6%。

没有出处的句子：推荐里的否定因此该交给 SQL；NevIR 的失败是嵌入在约束推荐上的失败。

## 4. ExcluIR（arXiv:2404.17288）

### 1. 论点与原文数字

主张：排除性查询（要 A 不要 B）是检索上被忽略的失败，而且独立于一般否定来研究。评测集 3452 条人工标注的排除性查询；训练集 70293 条，每条配一个正文档和一个负文档。例子是 “besides Avengers: Endgame” 这一类。

指标有 R@N、MRR、正负文档之差，以及 RR：正文档排在负文档前的比例。随机 RR 的期望是 50%。

BM25 在 ExcluIR 上的 RR 是 53.48。这个格子在 HotpotQA 训练表和 NQ320k 训练表里相同，因为稀疏模型不随训练集变。DocT5Query 的 RR 是 53.85。NQ320k 上训练的 GTR，RR 是 68.31，\(\Delta\)R@1 是 34.85。正文写：几乎所有模型的 RR 只比随机高不到 10 个百分点；NQ 上最好的 Sentence-T5 和 GTR 仍远未理想，因为负文档被排得很高。作者把稀疏模型的原因写成词法匹配抓不住排除短语。排除发生在自由文本，不是列上的硬谓词。补救是把排除性训练数据加进去，以及生成式检索。

### 2. 逻辑关系

并列：标准检索集上的高分，和 ExcluIR 上接近随机的 RR。转折：换训练集、加大模型，RR 有一点上升，作者仍写成远未理想。没有从自由文本排除滑到 `NOT IN`。

### 3. 隐含假设

一条「要 A 不要 B」的句子，等于推荐里已经落到属性列上的排除。正负文档是一对，RR 量的是这一对的相对名次，不是全库上的约束满足率。

### 4. 证据强度

「排除性自由文本上，BM25 的 RR 是 53.48，GTR 是 68.31，作者认为远未理想」是强的，表和正文对齐。写成「排除性推荐约束因此该换成 SQL」没有原文。

### 5. 结论

可以引用：ExcluIR 上 BM25 的 RR 是 53.48；NQ320k 上训练的 GTR 是 68.31；作者仍写远未理想；排除在自由文本里。

没有出处的句子：排除性推荐约束因此该换成 SQL。

## 5. NumConQ（BDMA 2026）

### 1. 论点与原文数字

摘要写：现有稠密检索器在数值约束上只有 16.3% 的准确率，并据此提出 NC-Retriever。正文把 16.3% 收窄了。第 3.4.1 节的实验是 Olympics 数据集加 Contriever，精确匹配查询，看 top-10 文档里的约束一致性。Height、Weight、Age 的一致性平均 16.3%。非数值属性 Gender、Country、Sport、Event、Medal 平均 73.64%。混合约束 Games（年份加季节，例如 2024 Summer）是 59.42%。16.3% 是这一组数值属性、这一个模型和这一个数据集上的一致性，摘要把它写成了稠密检索器的总准确率。

文档怎么来的：源数据是表。作者用模板把每条记录改写成自然语言，再把这些句子当成独立文档。查询也是模板（Equal、Less_than、Greater_than、Range）。相关与否由规则从句子里抽出数值再比对，每条查询的相关文档不超过 10。原表在检索时已经不在。

全表（表 3）BGE-M3 的 Recall@10 是 40.37%，Precision@10 是 10.45%。同表 BM25 的 Recall@10 是 28.93%，Precision@10 是 6.13%。四位数字切片上，最好的 BGE-M3 的 Recall@10 是 62.8%，Precision@10 是 12.4%。作者写多数检索器的 Recall@10 低于 30%，Precision@10 低于 10%。NC-Retriever 相对 BGE-M3 的涨幅，正文写 Recall@10 65.84%、Precision@10 78.28%。他们自己的补救仍是稠密检索器，不是查询语言。

### 2. 逻辑关系

递进：表格式条目改写成句子，再测稠密检索器能不能在句子里保住数值。转折：非数值属性的一致性是 73.64%，数值是 16.3%，所以失败集中在数值记号，不是「凡是约束嵌入都失败」。摘要把 16.3% 从 Contriever 加 Olympics 抬成了全体稠密检索器。

### 3. 隐含假设

模板句里的数字，等于用户库里仍可执行的列。规则抽取出的匹配，等于推荐相关性。把 Olympics 上的一致性写成推荐数值约束的失败率，这个滑移原文没有做，摘要对「全体稠密检索器」的写法已经比实验宽。

### 4. 证据强度

## 6. QUEST（ACL 2023）

### 1. 论点与原文数字

QUEST 评的是带逻辑算子的实体检索。表 4 同一张表上：T5-Large 双编码器的平均 Recall@100 是 0.476，MRecall@100 是 0.142；BM25 的 Recall@100 是 0.197，MRecall@100 是 0.037。正文定义：平均召回是每条查询相关文档集合的召回再平均；MRecall（Min et al., 2021）是候选集含全部相关文档的查询比例。0.142 是后一个定义。宏平均召回是另一列，就是 0.476。

### 2. 逻辑关系

并列两列：平均召回，以及「候选集是否含全部相关文档」。转折：双编码器两条都高于 BM25，但 0.476 仍把后面的分类器封顶。没有从「算子难」滑到「推荐约束上嵌入失败」，也没有滑到 SQL 已经胜出。

### 3. 隐含假设

实体约束写成逻辑模板之后，检索失败等于列谓词失败。QUEST 的文档是自由文本实体描述，约束在查询模板里，不在一张可执行的属性表上。

### 5. 结论

可以引用：T5-Large 双编码器的平均 Recall@100 是 0.476，MRecall@100 是 0.142；BM25 的 Recall@100 是 0.197。MRecall@100 是候选集含全部相关文档的查询比例。双编码器高于 BM25。

没有出处的句子：0.142 是宏召回；推荐约束上嵌入失败；SQL 已经胜出。

## 7. FollowIR（NAACL 2025）

### 5. 结论

可以引用：没有 Amazon 分割。MAG 和 PRIME 的 Hit@1 相对提升是 47.4% 和 54.9%，摘要平均 51%。系统是检索器银行加修正。

没有出处的句子：它在 Amazon 上打过 BM25，或没打过 BM25。

## 15. SAGE / SPARK（arXiv:2602.16964v1，2026-02-18）

文件名是 SPARK。论文标题是 SAGE: Structure Aware Graph Expansion for Retrieval of Heterogeneous Data。SPARK 是种子检索器，全称 Structure Aware Planning Agent for Retrieval over Knowledge Graphs。

### 1. 论点与原文数字

SAGE 先用一个种子检索器取 k 个节点，再扩张一跳邻居，然后用稠密加稀疏把邻居裁成 k′。在 STaRK 这种带模式的图上，种子检索器是 SPARK。SPARK 有两个工具：HNSW 语义搜索，以及 Neo4j 里的 Cypher 结构扩张。计划没有结果时，回退到 BM25 加余弦。邻居裁剪再用 BM25 和稠密嵌入。不是只执行 Cypher。

表 2 只报 Recall@20。合成 Amazon 的 n 是 1638：SPARK 53.95，BM25 53.77，multi-ada-002 55.12，ada-002 53.29。人工 Amazon 的 n 是 81：SPARK 33.56，BM25 15.23，ada-002 35.46。合成集上 SPARK 略高于 BM25，低于 multi-ada-002。人工集上 SPARK 高于 BM25，低于 ada-002。两格都不支持「只发 Cypher 就打过 BM25」。

同表把 KAR 的合成 Amazon R@20 印成 57.29，把 MoR 印成 59.90。KAR 原文是 57.24，MoR 原文是 59.92。转引用 SPARK 自己的表，不写回那两篇。

表 7 是人工集上的错误分布，每列加总 100。Cypher 的 Constraint 行是 Amazon 36、MAG 30、Prime 31。Over-Retrieval 是另一行：23、18、22。只留 Constraint 行。正文写 Amazon 和 Prime 上约束抽取失败占主导，不把两行加成 30%–36% 的合计数。

### 2. 逻辑关系

递进：扁平相似度看不见类型化的边，所以种子检索改成 HNSW 和 Cypher 交替，再加回退。转折：回退和邻居裁剪把 BM25 留在系统里。表 2 的合成 Amazon 上，这套混合只比 BM25 高 0.18 个 Recall@20，仍低于 multi-ada-002。错误分析再转折一次：Cypher 写出来之后，约束翻译仍是 Amazon 错误的 36%。

### 3. 隐含假设

智能体计划里的一次 Cypher，等于整条检索不再依赖向量或 BM25。系统描述把三处词法或向量步骤写在 Cypher 旁边。空结果回退尤其说明，只执行 Cypher 不被当成完整系统。

### 4. 证据强度

工具列表、表 2 的 n 和三行 R@20、表 7 的 Constraint 行，是强的。把 53.95 对 53.77 写成「只执行 Cypher 打过 BM25」，把 Constraint 和 Over-Retrieval 加在一起，都是弱的。

### 5. 结论

可以引用：合成 Amazon n=1638，R@20 为 SPARK 53.95、BM25 53.77、multi-ada-002 55.12。人工 n=81：SPARK 33.56，BM25 15.23，ada-002 35.46。工具是 HNSW、Cypher，空结果回退 BM25 加余弦。表 7 的 Cypher Constraint 行是 Amazon 36、MAG 30、Prime 31。表里的 KAR 是 57.29，不是 KAR 原文的 57.24。

没有出处的句子：只执行 Cypher 或 SQL 就能打过 BM25；约束抽取和过滤合计占错误的 30%–36%。

## 16. PCN-Rec（arXiv:2601.09771）

### 1. 论点与原文数字

PCN-Rec 把大模型当成提议者。候选窗口来自 MF/CF，窗口大小 \(W\)。两个智能体协商，调解模型写出 Top-N 和一份 JSON 证书。确定性校验器按物品元数据重算约束，不过就做约束贪心修复。约束是长尾曝光和类型多样性，符号是 \(\tau\)、\(\kappa\)、\(G_{min}\)。正文给了定义，没有给这三个符号的取值。可复现性清单要求报告它们，PDF 里仍没有数。不补。

式 (8) 的分母：PassRate 的分母是全体用户 \(|\mathcal{U}|\)，PassRate\(_\mathrm{feas}\) 的分母是窗口内存在可行名单的用户 \(|\mathcal{U}^+_W|\)。正文选 \(W=80\)，可行用户 551/943。表 1 的标题写明只在这 551 人上。

递进：先把不可满足的用户从方法失败里拆出去，再在可行用户上看通过率和 NDCG。转折：通过率从 0.000 到 0.985，NDCG 从 0.424 到 0.403。作者把这个下降写成硬约束的代价。另一处转折在伦理节：校验通过不等于解释忠实。

### 3. 隐含假设

MF/CF 窗口里的元数据标签是可信的。校验器只查已经写成代码的约束。候选生成器不是自然语言 SQL，名单也不是一条 SQL 的执行结果。

### 4. 证据强度

551/943、表 1 的四个数、伦理节的原句，是强的。摘要的 98.55% 和正文的 −0.022 与表内算术不完全一致，引用时两个都带上，不另造一个折中数。0.000 外推成大模型在约束推荐上的普遍通过率，分母只是这 551 人、这一次生成。\(\tau\)、\(\kappa\)、\(G_{min}\) 没有取值，补数会变成虚构。

### 5. 结论

可以引用：\(W=80\) 时可行用户 551/943，表 1 只在这 551 人上。一次生成的 PassRate 和 NDCG@10 是 0.000 与 0.424，校验后是 0.985 与 0.403。摘要把绝对差写成 0.021，正文又写成 −0.022。候选来自 MF/CF 窗口。伦理节写明解释声明本身不被验证。

没有出处的句子：0.000 是大模型在约束推荐上的普遍通过率；这是自然语言 SQL；解释因此忠实。

## 17. Faithful Chain-of-Thought（IJCNLP-AACL 2023）

### 1. 论点与原文数字

忠实的操作定义是：答案由确定性求解器执行符号链得到。推理被拆成两段。Translation：语言模型把问题译成带自然语言注释的符号程序。Problem Solving：外部求解器执行这段程序。脚注 2 写明：他们不声称生成推理链的过程、也就是 Translation 阶段，是可解释的。局限性一节再写：保证覆盖的是 Problem Solving；Translation 仍是不透明的。

相对普通思维链、Codex、贪心解码的涨幅，摘要和引言写的是：数学应用题 6.3%，规划 3.4%，多跳问答 5.5%，关系推理 21.4%。这些是推理基准，不是检索，也不是推荐。

StrategyQA 上「答案对、链里知识错」的例子还在。问题是 “Was Karachi a part of Alexander the Great’s success?”，模型答 True。链里的子问题把巴基斯坦写成包含巴基斯坦、阿富汗和印度。作者写：最终答案正确，并且忠实于这次生成，推理链仍含有错误知识。另一处图 7 的蜂鸟和豌豆是不同的失败：链里的重量关系被作者写成是对的，答案却不从链里推出。两例都留着，不并成一种。

### 2. 逻辑关系

递进：普通思维链的答案不必由链推出，所以把执行交给求解器。转折：求解器保证的是执行等式，翻译阶段仍可能写入错误知识，而 True/False 题上错误的链仍可能碰上正确的答案。忠实和事实正确被作者拆开了。

### 3. 隐含假设

符号链被求解器执行之后，用户看到的解释就是这条链。论文自己把翻译阶段放在保证之外，也把「答案正确」和「知识正确」拆开。

### 4. 证据强度

操作定义、脚注、四条相对涨幅、卡拉奇一例，是强的。把「返回行恰好是 SQL 结果」写成用户可用的忠实解释，超出了这篇的保证：执行等式可以当审计，链里的知识仍然可以是错的。

### 5. 结论

可以引用：忠实等于答案由确定性求解器执行符号链得到；脚注写明翻译阶段不在这个保证里。相对普通思维链的涨幅是数学应用题 6.3%、规划 3.4%、多跳问答 5.5%、关系推理 21.4%。StrategyQA 上答案对、链里知识错的例子还在。

没有出处的句子：返回行恰好是 SQL 结果，所以这是用户可用的忠实解释。执行等式可以当审计，不能当解释质量分数。

## 18. Atil 等：Non-Determinism of “Deterministic” LLM Settings（arXiv:2408.04667）

### 1. 论点与原文数字

五个模型、八个任务、零样本和少样本，温度 0，每个条件跑 10 次。TARr@N 是 N 次运行的原始字符串全部相同的题目比例。TARa@N 是解析后的答案全部相同。他们写明：可以出现准确率 100%、TARa@N 100%、TARr@N 0，因为原始字符串差一个字符就算不一致。

摘要的 15% 是各次运行准确率起伏的上限。正文写有些任务上，十次运行的最低准确率和最高准确率相差 5%–15%。70% 是 BestAcc 对 WorstAcc 的上限，也就是「每次挑对的那次」对「每次挑错的那次」，不是某一次运行的准确率自己晃了 70 个点。

表 2 是少样本。college math、Mixtral-8x7B 的 BestAcc、中位、WorstAcc 是 75.0、31.5、03.0。PDF 把最差印成 03.0。这一格的最好对最差是 72 个点。它是五个模型、八个任务里的一格，不改写成 70% 的唯一来源，也不改写成 15% 的来源。15% 属于运行之间的准确率起伏，70% 属于 BestAcc 对 WorstAcc。

SQL 上只能借用定义：TARr 看 SQL 字符串是否逐字相同，TARa 看解析后的查询是否相同。五个模型和八个任务上的起伏是生成器的起伏。ReproRAG 表 6 说明，固定输入下的索引和 CPU 搜索可以完全不变。SQL 执行器在同一条 SQL、同一个库上也不靠这 15% 或 70% 来晃。

### 2. 逻辑关系

并列两种不一致：字符串不一致，答案不一致。再并列两种幅度：运行之间的准确率差，以及最好可能对最坏可能。转折：温度 0 仍会让字符串变化，所以「确定性设置」不等于 TARr 为 100。执行器不在这条链上。

### 3. 隐含假设

这五个模型和八个任务上的晃动，会以同样的幅度出现在另一个 SQL 生成器上。论文没有测 SQL。借用的是定义，不是这两个上限。

### 4. 证据强度

定义、摘要的两个上限、表 2 的 75.0 / 31.5 / 03.0，是强的。把 15 或 70 写成本篇生成器的预期晃动，把某一格当成 70% 的唯一来源，或写成 SQL 执行器自己会晃，都没有原文。

### 5. 结论

可以引用：TARr@N 看原始字符串，TARa@N 看解析后的答案；可以出现准确率 100%、TARa 100%、TARr 0。摘要的 15% 是运行间准确率起伏的上限，70% 是 BestAcc 对 WorstAcc 的上限。表 2 少样本、college math、Mixtral 是 75.0、31.5、03.0。SQL 上只借用 TARr 的定义来看字符串。

没有出处的句子：15% 或 70% 是这篇 SQL 生成器的预期晃动；SQL 执行器自己会晃。

## 19. ReproRAG（arXiv:2509.18869，页眉 Workshop ’25）

### 1. 论点与原文数字

ReproRAG 量的是向量 RAG 跨次运行会不会漂。Jaccard 是 \(|A\cap B|/|A\cup B|\)，忽略名次。Kendall 的 tau 比较两边都出现的文档的名次；作者写 1.0 表示两边共同出现的文档顺序相同。只在一边出现的文档不进 tau。

表 6 的场景是：文档嵌入事先算好并缓存，随机种子固定，在 CPU 上从这些嵌入重建 FAISS，再跑同一批查询。Flat_L2、Flat_IP、IVF、HNSW_accurate、HNSW_fast、LSH 的精确匹配、Jaccard、Kendall 都是 1.00。作者写：在这个受控条件下，索引和 CPU 搜索本身可以完全复现。漂移来自数据插入、换模型和数值环境，不来自「FAISS 在固定输入下必然随机」。

同一条 SQL、同一个库，结果集的 Jaccard 应当为 1。没有 `ORDER BY` 时结果是集合，没有名次可排，Kendall 不当主稳定性指标。tau 只看交集，集合已经变了仍可以看起来很稳，所以稳定性以 Jaccard 为主。

这篇实际用的编码器是 bge-base-en-v1.5、e5-base-v2、Qwen3-0.6B-Base。五编码器、2,200 万到 80 亿参数、改写距离 32%–50% 不在这 21 份 PDF 里，不引。

### 2. 逻辑关系

并列几种漂移来源：插入数据、换模型、数值环境、固定种子下重建。转折：固定缓存嵌入和固定种子时，Jaccard 和 Kendall 可以是 1。没有从嵌入索引会漂，滑到 SQL 结果集会自己漂。

### 3. 隐含假设

两次 top-k 的集合重叠代表系统可复现。SQL 结果集借用这个定义时，两次执行看到的是同一个库、同一条 SQL。这个假设对精确 SQL 成立。论文自己把向量索引的漂移和固定输入下的可复现分开了。

### 4. 证据强度

定义和表 6 的 1.00 是强的。「索引会漂」只在插入、换模型、数值环境那些场景里是强的。写成「SQL 结果集会自己漂」不成立。

### 5. 结论

可以引用：Jaccard 是 \(|A\cap B|/|A\cup B|\)，忽略名次；Kendall 只比较两边都出现的文档。表 6 在固定缓存嵌入、固定种子、CPU 重建时，Flat、IVF、HNSW、LSH 的精确匹配、Jaccard、Kendall 都是 1.00。同一条 SQL、同一个库，结果集的 Jaccard 应当为 1。

没有出处的句子：SQL 执行不稳定；没有 `ORDER BY` 时把 Kendall 当主稳定性指标；五编码器、2,200 万到 80 亿参数、改写距离 32%–50%。
