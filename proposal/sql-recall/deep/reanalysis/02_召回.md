重复文件一行：`SIEVE-PVLDB18-li.pdf`（14 页，PVLDB 18(11):4723–4736, 2025）与 `SIEVE-2507.11907.pdf` 是同一篇。下面只分析更全的 arXiv 稿（16 页，含附录）。

不是重复、不要并成一篇的：RecSys 2019 与 TOIS 2021 是同一条复现工作的会议稿和期刊扩展，样本和结论口径不同。WebReco（IRS 2024）和 EARL（RecSys 2024 研讨会）是两篇，Q′ 的线上格子两份一致，那一组 CTR 只算一次观察。文件名 `Shevchenko-2505.09364.pdf` 的作者是 Benigni、Ferrari Dacrema、Jannach。

这一路要回答的问题是：有没有一篇已经占住「大模型写出一条协同 SQL 自连接，数据库执行，再用推荐的 Recall 或 NDCG 打分」。

## TIGER

文件 `TIGER-2305.05065.pdf`。Rajput 等。NeurIPS 2023。首页标题是 *Recommender Systems with Generative Retrieval*。

### 1. 论点与论据

问题：大规模召回通常是把查询和物品嵌到同一空间，再做近似最近邻。作者认为可以改成自回归地解码目标物品的标识。

主张：用 RQ-VAE 把文本嵌入收成有层级的 Semantic ID；序列到序列模型直接生成下一个物品的 ID，而不是最大内积；没有交互历史的物品仍可借语义 ID 被召回（摘要，第 1 页）。

方法：Sentence-T5 编码标题、价格、品牌、类目。RQ-VAE 三级码本、每级 256，再加一位消解冲突，得到长度 4 的唯一 ID。T5 编码器–解码器约 1300 万参数，输入是哈希后的用户 token 加历史 Semantic ID，预测下一项的 ID（第 5–6 页）。碰撞只在量化之后用查找表修一次。

实验：Amazon 2014 的 Beauty、Sports and Outdoors、Toys and Games。附录 C：用户评论少于 5 条的去掉；留一，最后一条测试、倒数第二条验证；训练时历史截到 20。表 6 只印用户数、物品数和序列长度，Beauty 是 22,363 用户、12,101 物品、平均长度 8.87，没有印交互次数。指标 Recall@5/10、NDCG@5/10。正文没有写「对全体物品打分」或「不用采样负例」。

表 1（第 7 页）：除 P5 外，基线数字来自 Zhou 等 S3-Rec 的公开结果。Beauty 上 TIGER 的 Recall@5 / NDCG@5 / Recall@10 / NDCG@10 是 0.0454 / 0.0321 / 0.0648 / 0.0384；SASRec 是 0.0387 / 0.0249 / 0.0605 / 0.0318；S3-Rec 的 Recall@10 是 0.0647。表底相对该数据集最好基线：Beauty 的 Recall@10 是 +0.15%，NDCG@5 是 +29.04%。附录表 9 三次运行的 Beauty 均值是 Recall@10 0.0642±0.00092、NDCG@10 0.0374±0.00061，低于主表的单次 0.0648 / 0.0384。脚注说标准误不显著。

冷启动（第 8–9 页，图 5）从 Beauty 测试物品里拿掉 5% 作为未见物品，对照的是语义空间上的 k 近邻，文中称为 Semantic_KNN。这不是主表里的协同近邻。

论文自己的限制写在方法里：生成出的 Semantic ID 可能对不上目录里的物品；附录说这种事件概率低，并讨论怎么处理。官方代码是否放出，这篇 PDF 没有写。

### 2. 逻辑

因果：文本嵌入可量化成短 ID，所以自回归解码可以代替向量近邻。递进：先证明 ID 有层级（图 4 是定性的），再报主表，再用消融说明 RQ-VAE 好于 LSH 和随机 ID（表 2），最后把冷启动和多样性说成这个表示带来的新能力。转折藏在表底：NDCG@5 的百分数很大，Recall@10 几乎和 S3-Rec 打平。

### 3. 隐含假设

- 「表里的 SASRec 就是强的已发表 SASRec」不成立。这篇写明该行来自 S3-Rec 公开结果，不是在本文里用全体物品交叉熵重训的。2018 年 SASRec 原文不在本目录，不能把 0.0605 / 0.0318 说成原文那一格。同目录 Xu 等写明 SASRec 原文训练用的是 BCE、每个正例一个负例。
- Hit@K 不能拿去和别的论文横比。这里印的是 Recall 和 NDCG，不是 Hit。绝对值和 Xu 的全库 NDCG 同一量级，但历史截断（这里训练限 20，Xu 的 SASRec 最大长度 50）和交互次数（TIGER 未印）都不对齐。
- 主表没有 KNN。冷启动图里的 Semantic_KNN 是嵌入近邻，不能代替调过邻域和收缩的 ItemKNN。
- 没有线上 CTR。
- SQL 表达不了这件事。自回归生成离散码不是自连接。共现计数可以用自连接写出来，但这篇没有把那一臂放进表 1。

### 4. 证据

强度：中。协议写清了留一和数据来源，表 1 和表 9 都在。漏洞：最好基线的数字是抄来的；主表单次高于三次均值；「显著超过 SOTA」在 Beauty 的 Recall@10 上是 +0.15%。没有 ItemKNN、EASE，也没有全量交叉熵 SASRec。

### 5. 能信什么

能信：在这份抄来的基线上，Semantic ID 生成的 NDCG 高于表内 SASRec；Recall@10 基本打平 S3-Rec。不能引用：生成式检索已经打赢调好的序列模型；SQL 写不出或写得出这种召回。Xu 在同一用户数、同一物品数的 Beauty 上，全量交叉熵 SASRec 的 NDCG@10 是 0.0597，高于这里的 0.0384。那是方向对照，不是配对实验。

## EAGER

文件 `EAGER-2406.14017.pdf`。Wang 等。KDD 2024。

### 1. 论点与论据

问题：生成式推荐要么只用行为码，要么只用语义码。作者认为两者互补，但直接在编码器侧融合特征会变差。

主张：共享编码器、两个解码器，分别生成行为 token 和语义 token；用预测熵做置信度合并；加全局对比和语义引导的迁移任务（摘要，第 1–2 页）。

方法：行为编码器是预训练 DIN，语义编码器是 Sentence-T5。层次 k-means 的簇数 256。训练损失是生成、对比、重建、识别四项相加。推理时每条流 beam search，再按对数概率排序（第 5 页）。

实验：表 1，Beauty / Sports / Toys / Yelp。Beauty 是 22,363 用户、12,101 物品、198,360 次交互。留一；训练历史截到 20；Recall 与 NDCG 的 5/10/20。没有写采样负例或全库排序。没有星号的基线来自 TIGER 和 S3-Rec 的公开结果；星号是他们重跑的（第 6 页）。

表 2 Beauty：EAGER 的 Recall@5/10/20 是 0.0618 / 0.0836 / 0.1124，NDCG@10 是 0.0525。SASRec 的 Recall@10 / NDCG@10 是 0.0605 / 0.0318，与 TIGER 表 1 相同。TIGER 的 Beauty Recall@10 是 0.0648。最好基线一栏：Recall@10 相对 Recforest 的 0.0664 是 +25.90%。Toys 的 Recall@20 是 0.1024，改进栏 −3.85%；同列 S3-Rec 是 0.1065，按 (0.1024−0.1065)/0.1065 就是这个负数。表注写明最后一列是相对该行最优基线。Beauty Recall@5 的 31.49% 对得上 Recforest 的 0.0470，对不上 TIGER 的 0.0454。正文双栏排版里有「compared to TIGER」的碎片，不能把 31.49% 改写成相对 TIGER。

### 2. 逻辑

递进：先论证单流生成浪费了另一种信息，再给出双流、对比、迁移三块，最后用消融表 3 把三块加回去。并列：四套数据上的胜负并不并列。Beauty 的 Recall 高于表内最好基线，Toys 的 Recall@20 为负。

### 3. 隐含假设

抄来的 SASRec 被当成「传统序列模型」的代表。它和 TIGER 是同一行弱数字，不是 Xu 的全量交叉熵。Hit 与 Recall 没有横比问题，因为这篇报的是 Recall/NDCG，但和 Xu 的 NDCG 仍只是方向：交互次数差 142（198,360 对 198,502）。没有用弱 KNN 充 ItemKNN。没有把线上 CTR 当成算子必要。SQL 表达不了双流生成；行为码来自交互嵌入的量化，不是一条连接语句。

### 4. 证据

强度：中。表 2 自己已经否定「全面超过」。NDCG@10 的 0.0525 低于 Xu 的 0.0597，这是跨论文方向，不是本文的失败宣告，但足够挡住「超过调好的 SASRec」。Yelp 的 NDCG@5 改进栏印着 3.51%，用同表 TIGER 的 0.0146 按相对差算出来对不上，这一格的百分数不要单独引用。

### 5. 能信什么

能信：在他们这套留一、历史长度 20、且多数基线抄自 TIGER 的表里，Beauty 的 Recall@10 高于表内最好基线。不能引用：双流生成已经打赢全量交叉熵 SASRec；Toys 也全面更好；这和 SQL 召回有关。

## LETTER

文件 `LETTER-2405.07314.pdf`。Wang 等。CIKM 2024。

### 1. 论点与论据

问题：量化语义 ID 时，码字分配会偏，而且和协同信号不对齐。

主张：量化时加协同正则和多样性正则，让码本靠近 SASRec 的物品向量，并减轻码字扎堆（第 2 页贡献）。

方法：LETTER 是插在 RQ-VAE 上的正则，不换召回引擎。后端仍是 TIGER 或 LC-Rec 的自回归生成。协同项用的是一个已经训好的 SASRec 物品向量。

实验：Instruments、Beauty、Yelp。5-core，留一，历史截到 20，跟 TIGER。表 1 的列是 R@5、R@10、N@5、N@10。Beauty：SASRec 0.0380 / 0.0588 / 0.0246 / 0.0313；他们重做的 TIGER 0.0395 / 0.0610 / 0.0262 / 0.0331；LETTER-TIGER 0.0431 / 0.0672 / 0.0286 / 0.0364；LC-Rec 0.0443 / 0.0642 / 0.0311 / 0.0374；LETTER-LC-Rec 0.0505 / 0.0703 / 0.0355 / 0.0418。原 TIGER 论文 Beauty 的 Recall@10 是 0.0648，这里重做是 0.0610，两篇的 Beauty 格子不要横比。

### 2. 逻辑

因果：码字若对齐协同向量并拉开多样性，后端生成会更准。递进是先定义两项损失，再在两个后端上各报一次。没有转折：表 1 上 LETTER 的四个 Beauty 指标都高于对应后端。

### 3. 隐含假设

表内 SASRec 的 Beauty NDCG@10 是 0.0313，仍是弱行，不是 Xu 的 0.0597。正则所对齐的那个 SASRec 向量，论文没有写是全量交叉熵训出来的。指标是同一张表内的 R/N，不能拿去和 Xu 或原 TIGER 比小数。没有 KNN，没有 CTR。SQL 表达不了码本正则。协同信号进的是量化损失，不是一条可执行连接。

### 4. 证据

强度：中，只在他们的重实现上。Beauty 上相对自己重做的 TIGER，Recall@10 从 0.0610 到 0.0672。没有全库声明，没有强序列基线，没有多次种子。

### 5. 能信什么

能信：在这张重实现表里，加上两项正则后，两个生成后端的 Beauty 指标都升了。不能引用：语义 ID 因此超过调好的 SASRec，或 SQL 做不到这件事。

## LC-Rec

文件 `LC-Rec-2311.09049.pdf`。Zheng 等。首页未印会议名。

### 1. 论点与论据

问题：把物品换成文本标题再让 LLM 做推荐，很难在全体物品上生成；语义 ID 若只靠语言、不对齐协同，也不够。

主张：索引用 RQ-VAE 做成唯一、可扩展的短码；再用一组对齐任务把语言语义和协同语义一起放进 LLaMA-7B。摘要写平均提升 25.5%，且是 full ranking（第 2 页）。

方法：LLaMA-7B。索引 4 层、每层 256。TIGER 按论文重做，因为官方代码未放出（第 8 页）。生成时 beam 为 20。

实验：Amazon 2018 的 Instruments、Arts、Games，不是 2014 Beauty。表 II：Games 50,547 用户、16,860 物品、452,989 次交互。留一。正文写明 full ranking，对全体物品排序，不用 sample-based evaluation（第 8 页）。表 III Games 的 HR@10：LC-Rec 0.1174，SASRec 0.0940，FDSA 0.1041，TIGER 0.0939，相对最好基线 +12.78%。Instruments 的 HR@10 是 0.1220 对 S3-Rec 0.1136（+7.39%）。Arts 是 0.1266 对 S3-Rec 0.1051（+20.46%）。25.5% 是正文的平均说法，不是这三格的算术平均，不要把两者写成同一个数。

### 2. 逻辑

递进：先说明文本方法做不了全库生成，再说明纯语义 ID 缺协同，然后用索引加对齐任务补上，最后用全库留一检验。因果依赖「对齐任务把协同写进了 LLM」；表 III 没有拆开「只换 ID」和「对齐任务」对 25.5% 的份额，消融在后面的表里。

### 3. 隐含假设

SASRec 是他们表里的 ID 序列模型，Games 上 HR@10 低于 FDSA 和 S3-Rec，不是最强基线，也没有写成全量交叉熵。数据年份和类目都不同于 TIGER Beauty，Hit/HR 不能横比。没有 KNN，没有 CTR。查询是语义 ID 的生成，执行器是 beam search。SQL 的自连接写得出共现，写不出这 7B 模型的生成分布。

### 4. 证据

强度：中。全库留一写明了，这是这批生成式论文里少数把评估协议说死的。漏洞：SASRec 是否弱，取决于它的损失，本文没有换成 Xu 的损失；25.5% 的平均口径和分表的 +7% 到 +20% 不是同一句话。

### 5. 能信什么

能信：在这三份 2018 数据的全库留一上，LC-Rec 的 HR@10 高于表内最好基线。不能引用：因此超过 Beauty 上的全量交叉熵 SASRec；也不能把「LLM 生成 ID」说成「LLM 写 SQL」。

## IDGenRec

文件 `IDGenRec-2403.19021.pdf`。Tan 等。SIGIR 2024。

### 1. 论点与论据

问题：整数语义码对人不可读，也不在语言模型的词空间里。

主张：用文本词当物品 ID；生成器和推荐器交替训练，让 ID 对齐推荐（摘要与第 3 节）。

方法：SentencePiece 词表。生成器产文本 ID，推荐器在这些 ID 上做序列推荐，再把推荐损失送回生成器。

实验：Sports、Beauty、Toys、Yelp。表 3 的 Beauty 是 22,363 / 12,101 / 198,502，与 Xu、STAR 相同。第 6 页写明：评估不用负采样，对全体物品排序。留一。表 4 Beauty 的 HR@10 / NDCG@10：IDGenRec 0.0814 / 0.0541，SASRec 仍是 0.0605 / 0.0318。作者写相对每行最好基线的平均提升，Sports / Beauty / Toys / Yelp 是 39.44% / 23.55% / 42.37% / 36.76%（第 6–7 页）。

### 2. 逻辑

因果：文本 ID 若按推荐损失改写，生成式推荐会比整数码更会用语言模型。递进是单数据集主表，再做交替训练的消融。转折没有出现在主表里：相对抄来的 SASRec，四套数据都更好。

### 3. 隐含假设

SASRec 一行与 TIGER 表 1 相同，是弱行。NDCG@10 0.0541 仍低于 Xu 同一用户数、同一物品数上的 0.0597。评估协议写了全库，所以和「100 个采样负例的 Hit」不是一回事，但和 Xu 的 NDCG 仍只是方向。没有 KNN，没有 CTR。文本 ID 是给语言模型生成的，不是给数据库执行的。

### 4. 证据

强度：中。全库这句写明了，数字来自一张表。漏洞：对照的 SASRec 是公开结果里的弱档；23.55% 是四个指标对各自最好基线的平均，不是单一 HR@10 的相对差。

### 5. 能信什么

能信：在「抄来的弱 SASRec + 全库留一」下，文本 ID 的 Beauty HR@10 和 NDCG@10 更高。不能引用：已经打赢全量交叉熵 SASRec，或文本 ID 等价于 SQL。

## OneRec-Think

文件 `OneRec-Think-2510.11639.pdf`。Liu、Wang 等。首页未印会议名。

### 1. 论点与论据

问题：生成式推荐直接吐物品 token，没有把推荐里的多步理由用起来。

主张：把物品 token 对齐到 LLM 词空间；用推荐场景的多步推理再增强；推理奖励允许多个都算对的下一物品；线上用 Think-Ahead 把推理挪到离线（第 2 页）。

方法：公开实验用 Qwen3-1.7B，四层语义 ID。工业模型是 Qwen-8B。评估 beam 宽度 10。

实验：表 1，Amazon Beauty、Toys、Sports，预处理引用 TIGER。留一；训练历史截到 50（附录 A.1）。没有写「对全体物品排序、不用负采样」。Beauty：OneRec-Think R@10 0.0791、N@10 0.0471；SASRec 0.0607 / 0.0320；他们的 TIGER 0.0623 / 0.0337。Toys 上他们的 TIGER R@10 是 0.0547，低于他们自己的 SASRec 0.0626；原 TIGER 论文 Toys 的 Recall@10 是 0.0712，两套不要横比。消融表 2：Base 的 R@10 0.0654，加对齐 0.0735，加推理 0.0791。线上表 3：1.29% 流量、对照线上模型、一周；App Stay Time +0.159%，Watch Time +0.169%。

### 2. 逻辑

递进：对齐提供表示，推理再加一截，表 2 是这个顺序。并列：公开表和快手 A/B 是两套任务。转折在 Toys：他们重做的 TIGER 低于他们自己的 SASRec，所以「全面高于生成式检索」依赖他们这次的 TIGER 实现。

### 3. 隐含假设

表内 SASRec 的 N@10 是 0.0320，不是 Xu 的 0.0597。0.0471 低于 0.0597，方向上没有打赢那一档。R@K 与 Xu 的 NDCG 不是同一指标。没有 KNN。线上 +0.159% 是整条工业系统相对线上模型，不能推出「推理算子在公开库上必要」。推理文本不是 SQL，也不是约束谓词。

### 4. 证据

强度：中，限于他们这套弱 SASRec 和这次重做的 TIGER。工业数字外部无法复核，流量和指标都写清了，但不是公开库 Recall。

### 5. 能信什么

能信：在表 1 的协议下，Beauty 的 R@10 高于他们自己的 SASRec 和 TIGER；表 2 里推理在对齐之后还有增量。不能引用：N@10 0.0471 打赢了全量交叉熵 SASRec；停留时长证明该用 SQL 或证明不该用 SQL。

## LLM2Rec

文件 `LLM2Rec-2506.21579.pdf`。He 等。KDD 2025。

### 1. 论点与论据

问题：通用文本嵌入缺协同，推荐模型又把物品只当成 ID。

主张：两阶段把 LLM 变成物品编码器。先做协同监督微调，再做物品级嵌入，使向量同时带语义和协同。下游仍是 GRU4Rec 或 SASRec（摘要）。

方法：解码器最后变成编码器。下游损失是交叉熵（附录）。嵌入投到 128 维。评估三次种子平均。

实验：第 6 页写明 full ranking，全体物品为候选，Recall 与 NDCG 的 10 和 20。数据是 Games、Arts、Movies，以及域外的 Sports、Baby、Goodreads，不是 TIGER 那份 Beauty。表 3 SASRec 行的 R@10 与论文印出的 %Improv.（相对同表最强嵌入基线）：Games 上 LLM2Rec 0.0865 对 LLMEmb 0.0813（6.42%）；Arts 0.0925 对 0.0865（6.95%）；Movies 0.0705 对 LLM2Vec 0.0662（6.49%）；Sports 0.1170 对 LLMEmb 0.1131（3.51%）；Baby 0.0708 对 0.0659（7.39%）；Goodreads 0.1530 对 BLAIR 0.1508（1.45%）。表里每一行都是「文本嵌入初始化的 SASRec」。没有从零训练的纯 ID SASRec，没有 ItemKNN，没有 EASE。

### 2. 逻辑

因果：协同微调改变了 LLM 的物品向量，所以同一个 SASRec 会涨。递进是域内再到域外。转折是 Goodreads 的 R@10 只剩 1.45%，域外并不均匀。

### 3. 隐含假设

这里的 SASRec 是交叉熵、全库，比 TIGER 抄来的那行更接近强序列模型，但它是嵌入初始化的，不是 Xu 那种从零训练的 ID SASRec。不能把 0.0865 和 Beauty 的 0.06 横比。没有用弱 KNN。没有用 CTR 证明召回算子。产出是向量，召回仍是内积。协同进了编码器，没有进一条可执行连接。SQL 可以存这些向量再做最近邻，那是另一条系统，不是这篇的方法。

### 4. 证据

强度：中。全库和三次平均写明了，%Improv. 是表内相对嵌入基线。漏洞：没有 ID 版 SASRec、ItemKNN、EASE，所以「LLM 嵌入优于协同模型」没有被检验，只检验了「优于其他文本嵌入」。

### 5. 能信什么

能信：在嵌入初始化、全库、交叉熵 SASRec 这个协议下，LLM2Rec 高于同表最好的嵌入基线，Goodreads 的相对增益很小。不能引用：因此超过调好的 ItemKNN 或从零训练的 SASRec；也不能说协同 SQL 被这篇占住。

## HLLM

文件 `HLLM-2409.12740.pdf`。Chen 等。首页未印会议名。

### 1. 论点与论据

问题：LLM 要迁到推荐，但不能只靠零样本；物品若每次现算，服务会太贵。

主张：物品 LLM 和用户 LLM 分层；必须用推荐目标微调；变大时还在涨；物品向量可以缓存，使训练和服务接近 ID 模型（第 2 页）。

方法：物品 LLM 产向量，用户 LLM 吃物品向量序列。Books 上默认 512 个负例、batch 128。带 † 的行把负例和 batch 加到 28k 和 512（表 7 注）。

实验：表 7，Pixel8M 和 Amazon Books，留一。表头是 R@10/50/200 与 N@10/50/200。格子大于 1，例如 Pixel8M 上 HLLM-1B 的 R@10 是 6.129，SASRec∗ 是 5.083。Books 上 SASRec (2018) 的 R@10 是 3.06，他们重跑的 SASRec∗ 是 5.35，HLLM-1B 是 6.97，HLLM-7B† 是 9.39，相对 SASRec (2018) 的平均改进栏是 +169.58%。论文没有写「这些格子是百分数」，但 Recall 按定义不能大于 1，所以只能按百分数口径读，不能和 TIGER 的 0–1 Recall 横比。评估是留一的 Recall，不是 100 个负例打分。线上是排序任务，「关键指标」增加 0.705%（第 7–8 页），没写是哪一个指标。

### 2. 逻辑

递进：分层，再微调，再放大参数和负例，再缓存以便上线。因果是「推荐目标微调加上更大的模型」带来表 7 的差距。转折：SASRec∗ 已经比 SASRec (2018) 高一截，所以 +169.58% 的分母是 2018 那一档，不是他们自己重跑的 5.35。

### 3. 隐含假设

SASRec (2018) 在这张表里是弱档。SASRec∗ 是他们重跑的，比抄表老实，但没有写是不是全量 softmax。负例数 512 或 28k 是训练用的，不是评估采样。没有 ItemKNN / EASE。0.705% 没有指标名，不能当成 CTR，也不能推出分层 LLM 是召回所必需。服务路径是缓存向量加现有排序模型。SQL 表达不了这套分层网络。

### 4. 证据

强度：中，限于 PixelRec / Books 的留一口径。漏洞：大于 1 的表没有单位声明；线上指标匿名；没有非序列强基线。

### 5. 能信什么

能信：在这张留一表里，HLLM-1B 高于他们重跑的 SASRec∗；把 2018 年那一档当对照，百分数会很大。不能引用：7B 因此是召回 SOTA，或这条路径已经覆盖协同 SQL。它太贵，不适合当先导主对照。

## NoteLLM

文件 `NoteLLM-2403.01744.pdf`。Zhang 等。WWW 2024 Companion。

### 1. 论点与论据

问题：笔记推荐要一条可检索的向量，而通用 LLM 不会把笔记压成适合对比学习的表示。

主张：压缩提示把笔记压成一个特殊 token，再做对比学习；同时生成话题标签或类目，并说这会反过来加强嵌入（摘要）。任务是小红书笔记到笔记，不是用户序列的下一物品。

实验：表 2（第 6 页）是百分数。测试池是下个月的笔记，训练笔记排除在外。拿一条笔记当查询，在池子里找配对的另一条。NoteLLM 7B 的 Recall@100 / 1k / 10k / 100k 是 84.02 / 95.23 / 99.23 / 99.96。RepLLaMA 是 83.63 / 95.10 / 99.27 / 99.94。PromptEOL+CSE 是 83.28 / 95.26 / 99.20 / 99.96。线上 SentenceBERT 是 70.72 / 87.88 / 96.29 / 99.62。线上（第 8 页）：相对 SentenceBERT，CTR +16.20%，评论数 +1.10%，周均发布者 +0.41%；新笔记一天内评论数 +3.58%。

### 2. 逻辑

并列：离线召回和线上点击是两套对照。因果句是「压缩 token 的对比学习带来可检索的笔记向量」。转折：相对 RepLLaMA，Recall@100 只高 0.39 个点；Recall@1k 是 95.23，低于 PromptEOL+CSE 的 95.26。大的差距只相对线上旧的 SentenceBERT。

### 3. 隐含假设

没有 SASRec。Recall@100 的百分数不能和 Amazon 的 Recall@10 横比。没有 KNN 冒充 ItemKNN。CTR +16.20% 的对照是 SentenceBERT 内容嵌入，不能推出「协同召回算子必要」。新笔记没有交互边，自连接帮不上。SQL 表达不了这条对比嵌入。

### 4. 证据

强度：强，只在「相对 SentenceBERT 的笔记检索和线上点击」。相对强嵌入，证据弱。

### 5. 能信什么

能信：对着线上 SentenceBERT，离线 Recall 和线上 CTR 都更高。不能引用：LLM 笔记编码器大幅优于强嵌入；也不能把 +3.58% 写成协同 SQL 成功或失败的证据。

## STAR

文件 `STAR-2410.16458.pdf`。Lee 等。首页未印会议名。

### 1. 论点与论据

问题：监督推荐模型要训练；作者想要一个不训练、还能跨类目用的 LLM 流程。

主张：检索分是语义相似度和共现的加权和，再乘时效，主实验里评分被关掉；排序阶段把候选、流行度和共现次数写进 Gemini 的提示，做 point-wise / pair-wise / list-wise（第 4–5 页）。共现是管线算好再填进提示，不是模型现写的查询。

实验：Amazon 2014 Beauty、Toys、Sports。表 1 的 Beauty 是 22,363 / 12,101 / 198,502。留一。指标是 Hits 和 NDCG 的 5 和 10。正文没写采样负例。同表 SASRec 的 Hits@10 是 0.061，与 TIGER 表 1 的 Recall@10 0.0605 对齐到同一量级。表 2：成对排序 Hits@10 为 0.101 / 0.120 / 0.056，NDCG@10 为 0.060 / 0.073 / 0.034。只检索 Hits@10 为 0.098 / 0.118 / 0.054。KNN 为 0.007 / 0.007 / 0.002。正文写的 KNN 是「找 10 个最相似用户再平均打分」的 UserKNN（第 5 页）。IDGenRec 在同表 Hits@10 是 0.081 / 0.087 / 0.057，Sports 高于 STAR 的 0.056。表 3：去掉评分后 Hits@10 更高。表 6：提示里加共现，Beauty 的 NDCG@10 到 0.0600；只加流行度没有同样的好处。

局限（第 9 页）：语义项依赖物品文本；没有文本时这一项会变弱。检索的可扩展性被列为限制。

### 2. 逻辑

并列：检索和排序是两段，排序只在检索候选上重排。因果：语义和共现都去掉时 Hits@50 会掉（图 4），所以两项都有贡献。转折：KNN 的 0.007 被放在同一张主表里，读者容易把它当成「近邻很弱」，但那是 top-10 UserKNN。

### 3. 隐含假设

SASRec 的 0.061 是生成式检索那一串里的弱行。Hits@10 与 TIGER 的 Recall@10 在同一份 Beauty 上数值接近，仍不要写成严格同一指标。0.007 的 KNN 不能代表调过的 ItemKNN，也不是语义近邻。没有线上 CTR。共现次数是自连接写得出来的计数；语义分是嵌入，不是连接。模型没有写 SQL。把共现填进提示，不等于模型生成了协同查询。

### 4. 证据

强度：中，限于这套留一和 Gemini 成对排序。漏洞是基线：UserKNN 和弱 SASRec 把检索衬得过高。成对排序的 Beauty NDCG@10 0.060 与 Xu 的 0.0597 粘在一起，不能写成谁赢谁。

### 5. 能信什么

能信：免训练的语义加共现检索，在这张表里高于他们列入的弱 SASRec；共现项对排序有贡献。不能引用：0.007 说明 ItemKNN 或 Swing 很弱；也不能把「提示里的共现句」当成 SQL 即解释。

## GPT4Rec

文件 `GPT4Rec-2304.03879.pdf`。Li 等。5 页。arXiv:2304.03879。PDF 仍是 ACM 模板占位会议名 *Conference acronym ’XX ... Woodstock*，版权行印着 2018。不当档案版引用。

### 1. 论点与论据

强度：中，只在这张用户级划分、截断 15 的表里。强基线缺失。模板占位会议名使它不能当档案论文引用。

### 5. 能信什么

能信：在这张表上，多查询加 BM25 的 Recall@40 高于 BERT4Rec，相对差是论文写的 75.7% 和 22.2%。不能引用：因此超过 SASRec 或 ItemKNN。它是「写查询、另一个引擎执行」的近邻，抄的是管线。差在引擎、查询语言，以及没有协同自连接。

## InteRecAgent

文件 `InteRecAgent-2308.16505.pdf`。Huang、Lian 等。首页标题是 *Recommender AI Agent*，系统名 InteRecAgent 在正文。首页未印会议名。

### 1. 论点与论据

问题：推荐模型会排序，但不会对话和解释；LLM 会对话，但没有领域目录和行为。

主张：LLM 做规划，推荐模型当工具；候选在工具之间用共享内存传递；工具分成信息查询、检索、排序；为了让小模型学会调工具，用 GPT-4 做模仿数据，得到 RecLlama（第 2 页）。

方法：硬条件用 SQL Retrieval Tool，软条件用 ItemCF，排序用去掉位置编码的 SASRec。SQL 用 pandasql 里的 SQLite。附录图 C4 把 SQL 检索限制死了：物品标题不能当条件；这个工具不能找相似物品；字符串列必须用 LIKE；SQL 里只能出现一张物品信息表；选出所有满足条件的物品，不许用 LIMIT；尽量用 OR 而不是 AND。相似物品走 ItemCF，输入是种子标题列表。Query Tool 是另一支，用来查描述、价格、计数，并且写明不能给推荐。

实验：Steam、MovieLens、Amazon Beauty。表 A1 的 Beauty 是 15,577 用户、8,679 物品、108,166 次交互，一轮对话样本 492。这不是标准 5-core Beauty。一轮推荐表 5（第 9 页）单位是百分数。检索从全库找，Recall@5：InteRecAgent 在 Steam / Movie / Beauty 上是 65.05 / 52.02 / 30.28，GPT-4 是 56.77 / 47.78 / 12.80。排序是用户给出的 20 个候选：1 个正例加 19 个随机负例，指标 NDCG@20。Beauty 上是 40.05 对 GPT-4 的 33.28。用户模拟器表 2 是多轮 Hit@5 和平均轮数，不是全库 Recall。没有 EASE，没有全库下一物品的 SASRec 对照。

### 2. 逻辑

因果：LLM 若会选工具，领域模型就能补上目录知识。递进：先定最小工具集，再加候选总线、计划式执行、反思和小模型蒸馏。转折写在工具说明里，不在实验结果里：协同相似被明确赶出 SQL。

### 3. 隐含假设

表 5 的 Recall@5 百分数和全库 0.06 不是一个协议，Beauty 的规模也不同。排序 NDCG 建立在 19 个随机负例上，不能和全库 NDCG 比。没有用弱 KNN 代替 ItemKNN；软条件就是 ItemCF，但是工具，不是 SQL。没有线上 CTR。关键的隐含句是「SQL 不能找相似物品」。这是提示里的禁令，不是关系代数的能力极限。自连接找共现，SQL 写得出来；这篇选择不让模型这么写。

### 4. 证据

## Xu 等，全量交叉熵 SASRec

文件 `Xu-SASRec-CE-2408.14238.pdf`。Xu、Zhu 等。标题是 *Are LLM-based Recommenders Already the Best?*。arXiv:2408.14238v1。首页无会议。

### 1. 论点与论据

问题：有人报告微调 LLM 在序列推荐上超过传统模型，但传统模型多用 BCE 或 BPR，LLM 用的是全体词表上的交叉熵。

主张：两边都用交叉熵时，SASRec 和 FMLP-Rec 反过来超过 LlamaRec、P5、E4SRec。交叉熵更贴排序指标，是因为归一化项的覆盖；它的紧度并不是最优。全量 softmax 算不动时，把采样归一化项乘一个放大系数，可以用很少的负例接近全量（摘要）。

方法：损失写在表 1。BCE 和 BPR 每个正例一个负例。CE 的归一化项扫全体物品。SCE 是均匀采样再乘 α。

实验：Beauty、Yelp。交互少于 5 次的去掉。留一，最后一条测试，倒数第二条验证。NDCG 和 MRR 由目标物品在全体物品中的名次算出（第 3 页）。附录表 4：Beauty 22,363 用户、12,101 物品、198,502 次交互，平均长度 8.9。表 3：全量交叉熵 SASRec 的 Beauty NDCG@5/10 是 0.0510 / 0.0597，Yelp 0.0345 / 0.0415。LlamaRec 是 Beauty 0.0405 / 0.0492，Yelp 0.0306 / 0.0367。BPR SASRec 的 Beauty NDCG@10 是 0.0374。BCE 是 0.0353。Yelp 上全量交叉熵 FMLP-Rec 的 NDCG@10 是 0.0444，高于 SASRec 的 0.0415。表 3 的 ▲% over LLM 在 CE 块、Beauty NDCG@10 是 +21.3%。没有 ItemKNN，没有 EASE。

局限（附录 A.9）：离线比较不能代表主观推荐；只做了序列推荐，换到一般协同过滤结论可能不同；SCE 在负例很少（K=1）时方差高，Beauty 上 K≥10 就够。

### 2. 逻辑

转折是全文的骨架：BPR/BCE 下传统模型落后，换成 CE 就反超。因果：覆盖加上对 NDCG/MRR 的下界，而不是 LLM 的世界知识。递进：先报表 3，再用截断损失说明紧度和覆盖要同时有，再用 SCE 处理全量 softmax 算不动的情况。

### 3. 隐含假设

这篇直接拆掉「已发表的 SASRec 就是强基线」。Xu 写明 SASRec 原文用 BCE。强的是他们换成全体物品交叉熵之后的 SASRec，不是 2018 年那个训练目标。Hit@K 没有出现；他们用的是全库名次上的 NDCG/MRR。没有 KNN。没有 CTR。SQL 表达不了自注意力序列模型。这篇也没有说自连接打得过或打不过这一档，因为没有测。

### 4. 证据

强度：强，在全库留一、全量 softmax 可算的 Beauty 和 Yelp 上，并且只针对表里的 LLM 推荐器。漏洞：没有非序列基线；离线留一是他们自己也列出的限制；与 TIGER 的历史长度不同，所以 0.0597 对 0.0384 只说明方向。

### 5. 能信什么

能信：先导里的序列基线必须是这一档，不能是 BPR-SASRec。不能引用：ItemKNN 或 SQL 自连接打不过它。那张表不存在。

## Ferrari Dacrema 等，RecSys 2019

### 1. 论点与论据

问题：2015–2018 的神经 top-n 论文宣称超过当时的最好方法，但基线常常没调好。

主张：不是新模型。18 个顶会方法里 7 个能以合理代价复现。这 7 个里 6 个经常输给近邻或基于图的简单方法。剩下的 Mult-VAE 明显好于这些简单基线，但没有稳定好于调好的非神经线性模型 SLIM（摘要）。

### 3. 隐含假设

### 4. 证据

强度：强，范围是这 18 篇里可复现的 7 篇，以及 Netflix 上这三行。漏洞：6/7「经常输」是跨原论文协议的概括，不能收成「神经方法都不行」。Mult-VAE 的 Recall@20 0.2626 高于 ItemKNN 的 0.2088，神经方法并非一律输给近邻。

### 5. 能信什么

能信：近邻和 SLIM 是强基线；在 Netflix 的这张 top-n 表上，SLIM 可以贴近或在 NDCG@20 上超过 Mult-VAE。不能引用：SASRec 全量交叉熵已经赢了 ItemKNN；也不能引用 SQL 版 ItemKNN 没前途。

### 1. 论点与论据

问题：带硬谓词的向量近邻。图方法靠小世界；谓词把图切稀之后，几跳之内到不了目标。选择率不高不低的一段被他们称为 unhappy middle。

主张：不要为每个谓词改遍历，而是按负载建一堆子索引；用索引大小、搜索时间、recall 的三维模型决定建哪些、查询时用哪个。摘要：加速最高 8.06 倍，建索引时间可低到对方的 1%，内存小于一份 HNSW 的 2.15 倍。

方法：底子是 HNSW。后过滤写在第 2 页：选择率 sel 的 top-k 查询先搜 top-k/sel，不够再翻倍。ACORN 在扩展时过滤，诱导子图会丢掉连通性，搜索提前停、recall 变低。

实验：图 9 是 Recall@10 对 QPS。数据集包括 YFCC-10M、Paper、UQV、GIST、SIFT、MSONG。谓词是他们生成的合取、析取或数值区间，不是下一物品标签。正文：低选择率的 YFCC、Paper、UQV 上，SIEVE 的 recall 可以到 0.99 以上，ACORN-γ 停在大约 0.95。引言里的「儿童向视频」和「价格区间里的戏服」没有对应的推荐 NDCG 实验。

### 2. 逻辑

因果：单张图覆盖不了所有谓词，所以用代价模型选一堆专用子图。递进：先写后过滤和 ACORN 为什么退化，再给模型和算法，再给 QPS–recall 曲线。并列：8.06 倍是吞吐，0.95 对 0.99 是近邻 recall，两句不要合成「推荐命中率」。

### 3. 隐含假设

这里的 recall 是找回真正的 top-k 向量近邻，不是推荐 Recall@K。没有 SASRec，没有 ItemKNN，没有 CTR。选择率很低时要多取，多取也不保证找回真正的近邻。SQL 的 `WHERE` 在同一谓词上是精确的，这是机制，不是这篇测过的推荐指标。

### 4. 证据

强度：强，对象是过滤向量搜索的吞吐和近邻 recall。弱，若被拿去证明推荐 NDCG 会塌。

### 5. 能信什么

能信：谓词下的图索引会退化；后过滤的多取倍数是大约 1/sel；ACORN 在那几份低选择率数据上近邻 recall 大约停在 0.95，不是 0.2。不能引用：推荐约束下的 Hit 或 NDCG。先导里若做后过滤向量臂，多取倍数按这里的 1/sel 写清楚。

## Lim 等

文件 `Lim-PVLDB19-filtered-ANN.pdf`。Lim、Kim、Kim、Do。PVLDB 19(10):2763–2776, 2026。

### 1. 论点与论据

问题：过滤近似搜索的难度不该用选择率或属性–向量相关来代表，现有基准偏容易，所以方法排名不可靠。

主张：定义 α-Hardness，用它生成可控负载 HCBGen。摘要说常用基准只覆盖偏容易的一段，更难的负载上排名会变。

方法：硬度按「为了拿到 k 个满足谓词的近邻，搜索要多看多少向量」来建，而不是只看全局选择率。

实验：第 11 页写，高难度负载上多数策略的 recall 急剧下降，often below 0.2，并说这与选择率大约 0.1% 或更低的已知困难一致。0.2 是对图 6 的概括，不是表里的一个格子。同页写 ACORN 的更密 HNSW 在选择率低于大约 0.1% 时连通性不够，搜索提前结束。负载是 SIFT、GIST 等上的合成属性，以及用来对齐硬度分布的半真实负载。首页例子是学术检索里的年份和会议，不是「这个品牌、这个价格、排除已买」。

### 2. 逻辑

因果：基准若只覆盖容易的硬度，方法排名就是假的。递进：先说明选择率不够用，再定义硬度，再生成负载，再看排名变化。转折：0.2 不是所有选择率下的事实，句子自己绑在高难度、大约 0.1% 或更低。

### 3. 隐含假设

recall 仍是向量近邻召回率。没有 SASRec，没有推荐 NDCG，没有 CTR。不能把 0.2 挪到选择率是百分之几的推荐谓词上。SQL 的精确过滤不会漏掉满足谓词的行；它也不会自动给出语义近邻。两件事要分开。

### 4. 证据

强度：强，对象是索引评测。弱，若写成推荐约束下的 Hit。

### 5. 能信什么

能信：引用这句时必须写明是向量近邻 recall、合成或半真实谓词、高难度档。不能引用：「推荐约束下 Hit 低于 0.2，所以该换成 SQL」。

## RepeatNet

文件 `RepeatNet-1812.02646.pdf`。Ren 等。arXiv 版带 AAAI 2019 版权行。

### 1. 论点与论据

问题：会话推荐里，下一次点击经常是历史里已经出现过的物品，普通编码器把重复和探索混在一起。

主张：显式建重复模式和解锁模式，用开关决定何时再推同一个物品（摘要）。

实验：表 3（第 6 页）单位是百分数。YOOCHOOSE、DIGINETICA、LASTFM。会话内下一物品，MRR 和 Recall 的 10 与 20。不是全库留一的 Amazon。DIGINETICA 的 Recall@20：去掉重复机制 42.56，RepeatNet 47.79，NARM 49.70，Improved-GRU4REC 46.16。47.79 没有显著性标记。LASTFM 的 Recall@20：去掉重复机制 29.96，RepeatNet 32.38，有显著性标记，NARM 是 29.94。YOOCHOOSE 的 Recall@20：RepeatNet 70.71，GRU4REC-TOPK 70.30，70.71 无显著性标记。同表 Item-KNN 在 DIGINETICA 的 Recall@20 是 35.75，那是会话近邻，不是 Ferrari 那种调过收缩的全库 ItemKNN。

### 2. 逻辑

因果：若模型能切换「再推历史里的物品」和「推新物品」，重复会话会更准。递进是消融掉重复头。转折：DIGINETICA 的 Recall@20 仍低于 NARM，所以消融涨了，并不等于打赢当时的会话模型。

### 3. 隐含假设

没有 SASRec。绝对 Recall 远高于 Amazon 留一，是因为会话推荐的常规尺度，不能横比。表内 Item-KNN 不能代表调好的 ItemKNN。没有 CTR。历史过滤或「只从本会话出现过的物品里取」可以用 SQL 写精确集合，这是机制，不是这张表的胜负。

### 4. 证据

强度：中，对「重复头相对自己的探索支路提高了 DIGINETICA 和 LASTFM 的 Recall@20」。弱，对「打赢会话推荐」。

### 5. 能信什么

能信：重复头是有用的消融。不能引用：47.79 是要超越的 SOTA。先导里报重复物品的命中时，对照应包括「只做集合过滤」的 SQL。

## 重新整理后的创新点

本目录 24 篇（SIEVE 两份算一篇）里，没有一篇是：模型读一句自然语言，写出用户–物品交互表上的自连接或物品–物品聚合，数据库执行，再用推荐的 Recall 或 NDCG 给这个结果打分。

已经占住的邻格，不能再当成创新：

- 属性 SQL。InteRecAgent 让 LLM 写 SQL，但提示禁止用 SQL 找相似物品，只许一张物品信息表，不许 `LIMIT`，标题不能当条件。协同走 ItemCF 工具。排序是 1 个正例加 19 个随机负例。
- 词法查询。GPT4Rec 用 GPT-2 写标题式查询，BM25 执行。EARL / WebReco 的 Q′ 用 LLM 写大约 6 条网页查询，Bing 取 top 10。都没有协同自连接。
- 事先算好的共现。STAR 把共现次数填进提示。计数本身是自连接写得出来的，模型没有写这条查询。表里的 KNN 是 top-10 UserKNN。
- 语义 ID 或物品向量。TIGER、EAGER、LETTER、LC-Rec、IDGenRec、OneRec-Think、LLM2Rec、LEARN、HLLM、NoteLLM、NoteLLM-2、RecGPT 的召回都是生成 ID、内积或标签塔。协同信号在参数里，不在一条可执行的连接里。

还空着的一格，才是这一路的创新点：自然语言里同时有硬谓词和协同意图时，模型写出带谓词的协同 SQL，引擎执行，在可行集上同时报 Recall、NDCG 和约束满足率。对照必须是全量交叉熵 SASRec 的后过滤，以及用同一条 SQL 写出来的、调过收缩的 ItemKNN。EASE 在内存放得下时另报，但不能把 EASE 说成自连接。

## 这一路的结论

没有一篇召回论文已经占住「LLM 写一条协同 SQL 自连接」。

可以相信的，是几条彼此不能拼成一张表的事实。

- 无约束的下一物品上，这批 PDF 没有把 SQL 自连接和全量交叉熵 SASRec、EASE 放在同一张全库排序表里。所以不能写「SQL 自连接打不过调好的 SASRec 或 EASE」。
- 矩阵式 top-n 上，调过的 ItemKNN 和 SLIM 经常是强基线。RecSys 2019 的 Netflix 表 8：Mult-VAE 的 REC@20 是 0.2626，SLIM 是 0.2551，ItemKNN 是 0.2088；表 9 的 NDCG@20 上 SLIM 是 0.2473，Mult-VAE 是 0.2448。TOIS 2021 的口径是 12 篇可复现里 8 篇输给近邻，计入线性模型后只有 1 篇在一个数据集上明确更好。Benigni 等的 Amazon-Books（clean）上，ItemKNN 的 Recall@10 是 0.1133，高于表内 DiffRec 变体；EASE 因 64 GB 内存缺席。自连接写得出这一类 ItemKNN，写不出 EASE，也写不出序列模型。
- 生成式检索主表里的 SASRec，是 S3-Rec 公开结果那一档。Beauty 上 NDCG@10 约 0.0318。Xu 等在同一用户数、同一物品数上，全量交叉熵 SASRec 的 NDCG@10 是 0.0597，高于 TIGER 的 0.0384、EAGER 的 0.0525、IDGenRec 的 0.0541、OneRec-Think 的 0.0471。历史长度和交互次数并不完全相同，这只说明方向。不能把「超过 SASRec」引用成「超过调好的序列模型」。
- Hit、Recall、NDCG 不能横比。口径包括：0–1 与百分数，全库名次与 19 个随机负例，留一与用户序列 8:1:1，笔记对笔记与下一物品，向量近邻 recall 与推荐 Recall，普通 Recall 与 Benigni 等表 7 的归一化 Recall。
- 线上 CTR 不证明某个召回算子必要。NoteLLM 的 +16.20% 对照的是 SentenceBERT。Q′ 的 +0.89% 和 +1.71% 是网页搜索路径。RecGPT 的 +6.33% 没有公开库。HLLM 的 0.705% 没写指标名。
- 过滤近似搜索的退化是近邻 recall。SIEVE 的低选择率数据上，ACORN-γ 大约停在 0.95，SIEVE 可以到 0.99 以上。Lim 等的「经常低于 0.2」绑在高难度、选择率大约 0.1% 或更低。两篇都不是推荐 NDCG。SQL 的精确 `WHERE` 可以引用为机制，不能引用为已经测过的推荐涨幅。

因此，先导里无约束的下一物品不要当主表。主表放带谓词的召回。序列臂用 Xu 的全量交叉熵，再套同一组谓词。平凡臂用 SQL 写的 ItemKNN。向量臂按 SIEVE 的大约 1/sel 多取。InteRecAgent 用来划界：属性 SQL 已经有人做了，而且对方明确不许用 SQL 做相似物品。
