# 垂直领域 Text-to-SQL：按原文逐条核对

> 2026-11-11。下面每条数字都来自当天打开的 PDF，不沿用 [01_垂直领域Text-to-SQL](../01_垂直领域Text-to-SQL.md) 里和 PDF 不一致的数。PDF 用全文抽取后通读实验、表和局限，没有停在摘要。22 篇全文检索 `NDCG`、`Recall@`、`Hit@`，零命中。

## 先回答这两句

**「领域 Text-to-SQL 不值得做」：原文不支持这句全称。** 这一路被接收的文章都在主张领域基准值得做。站得住的是更窄的一句：只换一个领域、用专家模板填槽、再报一个域内执行准确率，已经是重复贡献。顾问说的「练手」对准的是这种写法，不是整条文献。真正被接收的文章都多卖了一件东西：Spider 上的系统换库后崩掉、第二种查询语言、schema 里没有的统计惯例、拒答加惩罚，或者执行准确率本身会排错名次。

**「主指标必须是推荐效果」：这 22 篇都不支持。** 它们支持的是：字符串匹配不够；执行匹配会把错查询判对，也会把对查询判错；SQL 若只是流水线的一段，报告的应该是用户看到的结果。用户任务在这些论文里是问答对不对、约束满不满足、该不该拒答。没有一篇把生成 SQL 的执行结果当成推荐候选，再用 Recall、NDCG 或 Hit 打分。推荐指标是我们把「打用户任务」落到推荐上的推论，不能写成这些原文已经证明的结论。

和综述不一致、以 PDF 为准的地方：

- ScienceBenchmark 的 PVLDB 引用写的是 2023 年卷期，不是综述里的 2024。
- BiomedSQL 的 PDF 页眉是 COLM 2026，不是「仅 arXiv」。
- H-STAR 在 GPT-3.5-Turbo 上的 WikiTQ 是 69.56，不是 68.85。
- Arctic-Text2SQL-R1-7B 在论文表里是 BIRD 开发集 68.9，不是 BIRD 测试 68.5。同表里的 68.5 是另一篇模型 ExDPO-70B 的 BIRD 开发集。
- OmniSQL 的 PDF 没有 BIRD 测试 67.97。它报告的是 BIRD 开发集 63.9 / 66.1。
- Spider 2.0 正文把「平均 812 列」和「平均 144 个 token」连在一起写；对照表里这两组数分属不同子集。
- TAG 的 arXiv PDF 通篇没有 CIDR 字样。
- FinSQL 的 ACM 付费 PDF 没有下到，读的是 arXiv。

## ScienceBenchmark（PVLDB）

- 原文：`papers/sql-recall/01-text-to-sql/ScienceBenchmark_PVLDB2024_Stockinger.pdf`
- 打开的 URL：<https://www.vldb.org/pvldb/vol17/p685-stockinger.pdf>
- PDF 自署：`PVLDB, 17(4): 685-698, 2023`。综述写 PVLDB 2024。以 PDF 的 2023 为准。卷期和页码与这个 URL 一致。

作者把贡献写成三条。

1. **新基准：三个科学库、六千多对。** 证据是 Table 1 和 Table 2。每个库手工 100 条 seed 加 100 条 dev，合成分别是 CORDIS 1306、SDSS 2061、OncoMX 1065。手工题由 SQL 专家和领域专家写，项目是多年的 INODE。对照 Spider 是公平的复杂度对比，但 SDSS 被裁成 5 张原表加 1 张附加表，原因是「limitation of the input tokens」。全库有的表多到 804 列，实验库不是那个全库。合成 SQL 比手工 seed 更简单：OncoMX 的合成集 Hard 和 Extra Hard 都是 0。评测集是每库 100 条手工 dev，执行准确率。他们没有分析空结果或同结果异查询的假阳性。结论：**只在这三个裁过的库、这 100 条 dev 上成立。** 「第一个复杂真实科学库基准」比「第一个真实库基准」窄，他们自己在相关工作里列了 MIMICSQL。

2. **用少量种子加 GPT-3 回译，自动造训练数据。** 证据是第 4 节。Spider 上人工判定，微调 GPT-3 的正确率 0.731，零样本 GPT-3 是 0.765；他们仍选微调版，因为 SacreBLEU 和 SentenceBERT 更高。领域 dev 上 SQL 到问句的人工正确率是 CORDIS 82%、OncoMX 73%、SDSS 53%。合成对的抽查是每库 100 条：SQL 有意义 91%–97%，问句和 SQL 语义等价 75%–83%。他们写明不把不等价的对滤掉，理由是银标可以有噪声。这是模板填叶子节点，不是新的问法。结论：**造数据流程可用，这一点站得住；「质量高所以不用过滤」只在他们这 100 条抽查和后续微调涨点上成立。**

3. **Spider 榜上 82% 以上的系统，到这里只有 25%–60%。** 这句写在贡献列表里。Table 5 的实际对照不是同一套系统。他们没跑上 Picard，脚注写 Haskell 编译失败，T5-Large 是无约束解码。RESDSQL 因为 NatSQL 转换代码不可用被排除。Table 5 里微调模型的零样本是个位数到不到 20%：T5-Large 在 SDSS 上 0.05。加上种子和合成数据后，T5-Large 在 OncoMX 上到 0.56，这就是综述里的 56%。GPT-3.5 一点提示在 CORDIS 上 0.60，五点在 SDSS 上 0.33，和综述一致。0.60 和 0.33 是提示模型，0.56 是微调模型，贡献列表把它们收成「25–60%」。82% 是榜单上别的系统的 Spider 分数，Table 5 没有这些系统在 Spider 上的同配置复现。结论：**「这些库比 Spider 难」站得住。「从 82% 掉到 25–60%」作为同一系统的落差，不成立。**

对这篇选题：引用 Table 5，说明换库会崩，但要写明不是配对复现。避开「我们也做一个领域库并把域内执行准确率做高」。这篇不支持推荐指标。它的评测就是执行准确率。

## SM3-Text-to-Query（NeurIPS 2024 D&B）

- 原文：`papers/sql-recall/01-text-to-sql/SM3-Text-to-Query_NeurIPS2024.pdf`
- URL：<https://proceedings.neurips.cc/paper_files/paper/2024/file/a182a8e6ebc91728b6e6b6382c9f7b1e-Paper-Datasets_and_Benchmarks_Track.pdf>
- 页眉是 NeurIPS 2024 Datasets and Benchmarks Track。

1. **第一份同时覆盖关系、文档、图，以及 SQL、MQL、Cypher、SPARQL 的医学 Text-to-Query 基准。** 他们把 FootballDB 和一份 SQL/SPARQL 对照标成近亲，然后把「四种语言、同一批数据」当成空位。这个范围声明站得住。数据是 Synthea 合成病人，不是医院导出。第 6 节自己写：模板「only created with guidance from health professionals, but not directly formulated by them」，查询主要由两名本科生和一名博士生写、两名教员核对。正文又说项目和两家大学医院的人一起做了一年以上。两句话都在 PDF 里。综述把「两家医院、一年以上」写成数据采集主体，比局限节更满。结论：**「四种语言的第一份」在他们划定的范围内成立。把它写成临床真实问句，不成立。**

2. **408 个模板扩成每种语言 1 万对。** 正文如此。扩充是从库里抽病人名、过敏等槽值。他们自己写 SQL 和 Cypher 平均不到 10 个 token，可能太容易。结论：**规模数字成立，难度声明被他们自己的局限节削弱。**

3. **带 schema 的零样本，SQL 最高 47.05%，SPARQL 最高 3.3%。** Table 3 对得上：SQL 零样本 Llama3-70b 是 47.05；SPARQL 零样本最高是 GPT-3.5 的 3.30。同一张表里，SQL 五点提示 Llama3-70b 到 57.50。Table 4 用 BM25 从训练集抽 5 个相似问句，GPT-3.5 的 SQL 执行准确率到 88.55，比固定五点高 32.25；SPARQL 到 75.75。模板填槽之后，相似例检索等于把同一骨架的金 SQL 放进提示。他们用 Stack Overflow 帖子数解释语言差距，又承认 MQL 是反例。结论：**零样本的 47.05 和 3.30 只在 Table 3 的提示设置下成立。把 47% 当成医学推理的上限，不成立，因为换一种例题选择就到 88.55。**

对这篇选题：引用它，说明「领域」还可以被拆成数据模型这个变量，而且模板加检索会把执行准确率抬上去。反驳任何「医院场景所以问句是真的」的写法。不支持推荐指标。

## BiomedSQL（COLM 2026；arXiv:2505.20321v6）

- 原文：`papers/sql-recall/01-text-to-sql/BiomedSQL_arXiv2505.20321.pdf`
- URL：<https://arxiv.org/pdf/2505.20321.pdf>
- 页眉：`Published as a conference paper at COLM 2026`。arXiv 行是 `2505.20321v6 [cs.CL] 12 Aug 2026`。综述写「仅 arXiv，未见会议版」。以 PDF 为准，这是 COLM 2026。

1. **第一份专门评「科学推理」的生物医学 text-to-SQL，68,000 对。** Table 1 写 68,227。来源是 40 道专家题，程序填入疾病、基因和 SNP。金 SQL 由一名领域专家写，两名分析员审，但审前标注没留下，没有标注者一致率。推理指的是问句里不出现、SQL 里出现的惯例，例如 `p < 5e-08`。这和 ScienceBenchmark 的领域词表不是同一件事，这条区分站得住。Table 1 的「最大」只和 MIMICSQL、EHRSQL、SM3、BIRD 比，没有 WikiSQL 或 BookSQL。40 个骨架被算成 6.8 万道独立科学问题。结论：**「schema 里没有统计阈值」这个现象成立。规模和「第一」只在他们的对照表里成立。**

2. **评测：Gemini-3-Pro 执行准确率 58.1%，BMSQL 62.6%，专家 90%。** 评测集是按模板分布抽出的 546 条，不是 6.8 万条全评。Table 3：Gemini-3-Pro 的 EX 58.1、JAC 62.4、RQR 81.8，括号里是置信区间半宽。BMSQL-GPT-o3-mini 的 EX 是 62.6。正文写 DAIL-SQL-GPT-o3-mini 是 61.2，「margin ... falls within confidence intervals」。专家是两名分析员各做从 546 里抽的 20 条，EX 均值 90.0，JAC 90.0，RQR 95.0。他们自己给 EX 的 95% 置信区间约 [68%, 99%]，并写「should be read as an approximate reference」。贡献列表里的「25–30 个百分点差距」用的是 90 减 58.1 或 62.6。区间下界 68 对 62.6 只剩大约五个点。EX 被改成 UUID 集合或数值集合相等，金 SQL 还把结果帽在 100 行。两条不同的过滤可以在这个帽下撞车，他们用 JAC 作较松的对照，这是加分项。`stat-instruct` 会把阈值写进提示，所以「模型必须自己推断惯例」只对基线提示成立。结论：**58.1 和 62.6 在 546 条上成立。专家 90 和 25–30 个点的差距，只在把 20 条的点估计当成稳定人类上界时成立；按他们自己的区间，不成立。**

对这篇选题：引用「问句不写、SQL 必须写上的领域惯例」，这是领域 text-to-SQL 里还没被模板填槽耗尽的一种缺口。不要把 40 个模板的域内高分当成贡献。专家基线的写法（20 条、宽区间、摘要里写成 90.0）是我们不该学的报告方式。仍然没有推荐指标。

## BookSQL（NAACL 2024 长文）

- 原文：`papers/sql-recall/01-text-to-sql/BookSQL_NAACL2024.pdf`
- URL：<https://aclanthology.org/2024.naacl-long.28.pdf>
- 页眉页码 497–516，NAACL 2024 长文。一致。

1. **会计库上的大规模 text-to-SQL，100k 对、100 万行、单库。** 摘要、Table 2、Table 3 都写 100k。Table 3 又写 Hard 45,000。第 3.4 节写「BookSQL consists of 7,193 Hard SQL queries」。两句在同一篇里冲突。问题来自两名财务专家列出的 183 道典型问句，再模板化。库是一个 schema、27 家企业、约 100 万行。划分按模板 70/10/20，测试模板不在训练里出现，这一点比 EHRSQL「每个划分都有全部模板」更干净。结论：**单库、模板、专家起稿，这些事实成立。100k 和 7,193 道 hard 不能同时当成精确规模。**

2. **Spider 上强的模型到这里很差，所以需要领域模型。** Table 1 是 Spider 上训好的模型直接测 BookSQL 的精确匹配：UniSAr 3.8%，SEDE 0.0%，RESDSQL 10.8%。这是迁移失败，公平。Table 5 是在 BookSQL 上微调之后：RESDSQL 精确匹配 51.5%、执行准确率 54.4%，对照它在 Spider 上的 80.5% / 84.1%。GPT-4 只跑了测试集的随机 10%，因为 API 限额。DIN-SQL+GPT-4 执行准确率 7.6%，动态十例提示加 GPT-4 是 67.2%。同一张表把全量微调分和 10% 子集的 GPT-4 分放在一起。Table 6 的 GPT4 列没有写是哪一个 GPT-4 系统。Easy 全部 100%，困难度上的差距在 medium 和 hard。结论：**零样本迁移很差，站得住。微调之后的「GPT-4 仍有明显差距」只对 DIN-SQL 的 7.6% 成立；动态少样本的 67.2% 高于微调 RESDSQL 的 54.4%，而且样本不是全测试集。**

3. **第一份有多步嵌套、第一份有大量时间过滤的 text-to-SQL。** Table 2 自己列出 Spider 有 844 条嵌套。时间表达是这个会计库的真实特点，可以保留；「第一份嵌套」不成立。

对这篇选题：引用 Table 1 的迁移崩溃，以及「测试模板不可见」这个划分。避开单库模板把域内分做高。FINCH 后文报告 BookSQL 里有大量执行失败的 SQL，见下。没有推荐指标。

## FinSQL / BULL（SIGMOD 2024；读的是 arXiv）

- 原文：`papers/sql-recall/01-text-to-sql/FinSQL-BULL_arXiv2401.10506.pdf`
- 打开的 URL：<https://arxiv.org/pdf/2401.10506.pdf>
- ACM：<https://doi.org/10.1145/3626246.3653375>。付费 PDF 没有下。arXiv 摘要和 DOI 页摘要一致。FINCH 把这篇引成 SIGMOD 2024 Companion。arXiv PDF 页眉仍是模板占位「Conference’17, July 2017, Washington, DC, USA」。数字以这份 arXiv 为准。

1. **BULL：金融 text-to-SQL 的实用基准，4,966 对、三个库。** 第 5 节：基金、股票、宏观经济，表数 31、28、19。Table 1 的平均数是每库 26 张表、390 列。图注里单表平均列数约 14，最大约 30。摘要说的「wide tables」更像「一个库有很多列」，不是单表几百列。4,966 道中文问题由恒生的人在「more than one week」里写成，工程师写 SQL，三名实习生核对，再译成英文。不是多年采集。划分在实验节：基金 1744/405，股票 1672/464，宏观 550/131，加总 4,966。结论：**数据和一周标注的过程成立。「此前没有实用金融基准」是没有对照表支撑的宣言。宽表的修辞比图里的最大 30 列更强。**

2. **FinSQL 在 BULL 上达到当时最好，英文 LLaMA2 执行准确率 82.2%。** Table 4：FinSQL+LLaMA2 82.2，FinSQL+T5 81.5，Picard\*+T5 79.3，DAIL-SQL+GPT-4 75.0。GPT-4 方法只评了 20 条，ChatGPT 方法 100 条，DIN-SQL+GPT-4 因为超过 8192 token 没有跑出准确率，只估了价格。T5 系基线先被他们自己的交叉编码器裁到 3 张表、7 列，表上标了星号。schema 链接 AUC 在英文上是表 0.9984、列 0.9979，R@3 表 99.1%。问题是看 schema 写的，分类器又在同一批库上训练，这个 AUC 说明任务容易，不能说明链接方法有跨库能力。结论：**82.2 对 79.3 的域内优势很小，而且强闭源基线不是全量。站得住的只有「在这个划分上、这个预算下，LoRA 微调略高于他们跑完的基线」。**

3. **跨库少样本最高提升 36.64%。** 这句在摘要和贡献列表里。第 9.5 节把它落到一个方向：基金和股票的 LoRA 平均合并，再在宏观经济上做 k-shot，对照从零训练的 LoRA。10-shot 时四个模型分别高 36.64%、35.87%、34.35%、21.37%。图 13 的绝对执行准确率在文本抽取里是乱码，这里不补绝对分。交叉编码器也用了「varying amounts of macro data」，所以 schema 链接不是严格零样本。零样本合并相对从零 LoRA 的数字更大（LLaMA2 50.39%），但那是另一个 k。结论：**36.64% 只在「合并 LoRA 对从零 LoRA、宏观库、10-shot」这个设置下成立，不是 Table 4 主结果的提升。**

对这篇选题：引用时必须把 36.64% 放回 10-shot 迁移，不能写成主表涨点。一周模板级工业标注加 82% 域内分，正是审稿人会当成练手的形态。输出校准的消融只有 1.5 个执行准确率点（Table 9，英文 82.2 到 80.7）。没有推荐指标。

## FINCH（arXiv:2510.01887v1，2025-10-02）

- 原文：`papers/sql-recall/01-text-to-sql/FINCH_arXiv2510.01887.pdf`
- URL：<https://arxiv.org/pdf/2510.01887.pdf>
- PDF 没有会议页眉。

1. **把 BIRD、Spider、BULL、BookSQL 收成 33 个金融库、75,725 对，是最大的金融基准。** 贡献列表写 75,725。结论写「over 86,000」。Table 1 的入选规模是 Spider 1,100、BIRD 812、BULL 4,966、BookSQL 68,907。正文说 BookSQL 测试划分没有 SQL，所以丢掉；又说执行检查发现 BIRD 1,139 里 327 条失败、BULL 4,966 里 60 条有问题、BookSQL 78,433 里 9,526 条有错、Spider 子集没有错。1,139−327=812，78,433−9,526=68,907，和表一致，说明这些是删掉而不是改对。1,100+812+4,906+68,907=75,725，其中 4,906=4,966−60，但 Table 1 仍把 BULL 写成 4,966。结论的 86,000 接近未过滤总和。75,725 里约 6.9 万来自 BookSQL。结论：**「新采集的金融基准」不成立。它是过滤后的合并，而且 75,725、86,000 和表里的 BULL 4,966 互相打架。BookSQL 有 9,526 条执行失败的金 SQL，这条附带发现比 FINCH 自己的基准声明更有用。**

2. **推理型小模型可以超过大模型；Arctic-Text2SQL-R1-7B 是第三名。** Table 3 的执行准确率：GPT-OSS-120B 27.80，GPT-OSS-20B 7.50，Qwen3-235B 2.50，Arctic 2.30，Qwen3-8B 0.80，Phi-4-mini 0.20。FINCH Score：11.60、3.00、1.20、1.50、1.20、0.40。Arctic 只在 FINCH Score 上第三，执行准确率上第四，而且 1.50 对 1.20 是在全体不到 12 分的尺度上。结论写 Arctic「often surpasses ... even trillion-scale models」。表里没有万亿参数模型，Qwen3-235B 的执行准确率还高于 Arctic。他们称协议是 one-shot，Table 2 展示的提示没有例题。全文没有训练/测试划分，也没有讨论这些模型是否训练时见过 Spider、BIRD 或 BookSQL。结论：**「第三名、小模型打败规模」不成立。表上站得住的是：在这份合并数据、这一套提示下，最好的执行准确率是 27.80。**

3. **FINCH Score 比精确匹配更符合金融重要性。** 公式把子句相似度和带容差的执行结果乘在一起。正文说权重应按历史误查询造成的金额来估，实验里直接取 β=1、δ=0.3，没有报告那次估计。容差公式按单个数值结果来写，表查询的结果集怎么套进 `|r|`，没有定义。结论：**动机可以引用；这个分数作为已校准的金融指标，不成立。**

- 原文：`papers/sql-recall/01-text-to-sql/Jin_annotation-error_arXiv2601.08778.pdf`
- URL：<https://arxiv.org/pdf/2601.08778.pdf>
- 没有会议页眉。

1. **BIRD Mini-Dev 标注错误率 52.8%，Spider 2.0-Snow 公开金标 62.8%。** 人工核对之后：BIRD Mini-Dev 498 条里 263 条，52.8%；Spider 2.0-Snow 公开金 SQL 的 121 条里 76 条，62.8%。SAR-Agent 在 Mini-Dev 上的精确率 83%，相对 Arcwise 已报的 161 条命中率 85.7%，并多报 41.6%。检测器不是金标，金标是专家复核。结论：**这两个错误率在他们复核过的子集上成立。不能写成全部 BIRD 或全部 Spider 2.0 都是这个比例。**

2. **修正一个 BIRD 开发子集后，16 个可复现系统的相对执行准确率变化从 −7% 到 31%，名次最多动 9 位。** 正文：12 个系统变好，4 个变差。CHESS 从 62% 到 81%，相对 30.6%，名次从这 16 家里的第 7 到并列第 1。SFT CodeS-15B 从 56% 到 52%，相对降 7.1%。MAC-SQL 从第 14 到第 5，GSR 从第 4 到第 13。平均每个系统有 16.4 条从错变对、8.0 条从对变错。脏子集排名和全开发集的 Spearman 是 0.85（p=3.26e-5），和修正子集是 0.32（p=0.23）。系统是 2025-08-20 榜上能复现的 16 个。结论：**在这 16 个系统和这个修正子集上成立。相对百分比不是绝对点数。**

对这篇选题：主表如果靠执行匹配，或者靠「返回集合等于金 SQL 的结果」，这篇说明金 SQL 本身可能是错的，名次可以整表重排。推荐留出上的标签如果也是一条 SQL 算出来的，同样的审计适用。这篇不把替代指标指定为 NDCG。

## Wretblad 等（ACL 2024 短文）

- 原文：`papers/sql-recall/01-text-to-sql/Wretblad_BIRD-noise_ACL2024-short.pdf`
- URL：<https://aclanthology.org/2024.acl-short.34.pdf>
- 页 356–369，ACL 2024 短文。

1. **BIRD 的问句和金 SQL 有噪声，而且分布不均。** 主分析是开发集金融域 106 对，约占开发集 7.5%。Table 1：52/106（49%）有噪声，金 SQL 错误 22/106（20.7%），问句噪声 44/106（41.5%）。另外四个域各抽 20 条。Table 2 把错误类型拆开，金融域错误条数 72，大于 52，因为一对上可以有多类。结论：**106 条金融域上成立。不是全 BIRD 的错误率。**

## Spider 2.0（ICLR 2025；arXiv:2411.07763v2）

- 原文：`papers/sql-recall/01-text-to-sql/Spider2.0_arXiv2411.07763.pdf`
- URL：<https://arxiv.org/pdf/2411.07763.pdf>
- 页眉：ICLR 2025。arXiv 行是 v2，2025-03-17。

1. **企业工作流基准：长上下文、方言文档、项目代码、多条 SQL。** 632 个任务。对照表：Spider 2.0 全体平均每库 743.5 列、每条金 SQL 148.3 token；lite 是 803.6 列、144.5 token；snow 是 812.1 列、161.8 token。正文写「an average of 812 columns」，下一句写「each ground-truth SQL query contains 144 tokens」。812 和 144 对不上同一行。综述把这两句直接接在一起。以表为准。结论：**企业库又大又方言化，成立。单一的「812 列、144 token」不成立为同一个子集的一对平均数。**

## Arctic-Text2SQL-R1（ACL 2026 Findings）

- 原文：`papers/sql-recall/01-text-to-sql/Arctic-Text2SQL-R1_ACL2026-Findings.pdf`
- URL：<https://aclanthology.org/2026.findings-acl.1345.pdf>
- 页 26966–26995。

1. **只用执行对错做强化学习，不加碎奖励。** 这是方法声明。相关工作提到执行奖励可能被钻空子，他们的回应是奖励设计保持简单，不是证明执行匹配没有假阳性。FLEX 和 Jin 说明执行匹配会奖给结果碰巧相同的错 SQL。用这个奖励训练，会把那种碰巧写进策略。结论：**训练配方在论文里成立。奖励和「SQL 真的写对了」之间的等同，不成立。**

2. **7B 强、32B 在 BIRD 榜上 71.83%。** 正文：32B 在 BIRD 榜上执行准确率 71.83%，自洽后 73.84%。Table 里 Arctic-Text2SQL-R1-7B 是 BIRD（dev）68.9、SPIDER（test）88.8、Spider2.0-SQLite 15.6。综述的「BIRD 测试 68.5」不是这一行。同表 ExDPO-70B 的 BIRD（dev）是 68.5。7B 的 Spider 测试 88.8 和 Spider 2.0-SQLite 15.6 与综述一致。结论：**88.8 和 15.6 成立。把 68.9 的开发集写成 68.5 的测试集，不成立。**

对这篇选题：本地 7B 生成器用它是合理的工程选择。论文主指标不能用它的训练奖励，也就是执行对错。Spider 2.0-SQLite 15.6 说明这个 7B 一到多方言、大 schema 就不再是 68.9。

## 审稿人最容易当成「已经做过」的三个创新点

1. **专家写几十到几百个模板，程序填槽或让模型改写，再报一个新领域上的执行准确率，并附一张相对 Spider 或 BIRD 的下跌表。** ScienceBenchmark、BookSQL、EHRSQL、SM3、BiomedSQL、FinSQL、OMOP 都是这个骨架。OMOP 的 LoRA 已经把这种设定做到测试执行准确率 93.55。只把推荐库说成又一个领域，会被看成同一骨架。

2. **不可回答题、拒答令牌、以及错答比拒答更贵的可靠性分。** EHRSQL 把不可回答放进测试，TrustSQL 给出 RS(c)，EHRSQL 2024 用 RS(10) 排名，OMOP 用 `<NO_SQL>`，Query Carefully 把不可回答拆成八类。我们如果把「知道何时不写 SQL」写成主创新，这五篇已经占住。

3. **SQL 只是中间表示，分数看用户得到的答案或约束满不满足；纯 SQL 不够时就在查询里调用模型。** Binder 的 WikiTQ 测试 64.6，SUQL 的餐馆返回精度 90.3 / 93.8，TAG 的手写上界 55% 对自动方法不超过 20%，H-STAR 和 BlendSQL 是同一方向。SUQL 已经在公开餐馆表上做了「返回的物品是否满足话语里的每条约束」。我们若只把主指标从执行准确率改成「作者判断约束满足」，审稿人会指向 Table 5。

这三件事都还不是：在用户、物品、交互表上生成 SQL，把执行结果当作候选，用留出交互的 Recall 或 NDCG 打分。22 篇全文没有这些指标名。这个空位要写清楚，否则会被吸进上面第三条。

## 必须写进局限的三个失败模式

1. **执行匹配会把错查询判对，金标 SQL 也会错；如果推荐标签本身由一条 SQL 算出，Recall 就退回执行匹配。** FLEX 的 Table 3：200 对上 EX 对专家共识的 kappa 是 62.00，等价子集一致率 79、不等价子集 83，两个方向都有不一致。Jin 等：修正子集后 16 个系统的相对执行准确率从 −7% 到 31%，名次最多动 9 位；脏子集和全开发集的 Spearman 0.85，和修正子集 0.32。Wretblad 等在 106 条金融开发题里看到 22 条错误金 SQL。我们的局限要写：一次交互切分上「返回了对的物品」的 SQL，换切分可以错；标签若由 SQL 定义，则不报告该 SQL 与生成 SQL 的执行一致率作为主结果。

2. **模板、单库和相似例检索会制造虚假的高分。** SM3 的 Table 4：BM25 从训练集取相似问句，SQL 从五点提示的 56.30 邻域升到 88.55，因为问句是 408 个模板的填槽。EHRSQL 明确让全部模板出现在每个划分。BookSQL 是一个 schema。BiomedSQL 的 6.8 万对来自 40 个模板，专家上界只测了 20 条。OMOP 在合成模板上微调后执行准确率 93.55，未微调的同一底座是 10.54。局限要写我们的问句有多少来自模板、测试骨架是否在训练或提示里出现过、以及一个库上的召回不能写成跨目录结论。

3. **该拒答的题不是一个类；用执行对错训练或打分，会奖给冒险作答。** Query Carefully：80 题上的总体检测 0.8，缺值最高 0.5，列歧义最高 0.3。TrustSQL 把 c=0 定义成执行准确率的退化情形，c=N 时一次错误就使总分为负。EHRSQL 2024 第一名 RS(0) 88.17、RS(10) 81.32、RS(N) −711.83。OMOP 最好检查点的 RS(10) 只有 0.373。Arctic 的奖励「based solely on execution correctness」。局限要写：无约束或可答子集上的 Recall 和 NDCG 不衡量缺值、列歧义和越权 SQL；若生成器是 Arctic 这类执行奖励模型，它的错误模式要单独报，不能只报它在可答题上的召回。
