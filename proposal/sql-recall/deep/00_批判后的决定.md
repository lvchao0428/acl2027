## 还做的实验

主实验仍是 STaRK-Amazon。模型只把关系片段写成 SQL，文本交给 BM25 或小编码器。关系片段和整句分开报。纯 SQL 的集合召回在合成集上会被构造过程抬高，因为标签是关系候选再经文本筛选的子集。Hit@1 不会因此自动变高。81 条人工查询不是四个模板填出来的，但不少句子仍然点了图里有的品牌或另一件商品，同时夹着图里没有的价格和尺寸。发布文件里 9,100 条合成查询有 2,720 条答案多于 20 个，论文「答案都不超过 20」这句与文件不符，Recall@20 要同时报截断前后。

RecBench+ 电影仍是第二组，而且必须改成检索。检索主指标用全目录上满足条件的物品。官方 Precision 用的是历史子集，显式查询的中位数是 2 部，会罚掉「把满足条件的电影都返回」的 SQL。官方的 0.308 和 0.714 是没看过目录的生成分数，不放进主表。

Amazon-C4 仍是负对照。查询是 5 星评论改写、物品侧只有品类和一段标题描述，这是文件里的事实。官方 NDCG@100 0.1856。「精确 SQL 会输」还没被测过，先导里要测，不能写成已知结论。

RelBench 的 H&M 仍是协同是否成立的健全性检查，不是语言主实验。v1 加 v2 的推荐任务是 14 个，输入是实体和时间。先复现榜上的历史访问 0.0089095（论文表里的 0.89 是百分数），再跑带上限的物品到物品自连接。13.4M 是边数，不是目录。文章表是 105,542 行，测试是 67,144 个用户、窗口 7 天、K=12，CPU 上可以跑。特征不能用到种子时间之后。手写共现 SQL 是论文没跑的经典基线，不是新系统。H&M 上 MultiVAE 0.28、NGCF 0.75、GraphSAGE 0.80，都没有超过历史访问 0.89。

## 先导里必须有数字的对照

1. 同一组谓词下的全量交叉熵 SASRec，再做后过滤。同一份 Beauty 上它的 NDCG@10 是 0.0597，高于 TIGER 0.0384、EAGER 0.0525、OneRec-Think 0.0471。
2. 用 SQL 写的、调过的 ItemKNN。内存允许再加 EASE。自连接写得出 ItemKNN 或 Swing，写不出 EASE，也写不出序列模型。
3. 按大约 \(1/\text{选择率}\) 多取的后过滤向量检索。STaRK 合成 Amazon 上，BM25 的 Recall@20 是 53.77，SPARK 是 53.95，打平，而且 SPARK 仍混着向量检索。没有「只执行 Cypher 或 SQL」打过 BM25 的结果。

本地生成器仍用 7B。Arctic-7B 表里的 68.9 是 BIRD 开发集，不是测试集 68.5。不追 BIRD 榜。

## 不再写进论文的句子

- 「领域 Text-to-SQL 不值得做。」站得住的是：只换领域、模板填槽、再报域内执行准确率，已经是重复贡献。这 22 篇全文没有 Recall、NDCG 或 Hit。「主指标用推荐效果」是把「SQL 作为流水线一段时要打用户看到的结果」落到推荐上的推论。
- 「无约束的下一物品上，SQL 自连接打不过调好的 SASRec 或 EASE。」这批 PDF 里没有这张表。
- 「过滤近似搜索在选择率约 0.1% 时召回经常低于 0.2，所以推荐约束该换成 SQL。」那组实验是 SIFT/GIST 上的合成标签，不是品牌、价格或排除已买。
- 「LIMIT 说明嵌入搞不定推荐式查询。」查询表面是 “who likes Apples?”，相关集是 46 篇文档的全部两两组合。
- 「SQL 后过滤会丢掉 30% 以上的正确结果。」原文数字只是 ClickHouse 上 JOIN 那一档：UniVectorSQL-7B 的召回从 0.6 到 0.4。WHERE 没有这个数。两种顺序仍都要报，但不能把 30% 写成一般事实。
- 「返回行等于 SQL 结果」是解释质量。它只说明展示层没有私自增删。贡献句不写「SQL 是忠实解释」，否则审稿人会要用户研究。主表用条件匹配率、温度 0 下的字符串一致和结果集 Jaccard，外加执行审计。

不要当成证据引用的三行：STAR 表里 Hits@10 为 0.007 的 UserKNN；TIGER 系「超过 SASRec」而那行 SASRec 的 Beauty NDCG@10 只有 0.0318；RepeatNet 从 42.56 到 47.79，同表 NARM 是 49.70。
