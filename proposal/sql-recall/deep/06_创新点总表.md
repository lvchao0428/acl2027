# 创新点总表

> 2026-11-11。主张取自当天五份批判；批判只点名、没有逐条拆开的，改从 `papers/sql-recall/` 里已有的 PDF 摘作者自己的贡献列表。没有新下载，没有提交。综述笔记和批判不一致时，以批判为准，下面每一路用一句话标明。同一篇论文只占一节。判定只用四档：站得住 / 只在该设置下成立 / 不成立 / 批判未判。

## 每一路的结论

### 垂直领域 Text-to-SQL

只换领域、用模板填槽、再报一个域内执行准确率，已经是重复贡献；把整条文献说成不值得做，原文不支持。
被接收的文章另外卖的是换库之后系统崩掉、第二种查询语言、schema 里没有的统计惯例、拒答加惩罚，或者执行准确率本身会把名次排错。
这 22 篇全文检索不到 Recall、NDCG 或 Hit。
它们支持的是字符串匹配不够，执行匹配会把错查询判对、也会把对查询判错，以及 SQL 若只是流水线的一段，就该打用户最终看到的结果。
那些用户任务是问答对不对、约束满不满足、该不该拒答，没有一篇把 SQL 的执行结果当成推荐候选。
总览第 2 条把「数字必须是推荐任务上的」写成这路文献已经提出的要求，批判推翻这个全称，以批判为准：推荐指标是把「打用户任务」落到推荐上的推论。
审稿人会当成已经做过的三件事，是模板填槽加一张相对 Spider 或 BIRD 的下跌表、拒答可靠性分、以及把主指标改成「作者看约束满不满足」。
仍未知的是，在用户、物品、交互表上生成 SQL，再用留出交互打分，会不会被收成 SUQL 那种返回集合的人工精度。
本地生成器可以用 Arctic-7B 或 OmniSQL-7B，但不能用执行对错当主指标；Arctic 表里的 68.9 是 BIRD 开发集，不是测试集 68.5。
OMOP 的 LoRA 已经把这种域内设定做到测试执行准确率 93.55，高分本身不构成贡献。

### 召回 baseline

无约束的下一物品上，不能写「SQL 自连接打不过调好的 SASRec 或 EASE」。
自连接写得出的是 ItemKNN 或 Swing，写不出 EASE，也写不出吃序列顺序的 SASRec；后半句的对照表，这批 PDF 里没有。
总览第 3 条把「调好的 SASRec、EASE、ItemKNN 已经把共现吃掉，所以 SQL 必须躲开无约束 Recall」写成已有结论，批判推翻其中的胜负方向，以批判为准。
2015–2018 的矩阵式 top-n 里，近邻和线性模型经常赢过当时的神经方法，但那批复现里没有全量交叉熵 SASRec。
Benigni 等在清洗后的 Amazon-Books 上，ItemKNN 领先被复现的扩散模型，EASE 因为 64GB 内存不够没有出现。
序列任务上站得住的只有一句：BPR 或 BCE 的 SASRec 是弱基线；同一份 Beauty 上，全量交叉熵 SASRec 的 NDCG@10 是 0.0597，高于 TIGER 0.0384、EAGER 0.0525、IDGenRec 0.0541 和 OneRec-Think 0.0471。
过滤近似搜索里「经常低于 0.2」的是 SIFT/GIST 上的合成标签，不是品牌、价格或排除已买。
仍未知的是，同一组真实谓词下，全量交叉熵 SASRec 后过滤、用 SQL 写的调过的 ItemKNN、以及大约按 1/选择率多取的向量检索，谁的可行集召回更高。
GPT4Rec 和两份非档案的 Q′ 是「模型写查询、另一个引擎执行」的近亲；InteRecAgent 已经把硬条件交给 SQL，并写明不许用 SQL 找相似物品。

### 候选 benchmark

主实验仍然是 STaRK-Amazon：模型只把关系片段写成 SQL，文本交给 BM25 或小编码器，关系片段和整句分开报。
总览把「可以报纯 SQL 的 Hit」和「Amazon-C4 上精确 SQL 应该输给 0.1856」写成能照用的判断，批判推翻这两处，以批判为准。
合成标签是关系候选再经文本筛选的子集，只执行模板的 SQL，集合召回会被构造过程抬高；Hit@1 不会因此自动变高，因为没有排序就没有第一名，筛选前的候选集有多大，论文没有公布。
81 条人工查询不是四个模板填出来的，解析器背那四句模板解决不了它们，但不少句子仍然点了图里有的品牌、颜色、品类或另一件商品，同时夹着图里没有的价格和尺寸。
论文用「答案都不超过 20」解释为什么报 Recall@20；发布文件 9,100 条里有 2,720 条答案多于 20，这句话与文件不符，完美排序的 Recall@20 也到不了 1。
RecBench+ 电影仍是第二组，而且必须改成检索：官方 Precision 的相关集是历史子集，显式查询的中位数是 2 部，会罚掉「把满足条件的电影都返回」；0.308 和 0.714 是没看过目录的生成分数，不进主表。
Amazon-C4 仍是负对照。
查询是 5 星评论改写、物品侧只有品类字符串和一段标题描述，这是文件里的事实；官方 NDCG@100 0.1856 是嵌入分，「精确 SQL 会输」还没被测过。
仍未知的是关系超集比标签大多少，因为 3.52GB 的图没有打开。
EComAgentBench、REGEN、TalkPlay-Tools、InteRecAgent、AgentRecBench 和 QUEST 都不换到主实验的位置。

### 混合检索与指标

文献支持的是分工：已经落到列或边上的谓词交给数据库，语义留给检索或模型谓词。
用这些论文支撑「LLM 写的 SQL 应当替换向量召回」不成立；「先取出超集、再让检索排序」只在谓词已经落地的设置下成立。
总览写「先向量再 SQL 过滤会丢掉 30% 以上的正确命中」，批判把这句话收回，以批判为准：原文给出的一对数字只是 ClickHouse 上 UniVectorSQL-7B 从 Non-integration 的召回 0.6 降到 JOIN-integration 的 0.4，WHERE 没有这个数，也不是同一批查询的预过滤对后过滤。
LIMIT 的句式像在找偏好，相关集却是 46 篇文档的全部两两组合；小集合上 BM25 的 Recall@2 已经是 97.8，论文要的是更有表达力的检索结构，不是查询语言。
STaRK 合成 Amazon 上，SPARK 的 Recall@20 是 53.95，BM25 是 53.77，打平，而且低于 multi-ada-002 的 55.12；SPARK 交替使用 HNSW 和 Cypher，无结果时回退到 BM25 加余弦，没有「只执行 Cypher 或 SQL」打过 BM25 的结果。
返回行等于 SQL 结果，只说明展示层没有私自增删。
贡献句若写「SQL 是忠实解释」，审稿人会要用户研究，现有预算撑不住。
仍未知的是我们自己的 qrel 上两种顺序各自漏掉多少，30% 不能写成预期跌幅。
主表用条件匹配率、温度 0 下的 SQL 字符串一致、结果集 Jaccard，以及一条执行审计；不新造可解释性指数。
BRIGHT 同时说明，需要推理的缺口上 BM25 也很差，不能把每条难查询都路由到 SQL。

### RelBench

RelBench 的 H&M 购买仍是协同是否成立的健全性检查，不是语言主实验。
两篇 RelBench 都没有自然语言查询，输入是实体和种子时间；v1 的 9 个推荐任务加上 v2 新加的 5 个，一共 14 个，给每个任务套一句英文模板没有词汇变化，ACL 审稿人会同意把它逐出语言主实验。
综述把 13,428,473 写成 H&M 的目录，并写四层 GraphSAGE 会在这张表上因显存退出，批判推翻这两句，以批判为准：这个数是训练正例边加验证正例边，文章表是 105,542 行；H&M 的四层有结果，测试 MAP 是 0.68±0.06，低于历史访问 0.89，显存失败主要写在 RateBeer。
表里的 0.89 是百分数，先复现的是榜上的 0.008909512329806949。
历史访问和全局流行可以写成 SQL，但它们不是物品–物品自连接；论文没有跑 ItemKNN、Swing，也没有跑时间衰减的共现。
H&M 上 MultiVAE 0.28、NGCF 0.75、两层 GraphSAGE 0.80 都没有超过历史访问 0.89，这只是不利先验：那些模型做了邻居采样，不是精确的 ItemKNN，3 跳局部性仍有 0.417。
手写共现是漏掉的经典基线，不是新系统；没超过 0.89 只能写成这条 SQL 没有打过重复购买，不能写成协同连接没有信息。
仍未知的是，特征不用种子之后的行、验证矩阵另算一张时，这条 SQL 落在 0.89 和 ContextGNN 的 2.93 之间的哪一档。
Kumo 的 `RANK TOP` 看起来像带时间窗的查询，执行器仍是已经拟合的模型。

## 论文创新点逐条

跨两份批判的论文只在第一次出现时拆开：SUQL、TAG 在垂直领域；InteRecAgent 在召回；QUEST 在候选 benchmark。后文不再重复贡献列表。

### 垂直领域 Text-to-SQL

#### ScienceBenchmark

PVLDB，PDF 自署 2023 年卷期（综述写 2024，以 PDF 的 2023 为准）。`papers/sql-recall/01-text-to-sql/ScienceBenchmark_PVLDB2024_Stockinger.pdf`

1. 新基准：三个科学库、六千多对。[只在该设置下成立] 评测是每个裁过的库 100 条手工 dev 上的执行准确率，相关工作里他们自己列了 MIMICSQL，实验库也不是 804 列的全库。
2. 用少量种子加 GPT-3 回译，自动造训练数据。[站得住] 造数据流程可用；「质量高所以不用过滤」只在他们每库 100 条抽查和后续微调涨点上成立，而且他们写明不把不等价的对滤掉。
3. Spider 榜上 82% 以上的系统，到这里只有 25%–60%。[不成立] 作为同一系统的落差不成立，Table 5 没有这些榜单系统的同配置复现；「这些库比 Spider 难」仍然站得住。

#### SM3-Text-to-Query

NeurIPS 2024 Datasets and Benchmarks。`papers/sql-recall/01-text-to-sql/SM3-Text-to-Query_NeurIPS2024.pdf`

1. 第一份同时覆盖关系、文档、图，以及 SQL、MQL、Cypher、SPARQL 的医学 Text-to-Query 基准。[只在该设置下成立] 「四种语言的第一份」在他们划定的范围内成立；写成临床真实问句不成立，数据是 Synthea 合成病人，模板也不是医务人员直接写成的。
2. 408 个模板扩成每种语言 1 万对。[只在该设置下成立] 规模数字成立，他们自己写 SQL 和 Cypher 平均不到 10 个 token，可能太容易。
3. 带 schema 的零样本，SQL 最高 47.05%，SPARQL 最高 3.3%。[只在该设置下成立] 这两个数只在 Table 3 的提示设置下成立；BM25 抽相似例之后 GPT-3.5 的 SQL 执行准确率到 88.55，不能把 47% 当成医学推理的上限。

#### BiomedSQL

COLM 2026（arXiv:2505.20321v6；综述写仅 arXiv，以 PDF 页眉为准）。`papers/sql-recall/01-text-to-sql/BiomedSQL_arXiv2505.20321.pdf`

1. 第一份专门评「科学推理」的生物医学 text-to-SQL，68,000 对。[只在该设置下成立] 「问句不写、SQL 必须写上统计阈值」这个现象成立；68,227 来自 40 个骨架，规模和「第一」只在他们的对照表里成立。
2. Gemini-3-Pro 执行准确率 58.1%，BMSQL 62.6%，专家 90%。[只在该设置下成立] 58.1 和 62.6 在抽出的 546 条上成立；专家 90 和「25–30 个百分点」只在把 20 条的点估计当成稳定人类上界时成立，他们自己的区间约 [68%, 99%]。

#### BookSQL

NAACL 2024 长文。`papers/sql-recall/01-text-to-sql/BookSQL_NAACL2024.pdf`

1. 会计库上的大规模 text-to-SQL，100k 对、100 万行、单库。[只在该设置下成立] 单库、模板、专家起稿、测试模板不可见，这些成立；摘要的 100k 与正文「7,193 Hard SQL queries」不能同时当成精确规模。
2. Spider 上强的模型到这里很差，所以需要领域模型。[只在该设置下成立] 零样本迁移很差站得住；微调之后「GPT-4 仍有明显差距」只对 DIN-SQL 的 7.6% 成立，动态少样本的 67.2% 高于微调 RESDSQL 的 54.4%，而且 GPT-4 只跑了测试集的随机 10%。
3. 第一份有多步嵌套、第一份有大量时间过滤的 text-to-SQL。[不成立] 他们自己的 Table 2 列出 Spider 有 844 条嵌套，「第一份嵌套」不成立；时间表达可以保留为这个会计库的特点。

#### FinSQL / BULL

SIGMOD 2024；读的是 arXiv:2401.10506，付费 PDF 没有下。`papers/sql-recall/01-text-to-sql/FinSQL-BULL_arXiv2401.10506.pdf`

1. BULL：金融 text-to-SQL 的实用基准，4,966 对、三个库。[只在该设置下成立] 三个库和大约一周的标注过程成立；「此前没有实用金融基准」没有对照表，「宽表」比图里单表最大约 30 列更强。
2. FinSQL 在 BULL 上达到当时最好，英文 LLaMA2 执行准确率 82.2%。[只在该设置下成立] 82.2 对 Picard\*+T5 的 79.3 只是这个划分、这个预算下的小差距，强闭源基线不是全量，T5 系基线还被裁过 schema。
3. 跨库少样本最高提升 36.64%。[只在该设置下成立] 只在「合并 LoRA 对从零 LoRA、宏观库、10-shot」这个设置下成立，不是 Table 4 主结果的提升。

#### FINCH

arXiv:2510.01887v1，2025-10-02，PDF 没有会议页眉。`papers/sql-recall/01-text-to-sql/FINCH_arXiv2510.01887.pdf`

1. 把 BIRD、Spider、BULL、BookSQL 收成 33 个金融库、75,725 对，是最大的金融基准。[不成立] 这是过滤后的合并，不是新采集；75,725、结论里的 86,000 和表里的 BULL 4,966 互相打架。附带可用的是 BookSQL 有 9,526 条执行失败的金 SQL。
2. 推理型小模型可以超过大模型；Arctic-Text2SQL-R1-7B 是第三名。[不成立] Arctic 只在 FINCH Score 上第三、执行准确率上第四，表里没有万亿参数模型，最好的执行准确率是 27.80。
3. FINCH Score 比精确匹配更符合金融重要性。[不成立] 动机可以引用；实验里直接取 β=1、δ=0.3，没有报告按金额做的估计，表查询的结果集怎么套进容差公式也没有定义。

#### EHRSQL

NeurIPS 2022 Datasets and Benchmarks。`papers/sql-recall/01-text-to-sql/EHRSQL_NeurIPS2022.pdf`

1. 222 名医务人员的真实问句，收成模板。[只在该设置下成立] 问句来自医院人员成立；进模型的是去歧义之后的模板实例，SQL 不是这 222 人写的。
2. 时间表达。[只在该设置下成立] 时间过滤器是模板槽，作为数据特征成立；主表没有把「有时间」和「没有时间」拆开，所以不能当成模型学会了时间。
3. 不可回答题，以及可信语义解析。[只在该设置下成立] 「可回答和不可回答放进同一个集」成立；高 F1 发生在可回答模板已经出现在每个划分、不可回答又是分布外检测的时候。

#### EHRSQL 2024 共享任务

ClinicalNLP 2024。`papers/sql-recall/01-text-to-sql/EHRSQL2024-shared-task_ClinicalNLP2024.pdf`

1. 用可靠性而不是执行准确率给参赛系统排名。[站得住] 官方指标是 RS(10)，罚错会改写谁看起来能部署；第一名在 RS(N) 下仍是 −711.83，共享任务没有产生一个严格可靠的系统。
2. 任务数据沿用 EHRSQL，并用 ChatGPT 改写模板。[站得住] 这是对原数据的再加工，不是新的临床采集，模板泄漏原样留下。

#### TrustSQL

arXiv:2403.15879，打开的 PDF 没有会议页眉。`papers/sql-recall/01-text-to-sql/TrustSQL_arXiv2403.15879.pdf`

1. 可靠性定义为：能答的题写出执行正确的 SQL，不能答的题拒绝。[站得住] 任务定义清楚，不能答包括 schema 对不上和 SQL 表达不了。
2. 惩罚分 RS(c)。[站得住] c=0 时若只看可行题就退化成执行准确率，无惩罚时看起来不错的系统在严惩罚下大量为负；c 本身是作者选的，不是从临床损害估计出来的。

#### OMOP text-to-SQL

ClinicalNLP @ LREC 2026。`papers/sql-recall/01-text-to-sql/OMOP-text-to-SQL_ClinicalNLP2026.pdf`

1. 安全约定：只输出一条 SQL，否则输出 `<NO_SQL>`。[只在该设置下成立] 约定写清楚了；高分发生在合成 OMOP 库、概念已经归一、按模板划分之后。
2. LoRA Llama-3-8B 执行准确率 93.55%，并且拒答更可靠。[只在该设置下成立] 93.55 在这个合成测试集上成立，主要是域内 LoRA；同一检查点的 RS(10) 只有 0.373，只略高于零。

#### Query Carefully

arXiv:2512.21345v1，2025-12-19，没有会议页眉。`papers/sql-recall/01-text-to-sql/QueryCarefully_arXiv2512.21345.pdf`

1. 在 OncoMX 上建 80 道不可回答题，8 类、每类 10 道。[站得住] 数据集声明成立，规模就是作者自选的 80，统计功效很弱。
2. llama3.3:70b 加拒答规则和少样本，不可回答检测 0.8；缺值 0.5；列歧义 0.3。[只在该设置下成立] 「不可回答不是一类」在这 80 题、这一个模型上成立，0.8 不能写成生物医学拒答已解决。

#### Binder

ICLR 2023。`papers/sql-recall/01-text-to-sql/Binder_ICLR2023.pdf`

1. 在 SQL 或 Python 里嵌模型调用，覆盖纯 SQL 写不出的问题。[只在该设置下成立] 在 WikiTQ 上成立，Codex BINDER 测试执行准确率 64.6，相对 Codex SQL 的 61.1；这是小维基表上的问答，不是推荐召回。
2. 解释性来自中间程序。[不成立] 有中间程序不等于程序是对的，开发集 100 条的错误分析只说明错误类型存在。

#### SUQL

NAACL 2024 Findings。`papers/sql-recall/01-text-to-sql/SUQL_NAACL2024_Findings.pdf`。混合检索批判用的是同题的 `papers/sql-recall/04-metrics/SUQL_NAACL2024.pdf`，两份批判的数字一致。

#### LIMIT

arXiv:2508.21038v2，批判标 ICLR 2026。`papers/sql-recall/04-metrics/LIMIT_arXiv2508.21038.pdf`

## 综述该怎么用这张表

挤满的是四块：领域模板加域内执行准确率，拒答和可靠性分，无约束的下一物品（全量交叉熵序列模型，以及语义 ID），还有仍然带着检索器的半结构化混合系统。空着、而且这篇用得上的，是模型在物品、用户和交互上写出 SQL，数据库执行结果成为候选，再用留出的 Hit、Recall 或 NDCG 打分；STaRK-Amazon 上还没有只执行 SQL 或 Cypher 就打过 BM25 的一臂。InteRecAgent 把 SQL 写成一张物品信息表上的硬条件，明文不许用它找相似物品，标题不能当条件，相似物品交给 ItemCF。与领域 text-to-SQL 隔开的引用是 OMOP：合成模板上 LoRA 的测试执行准确率已经到 93.55，这种域内高分不构成贡献，而且那 22 篇没有推荐指标。与无约束序列推荐隔开的引用是 Xu 等：同一份 Beauty 上，全量交叉熵 SASRec 的 NDCG@10 是 0.0597，高于 TIGER 一系用来宣称胜利的那一档；自连接写不出这个模型，无约束格子不能当主表。
