## 结论

1. 没找到一篇论文是「大模型写 SQL，SQL 在用户、物品、交互表上直接出候选，并用 Recall@K 或 NDCG 打分」。SQL 出现在推荐系统里时，只做物品属性的硬过滤，协同召回仍交给向量或 ItemCF。也没有人让模型写出 I2I 或 U2U 的自连接。
2. 纯领域 Text-to-SQL 的发表方式已经挤满：专家模板加合成、报一个相对 Spider 或 BIRD 的下跌、再加拒答。执行准确率本身不可靠。这篇如果做，数字必须是推荐任务上的，不能是 SQL 对不对。
3. 无约束的「下一个物品」上，调好的 SASRec、EASE、ItemKNN 已经把共现吃掉了，还强过一批微调过的大模型推荐器。SQL 要显出优势，实验得放在带硬约束的召回上，而不是和这些方法比无约束的 Recall@K。不同论文的 Recall@K 协议不同，不能横着比。
4. 主实验用 STaRK-Amazon 的全库检索：SQL 只执行关系片段（品牌、颜色、品类、also_bought），文本仍交给 BM25 或小编码器。RecBench+ 电影要改成检索协议才能用。Amazon-C4 是 SQL 应该输的对照。指标用现成的条件匹配率、多次运行的集合重叠，以及「返回的候选就是这条 SQL 的执行结果」。文献不支持「SQL 替换向量检索」这个总判断，只支持「显式谓词交给数据库，语义交给检索」。
5. RelBench 上同样没有人做过「一句话进去，一条 SQL 的执行结果就是 top-K」。它的标签本身就是面向未来窗口的 DuckDB SQL，但输入是实体加时间，没有自然语言。它用来检验手写的协同 SQL 能不能动 MAP，不作为这篇的语言主实验。

## 跟老师对齐的做法

语言主实验和协同假设分开。前者有自然语言，后者才是 I2I 和 U2U 的自连接。没有一个公开集把两件事同时做好。

| 角色 | 数据 | 系统 | 要打过的数 | 不做什么 |
|---|---|---|---|---|
| 主实验 | STaRK-Amazon | 模型写出关系片段的 SQL，DuckDB 执行，BM25 或小编码器在超集里排序 | 合成集 BM25：Hit@1 44.94，R@20 53.77，MRR 55.30。人工 81 条另报 | 不报「纯 SQL、不看文本」的 Hit@1 当主结果 |
| 约束加历史 | RecBench+ 电影，改成检索 | 同一条 SQL 路径。全目录报条件匹配率，历史子集报 Precision 和 NDCG | 只作参照：GPT-4o 凭记忆生成的 Precision 0.308、CMR 0.714。论文写明对方没看目录 | 不把官方生成分数放进主表跟检索比 |
| 协同是否成立 | RelBench 的 H&M 购买，其次 Amazon 购买 | 先手写 SQL：历史访问、时间衰减的共现连接、再加种子时间谓词。模型生成 SQL 放在手写查询打赢平凡基线之后 | H&M：历史访问 0.89，ID-GNN 2.81，ContextGNN 2.93。Amazon 购买：历史访问 0.06，ContextGNN 2.93 | 不把 RelBench 写成语言实验。14 个任务各一句模板，不是 ACL 的语言贡献 |
| 负对照 | Amazon-C4 | 同一条 SQL 路径 | NDCG@100 0.1856 | 不在这里追求赢 |

本地 SQL 生成器用 Arctic-Text2SQL-R1-7B 或 OmniSQL-7B，API 用一个当时的前沿模型，给 schema，允许多次执行。不追 BIRD 榜首，也不用 DIN-SQL 当强基线。无约束的 SASRec 和 EASE 放进附录，用来说明「只把 ItemKNN 写成 SQL」在下一个物品上没有增益。

指标就这几列：Hit@1、Hit@5、Recall@20、MRR、NDCG、延迟；关系片段上的条件匹配率；温度 0 下 SQL 字符串和结果集的一致比例；每个返回物品是否有满足查询的见证行。不新造可解释性指数。两种顺序都报：先 SQL 再排序，以及先向量再 SQL 过滤。后者在 Text2VectorSQL 里会丢掉 30% 以上的正确命中。

## 两周先导，两个停点

从 2026-11-12 起。数据用 DuckDB 查 parquet 或 STaRK 的图，不把全量放进仓库。STaRK 的商品文本约 5.92 亿 token，先导只编码一个子集。

| 时间 | 做什么 | 停 |
|---|---|---|
| 11/12–11/18 | STaRK 抽样。手写 SQL 取出关系超集，再接 BM25。同一批查询上报 BM25、纯 SQL、SQL 再 BM25 | 11/18：在人工 81 条和一小组合成查询上，SQL 再 BM25 的 Hit@1 和 R@20 都不高于 BM25。关系片段没有贡献，生成器救不了。主实验停，只保留 RelBench 那条如果它还活着 |
| 11/12–11/18，并行 | RelBench H&M。手写的共现 SQL，严格早于种子时间 | 11/18：MAP 不高于历史访问的 0.89。协同自连接在这个任务上没有超出平凡 SQL 的空间，I2I 假设先放下。Amazon 购买的历史访问只有 0.06，若 H&M 失败，再用它确认一次，不并行开第三个数集 |
| 11/19–11/25 | 上 7B 和一次 API，只替换手写 SQL 那一段。报执行失败率、结果集抖动、以及相对手写 SQL 的 Hit 或 MAP 差 | 11/25：生成 SQL 的下游指标达不到手写 SQL 的八成，并且修提示也补不回。先写测量文，不设计新的生成算法 |
| 11/26 之后 | 过了上面两关，再扩到 RecBench+ 的检索协议和 Amazon-C4 负对照。写作从 12 月中开始 | 负对照上 SQL 意外打赢嵌入，先查是不是品类泄漏，不把它写成主结论 |

算力：SQL 和 BM25 是 CPU。5090 跑 7B 和一小批嵌入。不租 A100 去复现四层 GraphSAGE 或 ContextGNN。闭源 API 只在 11/19 之后、而且只在手写 SQL 已经证明关系片段有用的时候调用。
