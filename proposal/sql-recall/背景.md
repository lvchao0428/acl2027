# LLM 生成 SQL 作为推荐系统硬约束召回器的深度调研

## 结论摘要

本方向的可投稿问题不是“SQL 是否能替代所有推荐召回”，而是更窄地问：当用户请求包含品牌、价格、时效、实体、组合条件、库存、领域规则等硬约束时，LLM 能否把自然语言意图编译成可执行 SQL，用作第一阶段候选召回器，并在后续排序前提供更高的约束满足率、可审计执行路径和可解释失败处理。

现有证据支持这个方向的必要性：约束推荐和 faceted search 说明结构化属性适合硬过滤，现代 dense retrieval 的电商工作也承认 entity confusion 和 attribute hallucination 等语义漂移问题；但完整的 LLM→SQL→推荐端到端 benchmark 仍未被现有论文直接覆盖。

## 核心研究问题

1. 哪些自然语言推荐请求应该被视为硬约束召回，而不是语义偏好排序。
2. LLM 生成 SQL 时如何处理 schema linking、join 深度、空结果、过窄条件和约束放松。
3. 除 Recall/NDCG 外，如何单独测约束满足率、SQL 执行正确率、候选覆盖、执行效率、解释一致性和后续 ranker 的端到端收益。
4. 没有线上 A/B 时，离线实验只能证明可控数据上的候选质量和约束满足，不能直接声称线上长期收益。

## 历史发展链条

### 1. 约束推荐

早期约束推荐把用户需求、产品属性和规则建模为可满足的约束集合，并在无解时考虑约束冲突与放松。它证明结构化属性和硬约束是推荐中的真实问题，也提供了 SQL 召回的概念前身，但缺少 LLM 对自然语言的解析能力，也缺少与现代两阶段推荐和端到端指标的连接。

代表论文：Conflict-Directed Relaxation of Constraints in Content-Based Recommender Systems。

### 2. Faceted search 和结构化产品检索

Faceted search 和基于本体的产品检索把类别、属性和语义标注组织成可交互的过滤维度。它说明“把自然语言约束落到属性过滤”不是新需求，新的机会在于用 LLM 自动生成这些过滤条件。

代表论文：Faceted search and retrieval based on semantically annotated product family ontology。

### 3. 搜索与推荐联合建模

搜索和推荐技术长期分离，但电商等场景同时有 query-aware search 和 personalized recommendation。Joint Modeling and Optimization of Search and Recommendation 为把自然语言查询和推荐候选生成放进同一实验设置提供了基础，但没有处理硬约束执行、SQL 可审计性或 LLM 查询生成。

### 4. Dense retrieval for recommendation

Domain-Adaptive and Scalable Dense Retrieval for Content-Based Recommendation 把 content-based recommendation 建模为 recommendation-as-retrieval，用双塔编码器从自然语言意图召回商品。它是 SQL 召回必须比较的强 baseline；同时论文自身指出 dense retrieval 可能出现 semantic drift、entity confusion 和 attribute hallucination，这正是硬约束 SQL 召回可以补足的缺口。

### 5. Text-to-SQL 生成能力

DAIL-SQL 和 SQLForge 等工作通过 prompt engineering、示例选择和数据合成提高 Text-to-SQL 执行准确率。它们可以作为推荐 SQL 召回器的生成模块或数据合成基础，但它们不评估候选召回质量、约束满足对推荐排序的影响、用户历史建模或商品实时属性。

## 方法建议

最可行的方法形态是一个三段式候选生成器：

1. 把用户请求和上下文解析成硬约束、软偏好和排序目标。
2. 用 LLM 生成可执行 SQL，对商品或内容表进行候选召回。
3. 把候选交给现有 ranker、LLM ranker 或 hybrid retriever 排序。

论文贡献不应声称 SQL 取代 dense retrieval，而应证明 SQL 适合处理实体一致性、数值/时间范围、组合条件、实时库存、领域规则和可解释约束放松。Dense retrieval、KG-RAG 和 agentic recommendation 应作为对照路线。方法上最需要设计的是 schema linking、约束类型分类、空结果时的最小放松、SQL 执行效率控制，以及从 SQL trace 生成解释。

## 评测协议

评测必须避免 fixed-candidate setting 掩盖第一阶段召回器差异。建议至少有三层指标：

1. SQL 层：execution accuracy、validity、schema linking accuracy、latency。
2. 召回层：Recall@K、candidate coverage、constraint satisfaction rate、empty-result rate、relaxation cost。
3. 端到端层：NDCG/HitRate、集合级 utility、解释一致性和稳定性。

离线协议要固定数据切分、候选生成、后续 ranker 和统计检验。如果使用 LLM-as-a-judge，只能作为补充维度，并需要人类一致性或稳健统计检验支持。

## 当前限制

1. 已有检索和推荐论文能支撑硬约束问题存在，但尚没有一篇已读且通过核验的论文直接证明 LLM→SQL 召回在推荐端到端上优于所有向量或生成式召回。
2. 部分 2026 相关论文只能读到元数据或摘要，不能作为强实验结论。
3. 引用扩展多次因记录服务超时或缺少可跟踪标识失败，因此历史链条可能不完整。
4. 无线上 A/B 时，报告只能提出离线评测协议，不能保证线上长期用户行为收益。

## 最值得推进的 ACL 2027 选题

建议题目方向是：面向硬约束推荐召回的 Natural Language-to-SQL Benchmark and Retriever。

它应从 Amazon/H&M/电影/法律文档等已有推荐数据出发，构造带 schema 的商品或文档数据库，把用户请求分解成硬约束和软偏好，并用行为日志或可验证属性生成 ground truth 候选集合。论文可以把 DAIL-SQL/SQLForge 类 Text-to-SQL 方法、dense retrieval、电商 dense retriever、KG-RAG 和推荐 Agent 工具调用作为 baseline，主张贡献是：把约束满足、SQL 执行、候选召回和端到端推荐收益放到同一个可复现实验协议里。
