# 主题界定：这篇论文只回答一个问题

> 日期：2026-09-24 | 依据：[01 调研](01_ACL2024-2026_Agent+RecSys_调研.md)、[02 Proposal v0.1](02_ACL2027_Proposal_DelegationGap.md)
> 作用：把「Agent × RecSys」拆成彼此不能互相代替的主题，锁定 ACL 2027 这一篇写哪一条，并改掉 v0.1 里已经不新的主张。

---

## 0. 锁定的主题

**个性化受托差距（delegation gap）**：用户把一次可委托的购物选择交给 LLM agent 之后，agent 选中的商品，是不是**这个用户**会满意的那一个。

操作定义只有两句：

- 满意型（真实购买且事后高分）：好受托人**命中**该用户的选择。
- 后悔型（真实购买且事后低分、verified）：好受托人**避开**该选择，改选一个仍满足购前需求、但质量更高的替代。

一句话贡献：证明「复现这个人」的模拟器，和「给一个典型消费者挑」的无条件买家，都不是合格受托人；再用真实满意度把小模型训成受托人。

这篇**不**回答：推荐器会不会推理、agent 能不能把购物流程走完、agent 在没有这个用户时偏向位置还是赞助、平台该不该把 principal 写成自己、推荐系统如何同时优化人和 agent。

## 1. 十个相邻主题

同一批论文经常被说成「agent + 推荐」。下面按**问题**拆开。前五个是别人的论文，第六个是这篇，后四个明确不做。

| # | 主题 | 它问的问题 | 已经做到哪 | 这篇怎么用 |
|---|---|---|---|---|
| 1 | 推理式 / agent 化推荐器 | 推荐模型能否用推理、记忆、RL 把排序做准 | ACL'26 主线：OneRec-Think、ReRec、ROS、HARPO、MemRec | 不写。算力与工业数据都不匹配 |
| 2 | 购物任务完成 | 给定指令，agent 能否走完浏览、比较、下单 | ShopSimulator、OPeRA 的动作基准、EComAgentBench、ShopperBench | 只借环境与字段，不贡献新 benchmark |
| 3 | 用户模拟 | agent 的下一步是否像这个人，**包括这个人的错** | Mirroring Users、AlignUSER、OPeRA、SimUSER、PEPPER | **对照臂**。模拟器在后悔型上应当更忠实复现踩雷 |
| 4 | 无条件买家的决策面 | 没有这个用户的偏好时，agent 会买什么、被什么杠杆拉动 | **ACES**（*What Is Your AI Agent Buying?*，arXiv 2508.02630；DOI [10.1145/3774904.3792943](https://doi.org/10.1145/3774904.3792943)） | **引用，不当发现**。见第 2 节 |
| 5 | 受托人的委托人是谁 | system prompt 把 principal 写成用户还是平台，会不会改变对赞助的惩罚 | *Whom Do AI Agents Work For?*（arXiv 2609.17989）；*When Agents Shop for You*（arXiv 2604.26220，支付意愿泄漏） | 引用。它们没有真实用户的选择与满意度 |
| **6** | **个性化受托差距** | **替这个用户选，是否服务其利益（满意则命中，后悔则避开）** | 只有 Spotify position paper 的议程，加上 iAgent 的「用户侧 agent」范式；**没有真实满意度 ground truth，也没有训练目标** | **锁定** |
| 7 | 平台双受众优化 | 推荐系统如何同时产出给人看的列表和给 agent 消费的结构化结果 | Spotify 议程第 1 条，无实验 | 下一篇的平台侧问题，不进本文方法 |
| 8 | Agent 偏好协议 | RS 如何消化 agent 传来的组合约束（MCP / A2A） | Spotify 议程第 2 条，无实验 | 不做。那是平台接口，不是受托人是否忠于用户 |
| 9 | 模拟器作 reward 的 Goodhart | 用用户模拟器当 RL 奖励，agent 会不会学会讨好模拟器 | PEPPER、*How Reliable is Your Simulator?* 指出风险；推荐域无系统测量 | **Plan B，单独成篇**。若塞进这篇，贡献会从「受托」变成「训练诊断」 |
| 10 | 电商 GUI agent 的安全与个性化 | 欺骗界面、风险控制、长期记录如何改变 GUI agent | ACL'26 邻接：deceptive-interface benchmark、RISK、PersonalAlign、Personalization Trap | 只作背景：agent 已经在替人操作界面 |

Spotify position paper（*Who Are We Recommending To?*，RecSys'26，arXiv 2609.11945）自己的六条议程，对应关系是：

| Spotify 议程 | 落到上表 | 这篇是否认领 |
|---|---|---|
| Evaluation Beyond Engagement（任务结果、regret、约束满足） | 主题 6 的**指标** | 认领其中一种：用真实满意度定义 regret，而不是用合成约束打分 |
| Trust & Accountability（delegation confidence：agent 行为是否满足该用户） | 主题 6 的**问题** | 认领测量与训练，不认领审计追溯、责任分配 |
| Manipulation | 主题 4 已有因果实验；主题 10 是安全 | 不认领「发现 agent 可被操纵」。只把操纵当作训练时的不变性约束 |
| Monetization | 主题 4、5 | 不认领 |
| Dual-Audience Recommendation | 主题 7 | 不认领 |
| Agent Preference Modeling | 主题 8 | 不认领 |

## 2. v0.1 里必须降级的主张

02 号文档的 H1 把「偏差集中在均分、评论数、位置、价格、营销文案、赞助标签」写成主要假设。这条作为**发现**已经不成立。

ACES 在可编程的模拟货架上做了随机实验，结论包括：

- agent 被明确当成**受托的经济行动者**，而不是人类样本；实验用的是「给一个典型的人挑」的通用 prompt，故意不做个性化。
- 位置效应大且因模型而异；赞助标签降低被选概率，平台背书（Overall Pick）大幅提高被选概率；价格、评分、评论数的方向符合预期，幅度因模型差很多。
- 选择比人类更集中在少数「模态商品」上。
- 作者把两件事留成未来工作：和人类基线对比；让 agent **有效引出购买者偏好**。

因此本文的偏差实验改成一个更窄的句子：

> 这些杠杆（位置、赞助、背书、价格）会不会让受托人**偏离这个用户的满意选择**。ACES 测量的是无个人偏好时的决策面；本文测量的是该决策面与特定用户利益之间的距离。

身份刻板印象（*Stereotype or Personalization?*）同样降为可选探针，不进标题、不进三条贡献。

## 3. 四个角色，不要再混用

评测时每一行都要有自己的 prompt 和指标，不能都叫「agent」。

| 角色 | 输入 | 目标 | 满意型上该怎样 | 后悔型上该怎样 | 实现 |
|---|---|---|---|---|---|
| 模拟器 | 该用户的画像 / 历史 | 复现这个人 | 命中 | **也命中**（复现踩雷） | UserMirrorer-3B |
| 无条件买家 | 只有品类，无该用户 | 给典型消费者挑 | 不必命中 | 不必针对该用户避开 | ACES 式 generic prompt |
| 历史排序器 | 只有历史，无本次指令 | 拟合过去的交互 | 可能命中 | 可能继续踩雷 | SASRec / UniSRec / 历史-only LLM |
| **受托人** | 本次指令 + 可选的该用户信息 | 服务这个人的利益 | **命中** | **避开** | 本文的评测对象与训练对象 |

主题成立，当且仅当后两种对照在后悔型上与受托人分开：模拟器更常踩雷，无条件买家即使用「高分、多评论」挑对了质量，也说不清是不是**这个用户**要的。若两者和受托人统计上不可区分，这条主题没有经验内容，应停。

## 4. 这篇的边界（相对 02 号文档）

留下：

1. **定义与数据**：Amazon-C4 满意型 + 由低分 verified 评论改写的后悔型 + OPeRA 只作真人对照。DelegateBench 的卖点是真实选择与真实满意度，不是又一个任务成功率榜。
2. **主对照**：前沿 LLM 受托人 vs 模拟器 vs 无条件买家 vs 非 agent 排序器。报告 Hit@1（满意型）与 Regret-Avoidance（后悔型）。
3. **一个训练目标**：满意度加权 DPO（满意型 \(i^\*\succ\) 硬负例；后悔型反转）。操纵不变性只作为正则，不单独成章。
4. **一个偏好信息对照**：无该用户信息 vs 有该用户信息（指令 + 短历史或短画像，二选一作为主设置）。这对应 ACES 点名的未来工作，也对应 iAgent 没回答的「代表的是不是这个用户」。

移出主贡献、可放附录：

- 四通道完整曲线（指令 / 画像 / 长历史 / 1–3 个澄清问题）和 token 性价比。主文只保留「有没有该用户信息」。
- 位置、赞助、营销、价格、身份的全套干预。主文最多留一个操纵探针，用来支撑正则，不写成偏差分类学。
- 「4B–8B 超过 GPT-5」从题目降为结果。做不到时，论文仍成立。

移出本文：

- 平台侧双受众（候选呈 ranked list 还是结构化属性表）。
- ShopSimulator 中文迁移。时间不够就不做。
- Goodhart / 换模拟器掉点。留在 02 号文档第 4 节，作为第二篇。

## 5. 主题会被什么结果杀掉

| 如果出现 | 说明 | 动作 |
|---|---|---|
| 后悔型指令改写后仍含「结果很差」一类话 | ground truth 泄漏，避开 \(i^\*\) 变成阅读理解 | 停掉后悔型，主题退化为「个性化选择匹配」，与模拟器论文撞车 |
| 检索基线在满意型上接近前沿 LLM | Amazon-C4 的 \(q\) 太好猜，没有差距可测 | 收紧候选，使每件都满足 \(q\)；仍打平则换题 |
| 模拟器、无条件买家、受托人在两类 episode 上无差别 | 「delegate ≠ simulator」没有经验内容 | 不写训练，主题不成立 |
| 训练只提高满意型 Hit、后悔型踩雷率不变 | 学到的是模仿购买，不是服务利益 | 方法失败，可退回 benchmark + 分析投 Findings |

## 6. 仍建议拍板的一件事

主文的「有该用户信息」用哪一种载体：

- **短历史**（购买前最近若干条评论）：和推荐评测习惯一致，冷启动用户会空。
- **自然语言画像**（由历史离线生成）：token 短，但画像生成本身是一条误差来源。

建议主文用短历史，画像放附录。澄清提问依赖 UserMirrorer 当 oracle，和「模拟器当对照」缠在一起，不放进定义主题的实验。
